Building TensorRT Engines for One Linear Layer in FP32 and FP16

One MatMul → Add → Relu graph was built six ways in FP32 and FP16. This post checks which shapes each engine accepts, where FP16 overflows and what a reused execution context really costs per call.

Take one set of weights and one tiny MatMul → Add → Relu graph, and build six TensorRT engines from them: one with a wide range, one with two segments and one fixed at exactly 64 rows, each in FP32 and in FP16.

Writing the plan file to disk is only the beginning. Each engine still has to answer three questions, and each answer comes with its own checks:

  1. Which shapes does it accept?
  2. Can FP16 still hold the results of this graph?
  3. Can one execution context be reused, and what does each call actually cost?

Whether fixed shapes or half precision are faster must be measured, not assumed, and this post measures all six engines. All experiments ran on an RTX 5070 Laptop (SM120) under Windows 11, with the official TensorRT 10.14.1.48.post1 CU13 Windows wheel, so the APIs and the numerical behavior belong to this version. The graph is small enough to follow by hand, including the exact point where it overflows.

The post starts with the model, the build and a check of the ONNX path, and then takes the three questions in order. The first question covers profile constraints and a shape that the setters accept but execution rejects. The second covers FP16 overflow and the separation of representation error from execution error, and the third covers the lifecycle cost from the plan file to steady-state calls.

The model and the build

The model is

Y=ReLU⁡(XW+R),X,R∈RM×64,W∈R64×64.Y=\operatorname{ReLU}(XW+R),\qquad X,R\in\mathbb R^{M\times64},\quad W\in\mathbb R^{64\times64}.Y=ReLU(XW+R),X,R∈RM×64,W∈R64×64.

MMM is the row count of the request and can vary, while the width is fixed at 64. RRR is added elementwise and must have the same shape, so it is not a bias of length 64 that is broadcast. Inputs and outputs are contiguous and row-major.

Most weight columns are drawn from a normal distribution with a fixed seed and a standard deviation of 1/81/81/8. The first column is all ones, and the second column alternates between +1+1+1 and −1-1−1. The first column makes the accumulation range easy to compute by hand, and the second column makes the error easy to see when nearly equal inputs cancel each other. All six engines share the same original FP32 weights, and these weights are converted to the storage type only when the FP16 engines are built.

The network code maps one-to-one onto the formula. Names and logging are omitted, dt is trt.float32 or trt.float16, and weight is a NumPy array of the matching type:

flags = 1 << int(trt.NetworkDefinitionCreationFlag.STRONGLY_TYPED)
network = builder.create_network(flags)
x = network.add_input("x", dt, (-1, 64))
r = network.add_input("residual", dt, (-1, 64))
x.set_dimension_name(0, "rows")
r.set_dimension_name(0, "rows")

w = network.add_constant(weight.shape, weight).get_output(0)
z = network.add_matrix_multiply(
    x, trt.MatrixOperation.NONE, w, trt.MatrixOperation.NONE).get_output(0)
u = network.add_elementwise(z, r, trt.ElementWiseOperation.SUM).get_output(0)
y = network.add_activation(u, trt.ActivationType.RELU).get_output(0)
y.name = "y"
network.mark_output(y)

-1 leaves the row count open until runtime, and rows declares that both inputs share this dimension. The graph only describes the computation; it does not provide an execution plan for every shape. The builder also needs an optimization profile that bounds the min, opt and max of the dynamic dimension. Here these values are M=1/64/512M=1/64/512M=1/64/512, called wide below:

profile = builder.create_optimization_profile()
profile.set_shape("x", (1, 64), (64, 64), (512, 64))
profile.set_shape("residual", (1, 64), (64, 64), (512, 64))
config.add_optimization_profile(profile)
config.clear_flag(trt.BuilderFlag.TF32)
serialized = builder.build_serialized_network(network, config)

The serialized engine keeps the choices made at build time. After loading, an execution context holds the dynamic state that a particular run needs. With dynamic shapes, the two are cleanly separated: the network and the weights can be reused, while the row count of the request, the bound addresses and the execution resources belong to a specific context.

A request must select a profile, set both input shapes, infer the output shape, bind the actual device addresses and submit the work. Below, tx,tr,ty are pre-allocated CUDA tensors and stream is their stream:

assert context.set_optimization_profile_async(profile_id, stream.cuda_stream)
assert context.set_input_shape("x", tuple(tx.shape))
assert context.set_input_shape("residual", tuple(tr.shape))
assert not context.infer_shapes()
assert tuple(context.get_tensor_shape("y")) == tuple(ty.shape)

for name, tensor in [("x", tx), ("residual", tr), ("y", ty)]:
    assert context.set_tensor_address(name, tensor.data_ptr())
assert context.execute_async_v3(stream.cuda_stream)
stream.synchronize()

The script uses PyTorch to manage CUDA storage, streams and events, and it uses TensorRT for the computation. A raw pointer carries no dtype, stride or allocation length. Before binding, the caller must therefore guarantee that all three match the contract of the engine, and it must keep the tensor alive until the device has finished. If an FP32 pointer is passed to an FP16 engine, nothing converts the data.

Checking the ONNX path

A real model would usually be built through the ONNX parser, and the caller would have the same build and execution responsibilities. So the same MatMul → Add → Relu graph was also saved with ONNX 1.19.1, with the weights as initializers, the inputs declared as ['rows',64], opset 18 and IR version 9. The file passed the checker, went through the parser and was built into an FP32 wide engine.

This path does not use torch.onnx, so it validates only the ONNX file, the parsing and the TensorRT execution, not other exporters. The full outputs at seven row counts (1,3,17,64,65,257,5121,3,17,64,65,257,5121,3,17,64,65,257,512) were compared with both the ONNX CPU ReferenceEvaluator and an independent FP64 formula. The maximum error against FP64 ranged from 4.242×10−74.242\times10^{-7}4.242×10−7 to 7.585×10−67.585\times10^{-6}7.585×10−6, and the maximum difference against ONNX CPU was 7.629×10−67.629\times10^{-6}7.629×10−6, with all values finite and within the FP32 budget.

Figure 1: The ONNX-parsed engine against FP64 and ONNX CPU references.

After the parser reports success, the full output still needs a check, because a parser that accepts a file does not prove that the parsed computation matches the intended math.

Question 1: which shapes does an engine accept?

Besides wide, two more profile schemes are included in the comparison. Split uses two profiles for small and large row counts, and fixed accepts only 64 rows. Each scheme exists in FP32 and FP16, so there are six engines in total.

SchemeMin MMMOpt MMMMax MMM
wide164512
split, profile 013264
split, profile 165256512
fixed646464

The opt size is one target point for the builder when it chooses an implementation; it does not mean that every size in the range was tuned separately. Some tactics are available only when min, opt and max are equal, so fixed and wide may receive completely different implementations. Profiles are best chosen from the real distribution of requests, and neither “wider” nor “narrower” is better in general (dynamic shapes docs).

The constraint the profile doesn’t show

A profile only bounds each input on its own. In this graph, the two inputs must also satisfy MX=MRM_X=M_RMX​=MR​. With profile ppp selected, the real admission domain is

Dp={(X,R):Mmin⁡,p≤MX=MR≤Mmax⁡,p,KX=KR=64}.\mathcal D_p=\left\{(X,R): M_{\min,p}\le M_X=M_R\le M_{\max,p},\quad K_X=K_R=64 \right\}.Dp​={(X,R):Mmin,p​≤MX​=MR​≤Mmax,p​,KX​=KR​=64}.

Figure 2: Drawn for split profile 0. The rectangle holds combinations where each row count is individually legal; the network only accepts the diagonal. (7,9)(7,9)(7,9) is inside the rectangle and off the diagonal. That point is a real rejection experiment; the figure isn’t a sweep of every integer point.

The surprising part is this: when XXX is set to 7 rows and RRR to 9 rows, both set_input_shape calls return true. The shared-dimension relation fails only at execute_async_v3, and execution returns false. A caller that treats the setters as proof of success may then read whatever the previous call left in a reused output buffer.

Other errors are caught earlier. For wide and split, 0 or 513 rows are rejected when the shape is set; 63 columns are rejected for every scheme; and 63 or 65 rows are rejected for fixed. Across the six engines, these cases make 22 checks of shape rejection. The entry point of the application already knows the shapes of both tensors, so it can reject mismatches in advance, and it should still check the final return status of the backend.

One more detail is worth knowing: the two APIs report success in different ways. In this version, IOptimizationProfile.set_shape at build time returns None on success and throws an exception on inconsistency, while IExecutionContext.set_input_shape at runtime returns a boolean. So a uniform assert set_shape(...) would treat a successful build as a failure (Profile API).

Question 2: does FP16 hold the answer?

Both precisions use strongly typed graphs. The FP32 version has FP32 inputs, weights, residual and output, the FP16 version uses FP16 for all of them, and TF32 is explicitly disabled. This keeps the comparison clean, because the storage types are fixed in the graph instead of being a hint such as “prefer FP16 if possible” to the builder.

The storage type, however, does not mean that every internal step rounds in that type. Matrix multiplications change the accumulation, and the residual and the activation may be fused after the multiplication. The saved output of the engine inspector shows that wide FP32 keeps an independent GEMM followed by a fused residual addition and ReLU, while wide FP16 fuses the GEMM, the residual and the ReLU together. Both engines also contain shape logic, so the number of inspector entries is not the number of kernel launches (Engine Inspector).

The FP16 tactic names contain f16f16 and tensor16x8x16, while the name of the FP32 GEMM contains ffma. These names trace the build choices, but they give neither dynamic instruction counts nor Tensor Core utilization, and a string such as sm80 in a name does not identify the architecture (the hardware is SM120).

An overflow you can compute by hand

Output overflow can be found without guessing the internals. Set every element of XXX to 2000 and R=0R=0R=0. Because the first weight column is all ones,

Yi0=ReLU⁡(∑k=0632000×1)=128000.Y_{i0}=\operatorname{ReLU}\left(\sum_{k=0}^{63}2000\times1\right)=128000.Yi0​=ReLU(k=0∑63​2000×1)=128000.

2000, 0 and 1 are all exactly representable in FP16, but 128000 exceeds the maximum finite FP16 value of 65504. However precise the internal accumulation is, the result cannot be stored as a finite FP16 value. A smaller maximum row count in the profile does not help either, because each row accumulates its 64 terms independently and MMM does not enter the result at all (numeric range notes).

In the actual runs, all three FP16 engines submitted the work successfully and produced positive infinity in the entire first column, so 512 rows give 512 non-finite outputs. FP32 keeps the value 128000. Across the six directly built engines, four input patterns and the legal test shapes of each engine, there are 120 cases: 105 finite results pass the diagnostic budget, and the 15 FP16 overflows are recorded as failures of the numeric range, even though they were expected.

If a model really has to handle values of this size, it needs a wider type at the right place, or scaling and normalization where the model allows them. Finite inputs alone are not enough, because the outputs of operators and the accumulation ranges are also part of the type decision.

Two references, two kinds of error

Finite results need two references. The FP16 engine reads inputs and weights that are already rounded, so a direct comparison with the original FP32 model mixes the change of representation with the execution error. With ϕ\phiϕ for ReLU, define

Y0=ϕ(XW+R),Ys=ϕ(XsWs+Rs),Y_0=\phi(XW+R),\qquad Y_s=\phi(X_sW_s+R_s),Y0​=ϕ(XW+R),Ys​=ϕ(Xs​Ws​+Rs​),

both computed in FP64. Y0Y_0Y0​ uses the original stored FP32 values, while YsY_sYs​ first rounds the values to the actual storage type of the engine and then promotes them to FP64. With the engine output Y^\widehat YY, elementwise:

Erepr=Ys−Y0,Eexec=Y^−Ys,Etotal=Erepr+Eexec.E_{repr}=Y_s-Y_0,\quad E_{exec}=\widehat Y-Y_s,\quad E_{total}=E_{repr}+E_{exec}.Erepr​=Ys​−Y0​,Eexec​=Y−Ys​,Etotal​=Erepr​+Eexec​.

Figure 3: The two references and how the total error splits between them.

The first term measures how much the stored inputs, weights and residual changed the result, and the second term measures how much the actual arithmetic and the output rounding added once these stored values are fixed. The two terms can reinforce or cancel each other, so the sum of their squared RMSEs is generally not the squared RMSE of the total.

Expanding the change of representation before the activation gives:

ΔZ=XΔW+ΔXW+ΔXΔW+ΔR.\Delta Z=X\Delta W+\Delta XW+\Delta X\Delta W+\Delta R.ΔZ=XΔW+ΔXW+ΔXΔW+ΔR.

The same weight rounding is amplified by the size of the input, and the alternating second column makes nearly equal inputs cancel, so the rounding on small results becomes visible. ReLU is 1-Lipschitz in absolute difference, but it sets every negative value to zero and hides part of the difference before the activation, so the final output alone cannot locate the error layer by layer.

Question 3: what does a call cost?

Only after the numeric range is settled does it make sense to ask what a call costs. The lifecycle of TensorRT includes at least the build, deserialization, context creation, shape and address binding, the first execution and steady-state execution. The statement “the model is cached” does not say which of these stages are already done.

Build and plan size

Each of the six engines was built once, with an empty timing cache, a workspace limit of 64 MiB and optimization level 3. Wide FP32 took 5.575 s and produced a plan of 63652 bytes, while wide FP16 took 8.353 s and produced a plan of 140660 bytes. The FP16 weights are smaller, yet the file is larger, because the plan also contains execution implementations and other data, so the weight bytes do not predict the plan size.

Split FP32 and FP16 take 122044 and 263620 bytes, enlarged by the two profiles, and fixed takes 65060 and 148236 bytes. The build order was fixed and each engine has only one sample, so these build times cannot rank the schemes. The builder times candidate implementations one by one, and keeping the actual plan and the timing cache makes it possible to trace its choices (build reproducibility).

Context memory is reported on its own terms. Wide and split FP32 report 131072 B and fixed reports 18432 B. The two profiles of split report 16384 B and 131072 B, and a default context must account for the larger one. All three FP16 engines report 0 B. These values exclude inputs, outputs, weights, the CUDA context and the runtime libraries, so 0 B does not mean that the process uses no GPU memory.

From plan file to first call

After the file is loaded, whether a request has to build a context makes a visible difference. The experiment gave each engine a new process and recorded the import, the CUDA initialization, the deserialization, the context creation, the binding and the first execution. For wide:

These stages exclude input generation, allocation and transfer, so their sum is not a full end-to-end request. The operating system and the display driver were already running, so the result is not a cold start of the machine either. With one sample from a new process per engine, the table shows the order of magnitude, not a tail latency.

Even with a warm process and a warm engine, a new execution context alone costs a first submission: at 64 rows, 348.1 μs for wide FP32 and 299.3 μs for wide FP16. So saving the plan but rebuilding the context for each request still leaves a noticeable stage before the steady-state calls.

Figure 5: First submissions use host timing and wait for completion; steady batches are CUDA event intervals divided by 100. They show the order of magnitude of lifecycle cost rather than a kernel speedup.

Keeping a context also does not make shape changes free. In one diagnostic that switches from 64 to 257 rows, split must change its profile: for FP32, the setup took 3.484 ms and the next execution 219.6 μs, and for FP16 the values were 6.692 ms and 299.1 μs. Wide does not change its profile, and its setup takes about 0.120 and 0.113 ms. The setup here includes profile selection, shape inference and address binding, and the samples are few, so the difference cannot be attributed precisely to one profile API.

The steady-state time within one bucket does not represent a stream of requests that keeps crossing buckets, and the documentation states that execution must update related resources after a change of shape or profile (shape-change overhead). Bucketing gains better-suited implementations at the price of routing and switching, and only measurements on the real sequence of requests can show which side is larger.

Steady-state timing

In the last set of measurements, all resources are in place. The inputs and outputs are pre-allocated and bound, the same context warms up 20 times, and then three rounds of 20 batches of 100 calls run, for 1320 batch records in total. The timing excludes input generation, transfer, build, deserialization and output download. At 64 rows:

The values in parentheses are the 5th–95th percentiles of the batch means, not percentiles of single-request latency. The GPU clock was not locked, the order of the engines was fixed, and several ranges clearly overlap. Fixed FP32 is not faster, and FP16 wide and split are nearly identical. At 512 rows, wide and split take 26.73 and 27.04 μs for FP32 and 21.73 and 17.57 μs for FP16. A difference at one point does not show that bucketing is always faster.

Figure 6: Steady-state per-call time across schemes and precisions.

The host submission time closely follows the event interval. So the measurement of this small graph is strongly limited by how fast the host can submit work. The events time the stream, but Python still issues each execution individually, and gaps in which the GPU has finished and the next call has not arrived also count in the interval. So the value of about 20 μs is not pure device time for the GEMM and the activation.

The FP16 graph also changes the storage type and the fusion boundaries at the same time. Without a timeline and dynamic counters, the difference cannot be split further into Tensor Cores, memory traffic and fewer launches.

Conclusion

The post answered three questions. Which shapes an engine accepts is decided by the profiles and by the dimension relationships at the graph level, and the second kind of constraint can pass the shape setters undetected. Whether FP16 holds the answer depends on the output and accumulation ranges, not only on the input range, and the finite error splits cleanly into the part that the change of representation caused and the part that the execution added. What a call costs depends on which lifecycle stages a request actually pays for, and a new context or a profile switch can cost more than the steady-state call itself.

In practice, three rules follow. If requests repeat at fixed shapes, reuse a prepared context and measure that case. If requests often cross buckets, include the switching in the request path when measuring. If inputs can produce results such as 128000, fix the type range before optimizing microseconds. The APIs and the numerical behavior described here belong to TensorRT 10.14.1, and other versions need their own checks (release notes, support matrix).

An engine that builds successfully is a promise about shapes and types; only checking every return value and every output shows whether the engine keeps this promise.

Environment, full outputs and reproduction files

Environment and measurement method

Windows 11, RTX 5070 Laptop SM120 (8151 MiB), driver 610.88, Python 3.13.5, PyTorch 2.14.1+cu130, TensorRT 10.14.1.48.post1 official CU13 Windows wheel. Process runtime and driver API both report 13030. The experiments didn’t invoke nvcc; the installed Toolkit 13.1 doesn’t mean TensorRT compiled anything with it.

Both precisions use strongly typed graphs with TF32 disabled, a 64 MiB workspace cap, optimization level 3, one timing iteration per tactic, and an empty timing cache per engine. No other team tasks ran on the GPU during experiments, and the display GPU wasn’t clock-locked.

Entry points and records

Builds, 22 rejections, 120 numerical checks, six fresh processes and 1320 steady batches come from bench_mur/tensorrt/run.py, cold.py and plot.py, recorded in rep_mur/blog-rewrite/tensorrt/.

bench_mur/editorial/style-v2/tensorrt_outputs.py reruns the six engines’ 120 numerical cases plus seven ONNX cases, saving inputs, weights, residuals and full outputs, 127 arrays in all, in rep_mur/blog-rewrite/style-v2/tensorrt/. An independent check accumulates 64-column outer products without calling the original reference helper, confirming that 112 finite cases meet the budget and 15 FP16 overflows stay failures; profile latency wasn’t re-measured.

The ONNX engine build took 8.408 s, one sample; FP16 ONNX and other exporters weren’t tested. Source files, weights, engines and arrays all have SHA-256 hashes. run.py --output can target a new directory, but cold.py and plot.py don’t inherit it automatically, so reruns should use one path to avoid mixing old and new engines and timings.
