The Evolution of FlashAttention: From I/O-Aware Tiling to Asynchronous Pipelines

A row with 2,048 attention scores produces just 64 output values. Four generations of FlashAttention change where those scores live, who computes the output, and what can run while it waits. RTX 5070 measurements and the H100 and B200 papers show which limits each design addresses.

Row 37 of an attention head needs a score for every key it can see. With 2,048 keys and a head width of 64, those scores eventually produce just 64 output values. A conventional implementation writes the scores out, reads them back to compute probabilities, and reads the probabilities to form those values. FlashAttention is the history of what happened when implementers stopped treating those intermediate matrices as objects that had to survive between operations. Once the matrices disappeared, different constraints came into view. Among them were who owned row 37, how long its running output had to live, and whether another useful instruction could run while that row waited.

These questions lead to rather different performance results. On an RTX 5070 Laptop GPU, assigning each query tile its own block accelerated a teaching kernel by roughly 65 times when its baseline gave a whole head just one block. At 32 heads the same change gave about 2.8 times the speed. In the FlashAttention-3 paper, a controlled H100 comparison shows a much smaller gain from overlapping matrix multiplication and softmax in an already parallel kernel. FlashAttention-4 then finds that on a datacenter Blackwell GPU, exponentiating the scores of a tile can take as many idealized cycles as both matrix products combined. Each figure becomes intelligible once we identify the operation that previously kept the next result waiting.

Scaled dot-product attention and the cost of a materialized row

The Transformer introduced scaled dot-product attention as a batched calculation over queries, keys and values. Consider one head and omit the batch dimension for a moment. Every query represents a position asking for information. Its dot product with each eligible key assigns a score to that key, and the corresponding value is the information the query could receive. A key determines a weight, while a value carries the coordinates that will actually be averaged. If we fix the queries and keys and replace the values, every attention probability stays the same and the output generally changes. If we replace a key, it can change the weights applied to all the values in a row.

Write qiq_iqi​ for query iii, kjk_jkj​ for key jjj, and vjv_jvj​ for its value. For head width ddd, the score is sij=qiTkj/ds_{ij}=q_i^\mathsf{T}k_j/\sqrt dsij​=qiT​kj​/d​. Softmax divides esije^{s_{ij}}esij​ by the sum of the exponentials over keys for this query. The output vector oio_ioi​ is the sum of the vjv_jvj​ weighted by those probabilities. Two coordinates of the same output row share the same weights. Two different queries usually have different weights, even when they read exactly the same keys and values. That distinction between sharing an input and depending on another row’s result eventually determines how much of one head can run in parallel.

The scale inside the dot product has a numerical purpose. If the coordinates of a query and a key are independent, centered, and have unit variance, their unscaled dot product is a sum whose variance grows with the width. Dividing by the square root of the width keeps its typical magnitude comparable as the head grows. This is the motivation in the Transformer paper, rather than an assumption that every trained model produces independent Gaussian components. Scaling scores changes the distribution that softmax computes. Subtracting the same constant from every score in one row, on the other hand, leaves that distribution unchanged. The distinction matters because an optimized kernel can change the latter constant from tile to tile, but it must consistently implement the model’s prescribed score scale. Vaswani et al., §3.2

For row 37, imagine first writing all 2,048 scores to an array. Once the whole array is available we can find its maximum, subtract that maximum, exponentiate and sum the shifted scores, and divide every exponential by the sum. A final matrix multiplication then forms each of the 64 value coordinates. In matrix notation the three results are S=QKT/dS=QK^\mathsf{T}/\sqrt dS=QKT/d​, P=softmax⁡row(S)P=\operatorname{softmax}_{\rm row}(S)P=softmaxrow​(S), and O=PVO=PVO=PV. These operations are a good fit for a library interface. Both products can go to an exceptionally well optimized matrix multiplication routine. The cost is that the interface between successive routines now consists of the full score matrix followed by the full probability matrix. A fast implementation of each individual routine still has to deliver those inputs to the next one.

The unit of storage grows differently from the unit of output. At eight heads and 2,048 query and key positions, one full intermediate contains 8×2,04828\times 2{,}048^28×2,0482 entries. In the local materialized implementation the scores use FP32, so their allocation occupies 128 MiB. The probabilities use FP16 and occupy another 64 MiB. The output at the same head count and width 64 contains 8×2,048×648\times2{,}048\times648×2,048×64 FP16 numbers, or 2 MiB. Increasing the sequence length by a factor of two doubles the output and quadruples the intermediate storage. A model that actually asks for the entire attention map must pay to deliver it. The usual attention interface asks only for the weighted values. Its mathematical specification gives an implementation freedom over the two much larger arrays.

Masks determine which scores belong in the row. We will follow dense, unmasked row 37 unless stated otherwise. In causal self-attention with zero-based indexing and aligned query and key positions, it has only 38 eligible keys, positions 0 through 37. A key forbidden by the mask contributes zero weight to both numerator and denominator. Rows near the beginning then have less arithmetic to perform than rows near the end, which matters to a parallel schedule. The mask changes the permitted set of interactions. A different algorithm for evaluating those interactions need not change it. In particular, none of the dense laptop timings below obtains its speed from discarding score entries or pruning attention heads.

Online normalization before FlashAttention

A conventional numerically stable softmax makes one pass to find a maximum, one to sum shifted exponentials and, if individual probabilities are needed, another to normalize the outputs. The maximum seems to require seeing the last score before even the first exponential is useful. In 2018 Milakov and Gimelshein showed how to carry a maximum and an exponential sum through a stream of scores in the same pass. The observation that makes this possible is that a change of maximum rescales every previous term by the same factor. A sum already expressed in the old scale can be moved into the new one without seeing its individual terms again. Milakov and Gimelshein, §3

If another group BBB used a different maximum, choose M=max⁡(mA,mB)M=\max(m_A,m_B)M=max(mA​,mB​) as their common scale. Multiplying the two partial states by their respective conversion factors gives

The new state is (M,ℓ,u)(M,\ell,u)(M,ℓ,u). It represents precisely the union of the two groups as long as their keys are disjoint and together cover the desired set. To see why, multiply an individual term esj−mAe^{s_j-m_A}esj​−mA​ by emA−Me^{m_A-M}emA​−M. Its old maximum cancels, leaving the term that a single pass using MMM would have produced. The same cancellation holds after multiplication by any coordinate of vjv_jvj​. Only the sums survive in the state, so the additional memory for a row is one maximum, one scalar denominator and one vector the width of the value. The division o=u/ℓo=u/\ello=u/ℓ can wait until the last group arrives.

A three-key example will also serve later when we discuss backward and asynchronous scheduling. Give our query the scores (0,log⁡2,log⁡3)(0,\log 2,\log 3)(0,log2,log3) and use the scalar values (2,4,1)(2,4,1)(2,4,1). The first tile contains only the first key, so its state is (0,1,2)(0,1,2)(0,1,2). The second tile contains the other two keys and uses log⁡3\log 3log3 as its maximum. Their shifted weights are 2/32/32/3 and 111, hence the denominator is 5/35/35/3 and the numerator is 11/311/311/3. To merge, the first tile’s entries must both be multiplied by 1/31/31/3. The combined denominator is 222 and the numerator is 13/313/313/3, so the output is 13/613/613/6. A direct weighted mean with unnormalized weights 1,2,31,2,31,2,3 gives the same answer.

The two separately normalized tile outputs would have been 222 and 11/511/511/5. Giving these two results equal weight would yield 2.12.12.1, which differs from 13/613/613/6. A tile that contains more keys need not carry more probability mass, either. Here the second tile carries five sixths of the mass because its unshifted weights sum to five. It is the rescaled denominator that tells the merge how much each tile counts. This is also why knowing only the maximum is insufficient. A software implementation that saves an already normalized output can still recover a correct update if it retains the denominator and maximum needed to reconstruct the numerator in the new scale.

One can process the tiles sequentially or combine their summaries in a tree. In exact arithmetic those choices produce the same sum over keys. Floating-point additions round at different points, so a correct implementation need not match the bit pattern produced by a different grouping. A useful correctness check asks whether the error against a higher precision reference is consistent with the chosen input and accumulator formats. It also checks the masks and empty tiles. When no key in a tile is eligible, that tile contributes no mass and the current state can be left alone. Blindly subtracting an initial maximum of negative infinity from another negative infinity instead creates an undefined intermediate. This exceptional case matters even though the dense three-key calculation never encounters it.

In 2021 Rabe and Staats developed a memory-efficient implementation of exact attention from this kind of summary. In their chunked implementation, a block of queries sees one block of keys and values at a time. For each query, the chunk returns a maximum, an exponential sum and a summed value vector. A later reduction finds the maximum across chunks and rescales their contributions. Reading the value vectors while the local weights still exist avoids having to retain a complete probability vector just to multiply it by values later. The listing also detaches the maximum used for numerical stabilization from the gradient. The normalized result is invariant to an additive shift of the logits, so gradients through an auxiliary choice of shift are unnecessary for the desired derivative. Rabe and Staats, Figure 1

Their chunk size illustrates the distinction in terms of memory capacity. Fix a group of queries and the width, and let a key chunk contain ccc positions. Enlarging a chunk increases the scratch space for its scores roughly in proportion to ccc. It also decreases the number of retained chunk summaries roughly in proportion to N/cN/cN/c. Balancing the two terms leads to a key chunk of order N\sqrt NN​ in the memory-oriented construction. Hardware can favor another choice because a matrix unit needs useful tile dimensions and a launch has a cost of its own. The memory required for these auxiliary objects also excludes the input and output arrays, which the caller necessarily supplies.

This predecessor isolates a distinction that is easy to lose in the history of FlashAttention. A bounded or chunked intermediate can make a sequence fit in memory without specifying how many times the same data crosses a GPU’s memory hierarchy. One implementation might leave chunk summaries for a second kernel. Another might keep a particular query’s summary next to its accumulator until its last key arrives. Both exploit the same algebra and can return the same answer. To predict their performance we need to know where the summaries, tiles and matrix products live while the program runs. That question leads from the online normalizer to the first FlashAttention.

FlashAttention makes attention I/O-aware

A matrix multiplication performed one output element at a time would read the same query each time it advances to another key. Fast GPU matrix multiplication instead brings tiles of operands into on-chip storage where many threads can reuse them. The original FlashAttention paper applied this reasoning to the composition of two matrix products and a row reduction. A score tile has a short useful life. Once the kernel has used its entries to update the running normalizer and to weight the corresponding value tile, it can give that space to the next score tile. Fusing the three computations only helps if their temporary storage and required inputs can coexist on chip during this interval.

Suppose a block is working on 32 queries and 32 keys at a time. It needs a tile of scores with 1,024 entries. At four bytes per entry that is 4 KiB, independent of whether the head contains 512 positions or 2,048. If the head width is 64, the 32 queries also need 2,048 input coordinates and the partial outputs contain 2,048 accumulator coordinates. Keys, values and transient matrix fragments need space as well. Doubling the score tile’s width improves potential reuse of queries but also increases the number of scores the block must accommodate before their consumers finish. These sizes describe different objects with different lifetimes. Adding all the entries of the full tensors would hide the opportunity to recycle storage, while counting only the 4 KiB score tile would understate what the block needs to run.

Key-tile reuse in Algorithm 1

In the published forward algorithm, the outer loop chooses a key tile and its matching value tile and loads them into fast memory. An inner loop brings in a query tile and its existing partial state. The kernel computes scores between just those two tiles, updates the row statistics and partial output, and writes the updated query state back. It then keeps the same keys and values available for another query tile. After all queries have used that key tile, the outer loop advances. Row 37 therefore returns to the working set multiple times. At the end of its last visit, its partial output becomes the requested answer. FlashAttention, Algorithm 1

Consider the first two visits to our three-key example under this loop order. At the end of the first visit the output in the published algorithm is already normalized, so the stored value is 222, along with the maximum zero and denominator one. On the second visit the upcoming maximum makes the old numerator worth one third as much on the new scale. With a normalized old output, the kernel first recovers its weight by multiplying that output by its old denominator and the conversion factor. It then adds the new tile’s numerator and divides by the new combined denominator. If the intermediate output had instead been the unnormalized uuu, the old denominator would not appear in the numerator update. Confusing those two meanings of a stored output produces a kernel that can pass the single-tile case and fail as soon as a second tile changes the mass.

The I/O analysis makes the choice of loop order quantitative. Let NNN be the number of queries and keys in one head, ddd their width, and MMM the on-chip capacity in the paper’s units of scalar elements. In Algorithm 1 the number of keys that can be held together scales as M/dM/dM/d. There are then on the order of Nd/MNd/MNd/M outer iterations. Each one streams a collection of query and partial output rows proportional to NdNdNd. Multiplying those quantities yields the paper’s Θ(N2d2/M)\Theta(N^2d^2/M)Θ(N2d2/M) transfers between the two levels of its memory model for d≤M≤Ndd\le M\le Ndd≤M≤Nd. The materialized algorithm takes Θ(Nd+N2)\Theta(Nd+N^2)Θ(Nd+N2) transfers. Increasing the capacity permits the tiled algorithm to amortize a pass over the queries across more keys. The theorem counts elements moving between abstract levels, so plugging in a capacity expressed in bytes without converting the element size would give a misleading estimate. For long sequences, compare the two formulas at a fixed width. The tiled bound buys an asymptotic reduction over the quadratic term when the on-chip capacity grows faster than the square of that width. Proposition 3 makes a separate statement across capacities. A single exact algorithm cannot improve the asymptotic order for every capacity in the stated interval. This leaves room for a different algorithm to do better at a particular capacity. FlashAttention, Theorem 2 and Proposition 3

At fixed head width and fixed fast-memory capacity the tiled algorithm still evaluates all dense query–key interactions. It gains an important factor in transfers without making the attention arithmetic linear in sequence length. To see the difference, double the length along both axes. Every old query now sees new keys, and every new query sees all the old and new keys. There are four times as many scores to compute regardless of whether they live in a global array or a reusable tile. Output storage and per-row statistics only double. Time can respond to all three quantities, since the bottleneck can move after a large intermediate stops crossing the memory hierarchy.

Recomputing attention probabilities in backward

Discarding PPP after a forward pass is straightforward during inference. In training, the loss gradient arrives later and depends on the very probabilities that have disappeared. Saving them for backward would give back a large part of the memory advantage. The alternative is to retain enough information to reconstruct a small tile exactly in real arithmetic. Given the original query and key and the row’s normalization statistics, we can recompute a score and recover its probability. Represent the row normalizer by Li=mi+log⁡ℓiL_i=m_i+\log\ell_iLi​=mi​+logℓi​. Then Pij=exp⁡(sij−Li)P_{ij}=\exp(s_{ij}-L_i)Pij​=exp(sij​−Li​). An implementation retaining mim_imi​ and ℓi\ell_iℓi​ separately has the same information. The original paper’s Algorithm 1 returns them separately. FlashAttention-2 describes storing the single log-normalizer for backward.

Why store the normalizer at all if the score is cheap enough to recompute? If we know only the query and one key tile, that tile does not tell us how strongly excluded keys competed for the row’s probability mass. Dividing its weights by its own denominator would recreate a distribution that sums to one inside the tile. The gradient would incorrectly treat each tile as an entire attention row. A single saved scalar per query preserves exactly the piece of global context that the local computation needs. The numerator does not need to be rebuilt for each such reconstruction because the forward calculation already returned the normalized output vector.

Take the gradient with respect to one output vector, gi=∂L/∂oig_i=\partial{\cal L}/\partial o_igi​=∂L/∂oi​. The probability on an edge connects a value vector to that output, so the contribution from query iii to the gradient of vjv_jvj​ is PijgiP_{ij}g_iPij​gi​. To find how much the loss cares about the probability on this same edge, take the dot product giTvjg_i^\mathsf{T}v_jgiT​vj​ and call it dPijdP_{ij}dPij​. One last step passes through softmax. Increasing a score takes mass from all the other keys. The term to subtract from dPijdP_{ij}dPij​ is the probability-weighted average of dPdPdP for the whole row. Since gig_igi​ is fixed within the row, that average simplifies to

Di=∑jPij giTvj=giT ⁣(∑jPijvj)=giToi,dSij=Pij(dPij−Di).D_i=\sum_jP_{ij}\,g_i^\mathsf{T}v_j =g_i^\mathsf{T}\!\left(\sum_jP_{ij}v_j\right) =g_i^\mathsf{T}o_i,\qquad dS_{ij}=P_{ij}(dP_{ij}-D_i).Di​=j∑​Pij​giT​vj​=giT​(j∑​Pij​vj​)=giT​oi​,dSij​=Pij​(dPij​−Di​).

This identity turns a potentially expensive scan across every key into a dot product between two vectors the width of a single head. In the hand example give the scalar output an upstream gradient of one. The weighted average is then D=13/6D=13/6D=13/6. The gradient of the third score is (1/2)(1−13/6)=−7/12(1/2)(1-13/6)=-7/12(1/2)(1−13/6)=−7/12. That sign makes sense. Giving more weight to the third value, which is below the current average, reduces the output. The first and second score gradients are −1/36-1/36−1/36 and 11/1811/1811/18. Their sum with the third is zero, as required, since adding the same constant to all scores cannot move the output. This small check catches a mistake that a forward-only implementation cannot expose, namely using an unweighted mean in the softmax derivative.

The remaining gradients expose a different ownership problem. Each query collects contributions from all keys into dQdQdQ. Each key and value collects contributions from all queries into dKdKdK and dVdVdV. Recomputing a score tile supplies the common probabilities needed for both families. It also adds an extra matrix multiplication to the backward work. That can be a good exchange if reading a saved quadratic probability matrix costs more than repeating the dot products and processing them where they are used. Masking and dropout qualify this reasoning. If a forward pass randomly suppresses weights, backward needs the same suppression pattern. A reproducible random-number state or equivalent saved information must accompany recomputation. The dense local experiments use neither a mask nor dropout.

Recomputation describes how gradients can fit. It leaves a scheduling decision that will return in FlashAttention-4. A block that owns a key tile can complete its own dKdKdK and dVdVdV by visiting all queries, but other key tiles also contribute to the very same dQdQdQ rows. Independent blocks need a reduction or another coordination method there. Changing ownership can exchange which gradient stays private and which gradient several blocks must combine. The forward pass has an easier form of independence. Once a block owns a set of query rows, it can compute every one of their output coordinates without asking another query owner for a partial sum. FlashAttention-2 makes systematic use of that difference. FlashAttention, Algorithm 4 · FlashAttention-2, §3

FlashAttention-2 distributes query rows and reduces work between warps

The 2023 FlashAttention-2 paper starts from a kernel that already avoids the square intermediates. Improving it therefore calls for a different explanation from saving another copy of the score matrix. Large matrix products can use specialized Tensor Cores, while reductions, exponentiation, division and synchronization use resources with different throughputs. An instruction that looks negligible when every operation is counted as one mathematical step can be expensive on the path between two matrix multiplies. The revised algorithm reduces some of this row work and changes how the work that remains is distributed, at two distinct levels of the GPU.

One change follows directly from the normalized and unnormalized representations we saw in Algorithm 1. Suppose the old output is a normalized weighted average. Updating it tile after tile requires multiplying it back by an old denominator, adding the new contribution in the correct scale and dividing by the new denominator again. If a block can hold its query tile for the whole key traversal, it can instead maintain uuu throughout. It still rescales uuu whenever its reference changes, but it divides each output coordinate by ℓ\ellℓ only once, on the final store. A tile that raises the maximum still has an effect on every coordinate. A tile that merely adds probability mass no longer forces a round trip through normalized coordinates at that point. This choice saves actual scalar operations while giving the caller the same normalized result.

Query block assignment and output addresses

Row 37 needs all the keys and values in its head. It needs no result from row 36. In a grid that splits only by the number of batch–head pairs, many independent rows can be hidden behind one physical block’s loop. This matters most when there are few heads or few batch items and the sequence is long. FlashAttention-2 exposes query blocks along the sequence dimension. A block can load its own query tile and visit all its eligible key and value tiles, while another block computes the next query tile from the same arrays. Their global stores cover disjoint intervals. Once the input tensors are ready, neither block needs a signal from the other before it starts. FlashAttention-2, §3.2

This example explains how query splitting differs from splitting across the keys of a single query. Two blocks that independently handle different key subsets for row 37 can each compute a valid local summary, but neither has the final answer. The summaries must meet and be rescaled to a common reference. That is a perfectly sensible way to get more parallelism when only one query is available. It calls for an additional reduction. Giving different complete rows to the two blocks avoids that communication in the full-sequence forward problem. The best axis on which to buy parallelism depends on how many independent queries exist in the first place.

Sliced-Q and sliced-K inside a thread block

The same ownership question appears one level down. An NVIDIA warp contains 32 threads. Threads of a warp cooperate on matrix instructions, and several warps in a block can share data and synchronize through shared memory. Imagine two warps assigned to one tile of 32 queries by 32 keys. In a sliced-K organization, warp 0 could handle key columns 0–15 and warp 1 columns 16–31. Both warps then contribute weighted value coordinates for every query in that tile. When their partial value sums are on a common normalization scale, somebody must add the two contributions for row 37. Each warp can finish its own multiplication and still be unable to advance the final output without the other’s result.

In a sliced-Q organization, give warp 0 the first 16 query rows of the current block and warp 1 the other 16. In block 1, global row 37 is local row 5 and belongs to warp 0’s query range. That warp can form its rows’ entire value-product contribution for the current key tile. Both warps can still reuse the same key and value data. What changes is ownership of the accumulated output, and with it the need to exchange partial value sums through shared memory. The original paper illustrates this with four warps. The local code uses two. A production implementation may still use barriers for data staging or share other statistics. Eliminating one reduction does not eliminate every dependency within the block. FlashAttention-2, §3.3 and Figure 3

During softmax, one thread per local row calculates the shifted weights. It adds the FP32 weights to the FP32 denominator, rounds copies to FP16 for multiplication by VVV, and accumulates into an FP32 numerator. The two paths use the same final conversion to FP16. Because the warp split and the arithmetic are held fixed, their timing difference measures the effect of exposing additional query blocks in this implementation. FlashAttention-3 overlaps matrix multiplication, softmax and data movement on Hopper

Once row 37 has enough neighboring blocks to occupy the GPU, speeding it up requires looking inside a block’s execution. For a key tile jjj, the score product QKjTQK_j^\mathsf{T}QKjT​ must precede the exponential weights for that tile, and those weights must precede their product with VjV_jVj​. At first sight this appears to force a sequence of matrix multiplication, softmax and another matrix multiplication for every tile. The missing detail is the subscript. The score product for tile j+1j+1j+1 uses the same queries and the next keys. It does not consume the previous tile’s value product. Nor do the next tile’s row maximum and denominator require the old value accumulator to have finished. FlashAttention-3 exploits these points of independence on hardware that can keep a matrix operation in flight after its issuing group has moved on.

Hopper’s Tensor Memory Accelerator, or TMA, lets a designated issuing thread request a multidimensional transfer between global and shared memory using a tensor description. A producer warpgroup can arrange for the query data and successive key and value tiles to arrive in shared memory. Consumer warpgroups participate in warpgroup matrix multiply-accumulate instructions, abbreviated WGMMA. Four warps form one such group. In the forward pipeline the Tensor Cores can continue an issued matrix operation while independent instructions proceed. Issuing either a copy or a multiply starts work. A consumer is allowed to use the result only after the relevant completion condition holds. The distinction between issue and completion is what gives software a useful interval in which to place independent work. Hopper Tuning Guide, §1.4.1.2 · FlashAttention-3, §3.1

Shared-memory buffer ownership and the two-tile consumer pipeline

Think of two slots allocated for successive key tiles. While consumers read slot zero, a producer can ask TMA to populate slot one. Before any consumer uses slot one it must observe that its load has completed. Before the producer recycles slot zero for a later key, it must observe that the last consumer has stopped reading it. The first condition prevents a consumer from seeing partly transferred data. The second prevents an otherwise correct load from erasing a matrix operand still in use. Ring buffers require a phase or equivalent generation as well as a slot index, since slot zero will become ready many times during a long sequence. A previous notification about that index cannot certify that the newly requested tile has arrived. Released Hopper load path

This producer–consumer split addresses overlap between movement and arithmetic. Within a consumer warpgroup there is a second opportunity, between the two kinds of arithmetic. Number two successive key and value tiles zero and one in visitation order. Once the scores of tile zero are ready, the group can derive its shifted probabilities. The consumer first issues the score product for tile one, QK1TQK_1^\mathsf{T}QK1T​, then issues the tile-zero value product P~0V0\widetilde P_0V_0P0​V0​ when V0V_0V0​ is ready. Once the tile-one scores are available it can compute their shifted probabilities while the tile-zero value product is still in flight. Return to the three-key calculation. Tile one raises the maximum from zero to log⁡3\log 3log3. As soon as its scores are ready, the scalar instructions can find that maximum and compute the conversion factor of one third. Meanwhile the Tensor Cores may still be forming tile zero’s old numerator. Calculating a factor of one third is safe at that point because the factor depends only on the reference values. Applying it to an unfinished accumulator would race with the operation that is producing that accumulator. The correct schedule waits before the multiply that rescales the old numerator. It need not impose that same wait before calculating the factor. Separating these two actions preserves the recurrence more faithfully than treating “run softmax” as a black box that depends on the entire previous tile.

In the released Hopper consumer loop, two nearby waits make the distinction visible. After it issues the next score product and the earlier tile’s value product, warpgroup_wait<1>() allows one outstanding instruction group to remain. The code then applies masking and computes the row maximum, scale and online weights from the ready scores. The later warpgroup_wait<0>() drains the outstanding groups before the value operand is released. The template places the output rescaling according to its selected variant. Reading those waits together with the tile indices is more informative than counting barriers. Waiting for both products at the first point would discard overlap. Releasing the value tile after the first wait could allow the producer to overwrite an operand while its multiply was still in flight. Released Hopper consumer loop

The authors also describe a ping-pong schedule involving two consumer warpgroups. One group can do non-matrix work for its rows while the other issues matrix instructions for different rows. That is different from overlapping two tile stages inside the same consumer group. Both exploit spare execution resources during an interval when a particular result is unavailable, but their resource costs differ. Holding two sets of partially completed work consumes registers or buffers, and synchronization is needed at the point of reuse. A longer pipeline does not automatically keep the device busier. The extra live state can make it harder to admit other work, and the initial fill and final drain leave less useful overlap on short sequences. Tri Dao’s Hopper pipeline diagrams

FP8 quantization, outliers and matrix layouts

A separate part of FlashAttention-3 uses FP8 Tensor Core inputs. A smaller input format gives matrix hardware a higher potential throughput, but dots and probabilities depend on how values were represented before multiplication. The paper’s E4M3 format has four exponent bits and three explicit fraction bits. If one large entry sets the scale for an entire tensor, smaller entries share a quantization grid chosen to accommodate that outlier. Block quantization gives each query, key or value tile its own scale. Because the score calculation is already blocked, the scale for a particular query–key product can be constructed from the two input scales. This changes the amplitude of the approximation errors presented to softmax. The usual subtraction of a row maximum protects the exponential evaluation from large absolute scores, but cannot restore information lost when an input coordinate was rounded. FlashAttention-3, §3.3

The authors also transform queries and keys by the same orthogonal matrix before rounding. In exact arithmetic (QR)(KR)T=QRRTKT=QKT(QR)(KR)^\mathsf{T}=QRR^\mathsf{T}K^\mathsf{T}=QK^\mathsf{T}(QR)(KR)T=QRRTKT=QKT. For a two-coordinate illustration, take a query (a,0)(a,0)(a,0) and a key (b,0)(b,0)(b,0). A normalized Hadamard transform converts them to (a/2,a/2)(a/\sqrt2,a/\sqrt2)(a/2​,a/2​) and (b/2,b/2)(b/\sqrt2,b/\sqrt2)(b/2​,b/2​). Each product contributes half of ababab, so the original score survives. The large coordinate has been distributed over two entries. At larger widths, a randomized sign pattern and a fast Hadamard transform distribute concentrated features at a practical cost. Rounding the transformed vectors then yields a different approximation to the same target dot product. The algebra provides invariance before rounding, while numerical comparisons determine how the approximation behaves afterward.

Layout also matters. A value tensor normally places neighboring head coordinates next to each other. The FP8 instruction used for the probability–value multiply wants a different contiguous axis. Fetching the same bytes quickly into shared memory does not itself give them the layout required by that instruction. The implementation can transpose tiles on chip and arrange the intermediate probability fragment appropriately. This is another case where the attention formula stays unchanged while the cost of preparing an operand influences what hardware throughput is attainable. Using an FP8 format introduces these choices independently of the FP16 scheduling ablation in the preceding table.

The paper evaluates error against an FP64 reference on inputs with deliberately injected outliers. In the FP8 comparison the per-tensor baseline had an output root-mean-square error of about 0.024, while the block-quantized, transformed variant gave about 0.0091. That is roughly a factor of 2.6 for this error metric and distribution. It cannot be interpreted as a factor of 2.6 in model accuracy. One quantity measures coordinate errors for one operation on generated inputs, and the other would require a trained model, a task and an outcome metric. The example is nevertheless consequential for the kernel. Hardware that doubles nominal product throughput can be useful only after the operands have a workable layout and an acceptable numerical representation. FlashAttention-3, §4.3 and Table 3

FlashAttention-4 forward and backward pipelines on Blackwell

FlashAttention-3 brought the dependence between a score, its exponential and the corresponding value product into the schedule. FlashAttention-4, published as a preprint in 2026, asks what happens when the relative speeds of those operations change. The paper studies datacenter Blackwell devices, principally the B200. Tensor Core throughput grew faster than either shared-memory bandwidth or exponential throughput across the generations considered. Accelerating matrix multiplication under those conditions can make the intervening row operations a larger fraction of total time, even if no single row operation becomes slower. The laptop teaching kernel uses the WMMA path described above. The TMEM pipeline and B200 performance figures come from the datacenter study. FlashAttention-4, §§2–3

The cost of an exponential relative to two matrix products

Take 128 queries, 128 keys and head width 128. A score product performs 128 multiply-adds for each of 128×128128\times128128×128 scores. The value product does the same amount of arithmetic for an output tile of 128 rows by 128 coordinates. Counting a multiply and add as two floating-point operations, the two products total 4×1283=8,388,6084\times128^3=8{,}388{,}6084×1283=8,388,608 operations. Dividing by the paper’s B200 model of 8,192 BF16 matrix operations per clock per SM gives 1,024 cycles of matrix throughput. The same tile needs 16,384 exponentials. At 16 exponential results per clock per SM, those also require 1,024 cycles. The paper’s estimate for the shared-memory traffic in this particular forward configuration is 768 cycles.

These counts make the value of overlap more concrete. If execution can keep the matrix and exponential units busy concurrently, their service demands need not add in full. If a schedule serializes them, both the matrix and exponential times can appear on the critical path, even though an exponential is just one operation in the formula for a weight. Conversely, speeding up just the matrix side of an ideally overlapped schedule cannot push it below the time needed to form all those exponentials. The cycle counts are throughput calculations for a chosen tile and peak rates. They leave out launch cost, instruction issue details, synchronization, cache effects and startup. Confronted with an observed time for a whole head, we cannot label exactly 1,024 cycles of it “softmax” by pointing to this model. The calculation tells us which resource deserves investigation. FlashAttention-4, Table 1

Blackwell also changes the place where a matrix instruction leaves its answer. In the Hopper schedule a warpgroup’s matrix accumulators occupied registers. The fifth-generation tensor instructions used here can issue asynchronously and write their result into a separately managed on-chip space called tensor memory, abbreviated TMEM. TMA, the copy engine we met on Hopper, and TMEM, the storage for matrix operands and accumulators here, are different pieces of hardware. The kernel has to allocate its tensor memory, assign distinct regions to tiles whose lifetimes overlap, and perform the appropriate movement and synchronization before threads consume a result. Issuing a matrix instruction from a designated thread does not turn completion into a synchronous register assignment. NVIDIA PTX ISA, fifth-generation Tensor Core instructions

Follow row 37 across this new boundary. A score product writes a tile to TMEM. Threads doing softmax read the rows they own, determine the reference and exponential weights, and make the weights available for the value product. The output accumulator can reside in another TMEM region. The paper’s forward organization keeps two query tiles in progress. Two softmax warpgroups process their respective rows, with a thread able to handle a whole score row of the chosen tile. A separate correction group can rescale the previous output while other work advances. Row ownership has therefore moved again since the sliced-Q example. The reason is the new destination and layout of the matrix result, which changes the cost of reaching across threads to collect a complete row.

There is still an actual capacity limit. Two large output tiles must remain live, and scores and shifted probabilities compete for the remaining TMEM. A result cannot be overwritten simply because a later tile has been issued. The authors arrange for score and probability storage to overlap only where their lifetimes allow it. Softmax threads must still hold many working values in registers as they transform an entire row. Moving an accumulator out of registers permits a new schedule, while organizing each row’s scalar work can introduce a new register demand. This is why the position of the bytes and the identity of their next consumer remain more informative than a claim that a later architecture has “more memory.” FlashAttention-4, §3.1.2 and Figure 1

Selective exponential emulation and conditional rescaling

The paper uses a mixture of two ways to compute a base-two exponential. The hardware multifunction unit handles one part of a row. For selected entries the kernel uses ordinary arithmetic pipelines. Write x=k+rx=k+rx=k+r with integer k=⌊x⌋k=\lfloor x\rfloork=⌊x⌋ and 0≤r<10\le r<10≤r<1. Then 2x=2k2r2^x=2^k2^r2x=2k2r. The power of two can be formed by manipulating the floating-point exponent, while a short polynomial approximates 2r2^r2r over a bounded interval using fused multiply-add instructions. For example, x=−2.25x=-2.25x=−2.25 has k=−3k=-3k=−3 and r=0.75r=0.75r=0.75. The polynomial need only handle 0.750.750.75, and the power-of-two factor restores the negative magnitude. Rounding toward zero would produce a negative fractional argument for this input and place it outside the interval for which the coefficients were selected.

The advantage of emulation is the use of an additional execution resource at the point where the exponential unit is busy. It brings more instructions, live registers and approximation error. Computing every exponential by this route could simply shift the bottleneck. The authors use it for a tuned fraction, around ten to twenty-five percent of entries depending on configuration. They separately check the polynomial against an FP64 reference before and after rounding the result to BF16. A difference visible in an FP32 intermediate may largely disappear after conversion to a lower precision operand, although that observation about one numerical step cannot establish zero error for an entire attention row. FlashAttention-4, §§3.1.3–3.1.4

A second saving comes from asking when the old output actually needs a new reference. The usual online algorithm always uses the largest score seen so far. That choice keeps every newly shifted exponential at most one. Algebraically the numerator and denominator can just as well share a slightly lower reference, as long as the exponentials remain representable. Return to the weights 1,2,31,2,31,2,3. Using zero as the reference gives ℓ=6\ell=6ℓ=6 and u=13u=13u=13. Using the true maximum log⁡3\log 3log3 gives ℓ=2\ell=2ℓ=2 and u=13/3u=13/3u=13/3. Both representations produce the same normalized output. The former saves a rescaling of the old numerator in this example. It also allows a shifted weight to exceed one, so its range must be justified in the format the kernel actually uses.

FlashAttention-4 keeps the old reference when the new maximum exceeds it by only a bounded amount. The paper gives a typical threshold of eight in base-two log units, a factor of 256 in the exponent. On an update that retains the reference, new terms and old terms must still be expressed relative to that same reference. Silently recording the new maximum while leaving the old numerator untouched would repeat precisely the error the online derivation was designed to avoid. When the difference grows too large the kernel performs a correction, and the final division uses consistent statistics. To keep control flow uniform the implementation can correct a warp when any member needs the correction. Thus the saved vector multiplies depend on how a row’s reference evolves, whereas every eligible score continues to participate in the mathematical result.

Two-CTA cooperation in backward and the reduction into gradients

The backward path reprises the gradient-ownership problem from FlashAttention. Five matrix products cover the recomputation of scores, the gradients of probabilities and values, and the gradients of queries and keys. Each product reads two operands. A tensor-memory path can supply some of them directly, leaving substantial traffic in shared memory for the others and for intermediate gradients. In the paper’s model for a 128×128128\times128128×128 tile with width 128, the one-CTA backward configuration needs about 2,560 cycles of matrix throughput and 3,328 cycles of shared-memory traffic. Here the largest estimated demand belongs to a different unit from the forward example. Moving more exponentials to ordinary arithmetic is therefore an incomplete answer to the backward bottleneck. FlashAttention-4, §3.2 and Table 3

A cooperative thread array (CTA) is a CUDA thread block. Blackwell’s two-CTA matrix mode allows a pair of blocks in the same cluster to participate in one matrix operation. Each can stage a portion of a shared operand and retain its own slice of the output. The partner blocks have to be launched and remain able to participate for the operation’s lifetime. This is a stronger relationship than two ordinary query blocks reading similar keys and hoping for a cache hit. It gives the kernel a way to stop fetching redundant copies through shared memory, at the cost of explicit coordination and constraints on which blocks execute together.

To see where the gradient reduction enters, return to dQidQ_idQi​. Two owners of different key ranges can both calculate valid contributions to the same query gradient. If each sends a separate partial sum to global memory, they need two updates to that destination. In the two-CTA backward scheme the partners exchange part of their score gradients through distributed shared memory. After this rearrangement, each partner has the rows for its own slice and a reduction extent spanning both key ranges. A matrix product can combine the two contributions before the result leaves the pair. The paper reports that this decomposition halves the global atomic reductions relative to its one-CTA counterpart. Contributions from other block pairs can still target the same gradient, so the remaining global reduction and its ordering still matter. FlashAttention-4, §3.2.3 and Figure 3

The exchange itself costs time. In the source paper’s comparison, the two-CTA schedule trades some distributed shared-memory traffic for lower operand traffic and fewer reads and writes associated with the query-gradient reduction. An implementation can overlap the exchange of one tile with independent work from another, much as Hopper overlapped the next score calculation with the previous tile’s value product. The mathematical derivative tells us which pieces may move independently. The paired hardware gives the scheduler a place to combine them, and the relative bandwidths decide whether making that combination earlier is worthwhile.

Causal workloads add a separate scheduling choice that does not depend on tensor memory. A block that owns late query rows in a sequence must visit more key tiles than one that owns early rows. Finishing many short blocks first can leave a few long blocks on the device after most SMs have become idle. FlashAttention-4 arranges work to start expensive tiles earlier while preserving opportunities to reuse keys in L2. Sorting by duration without regard to batch and head could evict those keys before the next consumer arrives. This is the same ownership and reuse tradeoff that appeared in the original algorithm, now applied to the order in which independent work reaches different SMs. FlashAttention-4, §3.3

The B200 forward measurements in the paper compare BF16 implementations at specified sequence lengths, masks and head dimensions. At head width 128, Figure 4 reports about 1.1–1.3 times the performance of cuDNN 9.13.0 and 2.1–2.7 times that of the tested Triton baseline. The authors also note that newer releases of cuDNN adopted related techniques and reached similar performance. The opponent’s version is part of the result. The B200 curves measure an entire implementation that also schedules work tiles and handles load imbalance. They cannot assign that whole gain to polynomial exponentials, TMEM or paired CTAs taken individually. In particular, two-CTA gradient cooperation belongs to a backward explanation and cannot account for a forward-only timing curve. FlashAttention-4, §5 and Figure 4

The paper also separates the cost of making a kernel from the cost of running it. FlashAttention-4 expresses its schedules in the Python-embedded CuTe DSL and specializes them to tile and hardware choices. Table 4 reports 2.5 seconds to compile one forward kernel in that setup, compared with 55 seconds for one C++ template-based FA3 forward kernel in the authors’ comparison. Compilation latency matters to a developer testing new layouts or a deployment preparing many specializations. Once a binary exists, a forward timing measures a different interval. Mixing those two clocks would conceal whether an optimization improved developer iteration, first use or the steady-state attention operation. FlashAttention-4, §4 and Table 4

Selecting an attention implementation and interpreting its timing

A high-level attention call leaves many of these choices to the runtime. In PyTorch 2.9 the scaled dot-product attention interface can select backends according to the device, dtype, layout and supported features. The requested mask and dropout probability also matter. An application measuring inference should explicitly pass zero dropout when that is the intended operation. When diagnosing a specific fused path, the backend-selection context manager can limit the allowed implementations and expose why a desired backend cannot handle a particular input. Calling the interface by name establishes that the application requested attention. To attribute a measurement to an implementation one must also determine which kernel actually ran. PyTorch 2.9 scaled dot-product attention

The local study used Windows 11, CUDA 13.1.115, driver 610.88 and an RTX 5070 Laptop target of sm_120. For the query-grid comparison it supplied normal inputs with standard deviation 0.6 rounded to FP16. An independent FP64 CPU calculation checked ten query rows per head, including tile boundaries, and PyTorch’s efficient attention backend supplied a second full-tensor numerical comparison. The sampling scheme tests different failure modes. A wrong launch index often shows up at the first row of a new tile, while a warp or scaling error can affect many rows. Agreement with a separate reference makes the paired timings meaningful as measurements of equivalent output work on these inputs. It does not turn the teaching template into the implementation of any paper.

It is useful to decide what a measurement could distinguish before spending time collecting it. If changing sequence length makes the two square allocations dominate the working set, compare bytes and memory traffic with the output held fixed. If throughput falls at small batch and head counts, trace the launch grid and the first and last rows assigned to each block. Once there are enough blocks and no full intermediate to remove, a matched on-device pipeline comparison is informative. None of these tests requires extrapolating a laptop event time into an H100 or B200 performance prediction. The timing appendix records which variables the local experiment actually controlled.

In our opening example with head width 64, row 37 writes the same 64 output coordinates in every generation. To understand the first FlashAttention, follow the last use of a score and notice that no later kernel needs to read the complete score matrix. To understand the second, find the block and warp that can finish that row without exchanging partial outputs with its neighbors. On Hopper the important interval begins when an operation is issued and ends when its consumer must wait. On Blackwell the same dependency must be followed across tensor memory, the exponential pipelines and, for gradients, cooperating blocks. This history offers a practical order of investigation. Determine what the next consumer actually needs, where its input lives and whether enough independent work can reach the machine. Then use a baseline that changes the proposed limiting factor. That is how an exact attention formula can remain recognizable from the three-key example to a B200 kernel while the most effective optimization changes several times.
