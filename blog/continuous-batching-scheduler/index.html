How a Continuous-Batching LLM Scheduler Works

This note explains iteration-level scheduling, paged KV cache, chunked prefill, prefix caching and preemption. For each one, a reader can work out what it gains and what it costs.

A modern LLM serving loop keeps the GPU busy with five mechanisms: iteration-level scheduling, a paged KV cache, chunked prefill, prefix caching and preemption. For each mechanism, this note states the problem it solves, how it works, what it gains and what it costs. The arithmetic of prefill and decode that the note relies on is derived in The Arithmetic of Prefill and Decode in LLM Inference, and the split of the two phases onto separate GPUs is covered in DistServe: Serving Prefill and Decode on Separate GPUs.

The notation follows the arithmetic note. PPP is the number of parameters, bbb the batch size, LLL a prompt length, SSS the cached context length and MkvM_{\text{kv}}Mkv​ the KV bytes per token. The allocator works in blocks of kkk tokens, and kkk is 16 unless another value is stated. TPOT is the average interval between the output tokens of one request, as in DistServe: (tlast−tfirst)/(m−1)(t_{\text{last}}-t_{\text{first}})/(m-1)(tlast​−tfirst​)/(m−1) for mmm output tokens. A single interval between two consecutive tokens is called the time between tokens (TBT). Numbers marked (computed) are my own arithmetic on assumptions stated in place; all other numbers come from the sources listed at the end.

Why a static batch wastes the GPU

The simplest serving loop takes a batch of requests, prefills them, and then runs decode steps until every sequence in the batch has finished. The batch ends together, although the requests do not. Three kinds of waste follow, and each later mechanism removes one of them.

Slots stay idle after early finishes. Take four requests that generate 20, 100, 150 and 220 tokens (computed). A static batch runs 220 steps with four slots and so has 880 slot-steps of capacity, but only 490 tokens are produced, so the utilization is 56%. One slot idles from step 20, two slots from step 100, and three slots from step 150. Continuous batching first removes this waste of 44% of the decode capacity.

New requests wait for the slowest request. The same batch admits nothing new until step 220, so a request that arrives at step 30 waits 190 steps, and the queue behind it waits longer. In an interactive service, users see this wait as latency, and this is why admission cannot be tied to the end of a batch.

Decode and prefill collide. A request admitted in the middle of a batch needs its prompt prefilled. If the loop runs this prefill as a separate step, every running decode stalls for its duration; if the loop appends the prompt to the running batch, the rows have different shapes, and attention must handle them. Both cases are handled explicitly below.

Iteration-level scheduling

Orca (OSDI 2022) introduced the fix: the scheduler plans iterations instead of batches. After every forward pass, it may remove finished sequences and admit new ones, so the batch is formed again at every step. Because freed slots are refilled at once, the four-request example above rises from 56% to almost 100% of the slots, until memory or compute becomes the limit.

The cost is that one step now mixes two kinds of rows. Each decode request contributes one query token, while a newly admitted request contributes a prefill of LLL tokens. The linear projections work on each token separately, so they accept all rows concatenated into one matrix. Attention is different, because a prefill row attends over its whole prompt, whereas a decode row attends over its cached history plus one token. Orca’s answer is selective batching: it batches the projections across all requests and runs attention separately for each request.

The split has a price. Attention becomes one launch per request per layer, or one per group of requests with the same shape, so each step pays for more kernel launches and more bookkeeping as the batch grows. The scheduler also runs at every step, every few milliseconds, instead of once per batch, every few seconds. A decode step at small batch takes only a few milliseconds (computed in the arithmetic note: about 7.4 ms for the 7B model at batch 1), so a scheduler that needs a millisecond of CPU time per step already costs a visible share of each step. Serving systems therefore keep the work done in each iteration small.

The second effect concerns fairness of latency. Iteration-level scheduling admits a request as soon as a slot opens, and this shortens the queueing delay. However, the prefill of the new request now runs inside a decode step, and every running request waits for this step. The batch no longer waits for its slowest member, but it now contains a step that is expensive from time to time. Chunked prefill exists to limit the cost of this step.

The KV cache as pages

Contiguous allocation reserves memory for the longest allowed context. It reserves Smax⁡MkvS_{\max} M_{\text{kv}}Smax​Mkv​ bytes per sequence, where Smax⁡S_{\max}Smax​ is the longest context that the service allows. The reservation is made up front because the sequence may grow, and most sequences never use all of it.

An example shows the size of this waste (computed). Take a maximum context of 2,048 tokens, an average finished length of 500 tokens and 512 KiB per token. Contiguous allocation then reserves 2,048×512 KiB=12{,}048 \times 512\ \text{KiB} = 12,048×512 KiB=1 GiB per sequence and uses only 250 MiB, so 75% of the reservation is never written. A GPU with 66 GB free holds 61 reserved sequences, although the KV that these sequences actually write would allow 251. Lost capacity means a smaller batch, and a smaller batch means lower throughput.

PagedAttention (SOSP 2023) applies the paging idea of an operating system. The KV cache is stored in fixed-size blocks, and each sequence has a block table that maps its logical block index to a physical block. A sequence receives a new block only when it fills the last one, so its memory grows with the tokens it has produced, not with the tokens it may produce. Fragmentation is now limited to the unused tail of the last block, at most k−1k-1k−1 tokens. With k=16k = 16k=16 and an average length of 500 tokens, this is about 1.5% on average and 3% at worst (computed). The block table itself is small: 2,048 / 16 = 128 entries per sequence, four bytes each with 32-bit block IDs.

The indirection costs time inside the attention kernel. Reading the KV of a sequence is no longer a base pointer plus an offset; the kernel walks the block table and gathers blocks that are not contiguous. vLLM’s kernel does this walk inside the attention loop. The cost is extra address arithmetic and a less regular access pattern at small block sizes, and this is why kkk is a tuning parameter. Small blocks waste less memory at the tail and allocate in finer steps, whereas large blocks make the gather cheaper and waste more memory at the tail.

Paging also enables sharing. Two samples from one prompt, or the beams of one beam search, start from identical prefix blocks. The block tables of both sequences can point to the same physical blocks and mark them as copy-on-write. When one sequence appends a token into a shared block, the block is copied, and the table of that sequence is updated. The prompt KV is therefore stored once, however many samples read it. For nnn samples from one 2K prompt, the memory cost is one prompt plus nnn separate tails, not nnn full copies. A prefix cache reuses the same mechanism across requests.

Chunked prefill

A full prefill makes one step about ten times longer than its neighbors. A prefill of LLL tokens does 2PL2PL2PL FLOPs in one iteration. For the 7B reference model at 2K tokens, this is 28.7 TFLOP: 92 ms at the dense peak of an A100, or about 306 ms at 30% of peak (computed). A decode step of the same batch takes a few tens of milliseconds at most. When a full prefill runs inside the decode loop, the step becomes about ten times longer than its neighbors, and every running request sees one TBT that is about ten times longer than usual. The average TPOT rises much less: one stall of length Δ\DeltaΔ adds Δ/(m−1)\Delta/(m-1)Δ/(m−1) to the TPOT of a request with mmm output tokens. This is a direct result of the mechanism, not a scheduling bug.

Chunked prefill limits this jump with a token budget per iteration. The scheduler fills each step with up to BBB tokens of prefill work and with as many decode tokens as fit. A long prompt is split across several steps, and later chunks read the KV of earlier chunks from the cache. The FLOPs do not change, because the projection work adds up over the chunks and the attention work is the same in one call or in four. What changes is that each step now has a bounded cost, and decode tokens run between the chunks instead of waiting behind a full prefill.

The budget trades the time between tokens against TTFT. A smaller budget keeps the TBT of running requests flatter, but the prompt then needs more iterations, and this raises its TTFT and the per-iteration overhead. At B=512B = 512B=512 tokens, the 2K prompt becomes four chunks of about 76 ms each at 30% of peak (computed). A step that carries a chunk is then about 76 ms long instead of 306 ms. Sarathi-Serve (OSDI 2024) builds its scheduler on this idea and calls it stall-free batching: prefill chunks ride on decode steps up to the budget, so decode never stalls behind a full prefill, and the batch stays full. Its abstract reports results for Mistral-7B on one A100, Yi-34B on two A100s and Falcon-180B with pipeline parallelism.

Chunking has a second cost. The attention of each chunk reads the KV of the chunks before it, so the KV of the prompt is written chunk by chunk and read back by later chunks. For the four chunks above, this means 512, 1,024 and 1,536 tokens of KV read back at 512 KiB per token, about 1.5 GiB in total (computed). This traffic is small next to the 28.7 TFLOP of the prompt, but it is not zero on a step that is already limited by bandwidth. In addition, the attention of a chunk covers a rectangle over the cached prefix plus a triangle over its own tokens, and the kernel needs a code path for this shape.

Prefix caching

Many requests share a prefix word for word. Examples are a system prompt, a block of few-shot examples, a document followed by several questions, and a multi-turn conversation that sends its history again. If the KV for such a prefix already exists, computing it again is wasted work. A paged cache makes reuse possible, because a prefix is a run of blocks that a new block table can point to instead of copying.

SGLang’s RadixAttention stores cached prefixes in a radix tree whose keys are token IDs. A new request walks down the tree as far as its tokens match. The matched blocks are attached to its block table, and only the unmatched rest of the prompt is prefilled. New entries are inserted as sequences grow, and when the pool is full, the least recently used leaves are evicted. The tree finds the longest cached prefix of a request in time proportional to the length of the match, and it shares prefixes across requests automatically, without any declaration from the application.

The gain depends on the workload. A cache hit needs an exact token-level match of the prefix under the same model. A shared system prompt hits every time, whereas a document of one user hits only for the follow-up questions of that user. A hit removes 2PLprefix2PL_{\text{prefix}}2PLprefix​ FLOPs and the KV writes of the prefix, so the gain is large when prefixes are long and repeated, and zero when they are not. The cost is the bookkeeping: a lookup per request, block accounting at every append, and memory held by cached blocks that may never be used again. A cache that is too small, or a workload without repetition, therefore turns this bookkeeping into pure overhead. The automatic prefix caching of vLLM reaches the same result with a different mechanism: it identifies each full block by a hash of its tokens and the hash of its parent block, and it evicts in least-recently-used order.

Preemption: recompute or swap

When sequences grow long, a decode batch can need more blocks than the pool has. The scheduler must then take KV memory away from one sequence, the victim. Two policies exist, and their costs can be compared with simple arithmetic.

Recompute drops the KV of the victim and runs prefill again for all of its tokens when the victim is admitted again. The cost is 2PL2PL2PL FLOPs for LLL tokens, or 2P/Fpeak2P/F_{\text{peak}}2P/Fpeak​ seconds per token at peak. For the 7B model on an A100 at 312 TFLOPS, this is 45 µs per token at peak and about 150 µs at 30% of peak (computed).

Swap copies the blocks of the victim to host memory and later copies them back. The cost is 2LMkv2LM_{\text{kv}}2LMkv​ bytes over the host link. On PCIe 4.0 ×16 at about 32 GB/s, this is 33 µs per token at 512 KiB per token (computed). At realistic compute efficiency, swapping over PCIe is therefore faster than recomputing, and on a faster host link the gap grows.

The choice is not only about speed. vLLM’s V0 scheduler (v0.6.3) recomputes by default, and its source code gives the reason as lower overhead than swapping; it swaps only sequence groups with several sequences, such as beam search, because recomputation does not support them. Recomputation re-prefills the prompt together with every token generated so far. The new KV matches the dropped KV bit for bit only if the kernels give identical results for the new batch shape. Swapping keeps the exact state, but it holds host memory and uses link bandwidth. Recomputation delays the next token of the victim by a full prefill, whereas swapping delays it by the transfer, and both delays appear as one long TBT of the victim and raise its TPOT. Which sequence to evict, and whether to prefer the newest or the oldest, is a policy question on top of this arithmetic.

One scheduler iteration

Put together, one step looks like this:

  1. Free the blocks of finished sequences and return them to the pool.
  2. Admit waiting requests in order while blocks are available. When the pool runs out, preempt a victim and choose between recompute and swap.
  3. Fill the token budget: decode tokens for running sequences first, then prefill chunks for admitted requests, with the chunk size set by the remaining budget.
  4. Build the batch: concatenate the rows for the projections, and run attention per request or per group of requests with the same shape.
  5. Run the step, append the new KV blocks, sample the next tokens, and record the timing of each request.

Each mechanism in this note is a choice in one of these five lines. Iteration-level scheduling decides when to admit, paging decides how the KV is laid out, chunking decides how much work one iteration carries, the prefix tree decides whether a prompt needs prefill at all, and preemption decides who pays when memory runs out. None of them changes the arithmetic of the model, but all of them change how much of that arithmetic the GPU completes per second.
