What the MPI Standard Guarantees for Point-to-Point Messages

This note records what MPI 4.1 promises for matching, ordering, the four send modes, completion, datatypes and progress. With it, a reader can tell which programs are correct and which only work by chance.

MPI programs move data between processes with sends and receives, and many of their bugs come from assuming more than the standard promises. This note records what the MPI 4.1 standard guarantees for point-to-point communication and what it leaves to the implementation. It is organized around the questions that a programmer asks: how a receive finds its message, what “completed” means for a send, when two sends can deadlock, what a datatype changes, and whether a waiting process still makes progress. Where implementations differ, the note says so instead of picking one. The collective algorithms built from these operations are covered in The Cost of AllReduce Algorithms from Ring to Tree.

A few terms are fixed here. A communicator is a group of processes together with a private context. A rank is the index of a process within a communicator. The envelope of a message is what matching uses: the communicator, the source and the tag. Section numbers in this note refer to the MPI 4.1 standard.

The execution model

An MPI program is usually SPMD. Every process runs the same program, and its rank decides which branch it takes. MPI also allows different programs to run together, but the same-program form is the common case. MPI_Init starts the library, MPI_Comm_rank and MPI_Comm_size tell a process who it is and how many processes there are, and MPI_Finalize shuts the library down. Processes do not share memory, and one-sided communication is outside this note; apart from it, data moves only when a send is matched by a receive, or inside a collective operation.

Two consequences follow immediately, and they cause most beginner bugs:

  • Every process must call the same collective operations on the same communicator in the same order. A collective that only some ranks call usually hangs.
  • A point-to-point exchange is not symmetric. One side calls a send, the other side calls a receive, and the two calls match by their envelopes, not by the order of the calls or by the names of the variables.

A communicator is more than a list of ranks. It carries a context, and a message sent in one communicator never matches a receive in another, even when the ranks and the tags are the same. Because of this isolation, a library can call MPI_Comm_dup to get a private channel, and its messages can never be taken by the application. Splitting a communicator with MPI_Comm_split creates new contexts as well as new groups.

Matching: which receive takes which message

A receive names a communicator, a source and a tag. A send names the same three, plus a count and a datatype. A receive can take only a message whose envelope matches its own. The source or the tag may be a wildcard, MPI_ANY_SOURCE or MPI_ANY_TAG, and then the receive accepts any value in that field.

Three details hide in this rule.

Matching does not look at buffers or variable names. The message is copied into the receive buffer, and when MPI_Recv returns, the data is in that buffer. The sender may reuse its own buffer as soon as its send completes, and this can happen before the receive. Nothing in the protocol depends on the two programs using the same variable names or the same loop structure. The counts and datatypes must still be compatible, as described below.

A receive can be posted before or after the matching send. If the receive is posted first, it waits until a matching message arrives. If a message arrives first, an implementation typically keeps it in a queue of unexpected messages until a matching receive is posted. This difference explains why “send, then receive” sometimes works and sometimes hangs. Implementations typically send small messages eagerly into a buffer on the receiving side and hold large ones back until the receive is posted, and the size limit between the two is an implementation detail with no value in the standard.

Wildcards cost determinism. With MPI_ANY_SOURCE, the standard does not define the order in which messages from different sources are matched, so a program that depends on this order depends on one implementation. MPI_Probe lets a receiver inspect an envelope before it chooses a buffer. Variable-length messages are usually received this way: probe, read the count, allocate a buffer, then receive (§3.8).

Ordering: messages do not overtake each other

The standard guarantees a limited ordering (§3.5). Suppose one process sends two messages to the same destination, and both messages match the same receive. Then the receive cannot take the second message while the first one is still pending. In other words, messages between one pair of processes do not overtake each other when both can match the same receive.

The guarantee is deliberately narrow:

  • Two sends with different tags to the same destination may be received in either order, because each receive chooses by its tag.
  • Two sends on different communicators have no order relation at all.
  • Sends from different processes have no order relation. If two ranks send to a third, the arrival order is whatever the network and the implementation produce.

This rule makes protocols based on tags work: a receiver can expect a setup message and then a data message, with two tags. The same rule makes wildcard receives risky, because a wildcard receive that faces several senders has no defined order.

The four send modes

MPI_Send is the standard-mode send, and its completion rule is the one that people get wrong (§3.4). It returns when the send buffer can be reused. It does not mean that the receiver has the data, that a receive has been posted, or that the message has left the machine. The implementation may copy the message into an internal buffer and return at once, or it may wait for a matching receive before it copies, and it may choose differently by message size or by state. The standard allows both, and a program cannot tell which one happened, except by timing.

The other three modes make the choice explicit, and each has a condition:

  • MPI_Ssend (synchronous) completes only after a matching receive has been posted and has started to receive the message. Use it when the protocol needs the receiver to have started, or to keep the implementation from buffering.
  • MPI_Bsend (buffered) copies the message into a buffer that the user attached with MPI_Buffer_attach, and then returns. Its completion no longer depends on the receiver, but the user must size the buffer.
  • MPI_Rsend (ready) asserts that a matching receive is already posted. If no such receive exists, the program is erroneous; the mode exists to save a handshake when the sender knows that the receiver is waiting.

The practical rule is short: MPI_Send may buffer, or it may not, so a program that works only with buffering may deadlock. Code that relies on the buffering of small messages is correct only for the implementation and the message sizes with which it was tested.

Deadlock, and the two standard ways out

The classic deadlock is a ring. Every rank calls MPI_Send to its right neighbor and then MPI_Recv from its left neighbor. If the implementation does not buffer, every send waits for a receive that no rank has posted, and the program hangs; the same shape appears in a pairwise exchange in which both ranks send first.

Two kinds of calls avoid this deadlock without any assumption about buffering:

  • MPI_Sendrecv performs a send and a receive in one call, and the implementation guarantees that the pair does not deadlock against itself (§3.2.7). It is the right tool for a ring exchange or a halo exchange.
  • Nonblocking operations. MPI_Isend and MPI_Irecv start an operation and return a request handle at once, and MPI_Wait or MPI_Test later completes it (§3.7). Because neither call blocks, a program can start all of its sends and receives and then wait for all of them, and no rank can block another. Posting the receives first is still good practice, because a message then lands directly in its buffer instead of in the queue of unexpected messages.

Nonblocking completion is asymmetric. An MPI_Isend completes when the send buffer can be reused, and this again does not mean that the receiver has the data. An MPI_Irecv completes when the data is in the receive buffer. “The send completed” and “the receive completed” are statements about the local state of two different processes, and a program that confuses them has a race, not a performance problem.

MPI_Test returns a flag, and a false flag means “not complete yet”, not “failed”. Cancelling a send request with MPI_Cancel is deprecated in MPI 4.1 (§3.8.4). After MPI_Cancel, the request must still be completed with MPI_Wait or MPI_Test, and MPI_Test_cancelled then reports whether the cancellation succeeded or the operation completed normally.

Datatypes and the type-signature rule

MPI datatypes let the sender and the receiver describe non-contiguous data without packing it by hand (§5). MPI_Type_contiguous, MPI_Type_vector, MPI_Type_indexed and MPI_Type_create_struct build derived types from a base type, a count and a layout. MPI_Type_commit makes a type usable, and MPI_Type_free releases the type handle, not the data.

Matching compares type signatures, not bytes (§3.3.1). The type signature of a message is the sequence of basic types that it contains. The types of the message must match the types of the receive element by element, but the receive may describe more elements than the message contains (§3.2.4): a send of 10 MPI_INT matches a receive of 20 MPI_INT, and MPI_Get_count then reports 10. The layouts in memory may differ completely. A sender can send one column of a matrix with a vector type, and the receiver can receive it into a contiguous buffer. What the standard does not allow is a mismatch of signatures: sending 10 MPI_INT to a receive of 10 MPI_FLOAT is erroneous, even though both take 40 bytes on most systems.

Two practical consequences follow:

  • The count in MPI_Recv is a maximum, not a hint. If a message is longer than the receive buffer, the receive raises an overflow error, MPI_ERR_TRUNCATE.
  • MPI_BOTTOM with absolute addresses lets one datatype describe data spread over several variables, for example the fields of a structure stored in different places. This is powerful, and it is easy to get wrong.

Large counts need the _c functions. Classic MPI counts are int, so a message with more than 231−12^{31}-1231−1 elements needs the large-count functions such as MPI_Send_c, and these functions take an MPI_Count. MPI 4.0 added them for exactly this reason. A message of 2 GiB of MPI_BYTE already crosses the limit, and a program that passes a size_t into an int count can silently wrap the value.

Tags, null processes and communicators

The tag is an integer with an upper bound that the implementation defines. The bound is available as the attribute MPI_TAG_UB and is at least 32,767 (§9.1). Using MPI_PROC_NULL as a source or destination turns the call into a no-op: a receive returns at once with an empty message, and a send does nothing (§3.10). This is the clean way to handle the edges of a ring or a stencil without branches.

Collective operations are defined on communicators, and they are correct only if every member calls them in the same order. The context of a communicator keeps the internal collectives of a library apart from those of the application, and MPI_Comm_dup is the standard way to get this separation.

Progress, threads and errors

Three properties are easy to assume, and none of them is guaranteed.

Progress (§2.9). Part of the work of an operation can happen outside the call that started it. The standard allows an implementation to do this work in a separate progress thread, on the network card, or inside later MPI calls of the same process. A program therefore cannot assume that an outstanding MPI_Isend advances while the process computes outside MPI. On implementations that progress only inside MPI calls, it advances only when the process calls MPI again, for example MPI_Test. Code that needs overlap should call MPI_Test at regular points.

Threads (§11.6). MPI_Init_thread negotiates one of four levels:

  • MPI_THREAD_SINGLE: only one thread exists.
  • MPI_THREAD_FUNNELED: only the thread that initialized MPI makes MPI calls.
  • MPI_THREAD_SERIALIZED: any thread may call MPI, but never two at the same time.
  • MPI_THREAD_MULTIPLE: any thread may call MPI at any time.

Because the level that the library provides may be lower than the level requested, the program must check the level it receives.

Errors (§9.3). MPI calls return an error code, but by default an error on a communicator is fatal (MPI_ERRORS_ARE_FATAL), and the job aborts. The handler MPI_ERRORS_RETURN makes errors return to the caller, at the cost of checking every call. A mismatch in a point-to-point exchange usually means an erroneous program, not a recoverable condition, and the standard does not require the implementation to detect every such error.

What this means for a ring allreduce

The collective algorithms in the allreduce note are built from these primitives, and their correctness depends on the rules above. A ring allreduce runs a reduce-scatter and then an allgather, and each phase is a sequence of exchanges between neighbors. Each step must use MPI_Sendrecv or nonblocking calls, and the two phases need separate tags, so that a receive can never match a message from the wrong phase. The non-overtaking rule lets a receiver rely on the order of messages within one tag, and the context of the communicator keeps the phases apart from any other traffic between the same ranks.

MPI and NCCL differ here in their contracts. MPI treats matching by envelope as a core mechanism and leaves buffering to the implementation. NCCL’s collectives are collective calls without any matching. Its point-to-point calls, ncclSend and ncclRecv, take no tag, and the receiver must call ncclRecv with the same count and datatype as the sender. Both calls block the GPU stream, so concurrent sends and receives must be grouped between ncclGroupStart and ncclGroupEnd. The arithmetic of a ring is the same in both libraries, but the contract underneath is not.
