GPU Operator Development Basics: Parallel Execution, Memory Hierarchy, and Data Reuse

An introductory guide to GPU operator development explaining framework dispatch, thread and memory hierarchies, arithmetic intensity, tiling, fusion, and Tensor Cores.

Writing C = A @ B or y = torch.relu(x + b) in PyTorch takes a single line, yet almost all training and inference time is spent inside the low-level operators (also called kernels) dispatched underneath those calls. Two kernels that compute the exact same mathematical result can differ in runtime by an order of magnitude depending on how they divide work across GPU threads and how they move data through memory. This guide introduces GPU operator development for readers without prior CUDA experience: what an operator is, how a GPU organizes threads and memory, why data movement often dominates arithmetic, and how core optimizations—tiling, memory coalescing, kernel fusion, and Tensor Cores—address those bottlenecks.

Readers ready to inspect measured counters and PTX/SASS disassembly can continue to GPU Roofline bounds, CUDA GEMM tiling and vectorized loads, shared memory swizzling and double buffering, Tensor Cores from Volta to Blackwell, and PyTorch custom operator contracts. Arithmetic checks worked directly in the text are marked (computed).

What an operator is and how frameworks dispatch it

A deep learning model is a directed graph of mathematical operations: matrix multiplication, convolution, normalization, activation, softmax, and attention. Each node in that graph corresponds to an operator—a compiled routine implementing the forward pass (and, for training, the backward gradient pass) for specific data types and tensor layouts.

When Python executes C = A @ B, Python itself does not multiply numbers in a loop. The framework inspects the tensor device, data type (such as FP32, BF16, or FP16), and memory strides, then dispatches a pre-compiled GPU kernel from vendor libraries (such as cuBLAS or cuDNN) or a custom extension. Operator developers build new kernels when a model introduces an operation not covered by standard libraries, when multiple small operations need to be fused to eliminate intermediate memory traffic, or when a specific tensor shape underutilizes generic library heuristics.

CPU vs. GPU: latency-oriented vs. throughput-oriented hardware

A CPU devotes most of its silicon area to large caches, branch predictors, and complex out-of-order control logic so that a handful of threads finish sequential instructions as quickly as possible. A GPU flips that budget: it uses simpler cores replicated by the thousands, trading single-thread latency for massive aggregate throughput.

In the CUDA execution model, GPU parallelism is organized in three nested levels:

flowchart TB
    G[Grid: one kernel launch covering the whole output tensor]
    B1[Thread Block 0 on an SM: shares fast on-chip Shared Memory]
    B2[Thread Block 1 on an SM: executes independently]
    W1[Warp: 32 threads executing instructions in lockstep]
    T1[Individual Threads: private registers and coordinates]
    G --> B1
    G --> B2
    B1 --> W1
    W1 --> T1
  • Thread: The smallest execution unit, equipped with private registers. Each thread computes its own index to decide which output elements it owns.
  • Warp: On NVIDIA GPUs, hardware schedules threads in groups of 32 threads called warps. If threads in the same warp take different if/else branches (warp divergence), the hardware serializes both paths and masks off inactive lanes.
  • Thread Block: A group of warps assigned to a single Streaming Multiprocessor (SM). Threads inside one block can synchronize (__syncthreads()) and exchange data through fast on-chip shared memory. Blocks execute independently so the same kernel scales across GPUs with different SM counts.

The memory hierarchy and arithmetic intensity

A common misconception is that faster GPU operators come mainly from using fewer multiplications. On modern GPUs, moving bytes from off-chip memory is far scarcer than floating-point arithmetic.

Four core optimization mechanisms in GPU operators

Knowing the hardware model immediately explains the four techniques that dominate everyday GPU kernel engineering.

1. Blocking and data reuse (tiling)

In a naive matrix-multiplication kernel where each thread computes one element of CCC by reading an entire row of AAA and column of BBB directly from global memory, 102421024^210242 threads each load 2×10242 \times 10242×1024 floats. Total logical global loads reach 2×10243×4=8 GiB2 \times 1024^3 \times 4 = 8\text{ GiB}2×10243×4=8 GiB (computed)—over 680 times larger than the 8 MiB8\text{ MiB}8 MiB actually held by AAA and BBB combined.

Tiling fixes this by assigning each thread block a square output tile (for example, 32×3232 \times 3232×32). The block collaboratively loads a 32×3232 \times 3232×32 slice of AAA and a 32×3232 \times 3232×32 slice of BBB into on-chip shared memory, synchronizes, computes partial products inside registers, and advances to the next slice along KKK. Every element fetched from global memory is now reused by 32 threads in the block, reducing logical global loads 32×32\times32× from 8 GiB8\text{ GiB}8 GiB down to 256 MiB256\text{ MiB}256 MiB (computed). Extending reuse one level further—having each thread compute a small register sub-tile such as 4×44 \times 44×4—cuts shared-memory traffic as well.

2. Coalesced global access and shared-memory bank conflicts

Hardware fetches global memory in contiguous cache-line transactions (32-byte sectors). When the 32 threads of a warp read 32 adjacent 4-byte floats, the memory controller combines those requests into a single coalesced 128-byte transaction (memory coalescing). If threads instead read with large strides across columns, the hardware must issue many separate transactions, wasting most of the transferred bytes.

Inside on-chip shared memory, NVIDIA GPUs divide storage into 32 banks of 4-byte words. When 32 threads in a warp access 32 distinct banks simultaneously, the read completes in one pass. When multiple threads hit different addresses mapped to the same bank (for instance, accessing a matrix column with stride 32), the hardware serializes those accesses into a bank conflict. Padding or XOR-swizzling shared-memory indices shifts elements across banks so row and column accesses both stay conflict-free.

3. Kernel fusion

Memory-bound layers such as bias addition, activation, residual addition, and layer normalization pay the full cost of round-tripping tensors to global memory every time a separate kernel launches.

Consider y = relu(x + b) in FP32:

  • Unfused (two kernels): Kernel 1 reads x and b and writes an intermediate tensor t (12 B/element). Kernel 2 reads t and writes y (8 B/element). Total global traffic is 20 B/element (computed).
  • Fused (one kernel): Each thread reads x[i] and b[i], adds them and applies relu inside a register, and writes y[i] once. Total global traffic drops to 12 B/element—a 40% traffic reduction (computed)—and one kernel launch overhead disappears.

Modern flash-style attention kernels apply the same principle on a larger scale: instead of materializing the full N×NN \times NN×N attention score matrix in global memory, they tile Q,K,VQ, K, VQ,K,V on chip and accumulate the softmax normalization online. For that derivation, see online softmax and attention tiling.

4. Tensor Cores and reduced precision

Standard CUDA cores execute one scalar fused multiply-add per lane per cycle. Starting with the Volta architecture, NVIDIA GPUs added Tensor Cores—dedicated matrix units that perform small matrix multiply-accumulate operations (such as 16×8×1616 \times 8 \times 1616×8×16) across a warp or warp group in a single instruction. Tensor Cores target lower-precision inputs (FP16, BF16, TF32, FP8, and newer microscaled formats) while accumulating into higher precision (typically FP32) to preserve numerical stability.

Because Tensor Cores deliver multiples of scalar FP32 throughput, achieving their headline speed requires keeping both operand shapes aligned to hardware tile sizes and feeding them asynchronously from memory so the matrix units do not stall waiting for loads.

When custom operators pay off and how shape changes the design

No single parallel mapping wins for every input shape. A kernel that parallelizes across batch and channels runs fast when batch size is large, yet leaves most SMs idle when batch size drops to 1—at which point splitting work across the sequence or reduction dimension (such as parallel prefix scan or Split-K GEMM) can beat the original kernel by an order of magnitude, as analyzed in selective scan parallelization.

In practice, operator engineering follows a disciplined loop: verify mathematical correctness against a reference implementation first, profile hardware utilization (such as with Nsight Compute) to see whether memory bandwidth, latency, or compute limits the kernel, apply one targeted mechanism, and re-measure on the actual target shapes.
