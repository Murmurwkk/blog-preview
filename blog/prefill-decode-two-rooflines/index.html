The Arithmetic of Prefill and Decode in LLM Inference

This note derives the FLOPs, the KV-cache bytes and the roofline position of prefill and decode. With it, a reader can estimate TTFT, TPOT and the point where batching stops paying off.

An LLM serving system runs one model in two phases. Prefill processes the whole prompt at once, and decode generates one token per step. This note works out how much arithmetic each phase does, how many bytes the KV cache adds, where each phase sits on a roofline, and which terms set the time to first token (TTFT) and the time per output token (TPOT). The scheduling of the two phases is covered in How a Continuous-Batching LLM Scheduler Works, and running them on separate GPUs is covered in DistServe: Serving Prefill and Decode on Separate GPUs.

The notation is fixed here. PPP is the number of parameters, bbb the number of sequences in a batch, LLL the length of the prompt being prefilled, and SSS the context length already in the cache. One multiply-add counts as two FLOPs. Weights and cache are FP16 at two bytes per element, unless another format is named. Peak throughput and bandwidth are the dense datasheet numbers at boost clock, not what a kernel achieves. Numbers marked (computed) are my own arithmetic from the formulas in this note; all other numbers come from the sources listed at the end.

Two phases over one set of weights

A decoder-only model turns a prompt into tokens in two passes.

  • In prefill, the whole prompt is available at once, so every projection multiplies a matrix with LLL rows by a weight matrix. Attention uses a causal mask, so position iii sees only positions up to iii, and the hidden state of the last position produces the first output token.
  • In decode, one new token is appended, and the whole model runs again for this single position. Attention reads the keys and values of all earlier positions from a cache instead of recomputing them, and it appends the key and value of the new position.

Because the cache stores the keys and values of earlier positions, the cost of decode grows linearly with the context instead of quadratically, but each decode step also reads more memory than the step before. Both phases use the same weights, and they differ only in how many tokens share one read of those weights.

FLOPs per token

A dense model costs about 2P2P2P FLOPs per token in the forward pass, because each parameter takes part in one multiply and one add per token. The estimate leaves out the embedding lookups and the score matrix of attention; the lookups are small at serving scale, whereas the score matrix needs a separate term below.

Prefill with LLL tokens therefore costs

Fprefill≈2PL,F_{\text{prefill}} \approx 2PL ,Fprefill​≈2PL,

and one decode step costs 2P2P2P for each sequence in the batch:

Fdecode≈2Pb.F_{\text{decode}} \approx 2Pb .Fdecode​≈2Pb.

Attention adds a term that grows with L2L^2L2. Within one layer, forming QK⊤QK^\topQK⊤ and multiplying by VVV costs about 4L2d4L^2 d4L2d FLOPs, and the causal mask removes about half of this work. Summed over the layers, the attention work of a prompt grows with L2L^2L2, while its projection work grows with LLL. For the 7B reference model below, causal attention adds about 4% to the projection FLOPs at 2K tokens and about 15% at 8K (computed). This is why a long prompt costs more than its token count suggests.

Decode attention has a different shape. Because each step has only one query, the score computation costs O(Sd)O(Sd)O(Sd) per layer, and this cost grows linearly with the cached context while it stays small next to the projections. What limits decode is not the FLOPs of attention but the bytes that it reads.

The KV cache costs a fixed number of bytes per token

Each token in the cache keeps one key and one value in every layer. With nlayersn_{\text{layers}}nlayers​ layers, nkvn_{\text{kv}}nkv​ key/value heads, head dimension dhd_hdh​ and ccc bytes per element, the cache costs

Mkv=2 nlayers nkv dh cM_{\text{kv}} = 2 \, n_{\text{layers}} \, n_{\text{kv}} \, d_h \, cMkv​=2nlayers​nkv​dh​c

bytes per token. The leading factor of two counts the key and the value. Multi-head attention has as many KV heads as query heads. Grouped-query attention shares each KV head among a group of query heads, so a model with 64 query heads and 8 KV heads stores one eighth of the cache.

Two reference configurations make the formula concrete:

  • A 7B model with 32 layers, 32 KV heads of dimension 128 and FP16 stores 2×32×32×128×2=524,2882 \times 32 \times 32 \times 128 \times 2 = 524{,}2882×32×32×128×2=524,288 bytes per token, or 512 KiB (computed).
  • A 175B model with 96 layers and a hidden size of 12,288 stores about 4.5 MiB per token (computed). A context of 2,048 tokens then holds about 9 GiB of cache.

Neither number depends on the batch size; both depend only on how many tokens are stored.

At serving time, the cache competes with the weights for device memory. A 7B model in FP16 needs about 14 GB for its weights, so 66 GB remain on an 80 GB GPU. At 512 KiB per token, these 66 GB hold about 126K cached tokens (computed): one request with a 126K context, or 61 requests with 2K each, before fragmentation and runtime overhead. Because memory runs out this quickly, paging and prefix sharing are worth their complexity.

Arithmetic intensity and the roofline

The roofline model bounds the time of a kernel by two resources instead of one:

t≥max⁡(FFpeak,MBpeak).t \ge \max\left(\frac{F}{F_{\text{peak}}}, \frac{M}{B_{\text{peak}}}\right).t≥max(Fpeak​F​,Bpeak​M​).

FFF is the number of FLOPs, MMM the number of bytes moved, FpeakF_{\text{peak}}Fpeak​ the peak throughput and BpeakB_{\text{peak}}Bpeak​ the memory bandwidth. The ratio of FLOPs to bytes is the arithmetic intensity:

I=FMFLOP/byte.I = \frac{F}{M} \quad \text{FLOP/byte}.I=MF​FLOP/byte.

The two bounds meet at the ridge point I∗=Fpeak/BpeakI^{*} = F_{\text{peak}} / B_{\text{peak}}I∗=Fpeak​/Bpeak​. Below the ridge, the bytes set the time; above it, the FLOPs set the time. The model assumes that computation and memory traffic overlap perfectly, so it gives a lower bound on time, not a prediction. In this note, “compute-bound” and “memory-bound” name the lower of the two roofs; a real kernel can also be limited by latency or overhead.

The ridge point is a property of the GPU:

In FP8, the ridge point of the H100 doubles, because the throughput doubles while the bandwidth stays the same.

Prefill sits far above the ridge. Prefill processes LLL tokens with one read of the weights, so its intensity grows with LLL:

Iprefill≈2PL2P+activations≈L.I_{\text{prefill}} \approx \frac{2PL}{2P + \text{activations}} \approx L .Iprefill​≈2P+activations2PL​≈L.

At L=2,048L = 2{,}048L=2,048, the intensity is about 2,048 FLOP/byte, far above any ridge point in the table, so prefill is compute-bound, and its time is about 2PL/Fpeak2PL/F_{\text{peak}}2PL/Fpeak​ until attention or memory traffic starts to matter.

Decode sits far below the ridge. Every decode step reads the weights once, and it also reads the cache of every sequence in the batch:

Idecode≈2Pb2P+bSMkv.I_{\text{decode}} \approx \frac{2Pb}{2P + b S M_{\text{kv}}} .Idecode​≈2P+bSMkv​2Pb​.

At b=1b=1b=1 and a short context, the weight term dominates the denominator, and the intensity is about 1 FLOP/byte. As bbb grows, the weight read is shared by more sequences, but the cache read grows with bSbSbS, so the intensity approaches a ceiling from below:

Idecode→2PSMkv.I_{\text{decode}} \to \frac{2P}{S M_{\text{kv}}} .Idecode​→SMkv​2P​.

For the 7B model at S=2,048S = 2{,}048S=2,048, this ceiling is about 13 FLOP/byte (computed), more than ten times below the ridge point of the A100. No batch size makes this decode step compute-bound at this context length. The ceiling rises only when the cache per token shrinks, for example through grouped-query attention or a quantized cache, or when the context is short and the batch is large.

These conclusions follow from the numbers, not from the names of the phases. A single short prompt can be memory-bound, because a few tokens do not amortize one read of the weights, whereas a decode step on a small model with a short context and a large batch can come close to compute-bound. The name of the phase only says which formula applies.

What sets TTFT and TPOT

TTFT is the wait before the first output token appears. Without queueing, it is the prefill time plus the time for scheduling and transfers:

TTFT≈max⁡(2PLFpeak,2PBpeak)+tqueue+ttransfer.\mathrm{TTFT} \approx \max\left(\frac{2PL}{F_{\text{peak}}}, \frac{2P}{B_{\text{peak}}}\right) + t_{\text{queue}} + t_{\text{transfer}} .TTFT≈max(Fpeak​2PL​,Bpeak​2P​)+tqueue​+ttransfer​.

The first term is the computation, and the second is the read of the weights that cannot be avoided. For a 2K prompt on the 7B model, the prefill computation is about 29 TFLOP, or 92 ms at the peak of the A100 (computed). The weight read takes about 7 ms. Even at 30% of peak, the computation dominates TTFT for long prompts, and this is why parallelizing or chunking prefill changes TTFT more than extra bandwidth does.

TPOT is the average interval between the output tokens of a request. Each decode step advances every sequence in the batch by one token, so while the batch stays the same, the TPOT of a request equals the average step time:

TPOT≈max⁡(2PbFpeak,2P+bSMkvBpeak)+toverhead.\mathrm{TPOT} \approx \max\left(\frac{2Pb}{F_{\text{peak}}}, \frac{2P + b S M_{\text{kv}}}{B_{\text{peak}}}\right) + t_{\text{overhead}} .TPOT≈max(Fpeak​2Pb​,Bpeak​2P+bSMkv​​)+toverhead​.

The terms react differently to the batch size: the computation grows linearly with bbb, the weight read stays fixed, and the cache read grows with bSbSbS. Once the batch is so large that the cache read exceeds the weight read, a larger batch still raises throughput, but it makes every step longer for every request.

The same equations explain why serving systems separate the two phases. Prefill works best with long prompts in few, wide iterations, whereas decode works best with short, frequent steps and as large a batch as the latency target allows. When the two phases share one iteration, each phase waits for the other.

Batching, and where weight reuse stops paying off

A decode step at batch 1 reads the weights and produces one token. At batch bbb, it reads the same weights and produces bbb tokens, so the weight traffic per token falls by a factor of bbb. This is the whole throughput argument for batching, and it explains the shape of the intensity curve above: the intensity rises with bbb until the cache read catches up.

Three limits stop this growth:

  • Capacity. bbb sequences with context SSS need bSMkvbSM_{\text{kv}}bSMkv​ bytes of cache, and this memory is not available for weights and activations.
  • Compute. Once the compute term 2Pb/Fpeak2Pb/F_{\text{peak}}2Pb/Fpeak​ becomes larger than the memory term, the FLOPs set the step time.
  • Latency. Every request in a batch waits for the whole iteration. A long prefill inserted between decode steps delays all of them, and continuous batching and disaggregation are the two common answers to this interference.

Prefill batches differently. Its projection FLOPs grow linearly with the total number of prompt tokens, but its attention FLOPs grow quadratically within each request. A batch of four 512-token prompts therefore needs less attention work than one 2,048-token prompt with the same number of tokens. Batching prefill helps the projections and does not reduce the attention work, so the mix of prompt lengths decides the optimum.
