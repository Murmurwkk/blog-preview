How NVIDIA Tensor Cores Changed from Volta to Blackwell

This note follows the Tensor Core through five GPU generations: its numeric formats, its instruction tiles and the way data reaches it. It also shows what a datasheet peak assumes.

A Tensor Core is the matrix unit of an NVIDIA GPU, and most of the FLOPs in a modern datasheet come from it. This note follows the unit from Volta to Blackwell. Each generation changed the same three things: the numeric formats, the size of the matrix tile that one instruction covers, and the way data reaches the unit. The note ends with the conditions behind a datasheet peak. How the peak is used to bound a kernel’s time is covered in The Roofline Model: Bounding GPU Kernel Time with Two Numbers.

The notation is fixed here. MMM, NNN and KKK are the dimensions of a matrix multiply-accumulate, so its work is 2MNK2MNK2MNK FLOPs. “Dense” means that the unit performs every multiply. “Sparse” means the 2:4 structured form, in which two of every four weights are zero by construction. Peak figures are nominal and dense unless marked sparse, at the boost clock, and they assume that the operands are already where the unit needs them. Numbers marked (computed) are my own arithmetic; all other numbers come from the sources listed at the end.

What a Tensor Core is

A Tensor Core computes a small matrix multiply-accumulate per instruction: D=A×B+CD = A \times B + CD=A×B+C. The inputs AAA and BBB use a narrow format, while CCC and DDD usually use a wider one. The unit exists because a scalar FMA spends one instruction on one multiply-add, whereas a matrix instruction lets the hardware perform a whole tile of multiply-adds at once, with the operands staged in registers or shared memory instead of fetched again for every operation.

The size of the instruction matters more than the size of the unit. Each Volta Tensor Core works on a 4×4×4 tile, and the warp-level instruction combines several of them. On Ampere, a typical warp-level instruction is mma.m16n8k16. Hopper’s wgmma gives a tile of 64×N×16 to a warpgroup of four warps. On data-center Blackwell, one thread issues tcgen05.mma, and the accumulator lives in a separate tensor memory. Two things grow along this path: the tile that one instruction covers, and the number of threads that must cooperate to feed it.

Three numbers set the peak of a generation: the number of Tensor Cores, the FLOPs that each core does per clock, and the clock. For Volta, the arithmetic closes exactly. The V100 has 640 Tensor Cores, eight per SM on 80 SMs. Each core does 64 FMAs, or 128 FLOPs, per clock, and the boost clock is 1.53 GHz. The product is 125 TFLOPS (computed), the number on the datasheet. This check is useful, because it shows what the datasheet number means and which conditions it carries.

Volta (2017): the unit appears

The V100 introduced the Tensor Core with one format: FP16 inputs with FP32 accumulation. This choice defines the design. The multiply is done in half precision, but the sum is not, so a long dot product does not drift the way a pure FP16 sum would. The gain over the FP32 cores of the same chip is large: 125 against 15.7 TFLOPS. Per SM, the eight Tensor Cores do 1,024 FLOPs per clock, whereas the 64 FP32 cores do 128, a factor of eight (computed).

The conditions are already visible in this number. The 125 TFLOPS assume that every Tensor Core is busy at every clock, and this requires the operand tiles to arrive from registers and shared memory without stalls. A kernel that loads every tile from global memory, or whose matrices are too thin to fill the tile, reaches only a fraction of the peak. Volta also had no asynchronous copy. Data moved from global to shared memory through ordinary loads and __syncthreads, so the data movement and the math competed for the same issue slots. The Volta microbenchmark paper in the source table measured how far real code stays below the nominal peak.

Turing (2018): integer formats

Turing’s second-generation Tensor Cores added no new floating-point input format. They added INT8 and INT4 with INT32 accumulation, and each halving of the width doubled the rate. The T4 lists 65 TFLOPS in mixed-precision FP16, 130 TOPS in INT8 and 260 TOPS in INT4. The same pattern repeats in every later generation: a narrower multiply needs less area, so the same area fits more multipliers.

The consequence for inference is direct. An INT8 weight takes half the bytes of an FP16 weight, so a memory-bound decode step reads half as much, and INT4 cuts the bytes to a quarter. The open question is the quantization error. This is a numerical question, not an architectural one, and the hardware does not answer it; it only makes the narrow format fast. Choosing the scales and checking the accuracy remain the job of the kernel and of the model.

Turing also brought the Tensor Core into consumer GPUs, the RTX 20 series. For this history, the relevant fact is that by 2018 the unit supported two numeric families, floating point and integer, each with its own rate.

Ampere (2020): TF32, BF16, FP64 and sparsity

Ampere’s third-generation Tensor Cores added four features at once, and all four remain in later generations.

  • TF32. This format has 8 exponent bits and 10 mantissa bits. It keeps the range of FP32, and the Tensor Core multiplies its 10-bit mantissas. Inputs are rounded from FP32 on the fly, and the accumulator stays in FP32. Existing FP32 training code can therefore run on Tensor Cores with a single setting, at half the BF16 rate: the A100 lists 156 TFLOPS of dense TF32.
  • BF16. This format has 8 exponent bits and 7 mantissa bits, with FP32 accumulation. It also keeps the range of FP32 and gives up mantissa bits for throughput. The A100 lists 312 TFLOPS of dense BF16 or FP16, twice the TF32 rate.
  • FP64 Tensor Cores. The A100 added a double-precision path at 19.5 TFLOPS, one sixteenth of the BF16 rate.
  • 2:4 structured sparsity. Weights are stored as two nonzero values out of every four, with metadata that tells the hardware where they are. The unit skips the zero products and lists twice the dense rate: 624 TFLOPS of sparse BF16 on the A100. The condition is strict, because the pattern must be exactly two nonzeros in every group of four along the KKK dimension. Whether a model pruned to this pattern keeps its accuracy is a separate question from how fast the hardware runs it.

Ampere also introduced cp.async, an asynchronous copy from global to shared memory that does not pass through registers. With it, data movement can overlap the math. This is the first step of a trend that dominates the next two generations: the Tensor Core becomes so fast that feeding it becomes the main design problem.

The peak arithmetic closes again. Each A100 Tensor Core does 256 FP16 FMAs per clock, and each SM has four of them, so one SM does 1,024 FMAs, or 2,048 FLOPs, per clock. With 108 SMs at 1.41 GHz, the product is 312 TFLOPS (computed).

Hopper (2022): FP8 and an asynchronous pipeline

Hopper’s fourth-generation Tensor Cores added FP8 in two variants, with FP32 accumulation and twice the BF16 rate. E4M3 has 4 exponent bits and 3 mantissa bits and is usually used for weights and activations. E5M2 has 5 exponent bits and 2 mantissa bits and is usually used for gradients. The H100 SXM lists 1,979 TFLOPS of BF16 and 3,958 TFLOPS of FP8, both with sparsity, so the dense rates are 989 and 1,979 TFLOPS (computed). A float with only 2 or 3 mantissa bits is coarse. The Transformer Engine that comes with the format chooses scales per tensor, so that the coarse grid does not destroy accuracy. The hardware supplies the rate, while the scaling policy is software.

The larger change is how the unit is fed. With wgmma, a warpgroup of four warps issues one multiply-accumulate over a tile of 64×N×16. Operand AAA can come from registers or from shared memory, operand BBB must come from shared memory, and the accumulator stays in the registers of the warpgroup. Hopper also introduced the Tensor Memory Accelerator (TMA). The TMA is a dedicated engine that copies multidimensional tiles from global to shared memory asynchronously, and a kernel describes each copy with a descriptor instead of per-thread addresses. Together, wgmma and the TMA let a kernel keep the Tensor Cores busy while the data for the next tile is still on its way, with far fewer instructions per byte moved.

Hopper also added thread-block clusters and distributed shared memory. The blocks in a cluster can read each other’s shared memory, so a tile can be split across SMs without a trip through global memory. The direction is the same as before: data movement moves off the path of the math. For this reason, Hopper kernels are described as pipelines of producer warps, consumer warpgroups and barriers, rather than as loops over tiles.

Blackwell (2024): FP4, and the accumulator leaves the registers

Blackwell’s fifth-generation Tensor Cores add FP4 and FP6 with microscaling. A small block of values shares one scale factor, so the per-block scale makes up for the coarse mantissa. The HGX B200 table lists eight GPUs with 72 PFLOPS of dense FP4, 36 PFLOPS of dense FP8 and 18 PFLOPS of dense BF16 (computed from the listed sparse values for FP8 and BF16). FP4 therefore runs at twice the FP8 rate and four times the BF16 rate. Absolute figures are hard to compare across sources, because they are often given per system, per package or with sparsity, but the ratios are stable. The unit keeps trading mantissa bits for rate, and the scale metadata keeps the trade usable.

The instruction model of data-center Blackwell changes more than the formats. A single thread issues tcgen05.mma, not a warp or a warpgroup. The accumulator lives in tensor memory (TMEM), a dedicated on-chip store, instead of in registers. Optionally, a pair of SMs can cooperate on one larger multiply-accumulate: each SM loads its own part of AAA, the BBB tile is split between the two SMs, and the halves are exchanged between them. Because the threads no longer hold the accumulator, registers are freed, and one thread can drive a much larger tile. The programming model is now explicitly about allocating TMEM, staging operands and synchronizing the pair of SMs, so a kernel is a pipeline schedule rather than a sequence of warp instructions.

This instruction model belongs to the data-center Blackwell GPUs. The PTX ISA supports tcgen05 and tensor memory on the sm_100 and sm_110 families, such as the B200. Consumer Blackwell GPUs of compute capability 12.x (sm_120), such as the RTX 50 series and the RTX 5070 Laptop GPU used in other posts on this blog, do not support tcgen05 or TMEM. They program their Tensor Cores with warp-level mma instructions, and on sm_120a these instructions gained the FP6 and FP4 input types and block scaling. A kernel built around tcgen05 therefore does not run on a consumer Blackwell GPU.

Each B200 GPU also has 1.8 TB/s of fifth-generation NVLink bandwidth to the other GPUs. Bandwidth matters for the same reason as before: a decode step is memory-bound, and a narrower weight format means fewer bytes read per token.

The common thread

Across the generations, the same three changes repeat.

New formats, mostly narrower. FP16, then INT8 and INT4, then TF32 and BF16, then FP8, then FP4 and FP6. TF32 and BF16 are not narrower than INT8; they brought the range of FP32 to the Tensor Core. Each halving of the width doubles the rate per unit area and halves the bytes moved, and each one adds a numerical question that the hardware does not answer: where the scale comes from, how often it is updated, and how much accuracy the model loses.

Larger tiles. A 4×4×4 tile per core, then m16n8k16 per warp, then 64×N×16 per warpgroup, then tiles that can span a pair of SMs with the accumulator in TMEM. A larger tile spreads each operand fetch over more math, so the arithmetic intensity of the unit itself rises. It also raises the cost of coordination, because more threads, and finally a pair of SMs, must agree on staging and barriers.

More asynchronous data movement. Synchronous loads, then cp.async, then TMA descriptors, then distributed shared memory and TMEM. The rate of the Tensor Core grows faster than memory bandwidth, so every generation spends more of its design on keeping the unit fed without stalling the threads that issue the work.

The consequence for kernel authors stays the same. Only a kernel that stages a tile, issues a multiply-accumulate over it, and overlaps the movement of the next tile with the math of the current one can reach the nominal peak. The further a kernel is from this shape, the less of the peak it reaches. This is the roofline argument applied one level down, inside the unit.

What a datasheet peak assumes

A datasheet TFLOPS is a product: the number of units, times the FLOPs per unit per clock, times the clock. Five conditions hide inside this product:

  1. Dense or sparse. The sparse figure is twice the dense one and assumes exactly the 2:4 pattern. Comparing a sparse figure with a dense baseline overstates the gain by a factor of two.
  2. Clock. The boost clock holds only while power and temperature allow it. A long-running kernel can run at a lower clock, and the difference depends on the product and on its cooling.
  3. Format. The headline figure is usually the narrowest format with the highest rate. A TF32 kernel on an A100 sees half the BF16 peak, and an FP16 kernel on an H100 sees half the FP8 peak.
  4. Operands in place. The peak assumes that the operands sit in registers or shared memory and that the accumulator does not spill. A GEMM with M=1M=1M=1, as in decode, cannot fill the tile at all, so the unit sits mostly idle while the kernel is limited by memory.
  5. Power limit. A variant of the same GPU with a lower power limit cannot hold the same clock for as long. The H100 SXM is configurable up to 700 W, while the H100 NVL is configurable to 350–400 W and lists lower rates.

A worked example ties this back to serving. A 4,096 × 4,096 × 4,096 GEMM in FP16 costs 2×40963≈1.37×10112 \times 4096^3 \approx 1.37 \times 10^{11}2×40963≈1.37×1011 FLOPs. At the dense peak of 312 TFLOPS on an A100, this takes 0.44 ms (computed). Its operands and output take about 100 MB, and moving them takes 0.05 ms at 2,039 GB/s. The GEMM is compute-bound and can approach the peak. For one decode token, the same projection becomes a 1 × 4,096 by 4,096 × 4,096 product: the 33.5 MB weight matrix must still be read, but the FLOPs fall by a factor of 4,096, and the kernel is limited by the bytes. The Tensor Core is not slow in the second case; it simply has almost nothing to do.
