Hierarchical AllReduce and the Network-Card Bottleneck

This note follows one gradient through a hierarchical allreduce and then its bytes to the network card of the node. With it, a reader can check papers such as BlueConnect, TACCL and Trivance against the real bottleneck.

In data-parallel training, every GPU computes gradients on different samples, so every parameter receives G×HG\times HG×H contributions that must be summed. Inside a node the GPUs have NVLink, while between nodes they have the much slower InfiniBand. A common idea follows naturally: reduce inside the node first, so that less data has to leave the node, and then distribute the global result back.

However, “each GPU only sends one eighth of the gradient off the node” does not make anything eight times faster. In the end, all eight eighths may have to pass through the same network card. In addition, every position in the result still has to collect every input exactly once.

This note therefore follows one vector twice. It first follows the gradient through a hierarchical reduction and makes sure that every position receives every contribution exactly once, and it shows how two common mistakes break this property. It then follows the bytes to the egress of the node, and it explains what this means for papers such as BlueConnect, TACCL and Trivance, and for how communication connects back to a training step. My own checks are an integer model of the reduction, 84 boundary cases of the contribution count, and byte accounting under a declared bandwidth; their numbers are marked (computed). All throughput numbers come from the papers listed at the end.

Part 1: following the gradient

Splitting one gradient across three nodes

Take HHH nodes with GGG ranks each. A rank is one participant in the communication, and in this example each rank owns one GPU. The rank with local index ggg on node hhh has the input xh,g∈RNx_{h,g}\in\mathbb R^Nxh,g​∈RN, and position iii always means the same parameter. The goal is

y[i]=∑h=0H−1∑g=0G−1xh,g[i],0≤i<N.y[i]=\sum_{h=0}^{H-1}\sum_{g=0}^{G-1}x_{h,g}[i],\qquad 0\le i<N.y[i]=h=0∑H−1​g=0∑G−1​xh,g​[i],0≤i<N.

What is split is the range of vector positions, never the contribution of any rank. Each shard is responsible for some parameters, and every parameter that a shard is responsible for must include the contributions of all ranks.

A concrete example makes this clear: three nodes, four GPUs per node, 16 elements per GPU, and four shards covering the positions 0–3, 4–7, 8–11 and 12–15. The example follows only position 5, and this position belongs to shard 1. When the inputs are filled with consecutive integers starting from 1, the twelve values at this position are

g=0g=1g=2g=3node sumh=06223854120h=17086102118376h=2134150166182632\begin{array}{c|rrrr|r} &g=0&g=1&g=2&g=3&\text{node sum}\\\hline h=0&6&22&38&54&120\\ h=1&70&86&102&118&376\\ h=2&134&150&166&182&632 \end{array}h=0h=1h=2​g=0670134​g=12286150​g=238102166​g=354118182​node sum120376632​​

These values are only stand-ins for gradients that can be computed by hand. Every node should end up with 120+376+632=1128120+376+632=1128120+376+632=1128.

Step 1: ReduceScatter inside each node. Each node sums by position and then gives the results for different positions to different ranks. GPU 1 on the three nodes now holds 120, 376 and 632. The jjj-th owner on node hhh receives

sh(j)=∑g=0G−1xh,g(j),s_h^{(j)}=\sum_{g=0}^{G-1}x_{h,g}^{(j)},sh(j)​=g=0∑G−1​xh,g(j)​,

where the superscript (j)(j)(j) denotes a range of positions. At this point, a GPU holds all contributions of its node for one shard, and nothing about the other shards.

Step 2: AllReduce across nodes. Owners with the same number on different nodes form a group: shard 0 with shard 0, shard 1 with shard 1, and so on. Each group performs one AllReduce:

y(j)=∑hsh(j)=∑h∑gxh,g(j).y^{(j)}=\sum_hs_h^{(j)}=\sum_h\sum_gx_{h,g}^{(j)}.y(j)=h∑​sh(j)​=h∑​g∑​xh,g(j)​.

This step is where the three node sums of position 5 finally meet, in group 1. After this stage, GPU 1 on every node holds 1128. The other three GPUs do not have this position yet, but each of them holds a different correct shard.

Step 3: AllGather inside each node copies the four shards back into the full vector:

y=concat⁡(y(0),y(1),y(2),y(3)).y=\operatorname{concat}(y^{(0)},y^{(1)},y^{(2)},y^{(3)}).y=concat(y(0),y(1),y(2),y(3)).

This step only restores the ranges of positions and performs no more additions. After it, every GPU has the same global result (NCCL collective semantics).

Figure 1: Simplified to two nodes and shard 0 only, to show that each node sum enters the global sum exactly once. A real implementation sends every shard through, then distributes results as needed. The summing node in the figure doesn’t mean one GPU sends and receives everything.

Together, the three stages form RS–AR–AG: ReduceScatter inside the node, AllReduce across nodes, and AllGather inside the node. Correctness rests on two independent conditions: each shard collects every contribution, and the shards cover the full range of positions. The scheme does not need a node count that is a power of two, and it does not depend on which network layer is faster.

Two ways to get it wrong, and a counter that catches both

A common mistake is to read “GPU 1 holds all contributions of its node” as “GPU 1 holds the whole vector”. If only GPU 0 communicates across nodes after the ReduceScatter, the three node sums of position 5 never meet, because GPU 0 can represent shard 0 but not the other positions.

A scheme with a single proxy can be correct, however. It reduces the full node sum to one proxy, runs AllReduce among the proxies, and then broadcasts the result inside each node. This scheme differs from the sharded scheme only in which GPU holds each shard and which paths the shard takes, and the sum that it computes is identical.

The opposite mistake counts contributions twice. It first runs an AllReduce inside the node, so all four GPUs hold the same node sum, and it then feeds all these copies into one global sum:

∑h∑g=0G−1sh=G∑hsh=Gy.\sum_h\sum_{g=0}^{G-1}s_h=G\sum_hs_h=Gy.h∑​g=0∑G−1​sh​=Gh∑​sh​=Gy.

So 1128 becomes 4512. Every GPU still receives the same answer, and therefore “all GPUs agree” does not prove that the reduction was correct.

One case deserves a note. After an AllReduce inside the node, four independent groups of GPUs with the same number can be built, where each group takes one copy of the node sum from each node and reduces across nodes. All four groups correctly obtain 1128. This scheme sends four full vectors over the network, but no value is counted too many times. The difference is whether copies end up in the same addition.

To catch these mistakes directly, a provenance count is attached to every output position. The count has one column per original rank and increases each time the input of that rank is added. In a correct result, every real position contains only ones; a missing shard shows up as 0, and double counting shows up as values above 1.

Figure 2: From an actually run CPU integer model: three nodes, four GPUs each, length 13. The program pads to 16, processes four shards and trims the padding. The first 13 rows should each have 12 ones; padding has no original contributions. Sending only shard 0 cross-node keeps just the first four real positions; re-adding intra-node copies puts 4 in every cell.

The purpose of the model is not to simulate network time with NumPy. Its purpose is to make the values and the provenance counts travel the same path. Below is the reduction part of collective_case, without the input construction and the deliberately broken branches; local_chunks[h][j] holds both the values of a shard and its provenance matrix:

global_chunks = [
    (sum(local_chunks[h][j][0] for h in range(nodes)),
     sum(local_chunks[h][j][1] for h in range(nodes)))
    for j in range(local_ranks)
]
final_values = np.concatenate([x[0] for x in global_chunks])[:length]
final_counts = np.concatenate([x[1] for x in global_chunks])[:length]
assert np.array_equal(final_values, expected)
assert np.all(final_counts == 1)

The check covers node counts 1, 2, 3 and 4, local rank counts 1, 2 and 4, and lengths 1, 2, 3, 7, 8, 13 and 17, for 84 combinations in total, and the correct scheme passes all of them. Padding to G⌈N/G⌉G\lceil N/G\rceilG⌈N/G⌉ also covers the case N<GN<GN<G, because zero is the identity element of addition.

Using int64 values that cannot overflow separates the structure of the reduction from floating-point rounding. With real gradients, each contribution should still appear exactly once, but the hierarchy changes the order in which the additions are grouped, so the results need not match a serial summation bit for bit. High-precision references, checks for non-finite values and sensible tolerances therefore still matter, and the tolerance must not be so loose that a missing shard can pass.

📝 Note: The final AllGather doesn’t always need to run. If each GPU owns only one shard of optimizer state, it only needs the matching global gradient shard to update parameters. FSDP hybrid sharding’s gradient reduction is exactly a ReduceScatter within the shard group plus AllReduce of same-numbered shards across replica groups (see FSDP and Megatron); a parameter AllGather happens later when forward needs full parameters. That’s a different tensor with a different lifetime, not “copy the full gradient immediately” (FSDP §3.2.2).

Part 2: following the bytes

Ring traffic, counted at the right boundary

Only after the reduction is correct does it make sense to ask how much less data is sent. Let the full input of each rank be SSS bytes, and assume a standard chunked ring: PPP participants form a circle, and in each round every participant sends one chunk to the next participant.

ReduceScatter takes P−1P-1P−1 rounds of S/PS/PS/P, and AllGather takes another P−1P-1P−1 rounds. Each rank therefore sends

Vrank=2P−1PS.V_{\rm rank}=2\frac{P-1}{P}S.Vrank​=2PP−1​S.

This value counts the bytes sent, not the bytes sent plus received, for this ring algorithm. NCCL may choose other algorithms, and real links rarely run at full speed.

In the hierarchical scheme, the RS and AG inside the node send, per GPU,

Vlocal,rank=2G−1GS.V_{\rm local,rank}=2\frac{G-1}{G}S.Vlocal,rank​=2GG−1​S.

In the middle stage there are GGG groups across nodes, and each group handles a shard of size S/GS/GS/G with HHH participants. Each GPU therefore sends across nodes

Vcross,rank=2H−1HSG.V_{\rm cross,rank}=2\frac{H-1}{H}\frac SG.Vcross,rank​=2HH−1​GS​.

Here the factor 1/G1/G1/G appears. However, the GGG GPUs on the same node send at the same time, and their bytes add up, so at the egress of the node the volume is still

Vcross,node=2H−1HS.V_{\rm cross,node}=2\frac{H-1}{H}S.Vcross,node​=2HH−1​S.

This value is exactly the payload per node of the scheme with a single proxy and a ring AllReduce among the proxies. Sharding changes the owners and the opportunities for concurrency, but it does not reduce the amount that the whole node must exchange by another factor of GGG.

A flat ring must also be counted along its actual path. If all HGHGHG ranks form one ring in which ranks on the same node are neighbors, each node has only one ring edge that crosses to the next node. This edge carries S/(HG)S/(HG)S/(HG) per round over 2(HG−1)2(HG-1)2(HG−1) rounds, so the node sends across its boundary

Vflat,cross,node=2HG−1HGS.V_{\rm flat,cross,node}=2\frac{HG-1}{HG}S.Vflat,cross,node​=2HGHG−1​S.

Ring edges inside a node do not go through the NIC, so the cross-node traffic cannot be obtained by multiplying the bytes sent per rank by GGG. Interleaving the ranks would add more edges across nodes, and multiple channels, bidirectional rings or other topologies must be counted again along their paths.

With eight nodes of eight GPUs and a full vector of 256 MiB:

Accounting boundaryHierarchical send volume (computed)

Seen from the node, the hierarchy reduces 504 MiB to 448 MiB, while seen from one GPU, each GPU sends 56 MiB across nodes. These statements refer to different boundaries, and one cannot replace the other. In addition, as the number of nodes grows, both formulas for the egress of the node approach 2S2S2S, so a reduction of the payload alone helps less and less.

Bandwidth is per resource, not per communicator

If all 448 MiB leave through one egress with effective bandwidth BnodeB_{\rm node}Bnode​, the time cannot be lower than the following bound, even without launch, synchronization and contention:

Tcross≥Vcross,nodeBnode.T_{\rm cross}\ge \frac{V_{\rm cross,node}}{B_{\rm node}}.Tcross​≥Bnode​Vcross,node​​.

The bound becomes Vcross,node/(GB)V_{\rm cross,node}/(GB)Vcross,node​/(GB) only if there really are GGG concurrent paths without contention, each with effective bandwidth BBB, and the shards are split evenly. At an assumed 25 GB/s, the bound is about 18.79 ms through one egress and about 2.35 ms through eight independent egresses.

Figure 4: Left, payload by accounting boundary. Right, lower bounds under shared vs. independent egress.

The 8× gap in the right panel comes from eight physical resources, not from creating eight communicators. The value of 25 GB/s is an assumption for this calculation, not a measured NIC speed, and a NIC rated at 200 Gbit/s may not reach that speed in a real system either. Wherever paths merge again, at a PCIe uplink, a NIC or a switch port, the total bytes must be counted at that shared point.

Latency, launches and the alpha-beta view

For large messages, bandwidth is the dominant term, while for small messages the fixed latency per step matters more. With α\alphaα as the latency of one ring step and without the compute of the reduction, a simple model is

TAR(P,S)≈2(P−1)α+2P−1PSB.T_{\rm AR}(P,S)\approx2(P-1)\alpha+2\frac{P-1}{P}\frac SB.TAR​(P,S)≈2(P−1)α+2PP−1​BS​.

When the RS/AG inside the node is chained with the AR across nodes, and each shard has its own path across nodes with equal speed, the model becomes:

Thier≈2(G−1)αlocal+2G−1GSBlocal+2(H−1)αcross+2H−1HSGBcross.\begin{aligned} T_{\rm hier}\approx{}&2(G-1)\alpha_{\rm local} +2\frac{G-1}{G}\frac{S}{B_{\rm local}}\\ &+2(H-1)\alpha_{\rm cross} +2\frac{H-1}{H}\frac{S}{G B_{\rm cross}}. \end{aligned}Thier​≈​2(G−1)αlocal​+2GG−1​Blocal​S​+2(H−1)αcross​+2HH−1​GBcross​S​.​

If the nodes share bandwidth, the denominator of the last term becomes the total effective bandwidth of the node. Launches and queueing across groups may also fail to overlap, so this model remains rough. What the model does well is to put “fewer steps on the slow link”, “better use of concurrent paths” and “an extra stage inside the node” into one comparison.

What the papers assume

BlueConnect: the same decomposition, more levels

BlueConnect extends this decomposition to networks with several levels. The ranks are written as 3D coordinates (a,b,c)(a,b,c)(a,b,c) with axis sizes p0,p1,p2p_0,p_1,p_2p0​,p1​,p2​. The scheme runs a ReduceScatter along ccc, then a ReduceScatter of the result along bbb, and then one more along aaa. The payload of one owner shrinks as

S⟶Sp2⟶Sp2p1⟶Sp2p1p0.S\longrightarrow\frac S{p_2}\longrightarrow\frac S{p_2p_1} \longrightarrow\frac S{p_2p_1p_0}.S⟶p2​S​⟶p2​p1​S​⟶p2​p1​p0​S​.

At this point, each shard contains every contribution but is held by one owner, and AllGathers in the reverse order along a,b,ca,b,ca,b,c then restore the ranges of positions level by level. The AR across nodes in RS–AR–AG can itself be split into RS+AG, so the two schemes are mathematically continuous (BlueConnect §3; conditions and limitations in §3.4).

This decomposition can put the large early payloads on fast paths and the shrunken shards on slow paths. However, it still needs a suitable hierarchy of participants, and it is still limited by shared uplinks: a small shard per GPU at some level does not mean that the total traffic of the node is small.

The training experiments of the authors used 48 IBM S822LC machines, each with four P100-SXM2 GPUs, NVLink inside the node and single-port 100 Gbit/s InfiniBand. The workload was ResNet-50/ImageNet-1K with a batch of 32 per GPU and a total batch of 6144 on 192 GPUs, with FP32 gradients and data preloaded on a RAM disk. The baseline in the text is 163 ms per GPU, and at 192 GPUs, the GLOO comparison adds about 58 ms of overhead, while BlueConnect adds about 31 ms.

These numbers are easier to understand within a full step. The overhead dropped by (58−31)/58≈46.55%(58-31)/58\approx46.55\%(58−31)/58≈46.55% (computed), and the figure of about 87% in the paper is the same change measured the other way, 58/31−1≈87.10%58/31-1\approx87.10\%58/31−1≈87.10%. With the rounded values from the text, the step goes from 163+58=221163+58=221163+58=221 ms to 163+31=194163+31=194163+31=194 ms. The step is about 12.22% shorter, and the throughput ratio is about 1.139. So nearly halving the communication overhead is a real gain, and within a full training step this gain appears as a speedup of 12%.

These calculations use the rounded numbers of the paper, so they are approximate. (Figure 6(d) of the paper is a projection for future FP16 devices, not a P100 measurement, and the backends have changed since NCCL2.) What transfers best to other systems is the method of decomposing collectives by network level, not any particular speedup.

TACCL: shorter paths aren’t automatically faster kernels

The models above treat “send a shard and reduce it” as one step. On a GPU, this step may become receive, sum, write an intermediate buffer, read it again and send, and whether these operations can be fused changes the time directly. So a shorter path does not guarantee a faster implementation.

TACCL (NSDI 2023) synthesizes communication plans from a communication sketch provided by the user. Its authors openly report a useful negative result: for AllReduce across two DGX-2s with messages of at least 512 MB, TACCL was up to 9% slower than NCCL 2.8.4-1. They attribute this result to a backend without fused receive-reduce-copy-send operations, so that work saved at the level of paths can be cancelled out by extra instructions and synchronization (TACCL Figure 8(i)).

The best-known 6.7× result of the paper comes from small and medium AllGather messages on two DGX-2s (32 GPUs), a different setting from this AllReduce. Section 7.2 also shows that more execution instances increase the latency for small messages, and the authors suggest that this comes from synchronized scheduling of memory accesses at the start of each send. Larger messages are more likely to benefit from extra parallelism, so the message size decides the trade-off between launch cost and parallel bandwidth.

Trivance: the multi-port assumption

Multi-port algorithms change a different assumption: the number of directions in which a GPU can send at the same time. Trivance targets bidirectional rings and multi-dimensional tori and uses concurrency across directions to reduce the number of logical steps. Its evaluation (Section 6) is a packet-level SST simulation with 800 Gb/s links by default (Appendix E), and it assumes that these directions can really be used at the same time (Appendix D) (Trivance).

On a real machine where two directions end up sharing one congested uplink, the reduction is still mathematically correct, but the concurrency no longer exists. This is the same resource question as eight GPUs that share one NIC, in a different topology.

So each paper teaches something different: BlueConnect shows how to build levels, TACCL shows that the execution backend has costs of its own, and Trivance shows how much port concurrency can help. Since each paper assumes different hardware, their reported speedups cannot be compared directly.

Plugging communication back into training

Communication must also connect back to training. The backward pass writes gradients on the compute stream, and the communication stream must wait until a shard is ready before it reads the shard. The reduction across nodes waits for the result of the ReduceScatter inside the node, and the optimizer waits for the shard that it needs. When a normal NCCL call returns, this only means that the operation was enqueued on a CUDA stream, not that any consumer can use the data, so dependencies across streams need stream/event semantics (NCCL CUDA Stream Semantics).

In an implementation, the mathematical ownership of position 5 becomes a buffer offset, a shard length, a dtype and the rank mapping of the communicator. Every node must interpret “shard 1” by the same rule, with consistent padding and trimming. If a retry adds the same contribution again, the provenance count rises above 1, and resending alone does not fix this error.

What training actually waits for is the last gradient on the critical path. If some communication becomes much faster but was already hidden behind the backward compute, the step hardly changes, while a tiny reduction at the end that blocks the optimizer may decide the step time. For this reason, the stage inside the node, the stage across nodes, the full reduction and the training step should be measured separately. Bytes per GPU, bytes at the node egress, GB/s and step time each answer a different question.

Conclusion

The two parts of the post lead to two conclusions. Following the gradient shows that hierarchical AllReduce is correct when every shard collects every contribution exactly once and the shards cover all positions, and that a provenance counter detects both missing and double-counted shards, while the check “every GPU got the same answer” cannot detect them. Following the bytes shows that the hierarchy reduces the cross-node traffic per GPU by GGG, but the traffic at the node egress stays near 2S2S2S, so any further speedup needs physically independent paths. BlueConnect, TACCL and Trivance each work best under their own conditions of resources and backend.

Count the reduction for each position and count the bytes for each physical link; any number that is skipped will later cause a surprise.
