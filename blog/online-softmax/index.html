Online Softmax Attention in CUDA and Why It Ran Slower

Skipping the 16 MiB score matrix of 2048-token attention should save time, yet the online kernel ran slower. This post derives the online state, builds the CUDA kernel, fixes its bugs and shows why the cost lies outside the formula.

Online softmax solves one specific dependency. Every softmax term depends on a normalization over the whole row, but when a row is processed in tiles, the later scores have not been read yet. The derivation must therefore decide what state to keep when one row is split into pieces, and how the states of two pieces merge. Once this is decided, a more practical question follows: does an implementation that skips the full matrix actually run fast? And if it does not, does the reason lie inside the formula or outside it?

For single-head attention with a sequence length of 2048, the matrix of the scores of every query against every key takes 16 MiB of FP32, and it is read exactly once in a weighted sum and never used again. This post answers both questions with two implementations.

The post first derives the online state and checks it with a small example by hand. It then writes a CUDA kernel that gives each query its own block, including three bugs that I found along the way. Next, it times this kernel against a separated implementation and works out why it is slower. The last part covers the two-pass softmax for long rows, because an interface that requires the full probability vector needs it. All GPU experiments ran on an RTX 5070 Laptop (SM120), and the results describe these two hand-written implementations, not attention kernels in general.

Fundamentals: two scalars and a vector

The setup is as follows: Q∈RM×dQ\in\mathbb R^{M\times d}Q∈RM×d and K,V∈RN×dK,V\in\mathbb R^{N\times d}K,V∈RN×d, all contiguous FP32. MMM is the number of queries, NNN the number of keys and values, and ddd the feature dimension. Only the single-head dense forward pass is considered, without mask, dropout or backward pass.

S=QKTd,Pij=eSij∑k=0N−1eSik,O=PV.S=\frac{QK^\mathsf T}{\sqrt d},\qquad P_{ij}=\frac{e^{S_{ij}}}{\sum_{k=0}^{N-1}e^{S_{ik}}},\qquad O=PV.S=d​QKT​,Pij​=∑k=0N−1​eSik​eSij​​,O=PV.

For one fixed query, the score sjs_jsj​ is its scaled dot product with key jjj, and the output is a weighted sum of value vectors. The separated implementation runs four steps as four kernels: transpose KKK, QKQKQK, softmax and PVPVPV, and the storage for SSS is overwritten in place by PPP.

Figure 1: Separated attention materializes SSS/PPP; online attention keeps only per-row state.

Subtracting the maximum in softmax is usually described as protection against overflow, but it also sets the reference scale for merging tiles:

m=max⁡jsj,ℓ=∑jesj−m,pj=esj−m/ℓ.m=\max_j s_j,\qquad \ell=\sum_j e^{s_j-m},\qquad p_j=e^{s_j-m}/\ell.m=jmax​sj​,ℓ=j∑​esj​−m,pj​=esj​−m/ℓ.

Dividing the numerator and the denominator by eme^mem leaves the probabilities unchanged in exact arithmetic, and because no argument of the exponent exceeds zero, the overflow from exponentiating large positive values disappears. This assumes finite scores; with positive infinity, ∞−∞\infty-\infty∞−∞ needs a separately defined behavior.

Merging without rereading

The difficulty is that during tiling, the final maximum is not known yet. Take the three scores 0, 1 and 3. After the first two scores, the stored exponent sum at the maximum so far, 1, is e−1+1e^{-1}+1e−1+1. When 3 arrives, both old terms must move to the new reference 3:

(e−1+1)e−2+1=e−3+e−2+1.(e^{-1}+1)e^{-2}+1=e^{-3}+e^{-2}+1.(e−1+1)e−2+1=e−3+e−2+1.

No old score needs to be read again, because multiplying the whole stored sum by e−2e^{-2}e−2 rescales it. When this step is generalized, any processed set AAA stores two numbers:

mA=max⁡j∈Asj,ℓA=∑j∈Aesj−mA.m_A=\max_{j\in A}s_j,\qquad \ell_A=\sum_{j\in A}e^{s_j-m_A}.mA​=j∈Amax​sj​,ℓA​=j∈A∑​esj​−mA​.

Another block BBB has the same state, and joining the two takes one maximum, two rescaling factors and one addition:

m=max⁡(mA,mB),ℓ=emA−mℓA+emB−mℓB.m=\max(m_A,m_B),\qquad \ell=e^{m_A-m}\ell_A+e^{m_B-m}\ell_B.m=max(mA​,mB​),ℓ=emA​−mℓA​+emB​−mℓB​.

The new scale is not smaller than either old scale, so both factors are at most 1, and the sum cannot overflow upward. The merged result is the maximum and the exponent sum of the union, independent of the merge order in exact arithmetic. This property allows “read once in order” to generalize to tree reductions over threads, warps and blocks. In floating point, a different tree shape changes the last few bits, so two trees will not match bit for bit (online normalizer paper).

Attention also has to weight the values, so the state gains a ddd-dimensional vector:

uA=∑j∈Aesj−mAVj.u_A=\sum_{j\in A}e^{s_j-m_A}V_j.uA​=j∈A∑​esj​−mA​Vj​.

This vector merges with the same two factors:

u=emA−muA+emB−muB,O=u/ℓ.u=e^{m_A-m}u_A+e^{m_B-m}u_B, \qquad O=u/\ell.u=emA​−muA​+emB​−muB​,O=u/ℓ.

As long as no other caller needs the full probabilities, the contribution of each tile can be added into uuu as soon as VVV is read, and the scores of the tile can be thrown away. What remains is two scalars plus one ddd-dimensional vector, instead of NNN probabilities. FlashAttention combines exactly this online normalization with on-chip matrix tiling to avoid materializing the full attention matrix, and its speed depends on input reuse and compute layout.

The empty state also needs a definition. The kernel: one block per query

The most direct mapping gives each query its own block: 128 threads, the query in shared memory, and K/VK/VK/V read tile by tile along NNN. Once a tile is ready, four warps divide its keys. Each warp computes the QK dot product of one key, with the lanes dividing ddd and shuffles merging the partial sums. After the scores of the tile are computed, the block finds their maximum and exponent sum, and each thread updates the output dimensions that it owns.

With d=64d=64d=64, each lane handles two products and the warp reduces them to one score, so four warps compute four keys in parallel. In the PV phase, the threads switch to dividing the output features: the first 64 threads each accumulate one valid dimension with the same score weights and read their own column of VVV, and they finally write the 64-dimensional output of this query.

The fused update does not need to store uBu_BuB​ of the current tile separately; it accumulates directly at the common scale:

new_m = max(old_m, tile_max);
alpha = exp(old_m - new_m);
for (each valid key j in this tile)
    p[j] = exp(score[j] - new_m);

acc = alpha * acc + sum_j(p[j] * V[j]);
l   = alpha * l   + sum_j(p[j]);
m   = new_m;
// after all K/V tiles:
output = acc / l;

acc is a ddd-dimensional vector, while mmm and ℓ\ellℓ are shared by the block, and the output components live in the registers of different threads. In attention/softmax_new.cu, the multiply-adds use fmaf and the exponents use __expf, with the old state initialized to (-FLT_MAX,0,0); N>0N>0N>0 guarantees that every processed tile has at least one valid key. (__expf is an approximate exponential even without --use_fast_math.)

Three bugs worth knowing about

Bug 1: zero-padding tails. In GEMM, padding KKK with zeros is natural, because the extra products do not change the sum. Doing the same in softmax breaks the result: a nonexistent key padded with 0 still receives a positive weight and changes the denominator. So “pad the tile” has different semantics in the two operations, and the tail of NNN may only process min(TileN,N-tile_start) valid keys.

Bug 2: a legal value used as a sentinel. The reduction of the separated implementation originally checked max_next > -FLT_MAX to decide whether a thread had input, so it treated -FLT_MAX as an impossible sentinel. With d=1d=1d=1, QQQ all -FLT_MAX and KKK all 1, every score is exactly this legal finite value, and non-empty threads are treated as empty. At M=3M=3M=3, N=2N=2N=2, d=1d=1d=1, both probabilities in each row became 1, the row sums became 2, and the final OOO had a maximum error of 0.108322. The correct test is sum_next > 0: with NNN non-empty, the exponent sum is always positive, the same property as ”ℓ>0\ell>0ℓ>0 means non-empty” above. N=2N=2N=2, 33 and 257 cover small rows and striding across warps and threads.

Bug 3: a race on shared scratch. This bug has nothing to do with the formula. It lies in the shared scratch space that both the maximum reduction and the sum reduction use. The reduction helper lets warp 0 write the final result and then runs a block barrier, and the old ending was

__syncthreads();
return scratch[0];

A barrier makes the writes before it visible to other threads, but it does not guarantee that the reads after it have finished. A fast warp reads, returns, and may already be in the next sum reduction, overwriting the scratch space, while a slow warp only now reads the previous maximum. So two function calls appear one after another in the source code, but the warps do not keep this order.

The fix reads the value and then confirms that every reader has left:

__syncthreads();
const float result = scratch[0];
__syncthreads();
return result;

All 128 threads call this helper, so the second barrier is safe. Giving the maximum and the sum separate scratch space would also work.

What makes this bug hard to notice is that ordinary output comparisons do not detect it. The unfixed version passed all 72 output comparisons, yet racecheck on 31×37×6531\times37\times6531×37×65 reported 9 hazards (4 errors and 5 warnings), and the maximum output error of that run was 0.171574. After the fix, the same input gives 7.9103×10−87.9103\times10^{-8}7.9103×10−8, and memcheck, racecheck and synccheck all report no problems. So passing the output checks was not enough on its own, and the race checker found what the comparisons missed.

Figure 3: The race only shows up as error on some inputs.

The interface finally requires positive M/N/dM/N/dM/N/d with d≤1024d\le1024d≤1024 and checks the shared-memory capacity. The inputs, the QK accumulation and scaling, and the weighted sum of VVV must all be finite, but the interface does not scan every element for special values. uuu is not normalized yet, so a very large finite VVV can still overflow the accumulation: subtracting the maximum fixes the range of the exponent, not every numerical problem. All performance numbers below come from the code with these fixes.

The surprise: no matrix, more time

Removing the matrix should make the computation faster. The measurements fall into two groups. First, the conditions: both paths use workspace allocated in advance, with the inputs resident on the GPU, so the temporary allocation per call of the separated version does not distort the kernel comparison. The scores of the separated version take MNMNMN floats and the transposed KKK takes NdNdNd floats:

Wseparated=4MN+4Ndbytes.W_{\rm separated}=4MN+4Nd\quad\text{bytes}.Wseparated​=4MN+4Ndbytes.

The fused version does not allocate these two global workspaces, although it still uses shared memory, registers and the output. At M=N=2048M=N=2048M=N=2048, d=64d=64d=64, the separated scores take 16 MiB and KTK^\mathsf TKT 0.5 MiB, and the formula gives 258 MiB at 8192, a size that was not timed.

Where the time goes: the mapping, not the formula

The thread mapping explains the limit. One block serves one query, and every query reads all of K/VK/VK/V again from start to finish, about 2Nd2Nd2Nd floats requested in terms of the source code. Neighboring queries use exactly the same K/VK/VK/V, but they cannot share it within one shared tile. Caches serve some repeated requests, but loading, dot products and reductions are still organized query by query, and at M=1M=1M=1 exactly one block works on the whole GPU. Grouping several queries into one output tile would let one K/VK/VK/V sub-tile serve several rows at the same time, and nothing in the online formula requires one query per block.

A second resource issue can be checked separately: the default entry chooses the largest K/VK/VK/V tile that the capacity allows. With d=64d=64d=64 and N≥128N\ge128N≥128, TileN=128 needs this amount of dynamic shared memory:

4(d+2Td+T+128/32)=66320 B,T=128.4(d+2Td+T+128/32)=66320\text{ B},\qquad T=128.4(d+2Td+T+128/32)=66320 B,T=128.

The ddd term holds QQQ, 2Td2Td2Td holds K/VK/VK/V, TTT holds the current scores, and the last four floats are reduction scratch for four warps. TileN=32 needs only 16784 B, at the cost of four times as many loop iterations. Whether fewer iterations or more resident blocks matter more is a question for measurement.

When you need the probabilities: two passes

All of the above concerns attention. If the interface requires the full softmax vector, the situation changes, because (m,ℓ)(m,\ell)(m,ℓ) alone is not enough: it keeps what the denominator needs, but it cannot recover each original score. Unless the whole row stays on chip, the input must be read a second time once the state of the full row is known.

For a long row of 10610^6106 elements, a single block that scans the row leaves every other SM idle. Instead, GGG blocks can each compute a local state, and a second kernel produces the output. The real implementation for long rows is in attention/softmax_self.cu, with 512 threads per block in both passes.

The second pass does not launch a separate kernel for a global reduction of the states. Instead, warp 0 of every output block merges all GGG local states again, puts the result into its own shared memory, and then outputs its own slice of the input:

if (threadIdx.x < 32) {
    for (int i = threadIdx.x; i < num_blocks; i += 32) {
        float m = block_max[i], s = block_sum[i];
        // Merge into thread-local state, then reduce within warp 0.
    }
}

This saves one kernel launch, but the reads of the statistics grow as G2G^2G2. With N=1000000N=1000000N=1000000 and G=144G=144G=144, NCU reports 7813 global load requests and 125000 sectors for pass one, and 9253 and 130184 for pass two. The difference can be computed directly from the code:

Δrequest=144×2×⌈144/32⌉=1440,\Delta request=144\times2\times\lceil144/32\rceil=1440,Δrequest=144×2×⌈144/32⌉=1440, Δsector=144×2×144×432=5184.\Delta sector=144\times\frac{2\times144\times4}{32}=5184.Δsector=144×322×144×4​=5184.

Each output block reads two contiguous FP32 arrays of 144 statistics once, and this subtraction matches the samples exactly. These are L1TEX requests and sectors, not equal DRAM traffic, because repeated statistics can hit the cache. So more blocks raise the parallelism of the input scan and add repeated merging, and this implementation cannot become faster indefinitely by adding blocks.

In the disassembly, aligned input uses ld.global.v4.b32, the warp merges use shfl.sync.down.b32, and the exponential becomes ex2.approx.f32 (MUFU.EX2 in SASS). The natural exponent is first multiplied by log⁡2e\log_2 elog2​e to become a binary exponent. The approximate exponential and the reduction tree are the concrete sources of error when the real-number state formula is implemented in FP32. Neither pass has extra shared wavefronts or spilling requests at runtime, and the occupancy for long rows is about 85.85% and 86.33%. Short rows have only one block, so a local residency percentage says nothing about how busy the whole GPU is.

State has to belong to one request

The state between the two kernels must belong to one request. Suppose that all calls share a single global array, and two rows of length 65537 (A=0, B=10) are scheduled as A pass 1 → B pass 1 → A pass 2 → B pass 2. Then B overwrites the maximum and the exponent sum of A, and the output row sum of A becomes e−10≈4.53999×10−5e^{-10}\approx4.53999\times10^{-5}e−10≈4.53999×10−5. I arranged this interleaving on purpose. The original synchronous solve does not run into it in normal use, but the example shows that shared state is not safe behind a concurrent interface.

The interface therefore now takes a workspace of 2*G floats that is private to the request, together with a stream:

cudaError_t softmax_vector_launch(
    const float* input, float* output, int N,
    float* workspace, int num_blocks, cudaStream_t stream);

The workspace lives from before the launch of pass one until pass two finishes, it does not overlap the input or the output, and each request in flight has its own workspace. The input and the output may be exactly the same address, but partial overlap is not supported. The state for long rows is initialized to (-FLT_MAX,0) and merges directly by the formula; subtracting two empty states gives exactly zero, so no negative infinity appears. (This handles empty states differently from the non-empty test in the attention kernel above.)

Figure 8: Long-row timing and the shared-state counterexample.

With private workspaces, two streams each submitted 100 times, and both final output row sums are 0.999999999767. The alignment of the input and output addresses was checked separately, and the in-place and offset cases were verified. At 10610^6106 elements, the aligned and offset cases take 23.513 and 26.038 µs, and at 1024 elements, 16.773 and 17.278 µs. The fixed launch cost of two passes does not disappear with the row length, and for small rows, the variation from round to round is already close to the alignment difference. These event intervals exclude allocation and transfer, but they may include submission gaps.

Conclusion

The math part works exactly as described: two scalars and a ddd-vector per row are enough, and merges can happen in any order. The performance part depends on something that the math does not specify, namely the mapping. Giving each query its own block means that every query reads all of K/VK/VK/V again, and the largest tile that fits leaves one block per SM. This made the fused kernel up to 20× slower than writing out the full matrix. In addition, when the caller needs the probabilities, the online state cannot avoid a second pass; what it can do is make this pass parallel, at a measurable cost.

The remaining gap is consistent with “one block serves one query”, because the same K/VK/VK/V cannot serve several rows at once. No variant here changes the number of queries per block, so this cause is the leading explanation rather than a measured one. Grouping several queries into one output tile is the next experiment, and only measurement can show how many rows should fit into shared memory.

Online softmax removes the need to store the matrix; it does not remove the need to reuse the inputs.

In addition, the effective addresses of Q/K/V/output are deliberately offset by one float, so results don’t only hold at float4-aligned addresses, and outputs have a sentinel before and after. The separated path also reads the real probability matrix, checking non-negativity, finiteness, row sums and error against CPU probabilities; the fused path has no probability matrix, so its check target is the final output.

The elementwise acceptance condition is

After the fixes, 72 base checks, 6 finite-extreme boundary checks and 48 same-shape pre-timing checks, 126 output comparisons in all, pass this bar. Actual max absolute error is 2.6226×10⁻⁶ and max RMSE 8.2390×10⁻⁷; all outputs are finite and sentinels unchanged. The separated path’s max probability error is 7.8355×10⁻⁸ and max row-sum deviation 1.7919×10⁻⁷.

Constant V’s expected output is 3.25, and after accumulating many positive weights and normalizing, rounding errors tend to pile up in the same direction, so absolute error is higher than in some random cases. Darker heatmap cells are still within the range above, and these synthetic inputs can’t predict quality changes in real language models.

The 13.1 in the table is the build Toolkit version; the environment integration check recorded runtime 13.3 (13030) via cudaRuntimeGetVersion, with the raw ENV line saved separately. Since CUDA 13 the Windows runtime can ship with the display driver and may differ from the build Toolkit; see the versioning API docs.

Error bars in the figures are p05 to p95 of 90 batch means, not single-request p95 and not statistical confidence intervals. CUDA events bracket the entire submitted work, so short kernels may still include device idle time from late host submission. The fused entry in particular calls the attribute-setting API when its shared configuration is large; this experiment keeps that checked-dispatch cost, so not all of the time can be attributed to kernel instructions.

Source and entry points

Single-head attention and long-vector softmax are the two problems actually run. The repository also has three multi-head files: multihead_attention.cu calls the separated path head by head; multi_head_attention.cu’s local accumulator arrays cover at most four 32-dimension chunks; multi_head_attention_op.cu returns immediately for head dimensions above 64. None of them are in the performance tables.

Long-row raw records, the global-array counterexample and source snapshots are in rep_mur/blog-rewrite/style-v2/softmax/, and the attribute/tile comparison in style-v2/attention/. Long-row curves are aggregated per round by bench_mur/editorial/style-v2/operator_softmax_shapes.py, and the hand-example and state figures are generated by operator_figures.py, with each batch counted separately.

Main source SHA-256 prefixes: separated path 14f3aa480ffb, fixed fused path 011e1ea83bd4. Source, scripts, binary hashes, build output, per-batch times and Sanitizer logs are in rep_mur/blog-rewrite/attention/; the original draft is in originals/, the racy version in before-race-fix/, and the version before the empty-state boundary fix in before-finite-boundary-fix/.
