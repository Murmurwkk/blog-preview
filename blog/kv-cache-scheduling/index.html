INT8 KV-Cache Attention: Thread Mapping and Encoding Error

Two INT8 decode-attention kernels read the same cache with different thread mappings; one needs a tenth of the QK sectors. A CPU study shows how absmax, rotation and QJL change the output.

Every time a model generates its next token, attention reads the whole history again. The keys and values were computed in earlier steps and do not need to be recomputed, but they still have to take part in the dot products of the current query and then in the weighted sum. The longer the context, the bigger this cache, and the more sequences run at the same time, the more copies sit in GPU memory.

Compressing K/V from floats to integers is the direct way to shrink the cache. However, how much smaller the cache becomes and how much faster attention becomes are two different questions. The decoding of the integers, the addresses that neighboring threads read and the division of the reductions can each cancel out the benefit of moving fewer bytes. Lowering the bit width also changes the attention weights, and a quantizer that reconstructs vectors well does not necessarily preserve the dot product that the current query depends on.

So this post has two halves that use different encodings, and their results cannot be combined into one end-to-end speedup number. The first half is measured on the GPU: one head, one layer and one stretch of valid history, with K/V stored as contiguous INT8 and the output computed in FP32. It compares two kernels that read the same INT8 cache with different thread mappings, so it measures how the mapping changes the memory traffic and the time; it does not compare INT8 with an FP16 cache. The second half uses numerical experiments on the CPU to ask how different encodings change the attention output: absmax, random rotation with a spherical codebook, and a QJL residual.

What one decode step reads

Suppose there are NNN visible tokens, each key and value has ddd components, and the current query is q∈Rdq\in\mathbb R^dq∈Rd. The computation is

zt=1d∑j=0d−1qjkt,j,pt=exp⁡(zt−m)∑uexp⁡(zu−m),oj=∑t=0N−1ptvt,j,z_t=\frac{1}{\sqrt d}\sum_{j=0}^{d-1}q_jk_{t,j},\qquad p_t=\frac{\exp(z_t-m)}{\sum_u\exp(z_u-m)},\qquad o_j=\sum_{t=0}^{N-1}p_tv_{t,j},zt​=d​1​j=0∑d−1​qj​kt,j​,pt​=∑u​exp(zu​−m)exp(zt​−m)​,oj​=t=0∑N−1​pt​vt,j​,

with m=max⁡tztm=\max_tz_tm=maxt​zt​. Subtracting the maximum does not change the proportions of softmax; it only keeps large positive values out of the exponent. The first sum runs over channels and the last sum over historical tokens. These two reductions run in different directions, and this difference decides how the threads are organized.

The cache stores kt,vtk_t,v_tkt​,vt​, not the finished ptp_tpt​, because the query of the next step is different and the weights must be computed again. This entry point takes only valid history that the caller has already filtered, and it does not handle masks, the head mapping of GQA, paged addressing or appends to the cache. With HHH heads, K/V are laid out contiguously as [H,N,d], with the last dimension contiguous.

The INT8 format

The most direct compression gives the K vector and the V vector of each token their own scale. For one row xxx:

s=max⁡j∣xj∣127,cj=clip⁡(round⁡even(xj/s),−127,127),x^j=scj.s=\frac{\max_j|x_j|}{127},\qquad c_j=\operatorname{clip}\left(\operatorname{round}_{\rm even}(x_j/s),-127,127\right), \qquad \widehat x_j=sc_j.s=127maxj​∣xj​∣​,cj​=clip(roundeven​(xj​/s),−127,127),xj​=scj​.

Rounding goes to the nearest even value, the integer range excludes −128-128−128, and a zero vector stores a zero scale with all-zero integers. Decoding means reading a signed byte, converting it to float and multiplying by the scale. The scale itself is FP32, so validation must use the stored copy and must not quietly substitute a recomputed high-precision value.

Figure 1: The scale fields are drawn enlarged.

At d=64d=64d=64, one FP16 pair of K and V takes 256 bytes, while the INT8 data takes 128 bytes plus two FP32 scales, 136 bytes in total. For HHH heads and NNN tokens:

BFP16=4HNd,BINT8=2HNd+8HN.B_{\rm FP16}=4HNd,\qquad B_{\rm INT8}=2HNd+8HN.BFP16​=4HNd,BINT8​=2HNd+8HN.

So at d=64d=64d=64, this INT8 format really uses 8.5 bits per scalar, 136/256136/256136/256 of the original size, a compression of about 1.882×. In general, the budget is 8+32/d8+32/d8+32/d bits per scalar. This count includes only K/V and the scales, while the weights, Q, the outputs and the temporary workspace take space separately.

The implementation consists of three kernels: QK, softmax and PV. The intermediate scores go into an FP32 workspace S[H,N], softmax turns them into probabilities in place, and PV reads the probabilities. This structure costs an extra 4HN4HN4HN bytes, but in exchange the two reductions can be observed separately. Both paths below, simple and split, have this structure, and neither fuses the three steps into one kernel.

Two ways to map threads

One thread per token

The most straightforward layout for QK gives each thread one token: the thread takes the query and accumulates along the ddd components of its key row in order. The loop in kv_cache/new_kvint8.cu, with the original variable names, is:

float sum = 0.0f;
for (int i = 0; i < head_dim; i++) {
    float K = k_scale[row * seq_len + col]
        * static_cast<float>(
            K_int8[(row * seq_len + col) * head_dim + i]);
    sum += Q[row * head_dim + i] * K;
}
S[row * seq_len + col] = sum / sqrtf(float(head_dim));

row is the head and col the token. For one thread, this is certainly a contiguous read, but what the GPU sees is the set of addresses that one warp issues in the same instruction. This version uses block(16,16), so a warp splits into two groups of 16 lanes, and each group handles neighboring tokens of one head. With the loop variable i fixed, neighboring threads in a group are head_dim bytes apart. At d=64d=64d=64, each thread reads one byte, and neighboring threads are already two 32-byte sectors apart. So one thread that reads contiguously and one warp that reads contiguously at the same moment are different things.

One warp per token

The second layout reverses this choice and gives one token to a whole warp: lane 0 takes the channels 0, 32, 64, …, lane 1 takes 1, 33, 65, and so on. At d=64d=64d=64, each lane computes only two products, the 32 lanes in each round cover one contiguous stretch of 32 bytes, and warp shuffles combine the results.

The scale of a key is the same across the whole row, so it can move outside the sum:

q⊤(stct)=st∑jqjct,j.q^\top(s_tc_t)=s_t\sum_jq_jc_{t,j}.q⊤(st​ct​)=st​j∑​qj​ct,j​.

The compute part of kv_cache/KV_int8_split_optimized.cu therefore reads:

const int8_t* k_row = K_int8 + (head * seq_len + token) * head_dim;
float sum = 0.0f;
for (int d = lane; d < head_dim; d += WARP_SIZE) {
    sum = fmaf(q_smem[d], static_cast<float>(k_row[d]), sum);
}
sum = warp_sum(sum);
if (lane == 0) {
    S[head * seq_len + token] =
        sum * k_scale[head * seq_len + token] * inv_sqrt_dim;
}

A block has 8 warps that cover 8 tokens of one head. The block loads the query cooperatively into q_smem and reads it after a block synchronization, so one copy serves 8 dot products. warp_sum shuffles at the offsets 16, 8, 4, 2 and 1. The check for invalid tokens comes after the query is loaded and the block is synchronized, and every lane of a warp has the same token, so half a warp cannot skip the synchronization.

This change also has costs. One short dot product now occupies 32 threads and a reduction with five levels, and both the order of the FP32 additions and the place of the scale multiplication change. Real-number algebra makes the two versions equivalent, but this does not guarantee bitwise-identical floats, or that short inputs are always faster.

PV: reducing along the other axis

PV reduces along the token axis, and each thread owns one output channel and iterates over all tokens:

oj=∑t(ptstV)ct,jV.o_j=\sum_t (p_ts^V_t)c^V_{t,j}.oj​=t∑​(pt​stV​)ct,jV​.

The weight in the brackets does not depend on the output channel, so it can be shared. split stages 256 values of probability * v_scale in shared memory in each round, so that every output channel can reuse them, while in simple each output thread reads the probabilities and the scales itself. When the last tile has fewer than 256 tokens, only the valid length is traversed. Threads without an output channel still take part in the block synchronizations, so that the next round cannot overwrite weights that other threads are still using. Both versions read every key and combine every value; they differ only in the division of the work and in the number of outputs that share each read.

What the compiler and hardware say

No IMMA in sight

In the binary under test, the PTX of the inner QK loop of simple looks like this, with the line-number comments removed:

ld.global.s8 %rs1, [%rd17+-3];
cvt.rn.f32.s16 %r46, %rs1;
mul.f32 %r47, %r3, %r46;
ld.global.b32 %r48, [%rd43+-16];
fma.rn.f32 %r49, %r48, %r47, %r127;

ld.global.s8 reads a signed byte, and the byte is converted to FP32, multiplied by the scale and combined with the query in an FMA. The s16 in the source type of the conversion refers to the value in the register after loading, and it does not mean that the cache became 16-bit. split also shows five levels of shfl.sync.down.b32, and these instructions form the warp reduction. SASS agrees: it contains ordinary loads, conversions and FFMA, without IMMA or HMMA.

This result gives the performance analysis a specific object. What is reduced here is cache bytes and inefficient access, not the distance to the theoretical peak of INT8 matrix multiplication.

Splitting the error: implementation vs. representation

So far, both CUDA paths read the same INT8 data. Comparing them studies the implementation, but it cannot show whether compression hurts attention. For that question, the inputs before quantization must enter the comparison again.

For a general set of queries, write

P=softmax⁡(QK⊤/d),O=PV,P^=softmax⁡(QK^⊤/d).P=\operatorname{softmax}(QK^\top/\sqrt d),\quad O=PV, \qquad \widehat P=\operatorname{softmax}(Q\widehat K^\top/\sqrt d).P=softmax(QK⊤/d​),O=PV,P=softmax(QK⊤/d​).

The error of K is first projected by the query. A Δk\Delta kΔk of a given length changes the dot product along the direction of the query, while its component perpendicular to the query does not, and for this reason the reconstruction MSE of K alone cannot predict attention. V takes another route and enters the output directly in the weighted sum.

Figure 4: Two routes for quantization error.

With ΔV=V^−V\Delta V=\widehat V-VΔV=V−V, there is an exact decomposition:

O^−O=(P^−P)V+PΔV+(P^−P)ΔV.\widehat O-O=(\widehat P-P)V+P\Delta V+(\widehat P-P)\Delta V.O−O=(P−P)V+PΔV+(P−P)ΔV.

The first two terms correspond to quantizing only K and only V, and the last term is the interaction from quantizing both. So the errors of K alone and V alone cannot simply be added, and taking the RMSE introduces cross terms between the error vectors in addition.

The CUDA checks keep three answers: ooriginalo_{\rm original}ooriginal​ from the original FP32 K/V promoted to binary64 on the CPU, odecodedo_{\rm decoded}odecoded​ from the actual INT8 values plus FP32 scales decoded and computed in binary64, and oGPUo_{\rm GPU}oGPU​. They satisfy

oGPU−ooriginal=(oGPU−odecoded)+(odecoded−ooriginal).o_{\rm GPU}-o_{\rm original} =(o_{\rm GPU}-o_{\rm decoded})+(o_{\rm decoded}-o_{\rm original}).oGPU​−ooriginal​=(oGPU​−odecoded​)+(odecoded​−ooriginal​).

The first difference comes from the CUDA implementation and computation with finite precision, and the second from the representation of the cache. A kernel can compute quantized attention very accurately while quantized attention itself has already drifted, and this drift should not be “fixed” by loosening the kernel tolerances.

When the first channel is amplified, CUDA still follows the decoded reference closely, while the quantization error of the cache rises sharply. The cause is absmax scaling per row: one large coordinate sets the step size of the whole row, and every other coordinate must round onto a coarser grid. Amplifying the query also raises the error, because the same key perturbation now causes a larger perturbation of the logits.

When the starting point is model activations, the grouping can also change. KIVI quantizes keys per channel and values per token, and this grouping suits the way outliers appear in each (KIVI paper). Both paths here quantize per token, so they are a simpler baseline than KIVI. Another route keeps the encoding per vector but first changes the distribution of the coordinates, and this route leads to quantization with random rotation.

Random rotation: flattening the direction

absmax sets its step size from the maximum of each row. The MSE route of TurboQuant at a budget of 4 bits starts from a different idea: if every coordinate has a similar distribution before quantization, a shared codebook can be designed in advance, with more reconstruction values where values are more common (TurboQuant paper).

First write a nonzero vector as x=rux=rux=ru with r=∥x∥2r=\|x\|_2r=∥x∥2​ and ∥u∥2=1\|u\|_2=1∥u∥2​=1. The length rrr is stored, and only the direction is encoded. A random orthogonal matrix RRR then gives z=Ruz=Ruz=Ru. Rotation does not change the length, and without quantization, multiplying by R⊤R^\topR⊤ undoes it exactly; what the rotation does is scatter one fixed direction randomly over the sphere, and it loses no information by itself.

For a uniformly random direction on the sphere, a single coordinate ttt has the density

fd(t)=Γ(d/2)π Γ((d−1)/2)(1−t2)(d−3)/2,−1<t<1,f_d(t)=\frac{\Gamma(d/2)}{\sqrt\pi\,\Gamma((d-1)/2)} (1-t^2)^{(d-3)/2},\qquad -1<t<1,fd​(t)=π​Γ((d−1)/2)Γ(d/2)​(1−t2)(d−3)/2,−1<t<1,

with mean zero and variance 1/d1/d1/d. At d=64d=64d=64, a typical coordinate is about 1/81/81/8, so spreading 16 reconstruction values evenly over [−1,1][-1,1][−1,1] wastes most of them. Lloyd–Max iteration places the codepoints according to this density: each codepoint is the conditional mean of its interval, and each boundary is the midpoint between neighboring codepoints. After the iteration, the grid is denser where the probability concentrates.

This design does not need all coordinates to be fully independent. Their squares sum to 1, and the total squared reconstruction error is the sum of the squared errors of the coordinates, so the expectations add up term by term. With the codebook map CbC_bCb​, the reconstruction is

x^=rR⊤Cb(Ru).\widehat x=rR^\top C_b(Ru).x=rR⊤Cb​(Ru).

The CPU implementation builds the rotation from a QR decomposition of a Gaussian matrix and flips the columns by the signs of the diagonal of the triangular factor, so that the result is a uniformly random (Haar) orthogonal matrix. The codebook comes from integrating the spherical density above. The length of each row is stored in FP32, so the experiments include the rounding of this stored length. The rotation and the codebook are shared across many vectors, so their storage cost is spread over all of them.

This design spreads one large coordinate across many directions, and such an outlier channel is exactly what absmax tends to lose. However, if a vector was originally very sparse, rotation also turns exact zeros into ordinary nonzero values. Whether this trade-off is worth it at low bit widths cannot be judged by looking at the maximum coordinates before and after the rotation.

Unbiased only protects the mean

K is used for dot products with the query, so besides the reconstruction error of the vectors, the estimates of the dot products can be examined directly. The other route of TurboQuant adds a QJL residual after MSE quantization, so that for a fixed input, the dot product with a fixed query is unbiased in expectation over the random quantizer.

Let the coarse quantization be x0x_0x0​ and the residual e=x−x0e=x-x_0e=x−x0​. Fix this residual, draw mmm Gaussian vectors gi∼N(0,I)g_i\sim\mathcal N(0,I)gi​∼N(0,I) independently of the coarse quantization, store only the signs of the projections bi=sign⁡(gi⊤e)b_i=\operatorname{sign}(g_i^\top e)bi​=sign(gi⊤​e), and estimate the residual with

e^=∥e∥2mπ2∑i=1mbigi.\widehat e=\frac{\|e\|_2}{m}\sqrt{\frac\pi2}\sum_{i=1}^m b_i g_i.e=m∥e∥2​​2π​​i=1∑m​bi​gi​.

The coefficient follows directly. Let u=e/∥e∥u=e/\|e\|u=e/∥e∥, and split the Gaussian vector into a parallel part auauau and an orthogonal part g⊥g_\perpg⊥​. The sign depends only on aaa, and the orthogonal part is independent of it and has mean zero, so

E[sign⁡(g⊤e)g]=E[∣a∣]u=2/π u.\mathbb E[\operatorname{sign}(g^\top e)g] =\mathbb E[|a|]u=\sqrt{2/\pi}\,u.E[sign(g⊤e)g]=E[∣a∣]u=2/π​u.

Multiplying the scale back gives E[e^∣e]=e\mathbb E[\widehat e\mid e]=eE[e∣e]=e, so x0+e^x_0+\widehat ex0​+e has an unbiased dot product with any fixed query, and a zero residual returns zero separately. This is the core of the asymmetric inner-product estimate of QJL: the cache side keeps only signs, while the query side keeps real-valued projections (QJL paper).

Here m=dm=dm=d, so each coordinate spends 1 bit on average for the residual sign. To fit a codeword budget of roughly 4 bits, the base drops to MSE3 plus QJL1. K needs two FP32 norms, so at d=64d=64d=64 it actually uses 5 bits per value, while V uses MSE4 at 4.5 bits per value, for an average of 4.75 for K/V. The column K-prod4 / V-MSE4 of the earlier table is this configuration. It is one reasonable setting at about 4.75 bits per value, not the only choice in the paper.

So an unbiased dot product did not preserve the mean of the probability. In the earlier table, the combination with the residual has a larger attention output error on all three input classes. For Gaussian inputs, the mean DKL(P∥P^)D_{\rm KL}(P\|\widehat P)DKL​(P∥P) rises from 0.00458 for MSE4 to 0.02559, and for the outlier-channel group from 0.10742 to 0.56441. This result does not refute the theoretical goal of QJL; it only shows that at the current budget, “unbiased” cannot replace an evaluation at the output.

These CPU experiments all reconstruct the vectors explicitly, so that the errors can be compared. A real compressed dot product can compute bi(gi⊤q)b_i(g_i^\top q)bi​(gi⊤​q) directly without building e^\widehat ee, and whether projection, packing and reads are fast needs a separate measurement.

Conclusion

The two halves of the post lead to two conclusions. On the GPU, the same INT8 cache needs about one tenth of the QK sectors when one warp reads the channels of one token, while the full call is faster only on some shapes and also depends on the other work in the call. On the numerical side, quantization error reaches attention through two routes, K through the query and V through the weighted sum, so it must be measured at the output. Rotation helps exactly when the input does not match the distribution that the codebook assumes, and a format that preserves zeros can still beat it. Unbiased dot products protect the mean, while softmax and RMSE depend on more than the mean.

A smaller cache is a storage result; whether attention became faster and whether it stayed accurate are two more experiments.
