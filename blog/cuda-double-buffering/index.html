Why an XOR Swizzle Slowed a Double-Buffered CUDA GEMM

An XOR swizzle cut the extra shared wavefronts of a 1024³ FP32 GEMM to zero and its bank conflicts from 6.3 million to 7,399, yet the kernel became 19.5% slower. This post shows where the time went.

On a 1024³ FP32 GEMM, an XOR swizzle that removed almost all shared-memory bank conflicts made the kernel slower. With an ordinary row layout for A in shared memory, eight different addresses fall into the same bank. A 4-element-group XOR swizzle reduced the extra shared wavefronts in Nsight Compute from 4,194,304 to 0, the lowest possible value, and the hardware bank-conflict counter from 6,297,071 to 7,399. At the same time, the runtime of the same kernel rose from 0.30379 ms to 0.36307 ms, so the kernel became 19.5% slower.

This post records that trade-off. The extra wavefronts of the target reads really were removed, but whether the whole kernel became faster also depends on resources and residency. The FP32 GEMM here maps one block to 128×64 outputs, with 128 threads, 8×8 accumulation per thread and K advancing 32 at a time. Between versions, only the shared layout, the number of buffer slots and the copy instructions change. All four implementations handle non-aligned matrices, and everything ran on an RTX 5070 Laptop. The tile here is different from the tile in the data reuse post, so the timings of the two posts are reported separately.

My experiments here are rough, and this post is not a proper tutorial; it is mostly a record of my own learning by trial and error. To be honest, while putting it back together, I often felt that I had worried too much about details that did not matter. If the post feels dull, please skip to the end and read the question I still cannot answer. I would be grateful for any advice.

The post first sets up the thread mapping, derives the bank conflict from it and fixes the conflict with a swizzle. It then builds up single buffering, double buffering and cp.async, including one initialization bug that is worth knowing about. After making all versions correct on tails, offsets and grids, it compares four implementations that each differ by one step, using the compiler output, the profiler and the clock.

The setup: one 128×64 tile, 128 threads

The inputs are contiguous row-major matrices A[M,K]A[M,K]A[M,K] and B[K,N]B[K,N]B[K,N], and the output is C[M,N]=ABC[M,N]=ABC[M,N]=AB. Each K chunk needs a 128×32 slice of A and a 32×64 slice of B, and the two slices together hold 6144 floats or 24 KiB. The four warps of the block reuse these slices, and each thread keeps its 64 partial sums in registers.

int warp = threadIdx.x / 32;
int lane = threadIdx.x % 32;
int mr = (warp / 2) * 64 + (lane / 4) * 8;
int nc = (warp % 2) * 32 + (lane % 4) * 8;

Each thread owns [mr:mr+8,nc:nc+8] within the tile. Lanes 0–3 of warp 0 compute the same eight rows and four different groups of eight columns, so together they cover an 8×32 output strip, and lanes 4–7 cover the next strip. One warp covers 64×32, and four warps in a 2×2 arrangement cover exactly 128×64. For a fixed k, the four threads on the same rows need the same group of eight A elements and different B elements, so the reuse of A is good. However, if A is stored in shared memory with the plain index row*32+k, the reads cause bank conflicts.

Fundamentals: shared memory banks

For the 32-bit accesses discussed here, shared memory can be seen as 32 banks, and the word address modulo 32 chooses the bank. Different banks serve requests in parallel, while different words in the same bank need extra service. When several lanes read the same word, the hardware broadcasts it. This last case must be separated from “same bank”, or the number of conflicts is overestimated (CUDA shared memory docs).

Fix the row offset i within a thread. Then the address of A is

r=64⌊warp/2⌋+8⌊lane/4⌋+i,word=32r+k,bank=k mod 32.\begin{aligned} r&=64\lfloor warp/2\rfloor+8\lfloor lane/4\rfloor+i,\\ word&=32r+k,\\ bank&=k\bmod32. \end{aligned}rwordbank​=64⌊warp/2⌋+8⌊lane/4⌋+i,=32r+k,=kmod32.​

All 32 lanes fall into the same bank, but each group of four adjacent lanes reads the same A element. After removing these broadcast duplicates, eight distinct words still compete for one bank. The cause is that the row pitch is exactly equal to the bank period, so reading across rows never moves to a different bank.

The textbook fix is padding: one extra element per row breaks this period. Here I also wanted to keep 16-byte copies of four adjacent floats, so instead of padding I permuted groups of four elements. The 32 values of each row are split into eight groups, and only the positions of the groups move.

int a_index(int row, int col) {
    int group = (col / 4) ^ ((row / 8) % 8);
    return row * 32 + group * 4 + col % 4;
}

Take col=0 as an example. Rows 0–7 stay in group 0, rows 8–15 move to group 1, and rows 16–23 move to group 2. Along the access path through these eight row groups, the starting banks become 0, 4, 8, …, 28. The eight addresses spread out, and the broadcast among four adjacent lanes is kept.

Figure 1: Lanes, addresses and banks for the original and swizzled layouts.

For a fixed row, the XOR is a one-to-one permutation of eight groups. It therefore never drops or overwrites an element, and the four floats within a group stay contiguous for whole-group copies. The producer and the consumer must both use a_index. If only the read side changes, the kernel reads a different set of numbers, and the result is no longer a correct GEMM. In these experiments, B keeps its original layout.

I enumerated all four warps, 32 values of k and eight row offsets. In the original layout, at most eight distinct words share a bank, and in the XOR layout only one does. However, this result comes from scalar address arithmetic. The compiler may merge several scalar reads into wide instructions, and the real shared-memory pipeline may split requests again. So the sections below check the result with SASS and Nsight Compute, instead of reading “eight addresses” as “eight times the time”.

Fundamentals: why double buffering needs two slots

After the layout is fixed, the next step is advancing along K. Single buffering has one copy of the A and B tiles, and the order of operations is rigid:

load K chunk t
block barrier: all inputs written
compute every multiply-add for this chunk
block barrier: all consumers done reading
overwrite the same storage with chunk t+1

The first barrier protects read-after-write order, and the second barrier protects write-after-read order. CUDA does not keep the four warps in lockstep, so one warp finishing early does not mean that the other warps have finished reading.

With only one copy of storage, the next tile cannot be written early, even if its location is known, because the current computation is still reading that space. A second slot lets chunks t and t+1 exist at the same time for a short period. The loop loads tile 0 and then uses the current slot while it prepares the other slot. Once the other slot is ready and the current slot has been fully read, the two slots swap roles.

Figure 2: Slot lifetimes under double buffering.

The async version uses cp.async.cg.shared.global. This instruction copies data from global memory directly into shared memory, without registers visible to the program. After issuing the copy, the thread can continue and only waits when it needs the result. commit_group collects the copies that this thread has issued into a group, and wait_group 0 waits until all earlier groups of this thread are complete (PTX cp.async semantics).

In the tile loop, the pseudocode that matches the implementation is:

if (tiles > 0) {
    load_tile(0, slot0);   // each thread handles its own piece of input
    commit_group();
    wait_group_0();
    __syncthreads();
}
for (int t = 0; t < tiles; ++t) {
    if (t + 1 < tiles) {
        load_tile(t + 1, other_slot);
        commit_group();
    }
    compute_tile(current_slot);
    wait_group_0();
    __syncthreads();
    swap(current_slot, other_slot);
}

The wait cannot replace the block barrier. A thread only waits for its own copies, so it knows neither whether the copies of other threads are complete nor whether another warp is still reading the old slot. Only after every thread has waited and then reached the barrier is it certain that the next tile is fully written and the current tile is fully read. After that point, the next iteration can read the new slot and write an even later chunk into the old slot.

If loading and computation overlapped perfectly, the steady-state time per chunk would approach max⁡(Tload,Tcompute)\max(T_{\rm load},T_{\rm compute})max(Tload​,Tcompute​) instead of Tload+TcomputeT_{\rm load}+T_{\rm compute}Tload​+Tcompute​. This model ignores the first load, the last computation, synchronization and resource contention, so it only shows where the pipelining opportunity is. With only one K chunk there is no steady state at all, and this model cannot explain any speed difference in that case.

Register double buffering, and a priming bug

Once the data is in shared memory, there is another layer: the move from shared memory to registers. For each k, each thread fetches eight A values and eight B values and updates 64 accumulators. The implementation uses two sets of register operands. While the current set feeds the FMAs, the next set is already loading. This small loop must also prime the first set:

load_fragment(/* k */ 0, /* register slot */ 0);
for (int k = 0; k < 32; ++k) {
    int cur = k & 1;
    if (k + 1 < 32) load_fragment(k + 1, cur ^ 1);
    fma_fragment(cur);
}

Figure 3: Priming the first register set.

If the load before the loop is deleted, the first iteration fills only slot 1 while it runs the FMAs on slot 0. Setting slot 0 to zero is also wrong, because it always drops the k=0 term of the current tile. Every new shared tile must prime the first set again, unless a separate preload across tiles is designed for this purpose.

One implementation really had this bug. Its loop was written as “load the next set, compute the current set”, without priming. At M=128,N=512,K=64, all 65536 outputs exceeded the error budget, with a maximum absolute error of 0.992814749. The outputs were finite, the guards were intact, and memcheck reported zero errors. Uninitialized operands do not necessarily show up as illegal memory accesses, and this is why the numerical reference was so valuable. That run also contained other changes, so not all of the error necessarily came from the missing priming.

A more targeted input exists for this bug. Let A have a 1 only in the first position of every 32-element K chunk and 0 elsewhere, and let B be arbitrary. Then the output depends only on the contributions at k=0, 32, 64, …, so the test shows directly whether the first term of each tile reached the accumulator. This input locates pipeline-initialization errors much more easily than more random samples.

Making it correct off the happy path

With K=33, the second chunk has only one valid k. With M=129 or N=65, the output tiles at the edges have only some valid positions. The tiled computation stays the same: the loads write zero for invalid elements, and the write-back checks the actual rows and columns.

Zero-filling is legal for GEMM, because the extra products are zero. However, zero-filling does not remove the barriers of cooperating threads, and it does not allow a 16-byte read to be treated as “use only one element”. Even if the invalid addresses do not contribute to the output, the access itself is still out of bounds.

Each four-element group therefore first checks its range and its actual alignment. If all four elements are in range and the source pointer is 16-byte aligned, the group uses the async wide copy; otherwise, the code fetches the valid elements one by one and fills the rest with zeros. With K=33, the row pitch is 132 bytes, and different rows meet different alignment conditions, so one kernel can mix async copies and ordinary shared-memory writes.

Both paths write the same XOR layout into regions that do not overlap. The consumers read the data only after the async wait and the block barrier at the end of the loop. If the fallback branch still wrote the plain row layout, aligned matrices would pass the tests while edge elements would be wrong. So the range check, the layout and the stage protocol must be reviewed together.

The grid must also cover the output correctly. This post uses a direct 2D grid of ceil(N/64) × ceil(M/128). One implementation remapped the column tiles in groups of eight:

tile_row = blockIdx.x >> 3
tile_col = blockIdx.y * 8 + (blockIdx.x & 7)

This implementation did not exclude the padding tiles that the remapping created. N=64 needs only one column of tiles, but the extra column blocks still read B and wrote C. As a result, 128×64×64 produced 82 memcheck errors, and the first error was a 16-byte async read out of bounds. Such a remapping might improve cache locality between blocks, but only if it still maps correctly onto valid output tiles. Here I used the direct grid and did not use the out-of-bounds implementation as a performance baseline.

The four formal variants and one compatibility entry pass 240 FP64 numerical checks, including K=0, tails, offsets of 0–3 floats and first-term-only inputs. Each of the four variants also passes 48 memcheck runs and 48 racecheck runs with zero errors and zero hazards. These checks are the precondition for the timings below, and the appendix lists the shapes and error budgets.

Four implementations, one step apart

The four implementations share the thread mapping above, the 8×8 outer product and the priming of register fragments. Each pair of neighbors differs in exactly one design choice:

Short nameA’s shared layoutShared slotsglobal→shared
raw singlePlain row layout1Synchronous float4, scalar at edges
swizzle single4-element-group XOR1Same
swizzle double4-element-group XOR2Synchronous load into the next slot
async double4-element-group XOR2cp.async for valid groups, scalar at edges

These four versions form one rewrite path, not a full search over all combinations. They show what each step along this path cost and what it gained.

What the compiler emitted

The async version keeps cp.async.cg.shared.global, cp.async.commit_group, cp.async.wait_group 0 and bar.sync 0 in PTX. In SM120 SASS, these instructions become:

LDGSTS.E.BYPASS.128 ...
LDGDEPBAR
... compute and other instructions ...
DEPBAR.LE SB0, 0x0

This output confirms that the async copy from global to shared memory, the commit and the wait really reached the machine code. The static disassembly contains five LDGSTS sites, two commits and two waits across the preload, the loop and the branches. However, the number of sites is not the number of executions per tile, and it does not show how much copying is actually hidden behind computation.

The compiled resources changed at the same time:

VersionRegisters/threadProgram shared/blockSpill load/store

Introducing the XOR costs the whole kernel 40 more registers. One XOR does not need 40 registers by itself; the address expressions, the live ranges and the scheduling all changed together. Two slots then double the storage, and the register count reaches 211. Zero spills only means that nothing overflowed into extra storage; it does not mean that the extra registers had no effect on residency.

Figure 4: Wavefronts drop to ideal with the swizzle; occupancy drops too.

A wavefront can be understood as one unit of service in the shared-memory pipeline. Even a wide read without conflicts may need several ideal wavefronts. “Extra” means the actual count minus the ideal count, where the ideal count is computed from the real instructions and the participating threads; it does not mean the total minus one. In SASS, the main reads are LDS.128, with four floats per lane, so they do not match the earlier model of one scalar read with eight addresses.

I exported the counts per SASS address from the Source page of the raw version. The excess is concentrated at 64 LDS.128 sites. For example, LDS.128 R20,[R4] has an actual count of 131072 and an ideal count of 65536, and the differences at all 64 sites add up to 4194304, exactly the total. For this real wide instruction, the ratio of actual to ideal is 2, not the 8 that the scalar model predicted.

ncu --import pipeline-raw.ncu-rep --page source --print-source sass `
  --metrics memory_l1_wavefronts_shared,memory_l1_wavefronts_shared_ideal --csv

The order of this check matters. First select the same template instance, then take the differences by SASS address, and finally put the lane addresses of the target read back into the formula. With this order, it is possible to state exactly where an optimization acts, instead of only showing a screenshot of a “fewer conflicts” percentage (NCU metrics and SourceCounters).

For all three XOR implementations, the extra wavefronts drop to zero. The independent hardware counter l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum drops from 6297071 in the raw version to 7399 in swizzle single. This remaining value of 7399 is still not zero, so the kernel is not completely free of bank conflicts.

At the same time, the block limit from registers falls from 4 to 3 to 2, the block limit from shared memory falls from 4 to 2, and the achieved occupancy falls with them. The layout really did improve, but less resident work is now available to hide waiting. The total time depends on both effects, and also on other instruction changes that came with the rewrite.

On 1024³, XOR single buffering is about 19.5% slower. The three rounds of raw span 0.30325–0.30822 ms, and the three rounds of swizzle span 0.36302–0.36312 ms, so the ranges do not overlap. Removing the extra wavefronts of the target reads does not make up for the other costs of rewriting the layout. The counters show two candidate causes, 40 more registers and lower residency, but the rewrite also changed the address arithmetic and the instruction schedule, and this comparison does not separate these effects. A control that gives both layouts the same register budget, for example with __launch_bounds__ or -maxrregcount, would separate them.

Adding the second slot helps at 1024³, but at 2048³ the time rises from 2.47729 ms to 2.82787 ms. A second slot gives room to load ahead, and it also consumes another copy of the resources. Switching to async copies brings 2048³ down to 2.25238 ms. This time is about 20.4% lower than synchronous double buffering with the same layout, but only about 3.5% lower than the 2.33407 ms of the original raw single version. The first comparison measures the change of copy mechanism, while the second comparison measures the whole design, so the two comparisons should be kept apart.

Short K tests whether every change is being wrongly credited to pipeline overlap. 128×64×32 has one output tile and one K chunk, so there is nothing to prefetch, and async takes 11.78 µs against 12.54 µs for raw. This small difference only shows that the copy path and the compiled schedule changed as a whole; it is not evidence of overlap across tiles. At K=64, the two versions take 12.71 and 12.66 µs, and their three-round ranges overlap.

Figure 6: Small shapes, device-only and with host round trip.

When pageable host transfers and synchronization are included, the microsecond-level kernel differences become even smaller relative to the total waiting time. The end-to-end times in the figure exclude allocation, compilation and handle creation, and they should not be mixed with repeated calls on inputs that already reside on the GPU.

Eight more shapes test whether the tile fits other matrix shapes. The speed ratios below are relative to the raw single version in the same row, from a separate measurement batch:

Figure 7: Relative speed by shape.

8192×64×128 fills the output tiles exactly, and raw and async take 38.822 and 34.453 µs. When M and N are swapped, there are only 64 valid output rows, so half of each 128-row tile stays empty, and the times become 39.771 and 39.395 µs. The FLOPs are the same, but the tile mapping no longer fits. 512×512×16 also has no steady-state pipeline, so its change from 14.448 to 12.855 µs cannot be explained as overlap across chunks either.

On 4096³, the center value is 23.958 ms for raw and 24.898 ms for async, with three-round ranges of 22.838–28.531 and 22.793–32.870 ms. The variation is larger than the difference of about 4% between the centers, so the data does not show that async is slower. Async is still faster than synchronous double buffering with the same layout (31.950 ms), but this result does not show that the XOR async design as a whole beats the plain layout.

My open question

Looking back, my main lesson is that trying techniques on an operator without first modeling it, for example with a roofline model, does not help much. At this point I did try to build a roofline model and work through the math. However, the relationships I derived were very complicated, and small changes in a few parameter values made the arithmetic intensity change dramatically.

So I would really appreciate it if any reader could point me in the right direction. For a given operator, can its limiting factor only be judged from experience, or by running a baseline kernel and reading the Nsight results? And does deriving formulas from basic hardware parameters have real practical value in operator design?

Source interfaces, test scope and reproduction commands

📝 Note: Paths in this appendix such as bench_mur/ and rep_mur/ are in my private research repository, so they aren’t public; they’re listed so each result can be traced. The CUDA kernels the post cites are public in Murmurwkk/cuda-operators.

Environment and measurement method

Test device: RTX 5070 Laptop GPU, 8 GB, SM120, driver 610.88; built with CUDA Toolkit 13.1.115 and MSVC 2022. Environment cross-checks recorded runtime API version 13.3. Since CUDA 13 the Windows runtime can ship with the display driver, so it can differ from the build Toolkit; see the CUDA Runtime API versioning notes. The original GEMM environment records queried nvcc and the driver; the runtime field comes from a separate environment check.

The performance protocol follows the previous post: 20 device warm-ups, 10 pilot runs to estimate repeats per batch, a target of about 20 ms, 1–2000 repeats per batch, 30 batches, 3 rounds with shuffled task order. Data is reused and L2 isn’t flushed. End-to-end timing is separate and includes pageable host H2D (A, B), the kernel, D2H (C) and synchronization, excluding allocation, compilation and cuBLAS handle creation. Table centers are the median of three round medians; error bars in figures show the min–max of the three round medians, not statistical confidence intervals.

The four implementations are compiled into separate executables and don’t link against each other’s old solve. GPU experiments run serially; start and end temperatures and clocks are recorded, but clocks weren’t locked and the laptop’s full power state wasn’t controlled.

Interfaces and correctness checks

All inputs are contiguous row-major FP32 matrices A[M,K] and B[K,N], with output C[M,N]=A×B. Kernels use ordinary FP32 FMA, no Tensor Cores and no TF32. Only this explicit layout contract is supported; arbitrary strides, input/output aliasing and NaN/Inf special semantics are outside this validation.

The shared implementation is in gemm/gemm_pipeline.cuh. The two old files keep their own independently compilable solve entries, so same-named symbols in the repository don’t link against each other:

FileArgument order keptPurpose
mulmatrix_let_merged.cusolve(A,B,C,M,N,K)Original merged calling convention; also provides an async launch with a stream
mulmatrix_let2.cusolve(A,B,C,M,K,N)Keeps the dimension order the old implementation actually interpreted; the old function used to swap the last two internally

solve still returns synchronously for compatibility with old callers; timing uses the stream launch without host synchronization after every kernel. The two entries have different dimension orders, so the test wrapper adapts them explicitly; copying a uniform-looking declaration doesn’t make them the same ABI.

The old code was archived as-is with SHA-256 hashes, then the shared tile and consumer mapping were extracted to rebuild separable comparisons. The new implementation fixes boundaries, initial registers and the stage protocol, and drops the old eight-column grid remapping. Because more than one thing changed, differences between old and fixed versions aren’t used for single-optimization performance attribution.

The full CPU FP64 checks cover 12 shapes, in M, N, K order:

1×1×0, 1×1×1, 7×13×3, 15×17×15,
63×65×31, 64×64×32, 65×63×33, 127×129×17,
128×128×32 (one aligned, one offset), 129×131×65, 256×256×129

Pointer offsets cover 0, 1, 2 and 3 floats. Each shape has four distributions: random, all zeros, alternating signs and first-element-per-K-tile nonzero. Across the four performance versions plus the let2 compatibility entry, all 240 checks pass. Outputs are pre-filled with NaN and guarded before and after, separately checking for missed writes, non-finite values and sentinel damage from out-of-bounds writes.

The CPU reference accumulates term by term in double, with an error budget of 1e-6 + 16*FLT_EPSILON*sum(abs(Aik*Bkj)). This is an explicit budget for this experiment, not a floating-point error theorem for every K and input distribution. Large shapes in the performance experiments additionally check 257 deterministic positions against a CPU FP64 reference and compare against full cuBLAS pedantic FP32 output, with a cuBLAS budget of 3e-4 + 3e-4*abs(reference). Large matrices didn’t get a full CPU FP64 reference; their validation is a full GPU comparison plus a sampled high-precision reference.

Compute Sanitizer runs 48 memcheck and 48 racecheck cases for each of the four versions, all with zero errors and zero hazards. They cover short K, multiple K tiles, offsets and tails. Finite tests can’t prove correctness for all inputs and architectures, but they cover several independent failure types beyond ordinary numerical tests. Both checks for gemm_8 were rerun once, and those logs pass too.

The old mulmatrix_let2.cu has a truncated loop statement and reports 10 errors when compiled as-is, so it wasn’t used as a runnable old baseline. That compile log, the failure record for the merged version with only a type alias added, and the fixed version’s results are saved separately in the experiment directory.
