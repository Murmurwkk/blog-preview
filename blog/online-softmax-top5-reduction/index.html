Fusing Rowwise Softmax and Top-5: Merging Tile States in Two CUDA Launches

A score that misses the Top-5 still changes the winning probabilities. Carrying a 48-byte state per slice lets two CUDA kernels compute the result in one input scan.

A row has six scores, and the operator returns five probabilities. Why should the score in sixth place change the probability in first place? The output contains the five winning column indices and their probabilities under the softmax of the entire row. A score can lose its spot in the output and still contribute to the denominator. That distinction determines what each CUDA block has to save when the row is split across several blocks.

Take scores [0,ln⁡2,0,ln⁡4,0,ln⁡2][0,\ln 2,0,\ln 4,0,\ln 2][0,ln2,0,ln4,0,ln2], with columns numbered from zero. Their exponential weights are [1,2,1,4,1,2][1,2,1,4,1,2][1,2,1,4,1,2]. Sorting by score and breaking ties in favor of the smaller column gives [3,1,5,0,2][3,1,5,0,2][3,1,5,0,2]. Column 4 loses the last place. Discard its weight too, and the first probability comes out 4/104/104/10. The full weights sum to 11, so the correct winning probability is 4/114/114/11.

The 48-byte slice state for normalization and five candidates

A block can discard a score from its candidate list as soon as five better candidates exist in its own slice. Those five will still precede it when all slices are combined. The block accounts for every score in a separate running sum. Here is the complete intermediate layout used in the local kernel.

constexpr int top = 5;
struct State {
    float m, d, value[top];
    int index[top];
};
static_assert(sizeof(State) == 48);

Figure 1. Each cell is four bytes. m is the largest score seen and d is the sum of exponentials relative to m. A candidate’s score and column are paired by array position. The layout keeps the five scores together and then the five indices.

Consider two slices of our example, split after column 2. Their maxima and scaled sums are (ln⁡2,2)(\ln 2,2)(ln2,2) and (ln⁡4,7/4)(\ln 4,7/4)(ln4,7/4). The second maximum is larger, so the left sum must move to its scale. It contributes 2 eln⁡2−ln⁡4=12\,e^{\ln 2-\ln 4}=12eln2−ln4=1 to the common denominator, giving 1+7/4=11/41+7/4=11/41+7/4=11/4. The weight of the winner at this scale is eln⁡4−ln⁡4=1e^{\ln 4-\ln 4}=1eln4−ln4=1. Dividing by 11/411/411/4 recovers 4/114/114/11. Milakov and Gimelshein, online normalizer and Top-K

Merging thread candidates into rowwise Top-5 probabilities

The host launches global_part<true,false> with one block per slice. The block calls the device helper partial<true>, where each thread walks the slice at a stride of blockDim.x. These are the two operations in its input loop, with spacing expanded. The running maximum begins at negative infinity and the running sum at zero.

if (v > s.m) {
    s.d = s.d * expf(s.m - v) + 1;
    s.m = v;
} else {
    s.d += expf(v - s.m);
}
insert(s, v, i);

A new maximum accounts for itself with the + 1. Every other score enters through expf(v - s.m), including a score that insert immediately rejects. The candidate comparison orders by descending value, then ascending original column index. This makes two equal scores choose the same winner whether their threads met early or late in the reduction tree.

Each thread writes its state into shared memory. The block then reduces pairs with combine<true>. After the checks for an empty input, the online specialization uses the following lines to put the sums on a common scale and merge the two sorted lists. Local names and the comparison are from the implementation.

c.m = fmaxf(a.m, b.m);
c.d = a.d * expf(a.m - c.m) + b.d * expf(b.m - c.m);
int u = 0, v = 0;
for (int j = 0; j < top; ++j) {
    bool left = before(a.value[u], a.index[u], b.value[v], b.index[v]);
    c.value[j] = left ? a.value[u] : b.value[v];
    c.index[j] = left ? a.index[u++] : b.index[v++];
}

The merge makes one candidate comparison per output slot. Each one advances the cursor in the list that supplied the next candidate. Once the block has reduced all its thread states, thread 0 writes one State to global memory. The second kernel, finish<true>, assigns one thread per row. It applies the same combine operation to the row’s two or four slice states, then writes each retained index and the corresponding probability expf(s.value[j] - s.m) / s.d. Reading the sixth score has affected the probability at precisely that last division.

Online normalization reduces four kernel launches to two

The four-kernel baseline first finds each slice maximum, reduces the maxima to one per row, then rereads the scores with that common maximum available. A final kernel merges the slice states. The online kernel can publish its local maximum and sum as soon as its own scan ends. The next kernel already has everything it needs to change scales.

Figure 2. Each box is one CUDA launch. The arrow from the row maxima back to the slice scan explains why the four-kernel schedule visits the input twice.

At 32 rows by 32,768 columns, the FP32 input occupies 4 MiB. Reading every score twice requests two logical passes over those 4 MiB. The online version makes one. Both schedules hand the final kernel 128 states for four slices per row, totaling 6 KiB. These are counts from the indexing. A separate Nsight Systems trace at this shape confirmed the four launches and the two launches.

Rowwise Top-5 latency with two and four launches

On an RTX 5070 Laptop GPU, with four blocks per row and reused input addresses, the 32-row operator went from about 72 µs to 54 µs. Both runs wrote the same two outputs to device memory. Rotating the input addresses raised the time for both schedules and the online version kept its lead.

All 24 measured conditions favored the two-kernel path, with paired speedups ranging from 1.135× to 1.535×. The timings cover the saved scan and launches together with the extra rescaling arithmetic. The useful design question is what has to cross the block boundary. A list of five candidates preserves the ranking. Adding the maximum and scaled denominator also preserves the probability of every winner, so the final kernel can finish the row on its own.

Measurement, correctness checks and figure data

The CUDA 13.1 runs used FP32 scores and sums, 128 threads per block and one CUDA stream with ordinary launches. Timing started before the first reduction kernel and ended after both outputs were written on-device. Inputs and workspaces were already allocated. The study varied row count (1, 32, 512), width (4,096 or 32,768), scanning blocks per row (2 or 4) and input policy. Repeated inputs warmed the same address. The rotating policy cycled through four independently generated views and touched at least 48 MiB of other data before timing. Both paths in a pair received the same view.

Eight fresh processes contributed 20 paired observations per condition. The interval calculation used 4,000 bootstrap draws, sampling processes first and pairs within each chosen process second. The time columns are separate medians. The speedup column is the geometric mean of the within-pair four-kernel time divided by the two-kernel time.

An independent CPU reference sorted the original scores with a stable descending order and calculated the full denominator in FP64. Across 72 correctness checks with 128- and 256-thread blocks, both global-memory implementations returned exactly the reference indices. Tests included tied scores, a maximum in the last slice and exponent underflow. The largest absolute probability error was below 1.3×10−71.3\times10^{-7}1.3×10−7.
