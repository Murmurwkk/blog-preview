CUDA Graphs in an Inference Runtime: What Capture Saves and Binds

A graph cut a four-kernel attention chain from 33 μs to 12 μs on the GPU, yet the largest full request with copies became slower. This post explains what capture saves, what it binds and when replay is worth it.

CUDA Graphs merge many kernel launches into one replay. On a four-kernel attention chain, this reduces the device interval from about 33 μs to about 12 μs, a 2.7× speedup. When the copies of the inputs and the results are included, however, the full request does not always benefit: for the largest shape it becomes slower, and for the smallest shape the two submission styles cannot be told apart.

Both numbers are real, and the gap between them is the subject of this post. Two points are easy to overlook:

  • A graph saves submission work, not computation, so the time it saves depends on what the GPU was waiting for before.
  • Graph nodes store the device addresses from the time of capture. Whether these addresses still point to the right buffers in later replays is the responsibility of the program, not of CUDA.

For one replay to run correctly, the graph must be built in advance, the addresses must stay alive, and the next input must not overwrite an input that is still being read.

The setup has two explicit implementations: one launches four kernels individually, and the other captures the same four launches into a graph. The test subject is single-head dense attention without a causal or padding mask. All GPU experiments ran on an RTX 5070 Laptop (SM120), and the conclusions cover only these two implementations and the listed shapes.

The post first describes the test subject and what capture records, and then uses an experiment to determine the address semantics. After that, it measures device time against full-request time and the cost of building a graph. The last part covers resource lifetimes, that is, how to free memory safely while the GPU is still working, tested on a multi-stage Selective Scan.

The test subject: four-kernel materialized attention

The inputs are contiguous FP32 matrices Q∈RM×dQ\in\mathbb R^{M\times d}Q∈RM×d and K,V∈RN×dK,V\in\mathbb R^{N\times d}K,V∈RN×d, and the output is

O=softmax⁡(QKTd)V.O=\operatorname{softmax}\left(\frac{QK^T}{\sqrt d}\right)V.O=softmax(d​QKT​)V.

MMM is the number of queries, NNN the number of keys and values, and ddd the vector width. The implementation deliberately takes an observable, materialized path: it transposes KKK, computes the scores, applies a row-wise softmax and then multiplies by VVV. All four kernels run on the stream of the caller:

transpose K → QK / sqrt(d) → row softmax → PV

The transpose buffer needs NdNdNd floats and the score buffer MNMNMN floats, so the workspace takes 4(Nd+MN)4(Nd+MN)4(Nd+MN) bytes. Softmax overwrites the scores with probabilities in place, and PV consumes the probability matrix. Normal submission issues four launches in every call, while the graph version captures the same entry point, with the same algorithm and the same intermediate tensors.

The test does not use online (flash-style) attention, because that method does not fully materialize the probability matrix. It would change the kernel count, the memory traffic and the organization of the computation at the same time, and a performance difference could then no longer be attributed to the graph alone. The entry point used here, attention_materialized_launch, takes prepared inputs, outputs and workspace and does not allocate or synchronize internally, so the submission style can be compared on its own.

Fundamentals: what capture records

A normal call gives the operations to CUDA one at a time. However small the four kernels are, the host must prepare the arguments and submit each kernel, and the GPU may idle between the kernels while it waits for the next one. A graph does this repeated preparation in advance. Capture produces a description of nodes and dependencies, instantiation produces an executable instance, and from then on one launch submits the whole workflow (CUDA Graph programming guide).

The minimal skeleton, without error checks and with all pointers allocated before capture, is:

cudaStreamBeginCapture(stream, cudaStreamCaptureModeThreadLocal);
attention_materialized_launch(q, k, v, out, M, N, d,
                              score, kt, stream);
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, 0);

// Can be launched repeatedly afterwards; on the same stream, update inputs first, then run the graph.
upload_current_inputs(stream);
cudaGraphLaunch(exec, stream);

graph is a description, and exec is a prepared execution instance. Neither of them is an output, and neither stores data for anyone. Capture on a single stream fixes the order: softmax runs only after the scores are ready, and PV runs only after the probabilities are ready. The test checks that the graph contains exactly four nodes, so that an entry point that submits on another stream cannot capture something unexpected.

Capture also has an error path that must be handled. If a C++ exception is thrown after BeginCapture, the stream does not leave capture mode just because local variables are destroyed. The implementation therefore tracks the capture state, and on the exception branch it ends capture and discards the useless graph. A targeted test throws an exception after submitting four nodes and confirms that capture works again after the cleanup. Capturing again into an object that already holds a graph is rejected, so an old handle cannot be overwritten silently (capture invalidation and termination).

Graph nodes store addresses, not variables

The most important rule is as follows. A normal launch reads its function arguments in every call, while capture stores the arguments in the graph node as they were at capture time. Suppose that q points to address A at capture time, and later a C++ variable is changed to address B. The graph node does not see this change and keeps reading A in every replay. It does, however, read the contents of A again each time, so writing new data into A does produce new results.

Figure 1: The graph node holds the address captured at A; reassigning the host pointer to B doesn’t reach it.

Three operations separate these semantics. First, the test keeps the Q/K/V addresses fixed, writes inputs from seeds 0, 17 and 42 one after another, and checks each replay against an independent FP64 attention on the CPU. It then leaves the contents of A unchanged, allocates a separate B that stays alive, and points the member query_input of normal submission at B:

query_input = alternative_q;
cudaGraphLaunch(exec, stream); // node arguments still point at A from capture time

direct();                     // the normal call reads the current query_input, i.e. B

The graph receives the old Q with the old K/V, while the normal call receives the new Q with the old K/V, and both pass their respective reference checks. Finally, the test restores the pointer member and writes the contents for seed 99 into the original allocation, and the graph produces the correct result for the new input. The result follows the data, so the graph does not return a cached output.

📝 Note: Always using the same input can hide another bug. If the very first computation already filled the output correctly, a timed “graph” that never actually ran would keep passing validation by reading the last correct value. SOL-ExecBench §4.4.1 documents a case like this, where CuTe DSL didn’t pass the capture stream to the kernel. (The paper’s B200 performance isn’t compared with this laptop GPU.) (paper case)

The whole procedure was run on four boundary shapes, 1×31×331\times31\times331×31×33, 4×127×324\times127\times324×127×32, 32×128×6432\times128\times6432×128×64 and 17×129×6517\times129\times6517×129×65, with maximum absolute errors of 5.28×10−85.28\times10^{-8}5.28×10−8, 3.91×10−83.91\times10^{-8}3.91×10−8, 6.29×10−86.29\times10^{-8}6.29×10−8 and 8.53×10−88.53\times10^{-8}8.53×10−8. The reference first checks that all values are finite and then compares each element against 2×10−6+2×10−5∣OFP64∣2\times10^{-6}+2\times10^{-5}|O_{\mathrm{FP64}}|2×10−6+2×10−5∣OFP64​∣. This check is enough to confirm the argument binding, and the numerics of the attention kernels themselves are the topic of other posts.

Designing around fixed addresses

Since the addresses are fixed when the graph is captured, the structure of the wrapper changes as well. A Request holds a stream, Q/K/V/O, both workspaces, the graph and the exec, all for one fixed (M,N,d)(M,N,d)(M,N,d). A new input only updates the storage and replays the graph, while a different shape is rejected by the entry point before any copy and gets its own instance. These fixed shape buckets give up some generality in exchange for a guarantee that the graph and the storage cannot become inconsistent during argument updates.

CUDA Graphs do support certain updates of arguments and structure, so one graph is not limited to one shape; this post simply does not implement that update protocol. The graph update constraints also mean that a fallback to re-instantiation is needed when an update fails. If several fixed instances are cached, the cache key needs more than the shape: the dtype, the layout, the operator or weight version and the workspace requirements must all be part of the key.

Concurrency raises a problem of storage identity. If two requests of the same shape share one score buffer, the QK of request B may overwrite the freshly written scores of request A before the softmax of A reads them. So dependencies inside the graph can be perfectly correct and still fail to protect memory that is shared outside the graph.

The experiment gives two 4×127×324\times127\times324×127×32 requests their own streams, execs and full storage, interleaves 20 rounds of submissions, and obtains a maximum absolute error of 3.86×10−83.86\times10^{-8}3.86×10−8. This result checks isolation, not how much the two requests actually overlap. Launching one cudaGraphExec_t on two streams would not give the same result, because each launch of an exec is ordered after the previous launch of the same exec, so an exec never runs concurrently with itself (Runtime Graph API).

Measuring it: device interval vs. full request

On the RTX 5070 Laptop, Nsight Systems recorded both submission styles. The data comes from CUDA/CUPTI events: three consecutive normal calls and three replays after the first execution was skipped, each set to zero at the first kernel and drawn on a shared time scale. The colors mark transpose, QK, softmax and PV.

Figure 2: The gaps between the four nodes inside a graph disappear; gaps between graphs remain.

One graph replaces four individual launches, but the host must still start the next graph. The full trace records 20 normal calls and 20 replays after the first graph execution, and the figure shows a short stretch in which the nodes are visible.

Profilers disturb the timing, so the performance numbers come from separate runs without a profiler. With the inputs resident on the GPU, CUDA events bracket a batch of repeated computations, and the result is divided by the count. For requests that start on the host, the measurement covers the upload of Q/K/V from pinned memory, the execution, the download of the output and the synchronization, with the allocations done in advance. These two measurements answer different questions.

All four event intervals become shorter, but two of the four full requests do not benefit. For the smallest shape, the normal end-to-end time ranges over 104.60–120.35 μs and the graph time over 114.55–118.30 μs, so the ranges overlap. For the largest shape, the ranges are 120.95–130.20 μs and 133.00–138.25 μs. Copies, synchronization and host activity lie on the critical path, and this measurement does not separate their contributions to the slowdown.

A CUDA event interval is also not the sum of the kernel durations. It includes idle time in which the start event has already fired but the next kernel has not been submitted yet. A host batch average, on the other hand, includes both submission and waiting, and submission can overlap with device computation, so the two numbers cannot simply be added.

The right number depends on the use case. For a decode sub-chain whose inputs are already on the GPU, the event numbers are the direct signal. For an interface that copies the full Q/K/V from the CPU in every call, the last two columns are closer to the real cost. Real serving also involves queues, variable sequence lengths, KV addresses and request routing. This setup does not implement them, so an event speedup for a fixed request does not translate directly into goodput.

For the smallest shape, the instances ranged from 22.50 to 373.50 μs. A few preparations were much slower than the rest, so a single measurement is not a safe basis for a budget.

Call the preparation plus the first execution CCC, and the saving per steady-state reuse ΔT=Tdirect−Tgraph\Delta T=T_{direct}-T_{graph}ΔT=Tdirect​−Tgraph​. The approximate break-even count is

R=CΔT,ΔT>0.R=\frac{C}{\Delta T},\qquad\Delta T>0.R=ΔTC​,ΔT>0.

With the differences of the host batch averages as the denominator, the four shapes need about 1.23, 1.24, 1.44 and 2.78 reuses. This calculation counts the useful first execution as a cost, so it is conservative. With the more direct end-to-end differences, the two shapes that did not benefit have no finite break-even point at all.

So a graph cache should be reserved for instances that recur and actually benefit. A shape that appears only once may not be worth a graph, and keeping many shapes alive occupies static buffers. The preparation cost, the location of the inputs and the footprint of the cache must therefore be decided together.

Lifetimes: when is the GPU actually done?

When cudaGraphLaunch returns, this only means that the work was submitted, not that the last PV of the graph has finished. The graph holds device addresses but does not gain C++ ownership of these allocations. If a wrapper object is destroyed after the launch returns and frees Q/K/V or the score buffer, nodes that are still running will read freed memory.

For a long-lived object with a fixed request, the simplest and safest solution is acceptable: the destructor waits on its own stream and then destroys the exec, the graph and the storage. The object is reused for the whole life of the service and is not destroyed per request, so blocking the host once at shutdown is acceptable. The pinned host buffers in the end-to-end test are owned in the same way and are freed only after waiting on the relevant stream; otherwise, an H2D or D2H copy could still access freed host memory while an exception unwinds the stack.

Stream-ordered workspaces

Short-lived workspaces are a different case. If every operator call synchronized and freed a temporary workspace at its end, this would artificially break a chain of asynchronous submissions. Instead, the release of device memory can be placed on a stream: allocate, initialize, compute, and then submit cudaFreeAsync. The host may leave the scope before the device finishes, but the reuse of the memory cannot overtake earlier consumers (stream-ordered allocator).

This is a separate implementation from the waiting Request above. OrderedWorkspace, built to test this policy, can only be moved, not copied, and holds one allocation together with one chain of completion dependencies. A move transfers the pointer and the responsibility to free it, not the device data. The destructor submits the release at the end of the dependency chain. An explicit close() can report errors, while the destructor only records cleanup failures and does not throw.

Using a workspace across streams needs one more event edge. handoff(next) records an event on the old stream, makes the new stream wait for this event, and then passes the responsibility for the final release to the new stream:

Figure 5: Handing a workspace from one stream to another.

If streams A and B borrow the workspace at the same time, remembering which stream the most recent host call used is not enough. All outstanding uses must join into one completion chain before the release can follow. This wrapper supports only serial handoff, and it does not try to infer when arbitrary parallel borrowing ends.

Testing it on a multi-stage consumer: Selective Scan

To test early scope exit with a multi-stage device consumer, the lifetime experiment uses a Selective Scan with a zero initial state:

hb,t,d,s=eΔb,t,dAd,shb,t−1,d,s+Δb,t,dBb,t,sub,t,d,h_{b,t,d,s}=e^{\Delta_{b,t,d}A_{d,s}}h_{b,t-1,d,s} +\Delta_{b,t,d}B_{b,t,s}u_{b,t,d},hb,t,d,s​=eΔb,t,d​Ad,s​hb,t−1,d,s​+Δb,t,d​Bb,t,s​ub,t,d​, yb,t,d=∑sCb,t,shb,t,d,s+Ddub,t,d,hb,−1,d,s=0.y_{b,t,d}=\sum_s C_{b,t,s}h_{b,t,d,s}+D_du_{b,t,d}, \qquad h_{b,-1,d,s}=0.yb,t,d​=s∑​Cb,t,s​hb,t,d,s​+Dd​ub,t,d​,hb,−1,d,s​=0.

Here b,t,d,sb,t,d,sb,t,d,s index batch, time, channel and state. uuu is the input, Δ\DeltaΔ a positive step, AAA controls the state transition, BBB couples the input into the state, CCC reads the state out, and DDD is the direct term from input to output. The experiment uses a negative AAA and a positive Δ\DeltaΔ and verifies only this recurrence with a zero initial state, not full Mamba inference.

The implementation computes affine summaries for each chunk, propagates the prefixes, and then recomputes and reduces the outputs, so several kernels read and write the workspace one after another. The test size is batch 2, length 513, 3 channels and 33 states, split into three time chunks, one prefix group and two state tiles. After 256-byte alignment, the workspace takes 32,000 bytes.

The tests cover four cases: leaving the scope after a move, handoff across streams, an exception after submission, and calling close twice. All four cases match a time-recursive FP64 reference on the CPU with a maximum absolute error of 4.8432×10−84.8432\times10^{-8}4.8432×10−8, and each case performs exactly one allocation and one release submission, with zero cleanup errors. The moved-from object is set to null, and calling close twice does not free the memory twice.

To reliably open the window in which the host has returned but the device has not finished, the test inserts an artificial delay of 20,000,000 GPU cycles before the work. In all four cases without a profiler, a query of the completion event after the scope exit returns “not finished”. The delay exists only to create an observable window, and it is not part of any performance result for the Scan.

Figure 6: Purple is the CPU submitting the release, gray the artificial delay, orange the last use.

This figure uses separate small initialization and consumption kernels to widen the window, so that the stages of the Scan do not crowd together. The last use completes safely after the free API returns, because the release is ordered after the last use.

memcheck, racecheck and synccheck all report zero issues on both the Graph path and the Scan path. The ordering of global memory across streams still depends on the dependencies described above, because racecheck mainly checks hazards in shared memory. The streams, the context and any optional audit objects must also live longer than the workspace: once the context is destroyed, the resource class can no longer issue a legal release.

Conclusion

A CUDA Graph saves submission work, so it helps most when the GPU was idle between small launches, and it does nothing for copies and synchronization on the critical path. Capture binds addresses, not variables, so the program must guarantee that these addresses stay alive and hold the right data, and this requirement shapes everything from fixed shape buckets to storage per request. Because the return of a launch does not mean that the device has finished, every buffer needs an owner that either waits or orders its release after the last consumer.

A graph remembers where the data was; the program must make sure that the data is still there and still belongs to it.

Environment and measurement method

Hardware: RTX 5070 Laptop 8 GB on Windows 11, driver 610.88. NVCC from Toolkit 13.1.115 targeting sm_120; the process runtime and driver API queries both report 13030. GPU tasks ran serially, clocks weren’t locked, and L2 wasn’t flushed between batches.

Steady-state compute warms up 20 times, then a pilot picks a batch of about 20 ms, up to 4000 iterations; 30 batches per round, 3 rounds, with modes interleaved. Each round’s median is taken, then the median of three rounds; ranges in the figures are the min to max of the three round medians. End-to-end warms up 5 times per round and measures 30 requests, also over three rounds.
