Integrating a Custom SwiGLU CUDA Operator into PyTorch

The SwiGLU kernel is one sigmoid and two multiplications. To make the operator usable, it must also handle offset views, the current stream, autograd and FakeTensor, and each of these can break it on its own.

The elementwise part of SwiGLU uses one sigmoid and two multiplications. Writing that kernel is the easy part. Whether the operator is ready for real use depends on four requirements that PyTorch places on it:

  1. The tensor may come from an offset view.
  2. The call does not necessarily run on the default stream.
  3. Training needs to differentiate through the output.
  4. At compile time, there is no real data at all.

None of these requirements appears in the gating formula, and any one of them can make the kernel unusable.

The scope is defined first: only contiguous FP32 [2,N] tensors on CUDA, with the gate values in the first row and the gated values in the second row, returning a newly allocated [N]. The forward pass is hand-written CUDA, while the backward pass stays as differentiable PyTorch operations. In this way, the savings of one fusion stay visible, and the information that the framework needs can be added piece by piece.

The post starts with the layout and a scalar kernel, then adds a vector path and explains why “contiguous” is not the same as “aligned”. After that, it covers registration with PyTorch on the correct stream, a backward pass that needs no new kernel, and FakeTensor support for compilation. The last section measures where the time of the fused version actually goes.

Fundamentals: laying out the two inputs

A SwiGLU feed-forward layer has two linear projections. If their results are called aaa and bbb, the computation is

yi=SiLU⁡(ai)bi=aiσ(ai)bi,σ(a)=11+e−a.y_i=\operatorname{SiLU}(a_i)b_i =a_i\sigma(a_i)b_i,\qquad \sigma(a)=\frac{1}{1+e^{-a}}.yi​=SiLU(ai​)bi​=ai​σ(ai​)bi​,σ(a)=1+e−a1​.

Both projections and the output projection that follows are outside this operator, so the performance numbers below cover only the elementwise gate, not a speedup of the FFN. (The SwiGLU paper studies the full layer.)

Packing the inputs into [2,N] means that a0,…,aN−1a_0,\ldots,a_{N-1}a0​,…,aN−1​ lie contiguously in the first half and b0,…,bN−1b_0,\ldots,b_{N-1}b0​,…,bN−1​ in the second half, so output iii reads x[i] and x[N+i].

In [N,2], by contrast, the paired values are usually x[2*i] and x[2*i+1]. The element count is the same, but the meaning is completely different.

Figure 1: Same element count, different pairing.

The projection output of a real model may also be [batch,tokens,2*hidden], with the two halves inside each token. The total length matches, but this layout cannot be treated as the [2,N] layout, because after flattening, the two halves usually do not each occupy one half of the whole storage. Supporting that layout would require computing the halves for each row or explicitly paying for a reorder. I chose the two-row layout to make the relationship between the interface and the execution explicit, so the operator cannot directly accept the projection output of every model.

The formula with scalar access comes first. n is always the length of one half:

__device__ __forceinline__ float silu_times(float a, float b) {
    float e = __expf(-fabsf(a));
    float s = a >= 0.f ? 1.f / (1.f + e) : e / (1.f + e);
    return (a * s) * b;
}

__global__ void swiglu_scalar(const float* x, float* out, int64_t n) {
    for (int64_t i = int64_t(blockIdx.x) * blockDim.x + threadIdx.x;
         i < n; i += int64_t(blockDim.x) * gridDim.x) {
        out[i] = silu_times(x[i], x[n + i]);
    }
}

The code does not simply use 1 / (1 + exp(-a)), because for a very negative aaa, the answer of the sigmoid is near zero, but the intermediate value e−ae^{-a}e−a can overflow first. Taking e=e−∣a∣e=e^{-|a|}e=e−∣a∣ and computing 1/(1+e)1/(1+e)1/(1+e) or e/(1+e)e/(1+e)e/(1+e) depending on the sign keeps the intermediate value stable. The final product can still exceed the range of FP32, and the fast exponential __expf has an approximation error, so this implementation does not promise finite results for every floating-point input.

At the source level, each output reads two floats and writes one float, so the ideal traffic is 12N12N12N bytes. Computing SiLU and the multiplication separately adds one more write and read of the intermediate result, another 8N8N8N bytes. This value is a budget at the tensor boundaries, and the actual DRAM traffic also depends on caching. Fusion also merges two calls into one, and for small NNN this may matter more than the bytes saved.

Contiguous doesn’t mean 16-byte aligned

The scalar kernel works for any non-negative NNN. To read four neighboring values at once, a vector version is added: each thread reads two float4 values and computes four outputs. With this change, the question changes from “are the elements contiguous?” to “is the address of this wide access legal?”

What PyTorch calls contiguous is a relationship between strides and shape, and it does not require a view to start at the first byte of the allocation. For example:

N = 8
storage = torch.randn(2 * N + 8, device="cuda")
x = storage[1 : 1 + 2 * N].view(2, N)
assert x.is_contiguous()

There is no gap between the two rows of this tensor, but its start lies one float, or 4 bytes, after the start of the underlying allocation. If this pointer is forced into a float4*, the 16-byte alignment is broken, because reinterpret_cast only changes how a pointer is interpreted and does not move any data.

So the entry condition of the vector version is

N mod 4=0,addr⁡(a) mod 16=addr⁡(b) mod 16=addr⁡(y) mod 16=0.N\bmod4=0,\qquad \operatorname{addr}(a)\bmod16= \operatorname{addr}(b)\bmod16= \operatorname{addr}(y)\bmod16=0.Nmod4=0,addr(a)mod16=addr(b)mod16=addr(y)mod16=0.

The second half starts at x+N, so its address counts too, and the raw pointer of the output cannot be assumed to be aligned either. If any condition fails, the whole call falls back to the scalar version. There is no vector body with a scalar head and tail for a few edge elements, because I prefer a whole call that is slightly slower and a scope that is clear. CUDA’s device memory access rules state explicit natural-alignment requirements for this kind of access.

The host entry point follows these rules:

cudaError_t swiglu_launch(const float* input, float* output,
                         int64_t total_elements, cudaStream_t stream);

total_elements is the combined count of both halves, and the function divides it by two internally. A negative or odd total is an error, a zero total returns success immediately without launching zero blocks, and a non-empty task rejects null pointers. The function does not allocate memory or synchronize; the caller provides the input and output storage, and the two must not overlap.

A very short comparison can locate bugs at this layer. The simplified entry used for the comparison takes total_elements/2 as the length and chooses float4 when the length is divisible by four, but it checks neither odd totals nor pointer alignment. With a total length of 7, it “succeeds” on three values from each half and misses the last value. With a total length of 0, it tries to launch zero blocks and returns cudaErrorInvalidValue. On the input with a one-float offset shown above, the launch itself succeeds, and the error cudaErrorMisalignedAddress appears only when the kernel completes. These three problems lie in the semantics of the arguments, the launch configuration and the device access, so adding a tail loop fixes none of them.

The corrected entry ran 96 combinations of lengths and address offsets, with a maximum absolute error of 7.15×10−67.15\times10^{-6}7.15×10−6 and clean results from memcheck, racecheck and synccheck. In the disassembly, the vector branch really contains LDG.E.128 and STG.E.128, and the scalar branch contains LDG.E and STG.E. This result only shows that wide accesses were generated; it does not show a speedup, because the work per thread, the number of parallel threads and the actual call cost all change as well.

From torch.ops to the current CUDA stream

The raw entry works with pointers, lengths and streams, while PyTorch users only have tensors. Between them sits a C++ function that first checks the semantics of the tensor and then submits the computation:

at::Tensor swiglu_cuda(const at::Tensor& x) {
    TORCH_CHECK(x.is_cuda(), "SwiGLU requires a CUDA tensor");
    TORCH_CHECK(x.scalar_type() == at::kFloat, "SwiGLU requires float32");
    TORCH_CHECK(x.dim() == 2 && x.size(0) == 2,
                "SwiGLU requires shape [2,N]");
    TORCH_CHECK(x.is_contiguous(), "SwiGLU requires contiguous [2,N]");

    c10::cuda::CUDAGuard guard(x.device());
    auto out = at::empty({x.size(1)}, x.options());
    const auto stream = c10::cuda::getCurrentCUDAStream(x.get_device());
    C10_CUDA_CHECK(swiglu_launch(x.const_data_ptr<float>(),
        out.mutable_data_ptr<float>(), x.numel(), stream.stream()));
    return out;
}

The output inherits the device and dtype of the input but receives new storage, and the input stays unchanged. Non-contiguous tensors are rejected. Calling contiguous() internally would widen the interface, but it would also add a possible allocation and copy that the timing would have to include. The contiguous offset slice from the previous section, however, is legal, and the raw entry selects a safe access branch for it.

CUDAGuard and the current stream have two different jobs. The guard makes allocation and submission happen on the device of the input, while the current stream continues the order that the caller has already set up on that device. A user can produce x on a non-default stream and call the gate directly afterwards, and as long as both operations are submitted to the same stream, the gate runs after the producer. Hard-coding the default stream would lose this order.

Figure 2: The wrong path in this figure reads input that hasn’t been updated yet.

A device-wide synchronization afterwards does not help: it can wait until the wrong read finishes, but it cannot undo the wrong read. Consumption across streams needs events or waits to build the dependency, and storage that another stream borrows must follow the lifetime rules of the framework. The first job of an extension is to preserve the existing order of the caller, because it cannot infer every external producer from a pointer (PyTorch stream semantics).

Registering the operator with the dispatcher allows Python to find it by name:

TORCH_LIBRARY(mur_swiglu, m) {
    m.def("forward(Tensor x) -> Tensor");
}
TORCH_LIBRARY_IMPL(mur_swiglu, CUDA, m) {
    m.impl("forward", TORCH_FN(swiglu_cuda));
}

The first block defines the schema, and the second block registers the CUDA implementation. The schema has no annotations for input mutation or output aliasing, because the implementation really is out-of-place. The framework uses this information to check and transform programs, so a real in-place write must not hide behind a signature that claims to be pure. Only CUDA dispatch is registered here, and CPU tensors are outside the scope (official C++/CUDA extension tutorial).

Once the extension library is loaded, torch.ops.mur_swiglu.forward(x) can be called. Training support is still only half done, however, because PyTorch sees a custom node and does not know how to differentiate it.

Backward without another kernel

Write the upstream gradient as gi=∂L/∂yig_i=\partial L/\partial y_igi​=∂L/∂yi​. Since σ′(a)=σ(a)(1−σ(a))\sigma'(a)=\sigma(a)(1-\sigma(a))σ′(a)=σ(a)(1−σ(a)), the product rule on aσ(a)ba\sigma(a)baσ(a)b gives

∂L∂ai=gibiσ(ai)[1+ai(1−σ(ai))],∂L∂bi=giaiσ(ai).\frac{\partial L}{\partial a_i} =g_i b_i\sigma(a_i) \left[1+a_i(1-\sigma(a_i))\right], \qquad \frac{\partial L}{\partial b_i}=g_i a_i\sigma(a_i).∂ai​∂L​=gi​bi​σ(ai​)[1+ai​(1−σ(ai​))],∂bi​∂L​=gi​ai​σ(ai​).

Each output depends only on the two inputs at the same index, so the Jacobian has no coupling between elements. The backward pass therefore does not need to build a matrix: it multiplies elementwise by the upstream gradient and puts the gradients of the two halves back into [2,N].

def setup_context(ctx, inputs, output):
    (x,) = inputs
    ctx.save_for_backward(x)

def backward(ctx, grad):
    (x,) = ctx.saved_tensors
    a, b = x[0], x[1]
    s = torch.sigmoid(a)
    da = grad * b * s * (1 + a * (1 - s))
    db = grad * a * s
    return torch.stack((da, db), dim=0)

torch.library.register_autograd(
    "mur_swiglu::forward", backward, setup_context=setup_context)

What is saved is a tensor, not a raw address taken from a tensor. The backward pass needs the a,ba,ba,b of the forward pass, and save_for_backward both keeps the storage alive and takes part in version checking. If the user modifies the input in place after the forward pass, the backward pass should raise a version mismatch. Without this check, the backward pass would compute “the derivative at the new input” and attach it to the graph of the old output. A targeted test does trigger this version error.

Figure 3: The forward is a custom node; the backward is ordinary PyTorch.

Keeping the backward pass as PyTorch operations has another benefit: when higher-order gradients are enabled, the framework can continue tracing. For a single output,

∂2y∂a2=bσ(a)(1−σ(a))[2+a(1−2σ(a))],\frac{\partial^2y}{\partial a^2} =b\sigma(a)(1-\sigma(a))[2+a(1-2\sigma(a))],∂a2∂2y​=bσ(a)(1−σ(a))[2+a(1−2σ(a))], ∂2y∂a∂b=σ(a)[1+a(1−σ(a))].\frac{\partial^2y}{\partial a\partial b} =\sigma(a)[1+a(1-\sigma(a))].∂a∂b∂2y​=σ(a)[1+a(1−σ(a))].

The second-order gradients differ from an independent FP64 reference by at most 8.39×10−88.39\times10^{-8}8.39×10−8. This does not mean that hand-written CUDA automatically supports higher-order gradients; the reason is that the registered backward pass is itself differentiable. If the backward pass were replaced with another opaque CUDA kernel, derivative support would have to be added for that kernel as well.

A complete call looks like this:

from bench_mur.pytorch.extension import load_extension
import torch

custom = load_extension()  # compile and load the C++/CUDA code, and complete the Python registration
x = torch.randn(2, 33, device="cuda", requires_grad=True)
y = custom(x)
y.sum().backward()
assert y.shape == (33,)
assert x.grad.shape == (2, 33)

33 is not a multiple of four, but it is a legal length for one half. This call should take the scalar path and return the gradients of both rows normally, because a legal shape of a model should not have to change to suit float4.

FakeTensor only asks about shapes

Autograd handles derivatives, but tracing at compile time also needs the metadata of the output. In a FakeTensor environment, the inputs have a shape, a dtype and a device, but no values that a CUDA kernel could read. The output length of this operator depends only on x.shape[1], so a separate function can describe it:

@torch.library.register_fake("mur_swiglu::forward")
def fake(x):
    torch._check(x.device.type == "cuda")
    torch._check(x.dim() == 2)
    torch._check(x.shape[0] == 2)
    torch._check(x.dtype == torch.float32)
    torch._check(x.is_contiguous())
    return x.new_empty((x.shape[1],))

This function does not call CUDA, read pointers or compute a sigmoid. It only tells the compiler that a legal input produces a new tensor on the same device, with the same type and with length NNN. Its checks must match the checks of the real entry; otherwise, some programs compile and are then rejected at runtime. Operators whose output length depends on the data cannot copy this function. It works here only because the interface already fixes the relationship between the shapes (FakeTensor registration).

Registering a fake does not expose the sigmoid of the kernel to the compiler. Knowing how to connect this node in a compiled graph is different from being able to fuse its internals with neighboring operators. In the test environment, aot_eager, fullgraph=True, dynamic=True ran the forward and backward passes for N=17,33,65N=17,33,65N=17,33,65, with maximum differences of 1.19×10−71.19\times10^{-7}1.19×10−7 and 2.38×10−72.38\times10^{-7}2.38×10−7. The default Inductor backend failed with TritonMissing on both ordinary expressions and the custom operator, so only the AOT integration was confirmed.

Different tests answer different questions. opcheck checks whether the schema, the FakeTensor, the autograd registration and the AOT dispatch fit together, but it does not derive gradients. gradcheck checks numerical gradients with finite differences, and its default method targets double precision, while this interface implements only FP32. The experiment uses eps=0.001, atol=rtol=0.003 as an auxiliary check and keeps the warning about non-double precision. The main numerical evidence is still an independent forward and backward pass on the same FP32 inputs promoted to FP64 (opcheck and gradcheck).

The numerical tests cover N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536, each at storage offsets of 0, 1, 2 and 3 floats, with both random gate values and gate values cycled from [−100,−40,−5,−0.1,0,0.1,5,40,100][-100,-40,-5,-0.1,0,0.1,5,40,100][−100,−40,−5,−0.1,0,0.1,5,40,100], for 104 combinations in total. The maximum absolute errors of the forward and backward passes are both 1.526×10−51.526\times10^{-5}1.526×10−5, all values are finite, and each value is within an elementwise budget that combines an absolute and a relative part.

All four opcheck groups pass: empty input, odd NNN, aligned input and offset input. Seven unsupported inputs are explicitly rejected. A test with a delayed producer on a non-default stream matches the eager reference exactly, and changing the inputs after CUDA Graph capture and replaying gives a maximum difference of 2.98×10−82.98\times10^{-8}2.98×10−8. So the numerics, the layout and the execution order are each verified separately, instead of relying on one random output.

Where the fused time actually goes

The performance comparison uses two clearly defined entries: custom(x) and F.silu(x[0]) * x[1]. Both include the Python call, the dispatcher and the output allocation, and both exclude compilation, input generation and host transfers. The inputs do not require gradients, so there is no backward pass. The data comes from PyTorch 2.14.1+cu130 on an RTX 5070 Laptop.

Each group warms up 20 times and then runs three rounds of 30 batches, with 200 calls per batch for small lengths and 50 calls for large lengths, and the two methods alternate from round to round. The CPU wall clock records the Python submission loop, and CUDA events record the interval of the same batch on the stream. The event intervals include device time spent waiting for the next host submission, so they are not execution times of a single kernel.

For aligned inputs with N>0N>0N>0, the fused call is about 1.5–1.7× faster than eager. The row with zero length shows most clearly what is being measured. The implementation launches no kernel at all, yet the interval is still about 5.73 μs. The start event has already reached the device while Python is still running the call loop, and the end event is enqueued only after the loop has finished submitting. This gap is a real call cost, but it is not a CUDA computation, because no computation happened.

N=32N=32N=32 shows the same pattern. The host submission of aligned custom takes 18.21 μs against an event interval of 18.43 μs, and for eager the values are 26.65 μs and 26.91 μs. So whether a very short kernel receives its work in time already decides the order of magnitude. Fusion really does reduce framework work and intermediate tensors, and it really is faster, but most of the gain comes from less framework work, not from a faster sigmoid.

At N=1048576N=1048576N=1048576, the host submission of offset custom takes about 16.54 μs against an event interval of about 33.63 μs, while the aligned version takes 17.67 μs and 18.59 μs. With enough data, the cost of the scalar fallback finally becomes visible. These large-NNN calls also read warm data: one aligned call moves 12 MB in 18.59 µs, and this would need about 650 GB/s, more than the DRAM bandwidth of this laptop GPU, so repeated calls on the same input are served largely from the L2 cache. This comparison, however, changes both the address and the kernel branch, so it cannot isolate the contribution of any single wide load instruction.

The ranges in the figures are the 5th to 95th percentiles of 90 batch means, not the tail latency of single requests, and the clock of the laptop GPU was not locked. Because Inductor did not run on this machine, the existing data answers only the question “does hand-written fusion beat eager?”, not the question “is hand-written fusion still worth maintaining compared with compiler fusion of F.silu(a) * b?”

Conclusion

The kernel was a few lines of code, and everything else was a contract:

  • the layout states which elements form a pair;
  • the alignment checks cover what “contiguous” does not guarantee;
  • the launch uses whatever stream the caller is using;
  • the schema tells the truth about mutation;
  • the backward pass saves tensors instead of pointers;
  • the fake predicts the output shape without data.

Each of these parts has its own test, and checking that one random output looks right cannot replace any of them.

A usable custom operator must make these boundaries visible to its callers. This implementation covers FP32, the contiguous two-row layout, a CUDA forward pass and a traceable backward pass.

Writing the CUDA kernel is the smallest part of delivering a usable custom operator; the contract around the kernel is the operator.
