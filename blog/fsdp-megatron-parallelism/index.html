Megatron Tensor Parallelism and FSDP, Derived from a Two-Layer MLP

This note derives Megatron tensor parallelism, ZeRO and FSDP, and pipeline parallelism from one two-layer MLP. With it, a reader can tell what each method saves and where its communication comes from.

Megatron-style tensor parallelism and FSDP are the two most common ways to split one training step across GPUs. A 7B model with the usual 16 bytes per parameter for mixed-precision Adam already needs 104.31 GiB for its model state (computed), so eight GPUs must share the step in some way.

There are two fundamentally different ways to split it, and they save memory in different places:

  • Shard the state. Each GPU stores one eighth of the weights. When a layer is needed, the full weights are gathered, and each GPU processes different samples. This method saves the memory spent on storing the model state.
  • Shard the computation. The weights stay split from start to finish. All eight GPUs compute the matrix multiplications of the same sample together and sum the partial results at the end. This method splits the work in progress, not only the storage.

The first method is FSDP (built on ZeRO), and the second method is Megatron-style tensor parallelism. The two often appear in the same configuration file precisely because their communication happens in different places.

This note follows one two-layer MLP through one full update and asks two questions at every step: when does each array need to be complete, and when is a slice enough? These two questions are enough to derive tensor parallelism from the beginning, and then data parallelism and ZeRO. From there, the post derives the parameter lifecycle of FSDP and its trade-offs between memory and communication, shows how the two methods combine on a 2D device grid, and ends with pipeline parallelism and its effect on microbatch sizes. The numerical checks are my own verification on CPU: forward and backward passes of the full and the sharded MLP, finite-difference checks, state budgets and ideal pipeline bubbles. Numbers from these checks are marked (computed); all other facts come from the papers and documentation listed at the end.

The running example: one full update of an MLP

Rows are tokens, so the input is X∈Rn×hX\in\mathbb R^{n\times h}X∈Rn×h. The MLP widens the representation from hhh to fff, applies an elementwise activation and maps the result back to hhh:

Z=XA,H=ϕ(Z),Y=HB,Z=XA,\qquad H=\phi(Z),\qquad Y=HB,Z=XA,H=ϕ(Z),Y=HB, A∈Rh×f,B∈Rf×h,Y∈Rn×h.A\in\mathbb R^{h\times f},\qquad B\in\mathbb R^{f\times h},\qquad Y\in\mathbb R^{n\times h}.A∈Rh×f,B∈Rf×h,Y∈Rn×h.

Biases and dropout are omitted, so that the sources of communication are easy to see. In a Transformer, nnn usually combines the microbatch size and the sequence length, hhh is the hidden width and fff the intermediate width. ϕ\phiϕ can be GeLU or any elementwise function. What matters is that ϕ\phiϕ does not mix hidden channels, and everything below depends on this one property.

In the backward pass, call the incoming gradient G=∂L/∂YG=\partial L/\partial YG=∂L/∂Y:

∂L∂B=H⊤G,D=(GB⊤)⊙ϕ′(Z),\frac{\partial L}{\partial B}=H^\top G,\qquad D=(GB^\top)\odot\phi'(Z),∂B∂L​=H⊤G,D=(GB⊤)⊙ϕ′(Z), ∂L∂A=X⊤D,∂L∂X=DA⊤.\frac{\partial L}{\partial A}=X^\top D,\qquad \frac{\partial L}{\partial X}=DA^\top.∂A∂L​=X⊤D,∂X∂L​=DA⊤.

The forward pass needs the weights, while the backward pass needs the weights and some forward activations, and the optimizer then modifies the weights. So GPU memory never holds only AAA and BBB: activations, gradients and optimizer state all have their own lifetimes.

Whether a way of splitting this computation is valid depends on two things: which array this GPU computes, and which operation fills in the missing part. Matching shapes do not mean that the math requires adding the arrays.

Tensor parallelism: split on both sides of the nonlinearity

Start by splitting AAA along its output dimension:

A=[A0 A1 ⋯ AT−1],At∈Rh×(f/T).A=[A_0\ A_1\ \cdots\ A_{T-1}], \qquad A_t\in\mathbb R^{h\times(f/T)}.A=[A0​ A1​ ⋯ AT−1​],At​∈Rh×(f/T).

Every GPU has the full XXX and computes only its own group of hidden channels:

Zt=XAt,Ht=ϕ(Zt).Z_t=XA_t,\qquad H_t=\phi(Z_t).Zt​=XAt​,Ht​=ϕ(Zt​).

(In distributed programs, one process is called a rank; here, each rank corresponds to one GPU.) Because ϕ\phiϕ is elementwise, HtH_tHt​ needs nothing from the ZZZ of other ranks, so the computation can continue directly to the second layer.

The second layer is split along its input dimension, at the same boundaries:

B=[B0B1⋮BT−1],Bt∈R(f/T)×h.B= \begin{bmatrix} B_0\\B_1\\\vdots\\B_{T-1} \end{bmatrix}, \qquad B_t\in\mathbb R^{(f/T)\times h}.B=​B0​B1​⋮BT−1​​​,Bt​∈R(f/T)×h.

Then

Y=HB=∑t=0T−1HtBt.Y=HB=\sum_{t=0}^{T-1}H_tB_t.Y=HB=t=0∑T−1​Ht​Bt​.

The HtBtH_tB_tHt​Bt​ of each GPU has the size n×hn\times hn×h, but every element contains only the contribution of some hidden channels, so one sum is needed at this point. If the next layer needs the full YYY, this sum is an AllReduce: the contributions are reduced, and the same result is then placed on every GPU in the group. The wide HHH between the two matrix multiplications stays sharded the whole time, and it never has to be gathered and split again.

Figure 1: Megatron’s MLP split. N,H,FN,H,FN,H,F in the figure are n,h,fn,h,fn,h,f in the equations. Both paths compute on the same XXX with different intermediate channels; their outputs are partial results for the same tokens.1

The two layers cannot be split in the same way. If the first layer split its input dimension, the result would be Z=Z0+Z1Z=Z_0+Z_1Z=Z0​+Z1​, and the nonlinearity would immediately prevent independent computation:

ReLU⁡(1−2)=0,ReLU⁡(1)+ReLU⁡(−2)=1.\operatorname{ReLU}(1-2)=0, \qquad \operatorname{ReLU}(1)+\operatorname{ReLU}(-2)=1.ReLU(1−2)=0,ReLU(1)+ReLU(−2)=1.

So the partial sums must be collected before the activation. Splitting the first layer by columns and the second layer by rows postpones the single reduction until after both layers. The algebra, not tuning, decides where the communication happens.

The backward pass goes back through the same hidden channels. Each rank independently computes

∂L∂Bt=Ht⊤G,Dt=(GBt⊤)⊙ϕ′(XAt),\frac{\partial L}{\partial B_t}=H_t^\top G,\qquad D_t=(GB_t^\top)\odot\phi'(XA_t),∂Bt​∂L​=Ht⊤​G,Dt​=(GBt⊤​)⊙ϕ′(XAt​), ∂L∂At=X⊤Dt.\frac{\partial L}{\partial A_t}=X^\top D_t.∂At​∂L​=X⊤Dt​.

Only the input gradient needs a sum across shards:

∂L∂X=∑tDtAt⊤.\frac{\partial L}{\partial X}=\sum_tD_tA_t^\top.∂X∂L​=t∑​Dt​At⊤​.

The parameter gradients already match the weight shard of each rank, and only the input gradient carries partial contributions that must be merged.

📝 Note: The full GGG exists on several GPUs, but those are copies of one logical gradient. Replicating it TTT times isn’t the same as summing TTT independent losses. Each forward replication and reduction has a corresponding backward operation, and autodiff has to carry those semantics.1

I checked this algebra on the CPU in FP64. XXX is 11×811\times811×8, the weights are 8×248\times248×24 and 24×824\times824×8, the intermediate channels are split four ways, and the activation is tanh, so that it is easy to differentiate independently. This check covers only the algebra. (The original Megatron uses GeLU, and tanh relies on the same elementwise property.)

Data parallelism: replicate the computation, not the state

In tensor parallelism, several GPUs compute one input together. To process more samples per step, the whole computation can instead be replicated, with a different batch for each copy. The weights are logically identical, and the gradients come from different samples.

With a data-parallel degree DDD and equal data in each group, the target gradient is

g=1D∑d=0D−1gd.g=\frac1D\sum_{d=0}^{D-1}g_d.g=D1​d=0∑D−1​gd​.

This sum differs from the TP sum above, because the reduced object has changed: TP completes the contributions of the hidden channels of one operator, while DP merges the gradients of one parameter across samples. In addition, if each GPU computes a loss averaged over tokens with different effective token counts, the merge must be weighted by these counts; averaging the means of the GPUs silently changes the training objective.

In classic data parallelism, every replica stores the full weights, gradients and optimizer state. Plain Adam, however, updates each coordinate separately:

mi←β1mi+(1−β1)gi,vi←β2vi+(1−β2)gi2.m_i\leftarrow\beta_1m_i+(1-\beta_1)g_i,\qquad v_i\leftarrow\beta_2v_i+(1-\beta_2)g_i^2.mi​←β1​mi​+(1−β1​)gi​,vi​←β2​vi​+(1−β2​)gi2​.

The bias correction and the parameter update also work on each coordinate separately. A rank that is responsible for coordinate iii only needs the reduced gig_igi​ to maintain mim_imi​, viv_ivi​ and this parameter, and it never needs the moments of other coordinates. This redundant replication is the first thing that ZeRO removes.2

A typical record of mixed-precision Adam per parameter contains 2 bytes for the low-precision weight, 2 bytes for the gradient, 4 bytes for the master weight and two moments of 4 bytes each, for 16 bytes in total. With fixed dtypes and PPP parameters:

What gets shardedModel state per GPU
Everything replicated16P16P16P
Optimizer state sharded(4+12/D)P(4+12/D)P(4+12/D)P
Gradients sharded too(2+14/D)P(2+14/D)P(2+14/D)P

For 7B parameters and eight-way data parallelism, the four rows give 104.31, 35.86, 24.45 and 13.04 GiB (parameters counted in decimal, GiB as 2302^{30}230 bytes). FP32 gradients, or an implementation without a separately stored low-precision weight, would change these numbers, and none of the rows include activations or temporary buffers.

Reducing the gradient and then keeping only the slice of the owner is a ReduceScatter: the contributions to each coordinate are merged, and different slices of the result are then sent to different ranks. Each owner then updates its slice of the parameters with its slice of the gradient, so the full Adam state never needs to appear again on every GPU.

Operations that need global information still need communication. Suppose two gradient shards are 3 and 4 and the global clipping threshold is 1. Then the norm 32+42=5\sqrt{3^2+4^2}=532+42​=5 must be computed first, and the shards are scaled to (0.6,0.8)(0.6,0.8)(0.6,0.8). Clipping each shard separately would give (1,1)(1,1)(1,1), and this vector does not even have the target norm. In the same way, overflow detection requires all relevant ranks to agree on whether to skip the update.

FSDP: shards at rest, full weights in use

The optimizer can work on a slice of the parameters, but a matrix multiplication usually cannot. In the case of XAXAXA, with only state sharding and no TP, a rank holds only a fragment of AAA and cannot perform the full multiplication. Before computing, it must therefore AllGather the different parameter positions into the full AAA.

For fully sharded FSDP that reshards after the forward pass, the lifecycle of one parameter group is as follows:

resident parameter shard
    ↓ AllGather
full parameters for forward
    ↓ free full parameters
resident shard + activations needed by backward
    ↓ AllGather
full parameters for backward
    ↓ ReduceScatter
reduced gradient shard
    ↓ Adam
updated resident parameter shard

AllGather collects different parameter coordinates, while ReduceScatter merges gradients from different samples. Both names contain gather or scatter, but the math is completely different. The FSDP2 documentation describes full sharding with this lifecycle and represents parameters as DTensors, a different representation from the FlatParameter in the FSDP paper.3 The lifecycle is the same in both, but the exact grouping and resharding behavior depend on the actual API.

The memory you forgot: full buffers

A resident state of 13 GiB does not mean that training fits in 13 GiB. If the whole 7B model is wrapped as one parameter group, the full 2-byte weights need roughly another 13.04 GiB while they are in use. Finer sharding shrinks the resident shard further, but it cannot shrink this full expansion.

So the size of each parameter group becomes a setting that trades memory against communication. At 350M parameters per group, a full buffer takes about 0.652 GiB, and computing one group while prefetching the next means two buffers, about 1.304 GiB. Activations, gradients and workspace must be added to approach the real peak.

Let L(t)\mathcal L(t)L(t) be the set of full parameter groups that are alive at time ttt:

Mpeak=max⁡t[Mstate(t)+qp∑i∈L(t)Ui+Mactivation(t)+Mtemporary(t)].M_{\mathrm{peak}} =\max_t\left[ M_{\mathrm{state}}(t) +q_p\sum_{i\in\mathcal L(t)}U_i +M_{\mathrm{activation}}(t) +M_{\mathrm{temporary}}(t) \right].Mpeak​=tmax​​Mstate​(t)+qp​i∈L(t)∑​Ui​+Mactivation​(t)+Mtemporary​(t)​.

UiU_iUi​ is the number of parameters in group iii, and qpq_pqp​ is the number of bytes per expanded parameter. The formula assumes that the expanded buffer and the resident shard are separate copies, and implementations that reuse storage would subtract the overlap.

Figure 3: Budgets computed under the conventions above, excluding activation peaks. With the whole model as one group there’s no “next group,” so “current group” and “plus one prefetched” bars are the same height.

Finer groups mean smaller full buffers and more collectives. At 25M parameters per group, the 7B model needs 280 groups, and with two gathers and one reduce-scatter per group, one step needs 840 collectives. At 350M parameters per group, the model has 20 groups and needs 60 collectives. When the same bytes are split into many small operations, the launch and management overhead grows, and the compute window that can hide communication becomes smaller.

Prefetching: earlier isn’t always better

Gathering the weights early means that the computation waits less, but it also keeps the full buffers alive longer, and too many overlapping buffers can force the allocator to wait or to reclaim memory. The FSDP paper shows both sides. It trained GPT-175B on A100 80 GB GPUs over a 2 Tb/s RoCE network, with BF16, Adam, activation checkpointing and a block length of 2048. In its runs on 128 to 512 GPUs, the setting with 128 GPUs at batch 2 ran into allocator pressure, and limiting how far ahead the system prefetched helped in that case. In Figure 6 of the paper, however, the same limit barely helped RegNet and added about 5% overhead to DeepViT.4

These positive and negative results say the same thing: limiting the prefetch rate shortens the lifetimes of memory, but it can also leave communication unable to finish in time. So the memory savings alone do not predict the step time.

Chorus schedules “when to prefetch” together with “whether the full parameters of the forward pass should be kept for the backward pass”.5 A small example shows why this decision must be global. Suppose a stretch has only 16 MiB free, and the current group U and the next group V need 10 MiB each. Keeping U saves a gather in the backward pass, but then V cannot be materialized early. Each choice is worthwhile on its own, but together they exceed the budget, while in a stretch with 24 MiB of free memory, the combination works. So whether to keep a buffer depends on its whole live interval, not only on its next use.

That work profiles the compute time and the memory constraints and then schedules the materialization of the parameters, with implementations for both ZeRO-style sharding and SimpleFSDP. Its main experiments use 4–16 A100 PCIe 40 GB GPUs, four per node with four 100 Gb/s RoCE links, plus a sensitivity analysis on four H800 GPUs with NVLink. How much free memory can be gained depends on these conditions, so the right prefetch depth must be measured on each setup.

Counting the bytes

The communication volume can also be estimated. With parameter and gradient payloads of QQQ bytes each, ideal ring collectives and only the bytes sent per rank counted, the single gradient AllReduce of DDP sends

VDDP=2D−1DQ.V_{\mathrm{DDP}}=2\frac{D-1}{D}Q.VDDP​=2DD−1​Q.

Full sharding with release after the forward pass performs two AllGathers and one ReduceScatter:

VFSDP=3D−1DQ.V_{\mathrm{FSDP}}=3\frac{D-1}{D}Q.VFSDP​=3DD−1​Q.

The factor 1.5× comes from this particular lifecycle, and changing the communication precision, keeping parameters, accumulating gradients or changing the sharding scheme would change the count. It also does not mean that each step takes 50% longer. If communication takes ccc and aaa of independent computation is available to overlap with it, the ideal waiting time is max⁡(0,c−a)\max(0,c-a)max(0,c−a). Prefetching aims to make the data arrive just in time for its use, and arriving even earlier does not make the step faster.

Two dimensions: which axis is t and which is d?

Now both splits are combined on the same MLP. Two-way data parallelism times four-way tensor parallelism gives eight devices labeled (d,t)(d,t)(d,t).

When ddd is fixed and ttt varies, the devices form a TP group that processes one input together. When ttt is fixed and ddd varies, the devices form a DP/FSDP group that holds the same shard of hidden channels while processing different data.

Device groupRelationship between tensorsWhat needs merging
Same ddd, different tttDifferent hidden channels of the same tokensPartial sums of outputs and input gradients
Same ttt, different dddData replicas of the same logical weight shardParameter gradients from different samples

TP first defines the logical weights At,BtA_t,B_tAt​,Bt​. FSDP then shards the storage of this slice, and what it gathers before computing is still At,BtA_t,B_tAt​,Bt​, so it never assembles all ttt channels back into the full layer.

This distinction should stay explicit in code. Both arrays have the size n×hn\times hn×h, but one is a partial result for the same tokens, while the other is a complete result for different tokens. The communication library does not know these semantics, so with the wrong process group, every shape check still passes.

For this reason, TP solves a problem that FSDP alone cannot solve: when the full weights of a required compute unit are still too large, TP splits them along the compute dimension. The cost is a reduction inside each layer, on the critical path and in almost every layer. So placing TP across a slow link and letting the parameter prefetch cross the same link put the waiting in completely different places.

Pipeline parallelism: move layers, and the microbatch count moves with them

One more situation remains: each layer fits, but all layers together with their state still do not fit on one group of devices. In this case, consecutive layers are assigned to different stages, and the inputs pass through the stages in sequence; this is pipeline parallelism. A TP group from earlier can serve as the internal team of one stage.

With a single input, the later stages wait for the results of the earlier stages, and in the backward pass the earlier stages wait for the gradients of the later stages, so most of the cluster is idle. If a batch is split into several microbatches, different microbatches can be in different stages at the same time. They still form one parameter update, and the optimizer runs after the gradients are accumulated.

A slot model with balanced stages and free communication shows the general shape. With KKK stages, mmm microbatches and a unit slot τ\tauτ, the useful work is mτm\taumτ, and the bubble during filling and draining is (K−1)τ(K-1)\tau(K−1)τ:

TbubbleTuseful=K−1m,TbubbleTtotal=K−1m+K−1.\frac{T_{\mathrm{bubble}}}{T_{\mathrm{useful}}} =\frac{K-1}{m}, \qquad \frac{T_{\mathrm{bubble}}}{T_{\mathrm{total}}} =\frac{K-1}{m+K-1}.Tuseful​Tbubble​​=mK−1​,Ttotal​Tbubble​​=m+K−1K−1​.

The two ratios give different percentages, so a reported number should state which ratio it uses. Real 1F1B and interleaved schedules also handle the time difference between forward and backward, communication, activation storage and imbalance between stages, and this model only shows in which direction the microbatch count pushes.

With bbb samples per microbatch, the global batch is

Bglobal=Dmb.B_{\mathrm{global}}=Dmb.Bglobal​=Dmb.

TP and PP do not appear in this product, because they work together on the same data. If the global batch is fixed at 128 with DP=4 and PP=8, raising bbb from 1 to 8 reduces the microbatch count mmm from 32 to 4, and the ideal share of the bubble in the total time rises from 17.95% to 63.64%.

Figure 4: Ideal bubble fraction vs. microbatch size at a fixed global batch.

Large microbatches fill the matrix multiplications better, while small microbatches fill the pipeline better, and both pressures act on the same configuration. Raising the global batch to get more microbatches also changes how many samples each update combines and changes the optimization trajectory, so it is not an unconditional speedup of the system.

The release policy of FSDP adds another factor. If the full parameters are released after every microbatch, the next microbatch may need to gather them again, while if they are kept, the communication drops but the lifetimes grow. So two configurations that each use memory most efficiently on their own are not necessarily best together.

The large-scale results of Megatron are exactly an allocation of these axes. In Table 1 of the paper, the 1008B model runs on 3072 A100 80 GB GPUs with TP=8 and PP=64, so DP=6, with a global batch of 3072, a sequence length of 2048, 128 layers, a hidden width of 25600 and 160 attention heads. On Selene, the eight GPUs in a node use NVLink/NVSwitch, and each node has eight 200 Gbit/s InfiniBand NICs. This configuration measured 163 TFLOP/s per GPU, about 502 PFLOP/s in total.6

TP=8 matches the fast interconnect inside a node, PP carries most of the layer partitioning, and DP scales the sample throughput. These numbers are throughputs per iteration, and the 84 days in the paper are a projection for a full run on 450B tokens. The FLOP count includes activation recomputation, and the table grows the model, the batch size and the GPU count together, so it is a weak-scaling result, not the same model on more GPUs.

Conclusion

The MLP shows one last time that a training step always consists of the same set of mathematical operations:

  • partial sums over different hidden channels must be completed;
  • gradients from different samples must be merged with the right weights;
  • the state of Adam must match the parameter coordinates.

TP, FSDP and PP change where these objects live and when they appear. Once this correspondence is clear, an OOM or a stall has a specific meaning: a required operator is too large, too many full parameter copies are alive at the same time, or the pipeline does not have enough microbatches. Each of these causes requires a different change.

Every parallelism strategy answers one question: when does this array need to be complete?

Environment and method

Entry point:

py -3.13 bench_mur/systems/training_parallel_evidence.py

It runs full and sharded forward/backward for the two-layer MLP plus finite-difference checks, and computes the state budgets and ideal pipeline bubbles, with the full implementation as reference. In the materials directory rep_mur/blog-rewrite/systems/training/, tp_inputs.npz holds the first input set and tp_equivalence.csv the 32 error sets. Three budget CSVs back the state, parameter-group and pipeline figures, and run.json records environment and script hashes.

All of this runs on CPU. No 7B model was loaded and no multi-process FSDP/Megatron training was run. The papers’ multi-GPU throughput was not reproduced locally, and the budget figures don’t measure activations, allocators or real networks.
