The Roofline Model: Bounding GPU Kernel Time with Two Numbers

This note explains the roofline bound, the ridge point and the memory hierarchy behind them, and how to measure the two numbers. With it, a reader can tell which resource limits a kernel.

The roofline model describes a GPU with two numbers, peak FLOPs and peak memory bandwidth, and it uses them to bound the time of a kernel from its arithmetic intensity. This note covers where the two numbers come from, what the memory hierarchy does to the bound, how to measure the numbers on your own GPU, and how the model reads the arithmetic of LLM serving from The Arithmetic of Prefill and Decode in LLM Inference. The tensor-core rates behind the peak FLOPs are covered in How NVIDIA Tensor Cores Changed from Volta to Blackwell.

The notation is fixed here. FFF is the number of floating-point operations, and MMM is the number of bytes moved to and from HBM. I=F/MI = F/MI=F/M is the arithmetic intensity in FLOPs per byte. FpeakF_{\text{peak}}Fpeak​ is the dense floating-point rate of the GPU, and BpeakB_{\text{peak}}Bpeak​ is its HBM bandwidth. The ridge point is I∗=Fpeak/BpeakI^{*} = F_{\text{peak}}/B_{\text{peak}}I∗=Fpeak​/Bpeak​. Numbers marked (computed) are my own arithmetic from datasheet values; all other numbers come from the sources listed at the end.

The model

A kernel needs two resources, and the GPU limits both. It can do at most FpeakF_{\text{peak}}Fpeak​ FLOPs per second, and it can move at most BpeakB_{\text{peak}}Bpeak​ bytes per second. If the two kinds of work run independently and overlap perfectly, the time of the kernel is at least

t≥max⁡(FFpeak,MBpeak).t \ge \max\left(\frac{F}{F_{\text{peak}}}, \frac{M}{B_{\text{peak}}}\right).t≥max(Fpeak​F​,Bpeak​M​).

When the first term is larger, the compute roof is the lower roof; when the second term is larger, the memory roof is. Dividing both terms by MMM turns this into a statement about intensity: for I<I∗I < I^{*}I<I∗ the memory roof is lower, for I>I∗I > I^{*}I>I∗ the compute roof is lower, and at I=I∗I = I^{*}I=I∗ the two roofs meet. This tells which roof bounds the kernel, not what actually limits it. A kernel can sit far below both roofs because of latency, too little parallelism or overhead, as the sections below show. In this note, “memory-bound” and “compute-bound” name the lower roof.

The standard plot explains the name. Intensity is on a logarithmic axis, a rising line Bpeak⋅IB_{\text{peak}} \cdot IBpeak​⋅I is the limit set by bytes, and a flat line FpeakF_{\text{peak}}Fpeak​ is the limit set by FLOPs. Together, the two lines form a roof. Every kernel sits on or below the lower of the two lines, and its distance below the line measures what it loses to stalls, extra traffic or low occupancy.

Three assumptions carry the model.

  • Perfect overlap. Computation and memory traffic run at the same time, so the time is the larger term, not the sum. A kernel that alternates between loading and computing, with no loads in flight during the computation, is bounded by the sum instead.
  • Steady state. The kernel runs long enough that launch overhead and the first and last waves do not dominate.
  • MMM counts HBM traffic. Data served from L2 or shared memory does not count. If MMM is the number of bytes that really cross the HBM interface, the bound holds. If MMM is estimated as if every access went to HBM, a kernel that reuses data from cache can run faster than the estimate suggests.

The memory hierarchy behind the model

The two-number model flattens a hierarchy into one memory level. On an A100, each SM has a 256 KB register file and 192 KB of combined L1 cache and shared memory, of which up to 164 KB can be shared memory. All SMs share a 40 MB L2 cache, and the A100 80GB adds 80 GB of HBM at 2,039 GB/s. Each level is faster and smaller than the level below it, so a kernel that reuses a tile from registers or shared memory pays the HBM bandwidth once for many uses.

The hierarchy is what makes a GEMM fast. A 4,096 × 4,096 × 4,096 GEMM in FP16 reads three matrices of 33.5 MB each, about 100 MB in total. It does 1.37×10111.37 \times 10^{11}1.37×1011 FLOPs, so its intensity is about 1,360 FLOPs per byte (computed). This is far above the ridge point of the A100 at 153, so the compute roof is lower. Approaching 312 TFLOPS also requires enough parallel work and efficient use of the compute units. Reusing each tile from shared memory keeps the HBM traffic near the count above. A naive kernel that reads its operands from HBM for every output element moves about three orders of magnitude more bytes (computed). Such a kernel lands far below the ridge, however fast the tensor cores are.

The hierarchy also shows up as latency. Bandwidth is a rate, but every memory request also takes time to return, so a kernel reaches BpeakB_{\text{peak}}Bpeak​ only if enough requests are in flight to cover this latency. Little’s law gives the requirement: bytes in flight = latency × bandwidth. Take 500 ns as an assumed latency for illustration. At 2,039 GB/s, about 1 MB must then be in flight across the GPU, or about 9.4 KB per SM on the 108 SMs of an A100 (computed). A memory-bound kernel with too few resident warps cannot keep this much in flight, so its bandwidth falls short of the peak for a reason that the roofline does not show. Occupancy acts as a hidden third number.

Where the two numbers come from

The datasheet numbers are nominal. FpeakF_{\text{peak}}Fpeak​ is the product of the number of units, the rate per unit and the clock, taken at the boost clock with the operands already in place. For the A100, 108 SMs × 1,024 FMAs per SM per clock × 2 FLOPs × 1.41 GHz gives 312 TFLOPS (computed). BpeakB_{\text{peak}}Bpeak​ is the width of the HBM interface times its data rate. The memory controller can come close to it with a pure streaming pattern, but rarely with a mixed one.

The gap between nominal and achievable numbers depends on the kernel. The 989 TFLOPS of dense BF16 on an H100 assume large GEMMs whose tiles stay on chip, at the boost clock. A real kernel with small tiles or extra work in its epilogue reaches less, and how much less depends on the shape. A copy kernel needs enough requests in flight and large enough transactions to come close to the nominal bandwidth. How close it comes differs from GPU to GPU, so a measurement is the only reliable number.

Two tests measure the numbers on your own GPU.

  • Peak compute. Time a large square GEMM in FP16 or BF16 from a vendor library, sized so that the matrices do not fit in L2 (8,192³ or larger), and compute 2N3/t2N^3/t2N3/t. A vendor library such as cuBLAS gives the best available estimate of the achievable peak. On a laptop GPU, watch the clock: the GPU may lower its clock after a short time, so the sustained number can be well below the number at boost clock.
  • Peak bandwidth. Time a large copy, y.copy_(x), on tensors much larger than L2, and compute 2×bytes/t2 \times \text{bytes}/t2×bytes/t, because the copy reads every byte once and writes it once. Repeat the test with an elementwise add to check that the read path behaves the same way. The result is the streaming bandwidth; a strided or scattered access pattern reaches less.

Both tests give a sustained number, and the model needs a sustained number. The question is what the GPU does for the whole duration of a kernel, not what it does in the first millisecond.

Arithmetic intensity of common patterns

Three patterns cover most of what a serving stack runs, and their intensities differ by orders of magnitude.

Elementwise operations. Adding two FP16 arrays into a third reads 4 bytes, writes 2 bytes and does one FLOP per element, so I=1/6≈0.17I = 1/6 \approx 0.17I=1/6≈0.17 FLOPs per byte. This kernel sits at the bottom of the roofline, so its lower roof is always the memory roof, and its best possible time is the number of bytes divided by the bandwidth. A faster tensor core does not help it at all.

GEMM. Multiplying an M×KM \times KM×K matrix by a K×NK \times NK×N matrix costs 2MNK2MNK2MNK FLOPs. The minimum HBM traffic is (MK+KN+MN)(MK + KN + MN)(MK+KN+MN) elements of ccc bytes each, so I≈2MNK/((MK+KN+MN)c)I \approx 2MNK / ((MK+KN+MN)c)I≈2MNK/((MK+KN+MN)c). For square matrices, this is about 2N/(3c)2N/(3c)2N/(3c), and it grows with NNN, so larger GEMMs move toward the compute-roof side of the ridge. Reaching this minimum traffic requires tiling, and tiling is the main craft of GEMM kernels.

Attention. Prefill attention computes QK⊤QK^\topQK⊤ and then multiplies the result by VVV. Its intensity grows with the sequence length, but it stays well below that of a large GEMM if the score matrix is written to HBM and read back; a fused kernel that keeps the scores on chip avoids this traffic. Decode attention has one query token against a long cached context. In this model, reading the whole KV cache once per step gives little arithmetic per byte, so the memory roof is lower. The arithmetic note reaches the same result from the other direction.

What caches do to the bound

A working set that fits in L2 raises the roof. When the working set fits in L2, the effective bandwidth is the bandwidth of L2, and the L2 bandwidth is several times that of HBM. A kernel with a 20 MB working set on the 40 MB L2 of an A100 can therefore run several times faster than an HBM roofline suggests. The usual fix is to draw a second roof at the L2 bandwidth for such kernels.

This effect matters in practice. It is the reason why tiling works, and the reason why a fused kernel that keeps intermediate results on chip beats a chain of elementwise kernels. It also explains why the same arithmetic lands in different places at different batch sizes. The bound itself still holds, because a cached access does not cross the HBM interface and so does not belong in MMM. What fails is a naive count of MMM that treats every access as an HBM access.

Reading the serving arithmetic through the model

The arithmetic note computed two intensities for a 7B model on an A100 80GB. Decode at batch 1 has an intensity of about 0.93 FLOPs per byte, and prefill of 2K tokens has about 2,048. The ridge point is 153. Decode therefore sits more than a hundred times below the ridge with a lower memory roof, whereas prefill sits more than ten times above it with a lower compute roof. These positions specify theoretical ceilings; the actual bottlenecks depend on the execution.

The model also shows what moves a workload relative to the ridge. A shorter context raises the intensity of decode, because less KV is read per token. A larger batch raises it until the cache traffic catches up. A narrower weight format lowers the bytes and raises the intensity directly. None of these changes makes the tensor cores faster, but each of them changes which of the two limits applies.

When the model says nothing

The bound is silent in several cases, and knowing them keeps it from being over-read:

  • Latency-bound kernels. A kernel with one wave of blocks and too few requests in flight is limited by latency, not by either roof, and its time can be far above both. Occupancy and chains of dependent instructions decide its time, not its intensity.
  • Very short kernels. A kernel that runs for a few microseconds is dominated by launch overhead and by its first and last waves, and the model does not describe it.
  • Mixed traffic. Read-only patterns and write-heavy patterns reach different fractions of the nominal bandwidth, so the bandwidth of a pure copy is not a universal constant.
  • Clock changes. A GPU at its power limit lowers its clock, so the FpeakF_{\text{peak}}Fpeak​ at the start of a run is not the FpeakF_{\text{peak}}Fpeak​ ten seconds later.
  • Cache thrashing. A kernel whose working set thrashes L2 moves more HBM bytes than a count of its unique data suggests, and it can be slower than an estimate based on that count.

The model is most useful for comparisons. It tells which roof a kernel is near, whether halving the bytes or the FLOPs would matter, and whether an optimization target can be reached at all. It does not replace a measurement; it tells what to measure and what the result should look like.
