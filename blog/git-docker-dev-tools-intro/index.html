Git and Docker Fundamentals: Content-Addressed History and Container Isolation

An introductory guide explaining Git's snapshot object model, branching, merging, and recovery tools alongside Docker's Linux namespaces, layered images, volumes, and GPU container boundaries.

Almost every modern software or research project depends on two foundational engineering tools: Git to track and coordinate source-code history, and Docker to package the runtime environment so code behaves consistently across machines. Treating both tools as lists of memorized commands leads quickly to confusing merge conflicts, lost edits, bloated images, and broken GPU setups. This guide explains the underlying mental models behind Git and Docker—Git’s three-area workflow, content-addressed object graph, branching, and recovery mechanisms, followed by Docker’s OS-level isolation primitives, layered images, storage mounts, multi-stage builds, and container/host driver boundaries.

Readers who want to review the operating system concepts of processes, filesystems, and virtual environments behind containers can pair this note with Computer Science Foundations. Small numerical calculations worked in the text are marked (computed).

Part 1: Git and the snapshot object graph

Git is not a linear list of file diffs; it is a content-addressed filesystem storing snapshots of an entire repository as a directed acyclic graph (DAG) of commits.

The three areas of a local repository

Every file under Git moves across three distinct states:

flowchart LR
    W[Working Directory<br/>Files edited on disk] -->|git add| S[Staging Area / Index<br/>Exact snapshot queued for next commit]
    S -->|git commit| R[Local Repository .git<br/>Immutable commit graph]
    R -->|git push| RM[Remote Repository<br/>Shared collaboration mirror]
    RM -.->|git fetch / pull| R
  • Working directory: Your normal project files on disk where edits happen.
  • Staging area (Index): A deliberate buffer letting you select which changes belong in the next commit—so an unrelated formatting tweak does not get mixed into a bug fix.
  • Repository (.git): Permanent, hashed snapshots linked into history.

Objects, branches, and HEAD

Inside .git/objects/, Git stores four object types, each identified by a cryptographic hash of its content:

  • Blob: The raw content of a single file (no filename attached).
  • Tree: A directory listing mapping filenames and permissions to blob hashes or sub-tree hashes.
  • Commit: A small record pointing to one root tree (the full project snapshot), zero or more parent commit hashes, author metadata, and a commit message.
  • Tag: A named fixed reference pointing to a specific commit (commonly used for releases).

Because a branch is simply a 41-byte movable pointer holding one commit hash, creating or switching branches is nearly instantaneous. HEAD is a special pointer indicating which branch (or exact commit, in “detached HEAD” state) is currently checked out.

Merge vs. rebase

When a feature branch diverges from main, two ways exist to combine their histories:

  • git merge: Creates a new merge commit with two parents (or performs a fast-forward pointer move if main has not advanced). It preserves the exact historical topology of when work branched and rejoined.
  • git rebase: Replays your branch’s commits one by one on top of the latest main, producing new commit hashes and a clean linear timeline.

A universal safety rule separates them: rebase local, unshared feature branches freely, but never rebase commits that have already been pushed to a shared branch, because rewriting shared commit hashes forces every collaborator to reconcile diverging histories.

Safe undo, reflog, and binary-search debugging

Understanding pointers makes Git’s recovery tools straightforward:

  • git revert <commit>: Creates a new commit that applies the inverse change. Safe on shared branches because history only moves forward.
  • git reset: Moves the current branch pointer backward. --soft keeps changes staged; --mixed (default) unstages changes while keeping edits in the working directory; --hard discards working-directory edits as well.
  • git reflog: Records every position HEAD has pointed to locally (even after a mistaken reset or rebase), acting as a local safety net so “lost” commits can still be checked out by hash before garbage collection.
  • git bisect: Automates binary search across commit history when a bug appeared sometime in the past. Given one known-good commit and one known-bad commit spanning N=1,024N = 1{,}024N=1,024 commits, git bisect isolates the exact offending commit in at most ⌈log⁡21,024⌉=10\lceil \log_2 1{,}024 \rceil = 10⌈log2​1,024⌉=10 tests (computed)—and can run an automated test script at each step via git bisect run.

Part 2: Docker and OS-level container isolation

“It works on my machine” happens because software depends on far more than its own source files: system libraries (glibc), compiler versions, Python packages, environment variables, and filesystem layout. Docker packages those user-space dependencies into a portable image and runs it inside an isolated container.

Containers vs. virtual machines

A virtual machine (VM) emulates hardware through a hypervisor and boots an entire guest operating system kernel inside each VM. A Linux container takes a lighter approach: every container shares the host Linux kernel while two built-in kernel features isolate its view and resources:

  • Linux Namespaces: Give each container its own isolated view of process IDs (PID), network interfaces and ports (NET), mounted filesystems (MNT), hostname (UTS), inter-process communication (IPC), and user mappings (USER). Inside the container, the main application sees itself as PID 1.
  • Control Groups (cgroups): Enforce strict limits on how much CPU time, RAM, and disk I/O a container may consume so one runaway process cannot starve the host.

(On macOS and Windows, Docker Desktop runs a lightweight Linux VM transparently in the background to provide that Linux kernel.)

Images, layers, and OverlayFS

A Docker image is an immutable template built from instructions in a Dockerfile (FROM, RUN, COPY, ENV, CMD). Each instruction that modifies files produces a read-only filesystem layer. When you start a container from that image, the union filesystem (typically OverlayFS) stacks those read-only layers underneath a single thin writable container layer using copy-on-write.

This layered cache model drives one of the highest-impact Dockerfile habits: place slowly changing steps before frequently changing source files.

FROM python:3.12-slim
WORKDIR /app
# Dependencies change rarely -> cached layer reused across code edits
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
# Source code changes often -> placed last
COPY . .
CMD ["python", "main.py"]

If COPY . . came before pip install, editing one line of Python would invalidate the cache and force every dependency to re-download on every build.

For reproducible builds, pinning an image tag like :latest is unsafe because tags can be overwritten upstream. Pinning an exact image digest (image@sha256:...) guarantees bit-for-bit identical base layers across machines and time.

Persistent storage and container networking

Because a container’s top writable layer is discarded when the container is removed, persistent data and live source directories must be mounted explicitly:

  • Named volumes (-v pgdata:/var/lib/postgresql/data): Managed by Docker on the host; best for databases, caches, and build artifacts.
  • Bind mounts (-v "$(pwd)":/workspace): Map a specific host directory directly into the container; standard for active local development.
  • Port publishing and bridge networks: Containers run in isolated network namespaces. Publishing -p 8080:80 forwards traffic from host port 8080 to container port 80, while user-defined Docker bridge networks let sibling containers reach each other cleanly by service name.

Multi-stage builds and GPU containers

Two production patterns come up regularly in systems and AI engineering:

  • Multi-stage builds: A single Dockerfile can define a heavy builder stage containing compilers (gcc, cargo, Node build tools) and a minimal final stage (FROM debian:bookworm-slim or distroless) that copies only the compiled binary. This shrinks image size dramatically and removes unnecessary tools from the runtime attack surface.
  • GPU containers (NVIDIA Container Toolkit): Because containers share the host kernel, the host machine provides the kernel-level GPU driver, while the container image provides the user-space CUDA Toolkit, cuDNN, and deep learning framework. Compatibility depends on the host driver being new enough to support the container’s CUDA runtime version; you should never install a Linux GPU kernel driver inside a Dockerfile.
