Closing the Gap Between a Naive CUDA GEMM and cuBLAS

With one output per thread, a 1024³ GEMM took 3.26 ms, while cuBLAS took 0.62 ms. This post covers block tiling, register outer products and float4 loads, checks them in SASS and measures them on square, skinny and short-K shapes.

This is probably my first blog post about GEMM, and putting it together again now makes me feel nostalgic. For a long time I kept it to myself, because I was a little embarrassed to show it to anyone. I am sharing it now anyway, as light reading over tea or as study material for anyone who is learning this topic.

Matrix multiplication itself is not hard: A∈RM×KA\in\mathbb R^{M\times K}A∈RM×K, B∈RK×NB\in\mathbb R^{K\times N}B∈RK×N, C=ABC=ABC=AB, about 2MNK2MNK2MNK floating-point operations. The hard part is keeping the GPU busy. Every multiply-add waits for two operands, and if both operands must come from global memory every time, the multipliers spend most of their time idle. My first GEMM was exactly in this situation: on a 1024³ square matrix with one output element per thread, it took 3.2601 ms. On the same machine, also in FP32, cuBLAS took 0.6164 ms, more than five times faster.

This factor of 5 breaks down into three separate questions:

  1. Block tiling: can one element of A serve a whole block of outputs?
  2. Thread tiling: once an operand is in a register, can it be used for several multiplications?
  3. Vector loads: how many instructions does it take to move the same data?

The three questions interact, but none of them replaces another. This post goes through them in this order. It starts from a 64×64 output tile and then compares scalar, float4 and CUB loads under the same thread mapping. It then checks what the compiler actually emitted, and it ends by measuring everything on square, skinny and short-K shapes, all on one RTX 5070 Laptop.

Fundamentals: one output per thread

The layout comes first. A, B and C are contiguous row-major arrays, so A[i*K+k] is AikA_{ik}Aik​ and B[k*N+j] is BkjB_{kj}Bkj​. One output element is the dot product of a row and a column:

Cij=∑k=0K−1AikBkj.C_{ij}=\sum_{k=0}^{K-1}A_{ik}B_{kj}.Cij​=k=0∑K−1​Aik​Bkj​.

The most direct kernel gives each thread one output and accumulates along K:

// Teaching version: A[M,K], B[K,N], C[M,N], all contiguous row-major.
__global__ void gemm_naive(const float* A, const float* B, float* C,
                           int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= M || col >= N) return;
    float sum = 0.0f;
    for (int k = 0; k < K; ++k)
        sum = fmaf(A[row * K + k], B[k * N + col], sum);
    C[row * N + col] = sum;
}

fmaf(a,b,c) computes ab+cab+cab+c with a single rounding. When K=0, the loop does not run and the output is naturally 0. The threads do not communicate with each other, so threads at the boundary can simply return.

With 16×16 blocks, 256 threads cover 16×16 outputs. CUDA groups threads into warps of 32, and the index of a thread within its warp is its lane. In a 2D block, x varies fastest, so one warp covers two rows of 16 outputs each.

Fix k and look at one memory access. Threads on the same output row read the same element of A, while the column index of B varies contiguously across the threads. This address pattern decides the shape of the warp’s requests (same address, contiguous or strided), and the hardware handles each shape very differently.

But even with perfectly coalesced access, the same data is loaded again and again. The threads that compute Ci,jC_{i,j}Ci,j​ and Ci,j+1C_{i,j+1}Ci,j+1​ both need AikA_{ik}Aik​, and the threads that compute Ci,jC_{i,j}Ci,j​ and Ci+1,jC_{i+1,j}Ci+1,j​ both need BkjB_{kj}Bkj​. Caches may hold some of this data, but every load, every address calculation and every dependency still remains. I wanted the program to arrange this reuse explicitly, instead of hoping that the cache keeps the data.

This means using three kinds of storage deliberately:

  • Global memory holds the full matrices.
  • Shared memory lets the threads of one block share a small piece of the input.
  • Registers hold the accumulators of each thread.

A block resides on one SM, and whether several blocks can reside there together depends on the registers, the shared-memory capacity and the thread count. Shared memory and registers are close to the compute units, but they are small, and a whole matrix does not fit into them.

Level 1: block tiling, so one load serves many outputs

Take one 64×64 block of C. It needs 64 rows of A and 64 columns of B. There is no need to read all of K at once: K can be cut into chunks of 32, and for each chunk the block loads only a 64×32 slice of A and a 32×64 slice of B. The block computes with this chunk and then loads the next one, while the partial sums stay in the same threads throughout.

This decomposition does not change the product:

Ctile=∑tAtile,tBt,tile.C_{\rm tile}=\sum_{t}A_{\rm tile,t}B_{t,\rm tile}.Ctile​=t∑​Atile,t​Bt,tile​.

Each chunk of input contains 64×32+32×64=409664\times32+32\times64=409664×32+32×64=4096 floats, or 16 KiB, and it performs 64×64×3264\times64\times3264×64×32 FMAs, or 262144 FLOP. Without the cost of writing C, the logical arithmetic intensity of the input at this level is 16 FLOP/B. For a general BM×BN×BKB_M\times B_N\times B_KBM​×BN​×BK​ tile,

Itile=2BMBNBK4(BMBK+BKBN)=BMBN2(BM+BN).I_{\rm tile} =\frac{2B_MB_NB_K}{4(B_MB_K+B_KB_N)} =\frac{B_MB_N}{2(B_M+B_N)}.Itile​=4(BM​BK​+BK​BN​)2BM​BN​BK​​=2(BM​+BN​)BM​BN​​.

Note that BKB_KBK​ cancels. A bigger K chunk does not improve this ratio of input reuse; it only changes the loop count, the synchronization frequency and the shared-memory needs. What makes each element take part in more outputs is a bigger output tile. For this reason, output tiling matters more in GEMM than “reading a bit more of K at a time”.

📝 Note: This formula counts input bytes the algorithm requests, not DRAM bytes. Neighboring blocks can still reuse L2, and even the naive kernel may hit in cache. Use it to decide which direction to tile, not to predict time; for that, measure.

Level 2: thread tiling, outer products in registers

A 64×64 tile has 4096 outputs, and 256 threads still handle them, so each thread gets a 4×4 block:

int local_m = (threadIdx.x / 16) * 4;
int local_n = (threadIdx.x % 16) * 4;
float acc[4][4] = {};

Thread 0 computes rows 0–3 and columns 0–3, thread 1 computes rows 0–3 and columns 4–7, and thread 16 computes rows 4–7 and columns 0–3. 16×16 of these small blocks cover the output exactly, without overlaps or gaps.

At this point it is more natural to think of matrix multiplication as a sum of outer products. For a fixed k, a thread needs only 4 elements of A and 4 elements of B, and these 8 numbers update 16 outputs:

for (int kk = 0; kk < 32; ++kk) {
    float a[4], b[4];
    for (int i = 0; i < 4; ++i)
        a[i] = shared_a[(local_m + i) * 32 + kk];
    for (int j = 0; j < 4; ++j)
        b[j] = shared_b[kk * 64 + local_n + j];
    for (int i = 0; i < 4; ++i)
        for (int j = 0; j < 4; ++j)
            acc[i][j] = fmaf(a[i], b[j], acc[i][j]);
}

Figure 1: Two levels of reuse. A shared tile serves many threads; a register operand serves four FMAs within one thread.

So reuse now happens at two levels: one load of input from global to shared memory serves many threads, and one operand moved from shared memory to a register takes part in four multiply-adds within its thread. After unrolling, several independent accumulators also give the compiler room to interleave FMAs, so a single dependency chain of accumulation is no longer the only limit.

Loading and consuming shared memory requires block barriers. All threads must finish filling the A/B tiles before any thread reads data that another thread brought in. After the current tile is consumed, all threads must meet again before the next K chunk overwrites the same storage; otherwise, a fast warp may already write the next tile while a slow warp is still reading the last one. The full structure therefore has four steps: cooperative load, barrier, outer-product accumulation, barrier. C is written once, after all K chunks.

One more step up is possible. A 128×128 output tile with 8×8 accumulators per thread raises the logical input intensity to 32 FLOP/B, at the cost of 64 outputs held by each thread. Below, this version is called the 128² register-tiled version: 256 threads, BK=16, A transposed in shared memory with padding, and separate handling for full interior tiles and for boundary tiles. It changes several design parameters at once, so its results show the combined effect of a larger reuse scope, not the change of a single parameter from the 64² version.

Level 3: fewer instructions with float4

Now fix the 64² output tile, BK=32 and 4×4 outputs per thread, without enlarging the tile. The A and B tiles each have 2048 elements, so each of the 256 threads loads eight. Thread t takes the logical indices 8*t to 8*t+7. This is a blocked assignment: each thread receives a contiguous range instead of alternating by lane.

This assignment is easy to reason about, but instruction by instruction, the access is not contiguous. In iteration i of a scalar loop, lane 0 reads i, lane 1 reads 8+i and lane 2 reads 16+i. So neighboring lanes are eight floats, or 32 bytes, apart, and the only contiguity is within the eight elements of each thread.

float4 uses exactly this contiguity: each thread moves its eight elements with two wide loads. It does not change which inputs a thread is responsible for, it does not change the shared-memory layout, and not a single line of the multiply-add code moves. For this reason, the three versions can be compared directly:

Load methodElements each thread obtainsShared layout and compute
Hand-written scalarEight scalar reads, logical indices 8*t+iSame
Hand-written float4Wide reads for two fully aligned groups, scalar fallback otherwiseSame
CUB DIRECTThe same blocked assignment expressed with BlockLoadSame

The implementation uses a 2D iterator that maps the logical index of a tile back to the real address in the matrix and returns zero outside the bounds. A common mistake here is to treat a 2D tile as one long contiguous run in global memory. Each row of the A tile has only 32 valid positions, and the real stride to the next row is K, while for B the row stride is N.

int row = index / TileCols;
int col = index % TileCols;
return row < valid_rows && col < valid_cols
     ? base[row * stride + col] : 0.0f;

The CUB version simply passes this iterator to cub::BlockLoad<..., BLOCK_LOAD_DIRECT>. DIRECT keeps the blocked ownership of the elements, and it does not switch to lane-contiguous striped loading by itself. Changing the load strategy would require checking the order in which each thread receives its elements and rewriting the shared-memory indexing. A library can express the loading method clearly, but it does not decide the whole data layout of the GEMM (BlockLoad implementation).

When a wide load is allowed

Wide loads have conditions. Four floats take 16 bytes, so the start must be aligned, and all four elements must be in range:

if (row_valid && col + 3 < valid_cols && aligned_16(ptr)) {
    float4 value = *reinterpret_cast<const float4*>(ptr);
    // The four components go into four consecutive positions owned by this thread.
} else {
    // Check element by element; read if valid, otherwise write zero.
}

Figure 2: Even with an aligned allocation, a view starting one float in is misaligned for 16-byte access.

Even if the base of the allocation is aligned, passing A_allocation+1 shifts the start by four bytes. And even when M, N and K are all exact multiples of the tile, unconditional wide loads are not allowed. With K=33, the row pitch of A is 132 bytes, and every row starts with a different alignment (CUDA natural alignment requirements).

I ran into this problem myself. The 128² version originally chose its fast path based on the shape alone, and at M=N=128,K=32,offset=1 it issued a misaligned 16-byte read, and memcheck immediately reported misaligned. After the fix, the fast path also checks the actual base addresses of A, B and C, and the boundary path checks each group of wide reads and writes. All 36 memcheck runs, including this counterexample, now report zero errors. The condition is specific: the matrix size did not change, but the address of the array view passed into the kernel did.

Tails also need care. M/N tails need an output mask, and K tails need invalid inputs to be filled with zeros. Threads that take part in cooperative loads cannot return early even if they have no valid output, because other threads wait for them to load data and reach the barrier. So whether a thread may exit depends on the cooperation it is part of, not only on whether it has an element of C to write.

Checking what the compiler actually emitted

float4 is only a type in the source code, and whether wide instructions exist depends on what the compiler produces. PTX is a virtual instruction representation for the GPU, while SASS is the machine code that the target architecture executes. I compiled the code with CUDA 13.1 and -O3 -lineinfo -arch=sm_120 and extracted both representations along the actual load template.

A PTX excerpt from the float4 branch, with register numbers assigned by the compiler:

@%p5 bra $L__BB2_5;
shl.b64 %rd28, %rd2, 2;
add.s64 %rd29, %rd4, %rd28;
ld.global.v4.b32 {%r1084, %r1083, %r1082, %r1081}, [%rd29];
bra.uni $L__BB2_13;

The index is shifted left by two to obtain a byte offset and added to the base, and then v4.b32 loads four 32-bit components at once. In SASS, this load becomes LDG.E.128. If the conditions fail, control jumps to the scalar fallback, so the presence of both scalar and vector instructions in one function is not a contradiction.

The site counts are static code locations, and the compiler reports no spills for any of the three versions. One detail is interesting. After the symbol names and the encoding comments are removed, the SASS instruction text of the scalar version and of CUB DIRECT has the same SHA256. This CUB abstraction therefore compiled to exactly the same code. float4 uses 15 more registers: wide loads save instructions, but they also change how the temporaries and the branches are compiled.

Next come the runtime counters. A request is something submitted to L1TEX, and a sector is a 32-byte region that a request touches; the same sector touched by different requests is counted again. Both counters measure activity in the middle of the memory hierarchy, so sectors × 32 is not the same as DRAM read traffic (NCU metrics guide).

With M=N=K=1024,offset=0, for one kernel launch:

Figure 3: float4 cuts both requests and sector accesses to a quarter on aligned 1024³.

The reason is as follows. The blocked assignment puts neighboring lanes 32 bytes apart, so one scalar instruction touches 32 sectors. The thread then reads the next three floats, and these three instructions touch the same set of sectors again. With float4, the four elements arrive in one wide read: the warp still touches 32 sectors, but the request count and the sector accesses both drop to a quarter.

More registers also do not necessarily mean a proportionally lower residency. Occupancy is the number of resident warps as a fraction of the hardware capacity; SMs allocate resources per block, and the resource limits have discrete thresholds. For this input, NCU reports a register block limit of 3 for both versions, and the actual occupancy only moves from 45.14% to 44.12%, with zero local or shared spilling at runtime. So no new residency threshold has been crossed here, but changing the thread count or the accumulator size would require a new check.

As soon as the shape is not regular, the relationship of 4× breaks. At 129×131×65,offset=1, the float4 template makes 2220 requests and 41484 sectors: some lanes are invalid, some rows happen to be aligned, and wide and scalar loads mix. So a template named float4 only shows that the path exists, and dynamic counts are needed to see how often the branch is actually taken.

The biggest step comes from reuse: going from the naive kernel to 64² tiling reduces 1024³ from 3.2601 ms to 0.9029 ms. With both levels of reuse in place, switching to wide loads gives 0.9029→0.7338 ms, a factor of 1.23, and 1.20 at 2048³. The requests fell by three quarters while the total time fell only partly, and this is expected, because the two numbers measure different things.

The 128² version is faster on these two shapes, but it also changes the shared-memory layout, BK and the dispatch of interior tiles, so its gain reflects all of these changes together, not only the bigger output tile. It is also faster than cuBLAS here. That comparison uses one cuBLAS configuration, pedantic FP32 with the algorithm that its heuristics pick, on one laptop GPU, and cuBLAS is 1.6 times faster at 4096³ below, so it does not show that the hand-written kernel is generally faster than cuBLAS. On the cuBLAS side, the call is cublasSgemm under CUBLAS_PEDANTIC_MATH, adapted to row-major via CT=BTATC^T=B^TA^TCT=BTAT without actually transposing the inputs, and it is not a library configuration with TF32 enabled (cuBLAS layout and math modes).

Figure 5: Throughput across square sizes.

Small matrices immediately show the other side of big tiles. A 128³ problem with 128² output tiles produces exactly one block and leaves every other SM idle: it takes 0.01724 ms and is slower than the 0.01133 ms of the naive kernel. So the number of reads that a block saves and the number of outputs that the whole GPU can compute at the same time are two scales that must be watched together.

Skinny and short-K matrices

Non-square shapes also waste work inside the tiles. These results come from a separate measurement batch, and the speed ratio in each row is relative to the scalar version of that batch:

Figure 6: Relative speed by shape.

8192×64×128 has only 64 valid output columns, but the 128² version still organizes the work around 128 columns and throws half of it away: it takes 41.089 µs, against 27.985 µs for 64² float4. When M and N are swapped, the times are 35.394 and 28.510 µs. The arithmetic is the same, but the useful work per thread differs.

Short K dilutes the optimizations of the inner loop. 512×512×16 is only half of a BK, and 64² scalar takes 10.576 µs while float4 takes 10.919 µs. Boundary handling, load organization and launch cost all remain, and wide loads bring no benefit. The offset tail at 129×131×65 behaves in the same way: float4 takes 11.74 µs and scalar 10.69 µs.

At 4096³ the ranking changes again: cuBLAS takes 15.201 ms and 128² 24.321 ms, while scalar, float4 and CUB take 46.377, 27.580 and 35.097 ms. The scalar and CUB versions compile to identical SASS, however, so their gap of 1.32× here is noise, not a real difference. The three round medians of scalar are 46.377, 34.922 and 56.674 ms, and those of CUB are 35.097, 33.621 and 57.413 ms, with ranges that overlap heavily. The laptop warmed up from 56°C to 63°C during the measurement with unlocked clocks, so the spread may come from temperature, clock speed or other factors. Because two identical programs differ by 1.32× at this size, the order of the three 64² loaders at 4096³ is not established; only the gap between cuBLAS and the hand-written kernels is larger than this spread.

Where launch overhead takes over

For kernels of around ten microseconds, the timing also includes the rhythm of host submission. CUDA events mark points on the device, but when the GPU finishes faster than the CPU submits, the interval between two events includes the waiting time for the next launch. The denominator of the gap share runs from the start of the first kernel to the end of the last kernel, without the warm-up before the capture. For short K, more than half of this span has no kernel activity, so the batched event average is clearly affected by submission and is not the time that a single GEMM occupies the device. Tracing has its own overhead, so this timeline shows the shape of the execution, while the independent benchmark above compares the latency. With the device activity separated out, short-K float4 is still slightly slower and the skinny matrices are still faster, so the direction of the results holds.

Figure 9: Device-only vs. host round trip at 1024³.

If the application also uploads A/B, downloads C and synchronizes every time, the waiting time at 1024³ is 1.772 ms for scalar and 1.622 ms for float4, excluding allocation and compilation. The saving in the compute phase still exists, but pageable host transfers cancel out a good part of it. So choosing a kernel requires more than M/N/K: it also requires knowing whether the matrices stay on the device, whether other operators follow, and whether the calls come one after another.

Conclusion

The three questions from the beginning now have answers. Block tiling made each loaded element serve a whole tile of outputs, and most of the factor of 5 came from this step. Thread tiling turned the inner loop into register outer products, so each operand feeds several FMAs. Vector loads reduced the instruction and request counts: a real but smaller gain, and only on aligned, regular shapes. In this implementation, 64² float4 really reduced the load requests and won on a set of large squares, but it did not replace decisions about output tiling, thread mapping and the way the kernel is called.

The next problem moves into shared memory: do consumers collide on the same bank, and can the current tile keep computing while the next one loads? The post on shared layout and double buffering continues with these questions, using the same thread mapping.

📝 Further reading: To see how TMA, WGMMA and persistent scheduling on Hopper hand loading and compute to different hardware paths, read Aleksa Gordić’s long post on matmul. Tiling and synchronization both change under those mechanisms; the FP32 SIMT measurements here describe only this SM120 implementation.

Most of the work of making GEMM fast is making each loaded byte do more work; the instruction count only matters after that.

Experimental setup and method, correctness checks, reproduction

📝 Note: Paths in this appendix such as bench_mur/ and rep_mur/ are in my private research repository, so they aren’t public; they’re listed so each result can be traced.

Experimental setup and method

Test device: RTX 5070 Laptop GPU, SM120, about 8 GB. Compiled with Toolkit 13.1.115, MSVC 2022 14.44, driver 610.88, options -O3 -arch=sm_120 -lineinfo. Environment cross-checks recorded runtime API version 13.3. Since CUDA 13 the Windows runtime can ship with the display driver, so this value can differ from the build Toolkit; see the Runtime API version notes. The original GEMM CSVs didn’t query this field. Consumer SM120 and B200/SM100 differ in resources and instruction capability and should be considered separately.

All implementations use ordinary FP32 multiply-add, and the cuBLAS reference also runs pedantic FP32 without TF32, so speed differences can be explained purely by data organization without also dealing with reduced input precision.

Device timing uses CUDA events: 20 warm-ups, then batches sized to about 20 ms from a single-run estimate, with repeats per batch limited to 1–2000. Slower kernels exceed 20 ms in one run, and very short kernels may fall short of 20 ms after hitting the repeat cap; raw records keep the actual repeat count. Each round has 30 batches, three rounds in all, with in-round task order shuffled by a fixed seed. Inputs are reused and L2 isn’t flushed, so this measures repeated calls with a warm cache. The laptop’s clocks weren’t locked, and round-to-round variation is shown as-is.

End-to-end is timed separately: pageable host upload of A/B, one GEMM, C download and completion synchronization, excluding allocation, compilation and handle creation. Each round warms up five times then measures 30, calling once each time, so the amortized accounting of GPU-resident repeated calls isn’t applied to host-transfer scenarios.

Correctness checks

First, six variants × 12 shapes × three inputs, 216 checks: uniform random, all zeros and alternating-sign cancelling inputs; shapes covering K=0, a single element, tails near 63/64/65 and 127/128/129, asymmetric matrices and offsets of 1/2/3 floats. Outputs are pre-filled with NaN and guarded by sentinels before and after, so missed computation and out-of-bounds writes can’t be masked by initialization.

Small shapes are compared elementwise with CPU FP64. Each output’s engineering error budget is

∣Cij−Cij64∣≤10−6+16ϵ32∑k∣AikBkj∣.|C_{ij}-C^{64}_{ij}|\le 10^{-6}+16\epsilon_{32}\sum_k|A_{ik}B_{kj}|.∣Cij​−Cij64​∣≤10−6+16ϵ32​k∑​∣Aik​Bkj​∣.

This is this experiment’s acceptance threshold, not a floating-point proof for arbitrary inputs and K. All 216 pass, with max absolute error 6.6622e-6 and max actual-error-to-threshold ratio 0.1123. memcheck reports zero errors on all four corrected hand-written kernels.

Large matrices are compared in full against cuBLAS FP32 with atol=3e-4,rtol=3e-4, plus 257 deterministic positions (including first, last and scattered ones) against CPU FP64. That provides a full GPU comparison and a partial independent high-precision reference; it can’t be called full FP64 validation. Every performance task first passes its corresponding correctness check.

Entry points and data locations

The compatibility entry solve(A,B,C,M,K,N) still synchronizes before returning; timing uses a newly added stream launch. Each variant compiles separately so multiple same-named solves don’t link against each other. Scripts are in bench_mur/gemm/{build.ps1,run.py,plot.py}, and per-batch data, raw failures, source hashes, SASS and sanitizer logs are in rep_mur/blog-rewrite/gemm/. The address map and outer-product figure are diagrams drawn from the source, not profiler screenshots.

The second batch shared by both GEMM posts includes 10 variants, 240 pre-timing correctness checks and 14,400 device/end-to-end timing records. Shapes with over 30 million product terms use full cuBLAS pedantic FP32 plus 257 CPU FP64 points; smaller cases are compared in full against CPU FP64. The second batch’s raw files and independent aggregation are in rep_mur/blog-rewrite/style-v2/gemm/ and weren’t mixed with the first batch’s timings.

Binaries and reports are all hashed.
