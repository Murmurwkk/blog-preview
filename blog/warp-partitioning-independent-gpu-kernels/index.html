Horizontal Fusion with HFuse: Warp Partitioning for Im2Col and Bilinear Resize

Follow the two threads on either side of an HFuse warp partition through Im2Col and bilinear resize. Their output addresses explain the mapping and which completion event to time.

Thread 511 in one CUDA block copies a pixel into an Im2Col buffer. Its neighbor, thread 512, interpolates a different image. How can both threads do the right amount of work when each operator originally had the entire block to itself?

HFuse puts a boundary between two warps in the block and gives each group its own numbering. In the measured Im2Col–resize pairing, the break falls exactly halfway through a block of 1,024 threads. The last lane of warp 15 and the first lane of warp 16 make a useful test. If those two threads start at the right positions and take the right stride, the rest of the mapping follows.

Output indexing for Im2Col and bilinear resize

The workload uses the first Im2Col and bilinear resize shape in the HFuse authors’ V100 sweep. Im2Col runs a vertical window of 13 values over a single-channel FP32 input of 2,512×2,0482{,}512\times2{,}0482,512×2,048. At output position (y,x)(y,x)(y,x) it copies (y+r,x)(y+r,x)(y+r,x) into plane rrr for 0≤r<130\le r<130≤r<13. The output has 2,500 valid window starts per column. Resize takes a separate image with eight channels and spatial shape 256×100256\times100256×100, then writes eight planes of 2,000×2,5602{,}000\times2{,}5602,000×2,560 pixels. With aligned corners, coordinate (y,x)(y,x)(y,x) maps to (255y/1999,99x/2559)(255y/1999,99x/2559)(255y/1999,99x/2559) in the input. The last output pixel in each plane copies input pixel (255,99)(255,99)(255,99). HFuse authors’ V100 workload and wrapper

Both operators happen to have 5,120,000 spatial positions. Im2Col writes 13 FP32 numbers per position, for 66,560,000 values. Resize interpolates eight channel values per position, for 40,960,000 values. That common spatial count lets each branch use the same bound for its grid-stride loop. The two branches still write different tensors and have different work per position.

Local worker indices and grid strides at the warp partition

The following excerpt specializes the local deep_split kernel to the Im2Col–resize case, with tracing omitted and expressions spaced out. cut is 512. It is both the width of the Im2Col group and the physical thread index where resize begins.

if (threadIdx.x < cut) {
    int worker = blockIdx.x * cut + threadIdx.x;
    im2col(w, worker, gridDim.x * cut);
} else {
    int width = blockDim.x - cut;
    int worker = blockIdx.x * width + threadIdx.x - cut;
    bilinear(w, worker, gridDim.x * width);
}

Set blockIdx.x to 1. The last lane of warp 15 has physical index 511 and Im2Col group index 511. Its first spatial position is 1×512+511=10231\times512+511=10231×512+511=1023. The first lane of warp 16 has physical index 512 but resize group index 0. Its first spatial position is 1×512+0=5121\times512+0=5121×512+0=512.

A grid of 1,080 blocks gives each branch 1,080×512=552,9601{,}080\times512=552{,}9601,080×512=552,960 distinct first positions. The example Im2Col thread next owns 553,983 and the resize thread 553,472. Every spatial position has exactly one remainder modulo 552,960, and every such remainder is assigned once in each group. This establishes complete coverage on each side. In the local check, every Im2Col output matched an independent CPU gather, and the largest absolute resize error across all output values was 4.42×10−74.42\times10^{-7}4.42×10−7.

The paper’s transformation also adjusts barrier identifiers and participant counts for operations that use a block barrier. These two operators are marked barrier-free in the authors’ configuration. The scheduling idea is that a ready warp of one group can issue when a warp from the other is waiting. The local port implements the ownership by hand. A separate pilot tried seven splits at each of three grid sizes and selected 16 warps per group at 1,080 blocks before collecting the timings. HFuse, §III and Figures 5–6 · Authors’ artifact

Time to complete both outputs under serial, dual-stream and fused execution

The HFuse paper compares against native execution in concurrent streams. I also want to know what the partition buys over running the same two operations back-to-back. On the RTX 5070 Laptop, with reused buffers, the fused launch finished both tensors in about 1.50 ms. Serial execution took about 1.52 ms, and two streams about 1.73 ms. The standalone launches each used 360 blocks of 1,024 threads. Because the fused launch uses its pilot-selected 1,080-block grid, the timing includes the choice of geometry along with the warp split. Two streams give the larger speedup figure, about 1.15×. A caller who can use either measured baseline would select serial execution here. Against that choice, fusion saved about 25 µs in geometric mean times. Its paired interval clears one by a small margin on these inputs. Recording the stop event as soon as the first stream finishes would change the question, since a caller still needs the other tensor. CUDA Graphs and timing boundaries

A separate instrumented run recorded the first and last device-clock tick for every warp. In the first launch, measured from the earliest group entry, the last resize warp reached its endpoint at 1,446.176 µs and the last Im2Col warp at 1,454.176 µs. The completion gap was 8 µs. Across all three launches, the gap lay between 7.296 and 8.000 µs. These timestamps include waiting for execution. The table above times uninstrumented kernels.

For a new operator pair, write the index formula down on each side of the cut and check it first against the destination shapes. Then trace the event that hands the outputs to their next user. Those two checks cover different ways a fused kernel can appear fast while delivering too little work.

Timing protocol, correctness and reproduction

The local FP32 port used CUDA 13.1.115, target sm_120, driver 610.88 and Windows WDDM on a 36-SM RTX 5070 Laptop GPU. The input generator sampled standard-normal FP32 values with seed 20261130. Each recorded interval was preceded by one execution of the same schedule on the same addresses. Adjacent timing blocks used a shuffled method order and its reverse. The device event interval includes waiting and the gaps between its start and stop. Allocation, host-to-device copies and output checks were outside.

Eight independent processes supplied 20 matched blocks each. The table gives the geometric mean of 160 complete-pair durations per schedule, and speedup is the geometric mean of the within-block ratios. The 95% intervals use the 2.5th and 97.5th percentiles of 10,000 bootstrap draws, resampling processes and then complete timing blocks within each chosen process.

In a project checkout, bench_mur/warp-partitioning-independent-gpu-kernels/ contains paired-times-us.csv (480 uninstrumented durations) and warp-endpoints-ns.csv (the six pairs of group endpoints). With Python, NumPy and Matplotlib, the first command reproduces both figures. The second also regenerates the small CSVs and needs the private per-process event and per-warp archive. The CUDA port and harness are kept in bench_mur/gpu_composition/independent/ in the experiment checkout.
