What TVM Relax Fusion Removes from a Small Program

Two matmuls became one and five functions became two, yet three temporary matrices survived. This post follows one Relax program down to TIR loops to see what TVM's fusion actually removed.

When a compiler reports that it “performed fusion”, it may have removed things at several different levels: function calls, intermediate matrices, or only a grouping of a few operators into one region. These levels have very different performance consequences.

In this post I give a very short Relax program to TVM and save the intermediate representation at every stage. Two identical matrix multiplications are deduplicated into one, and five tensor-compute functions are fused into two. Yet in the TIR that is handed to LLVM, the generated fused_* function still contains three 32×6432\times6432×64 intermediate buffers and makes four full passes over the data, one after another. The program compiles and the numbers are correct, but only a layer-by-layer reading of the artifacts shows which optimization actually happened.

The environment is Relax in Apache TVM 0.27.0.post1, with an LLVM CPU target. The Relay paper provides the design background, but the code and the observations come from Relax artifacts, and the interfaces, pipelines and performance numbers of the two generations cannot be transferred directly from one to the other.

The post follows the program through four stages. The first stage is folding and CSE. The second stage is fusion, where the post examines what was merged and what was not. The third stage is a symbolic batch dimension, and the fourth stage is int8 quantization, the only stage that deliberately changes the meaning of the program. Along the way, the post counts the bytes that full fusion would save.

The test program

X∈RB×DX\in\mathbb R^{B\times D}X∈RB×D is the input and W∈RD×DW\in\mathbb R^{D\times D}W∈RD×D is a constant weight. The program computes Z=XWZ=XWZ=XW and then splits into two paths: one path adds a bias and applies ReLU, the other path multiplies by a constant, and the two results are added.

Z=XW,b=b0+b1,Y=ReLU⁡(Z+b)+αZ,α=0.125.Z=XW,\quad b=b_0+b_1,\quad Y=\operatorname{ReLU}(Z+b)+\alpha Z, \qquad\alpha=0.125.Z=XW,b=b0​+b1​,Y=ReLU(Z+b)+αZ,α=0.125.

DDD is fixed at 64 and BBB is the number of rows. b0,b1b_0,b_1b0​,b1​ are constant vectors of length 64 that are broadcast across the rows. This program is not a reduced version of a real model. It only puts three things side by side: a constant that can be computed in advance, a duplicated computation that can be shared, and an intermediate value that two consumers read.

Written informally as array code, the program is:

z0 = x @ W
z1 = x @ W
bias = b0 + b1
r = maximum(z0 + bias, 0)
y = r + 0.125 * z1

A human reader sees the second line and wants to reuse z0. A compiler, however, must first establish that the two computations are interchangeable. Here the inputs are the same and there are no side effects, so the two computations can be shared; with random sampling, mutable state or calls with side effects, identical names and arguments would not be enough. For this reason, Section 3.1 of the Relay paper discusses explicit bindings and evaluation order in detail, because a program is not just a DAG of operators without side effects (Relay paper).

In Relax, bb.emit creates a binding that later code can reference. The program deliberately emits two independent matmul operations, so that CSE must discover the duplicate itself, instead of z0 being shared while the graph is built in Python:

x = relax.Var("x", relax.TensorType((32, 64), "float32"))
bb = relax.BlockBuilder()
with bb.function("main", [x]):
    with bb.dataflow():
        z0 = bb.emit(relax.op.matmul(x, relax.const(W)))
        z1 = bb.emit(relax.op.matmul(x, relax.const(W)))
        bias = bb.emit(relax.op.add(relax.const(b0), relax.const(b1)))
        a = bb.emit(relax.op.add(z0, bias))
        r = bb.emit(relax.op.nn.relu(a))
        s = bb.emit(relax.op.multiply(z1, relax.const(np.float32(.125))))
        y = bb.emit_output(relax.op.add(r, s))
    bb.emit_func_output(y)
mod = bb.get()

Stage 1: folding and CSE

At this level the program has seven high-level operations. FoldConstant computes b0+b1b_0+b_1b0​+b1​ into one constant, so six operations remain, and EliminateCommonSubexpr merges the two XWXWXW into one, so five operations remain:

mod = relax.transform.FoldConstant()(mod)
mod = relax.transform.EliminateCommonSubexpr()(mod)

In the saved IR, the binding of the second multiplication becomes lv1 = lv, and the scale branch uses the existing lv directly. lv is the ZZZ of the formula, and no second copy is allocated.

The weight is also a constant, but the matrix multiplication cannot be folded away, because XXX only exists for each request. The compiler can store and prepare WWW, but XWXWXW still runs at runtime. This is also the boundary between constant folding and CSE: folding uses values that are known at compile time, while CSE makes identical computations within one run happen only once.

Figure 1: Operation and function counts at each stage, from the saved IR.

Going from seven operations to five does not mean that the time drops by two sevenths. One multiplication of B×DB\times DB×D by D×DD\times DD×D costs about 2BD22BD^22BD2 FLOPs, while each elementwise operation costs on the order of BDBDBD, and the sizes of the nodes in a graph do not reflect this gap. Operation counts show whether a rewrite happened, but they are a poor guide to performance.

Stage 2: fusion, and what didn’t fuse

After these two steps, the compute dependencies are clear, but the memory traffic is not decided yet. Relax stays at the tensor level, TIR expands the operators into loops, reductions and buffers, and LLVM finally generates the CPU code. A TIR PrimFunc can be understood as a low-level function that describes a tensor computation explicitly, and it may contain several loop nests and several temporary arrays.

Figure 2: The compilation route from tensor expressions to CPU code.

The same folded and deduplicated program went down two compilation paths. One path goes directly into build lowering, while the other path first inserts an explicit sequence of passes:

passes = tvm.transform.Sequential([
    relax.transform.LegalizeOps(),
    relax.transform.AnnotateTIROpPattern(),
    relax.transform.FuseOps(),
    relax.transform.FuseTIR(),
])
mod = passes(mod)

The order is deliberate. LegalizeOps replaces the high-level operations with callable low-level computations. The pattern annotation identifies access patterns such as elementwise, broadcast and reduction. FuseOps selects regions that can be processed together, and FuseTIR then merges the low-level functions within each region. So choosing regions and arranging loops are different levels of the problem (TVM fusion docs).

This small graph has a fork: ZZZ feeds both the bias branch and the scale branch, and all uses meet at the final addition. If only the first branch is absorbed into the matrix multiplication, the second branch still needs to read ZZZ, so the storage of ZZZ may not disappear. Region analysis must therefore account for every consumer, and if the program also returned ZZZ as an extra output, the externally visible lifetime of ZZZ could not be shortened at all.

The actual artifacts are as follows. The base path has five compute PrimFuncs, matmul/add/relu/multiply/add1. The explicit fusion path has only two, matmul and fused_add_relu_multiply_add1. The second name is long and lists all four elementwise operations, so the real question is how much this name actually includes.

The generated function starts with three 32×6432\times6432×64 buffers:

T_add_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))
compute_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))
T_multiply_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))

These buffers hold the results of the bias addition, the ReLU and the scaling. After them come four full passes over the data. The first two passes, as generated, are:

for ax0, ax1 in T.grid(T.int64(32), T.int64(64)):
    with T.sblock("T_add"):
        v_ax0, v_ax1 = T.axis.remap("SS", [ax0, ax1])
        T.reads(lv[v_ax0, v_ax1], param_0[v_ax1])
        T.writes(T_add_intermediate[v_ax0, v_ax1])
        T_add_intermediate[v_ax0, v_ax1] = lv[v_ax0, v_ax1] + param_0[v_ax1]
for i0, i1 in T.grid(T.int64(32), T.int64(64)):
    with T.sblock("compute"):
        v_i0, v_i1 = T.axis.remap("SS", [i0, i1])
        T.reads(T_add_intermediate[v_i0, v_i1])
        T.writes(compute_intermediate[v_i0, v_i1])
        compute_intermediate[v_i0, v_i1] = T.max(T_add_intermediate[v_i0, v_i1], T.float32(0.0))

T.grid gives the iteration space, SS marks both axes as spatial, and T.reads/writes declare which buffers each block accesses. Even without knowledge of TVMScript, the last assignment in each block shows what happens: the first pass writes the whole of lv+bias, and the second pass reads it back for ReLU. The scaling loop and the final addition loop follow.

So at this stage, the function boundaries have been merged, but not a single loop has been merged. A fusion of only the elementwise part would look more like this pseudocode:

for i in range(B):
    for j in range(D):
        z = Z[i, j]
        Y[i, j] = max(z + bias[j], 0) + 0.125 * z

Here one scalar z would serve both branches, and none of the three intermediate matrices would need to be stored. If this logic went one step further into the epilogue of the matrix multiplication, z would come directly from the accumulator, and even the write and the second read of ZZZ would disappear. Each step has different preconditions, and in this artifact, function merging has happened, while elementwise loop fusion and a GEMM epilogue have not.

These observations come from static-fused-fusion.py, from the IR just before LLVM. Later optimization can still change storage and instructions, so the number of buffers here is not a measured count of DRAM accesses, and it does not show that no TVM backend can fuse this graph. The target, the pass configuration, the schedule and the version all change the result, and this artifact shows how far one specific compilation path went.

Counting the bytes: from 10Q10Q10Q to 3Q3Q3Q to QQQ

To measure the gap described in the previous section, let Q=4BDQ=4BDQ=4BD, the number of bytes in one FP32 output matrix. This ledger counts only the reads and writes at the tensor boundaries of ZZZ, AAA, RRR, SSS and YYY. It excludes the inputs X,WX,WX,W of the matrix multiplication, the bias, the scalars and the caches.

Five separate stages cost 10Q10Q10Q. At B=256,D=64B=256,D=64B=256,D=64, these three levels are 640 KiB, 192 KiB and 64 KiB. The middle value of 192 KiB is a budget derived from the loop sketch above, and the figure shows only the two ends, 640 KiB and 64 KiB. None of these values are hardware counter measurements.

Figure 3: Rewrite counts and the ideal traffic budget at the two extremes.

Less traffic also does not mean a proportional speedup. The reads of X,WX,WX,W by the matrix multiplication and its compute on the scale of 2BD22BD^22BD2 remain. CPU caches hold some temporary matrices between neighboring stages. In addition, putting too much work into one kernel can change register pressure and vectorization. The next step would be to schedule the generated loops and then measure the runtime and the real memory behavior.

What the saved IR does provide is a target that can be tested: removing three intermediate matrices and several separate passes. Anyone who only watches the operator count drop from five to two can easily report an optimization that has not happened yet as a gain that already exists.

Stage 3: a symbolic batch dimension

None of this computation needs BBB at compile time. If the first dimension 32 in the input type is replaced with a symbolic batch, the shape relationships of the matrix multiplication, the broadcast and the join of the branches are still determined. The counts for constant folding and CSE do not change either, because these passes do not need to know the number of rows.

With a more general WWW of shape D×HD\times HD×H:

[B,D]×[D,H]⟶[B,H],[B,H]+[H]⟶[B,H].[B,D]\times[D,H]\longrightarrow[B,H],\qquad [B,H]+[H]\longrightarrow[B,H].[B,D]×[D,H]⟶[B,H],[B,H]+[H]⟶[B,H].

A dynamic first dimension is not an arbitrary shape. The reduction dimension must match, the width of the bias must equal HHH, and the outputs of the two branches must be compatible. This information helps the compiler plan storage and gives the runtime entry a way to reject wrong input. Type relationships cannot prove the safety of low-level addresses, but they do prevent a matrix with 63 columns from entering a computation built for 64 columns.

The actual runs produced four LLVM CPU .so files: static batch and symbolic batch, each with the base path and the explicit fusion path. The symbolic version was compiled once and run at B=1,7,32,129B=1,7,32,129B=1,7,32,129, and the static version was run at B=32B=32B=32. The last build steps are:

with tvm.target.Target("llvm"):
    lowered = relax.get_pipeline("default")(mod)
executable = relax.build(lowered, target="llvm", relax_pipeline=None)
executable.export_library("model.so")
vm = relax.VirtualMachine(executable, tvm.cpu())
actual = vm["main"](tvm.runtime.tensor(x, tvm.cpu())).numpy()

The argument relax_pipeline=None is there because the script has already run and saved the lowering explicitly and should not run the same pipeline twice. The exported library was loaded again, a new VM was built and given the same input, and the outputs matched the outputs from before the export bit for bit.

The reference values contain a small trap. During folding, b0+b1b_0+b_1b0​+b1​ was already added in FP32, so an independent reference must take this FP32 bias together with the actually stored X,WX,WX,W and promote all of them to FP64. If the two biases were added in FP64 from the start, the reference would remove a rounding step that really exists in the program, and the comparison would no longer compare the same computation.

The symbolic version also contains a shape_func. When this function is counted, the base path and the fused path have six and three PrimFuncs, while the earlier counts of five and two included only the tensor-compute functions. So if the shape function is forgotten, the question “how many functions were generated” has two answers.

What changes here is the loop bounds, not the data dependency graph. This is a different kind of dynamism from “look at an intermediate result and then decide how many iterations to run”. Relay handles more general programs with conditionals, recursion and type structure, and this generality explains why a high-level IR is more than operators connected together.

Stage 4: int8 changes what equivalence means

All the steps so far, folding, sharing and fusion, aim to preserve the semantics of the program. Lowering to int8 is different: it deliberately changes the represented values and introduces rounding and saturation. The compiler must be able to see this boundary, or an arithmetic reordering that looks harmless can change the result.

Keep the same Z=XWZ=XWZ=XW and use symmetric quantization:

q(z)=clip⁡(round⁡(z/s),−127,127),z^=sq(z),q(z)=\operatorname{clip}(\operatorname{round}(z/s),-127,127), \qquad \hat z=sq(z),q(z)=clip(round(z/s),−127,127),z^=sq(z),

and then give the same Z^\hat ZZ^ to both the bias/ReLU branch and the scale branch. The quantization happens at the shared point, so both consumers see the same represented values. If each branch quantized separately with different scales, the result would be a different program, and the original sharing relationship would no longer apply.

A smaller sss represents ordinary values more finely but saturates large values sooner, while a larger sss widens the range but makes the rounding step for ordinary values coarser. Fusion does not remove this trade-off. In general, q(a+b)q(a+b)q(a+b) cannot be replaced with q(a)+q(b)q(a)+q(b)q(a)+q(b), and a saturation point cannot be moved freely. Relay splits quantization into annotation, calibration and realization, so that these numerical decisions connect with the later compiler transforms (Relay §4.2).

To see how much the calibration target matters, an independent NumPy experiment built a 256×64256\times64256×64 FP32 input and a 64×6464\times6464×64 weight, and it deliberately scaled row 0 of the input by 20×. Only ZZZ is quantized, both downstream branches use the dequantized values, and the final YYY is compared. The inputs are constructed, not sampled from a real model.

When the error is measured over all rows, the amplified row 0 matters most, so calibration with the maximum gives the best result. When the error is measured over the ordinary rows, the 99.5th percentile gives the best result, and widening the range further loses precision. A tiny clipping fraction is not enough on its own either: 0.1038% counts elements, not the clipped magnitude, and the overall output error is still 22.1182%.

Without a model accuracy metric, this experiment cannot say which threshold is better. What it shows is that the calibration criterion must match the evaluation criterion. A compiler can merge an already-decided quantized computation into fewer loops, but fusion cannot decide for the application whether to preserve the outliers or the ordinary values.

Conclusion

Whether this one line of math is ready for deployment breaks down into three questions that can be answered separately:

  1. Was the duplicated multiplication eliminated? Yes, and the IR proves it.
  2. Do the generated loops make extra passes over intermediate results? Yes: three buffers and four passes remain after “fusion”.
  3. Does the chosen numerical representation still serve the task? As the int8 experiment shows, the answer depends on the calibration target.

Reading compiler artifacts in this way comes much closer to the optimization that actually happened than remembering which passes ran.

“Fused” is a statement about function boundaries; only the IR shows whether the loops and buffers were merged as well.

Environment and entry points

Measured on WSL2 Ubuntu, Python 3.12.3, NumPy 2.5.4 and Apache TVM 0.27.0.post1, targeting LLVM CPU. bench_mur/editorial/style-v2/systems_tvm_cpu/bootstrap.sh installs pinned dependencies, and run.sh runs experiment.py, saving the four libraries, IR at each stage, inputs/outputs and rejection diagnostics. Results are in rep_mur/blog-rewrite/style-v2/systems/tvm-cpu/; the loop analysis corresponds to static-fused-fusion.py there.

Material boundaries

IR printouts omit constant metadata, and constants are saved separately as NPZ, so the full program can’t be rebuilt from the printouts alone; rebuild from experiment.py. This version uses TensorType; don’t copy TensorStructInfo from other versions’ examples. Export and reload were verified in the same environment; cross-version and cross-machine compatibility weren’t tested.

The quantization and ideal-traffic ledger come from bench_mur/systems/relay_design_evidence.py, with results stored separately in rep_mur/blog-rewrite/systems/relay/; they’re not results from a TVM int8 backend. Real CPU outputs were re-checked through an independent NumPy path by systems_tvm_plot.py.

The Relay paper’s performance experiments ran on a Threadripper 1950X, Titan V and similar, with different devices, runtimes and batch sizes for vision and NLP. Its pass ablations reflect incremental effects under the combined configurations of the time and can’t be used to attach a speedup to this Relax CPU artifact. This post didn’t rerun the paper’s model accuracy or performance benchmarks, and didn’t sample CPU memory-access hardware counters.
