GPU Kernel Fusion and Co-location: From Instruction-Level Parallelism to QoS

A convolution can pass a tile directly to its consumer. Independent kernels can instead share an SM or expose ready instructions within a warp. An Im2Col–resize measurement and a VGG16 serving example show why finishing two outputs sooner and meeting a foreground deadline require different decisions.

A VGG16 convolution has just finished accumulating one pixel. Its next consumer, ReLU, needs the sign and magnitude of that pixel and can immediately produce the activated value. Writing the convolution result to global memory, launching another kernel and reading the value back will work. Applying the activation before the store will also work. Now put an image resize beside an Im2Col operating on a different input. The instructions could again share a launch. Yet resize cannot consume a single one of the values produced by Im2Col. Both complete output tensors still have to reach their callers. The same request to “fuse these kernels” has moved from a question about the lifetime of a tensor to one about sharing execution resources.

Suppose next that one image operation belongs to a client waiting for an inference result. A GPU schedule that finishes both images earlier can still make that client wait longer. A service might rationally decline an optimization that wins a two-output benchmark. The distinction follows from three observable facts: which consumer needs a value, which execution resource can advance the work while another operation waits, and when the consumer can actually use the result. We will keep those facts in view while following a convolution tile, the two workers on either side of a fused warp partition, and a foreground request deciding whether to admit background computation before its deadline.

Vertical fusion follows a producer’s values to their consumers

For a single image, the output of VGG16’s conv3_1 has 56 rows, 56 columns and 256 channels. A convolution block accumulates products across the input channels and filter positions before one output value is complete. ReLU then evaluates the maximum of that value and zero. Applying ReLU to an unfinished partial sum would be wrong. For example, partial sums of negative three and positive five add to positive two. Clipping the negative partial sum before adding the positive one would give five. Waiting until the last addition is therefore a genuine dependency even when both operations are moved into one kernel. No agreement between different output pixels is required for a pointwise activation. Once a thread or a cooperating group has finished its particular output, it can apply the activation and write the activated result.

This is vertical fusion along an edge of a computation graph. The data that crosses the edge can have a shorter lifetime and remain at a cheaper level of the memory hierarchy. The benefit can be estimated before timing. The feature map contains 56×56×256=802,81656\times56\times256=802{,}81656×56×256=802,816 values. At two bytes per FP16 value, a complete copy represents 1,605,632 bytes. The separate convolution writes that copy, and the separate ReLU reads it. If ReLU is the only consumer, the fused path can omit both transfers and save about 3.21 MB of logical traffic. The final activated tensor is still needed by the next layer and still has to be written. Counting that write as another saving would promise an output that the program never delivered. Welder, §§3.1–3.2 · VGG16 convolution examples

Now add a second branch that is separately launched and reads the entire unactivated convolution output from global memory. Its presence changes the same calculation. ReLU can still use the locally computed value, saving its own read, but the producer now has to write the original tensor for the other branch. The removable traffic drops to about 1.61 MB. If the extra branch is also fused, uses only part of the tensor or can legally recompute it, the accounting changes again. A planner must follow the consumers of the original value. Counting how many operators have been folded into the graph tells us little about whether an externally visible intermediate has disappeared.

Those are logical bytes in the program. A producer store can leave data in cache where the next kernel’s load finds it. The load still names a global address, and the implementation still needs storage large enough for the intermediate, but those facts do not specify how many bytes crossed the physical DRAM interface. Conversely, additional accesses due to eviction or a poorly chosen tile can appear in the device counters without changing the size of the intermediate. This difference is important for interpreting experiments. A tensor-size calculation provides a testable reason to expect a saving. A reduction in measured global allocation, a reduction in off-chip traffic and a reduction in end-to-end time each answer a different question.

Tiling determines where reuse survives fusion

The pointwise ReLU example gives every tile a clean boundary. Neighboring convolutions are less convenient. Consider an interior eight-by-eight output tile of a stride-one, undilated convolution with a three-by-three filter. The first output column needs three input columns and each subsequent output needs one new column, so eight adjacent outputs cover ten input columns. The eight rows likewise cover ten input rows. A neighboring eight-by-eight output tile, shifted eight columns to the right, covers columns eight through seventeen in the same coordinates. Its leftmost two columns are the rightmost two of the first tile. If the two blocks each regenerate their own upstream input region, they compute 200 input positions between them even though their union contains only 180. The extra twenty are the two shared columns times ten rows.

This is a different cost from writing one large matrix to memory. A transformation can remove an intermediate yet compute some of its elements twice. It might be sensible to regenerate a cheap pointwise expression for twenty halo positions. It could be expensive to repeat a substantial convolution there. Enlarging an output tile reduces the fraction of positions at the shared border, but also increases the number of values that must be available together. The attainable tile sizes depend on shared memory, registers and how the block maps outputs to threads. The compiler must choose both a group of operators to fuse and a way to execute their tiles. Welder works backward from a consumer tile’s needed region to reason about upstream regions, tile capacity and transfers across a group boundary. Welder, tile inference and traffic estimation

That reasoning also gives a simple way to reject a spurious fusion opportunity. Trace the output address of the Im2Col in the independent image pair. Its next user expects a matrix whose planes contain extracted pixel neighborhoods. Trace a resize read. It reads four nearby pixels from an unrelated image and interpolates its own output. There is no producer–consumer edge between those two addresses. Putting the instructions in one binary cannot eliminate the Im2Col output on behalf of resize. Any gain must come from how the GPU schedules the still necessary work, from a changed launch or memory-access pattern, or from another explicitly identified difference between the implementations.

Independent launches, block placement and the completion of two outputs

The least restrictive way to offer independent work to CUDA is to submit the two operations in different streams with independent input and output storage. Operations in one stream have an ordering relationship. Across streams, compatible work may overlap when dependencies and hardware resources allow it. Two streams do not assign half of an SM to each operation, put one block from each program on the same SM, or guarantee that their intervals overlap. One kernel can occupy many of the available block slots before blocks of the other become eligible for placement. Library calls can introduce dependencies of their own. If work arrives too late to find a partner still running, there is no overlap left to exploit. CUDA Best Practices Guide, concurrent kernel execution

Before trying a more prescriptive placement, decide what a caller would count as completion. Suppose a stream recording the timer releases two worker streams from a common start event. Each worker launches its kernel and records its own completion event. The timing stream waits for both events before recording its stop. The measured interval now ends when both tensors could be consumed. Timing only the first stream to return would favor whichever schedule happened to deliver that one tensor early. Measuring two independent events and adding their durations would count a period of overlap twice. The start-and-join arrangement gives a single elapsed time that can be compared directly with two back-to-back kernels measured over the same start and stop boundary.

For a small timeline example, let two independent kernels take six and four time units when run back-to-back. If they start together, the faster one might now take five units under competition and the slower one seven. Both outputs are available at time seven, a reduction from ten even though each individual kernel took longer in the overlapping execution. If the six-unit operation was the foreground request and ran first in the serial schedule, its client sees a regression from six to seven. These numbers are illustrative. They show exactly how a “speedup” and a longer latency can coexist once the completion event is stated. The measured example that follows uses the common two-output boundary. We will return to the foreground interpretation when the scheduler has to protect an inference deadline.

HFuse partitions a block between independent warps

A streaming multiprocessor (SM) admits thread blocks subject to its resource limits. The threads in a resident block execute in warps, normally 32 threads per warp on NVIDIA GPUs. On an issue opportunity a warp scheduler considers the warps assigned to it. A resident warp is active in the terminology of Nsight Compute. An active warp whose next instruction can issue is eligible. The scheduler selects from that eligible set. Ten active warps may all be waiting for a load, a barrier or a busy execution unit. In that interval the mere presence of ten warps does not let the scheduler issue ten instructions. Equally, a modest number of active warps can be enough if some warp supplies useful work whenever an issue opportunity is available. CUDA hardware multithreading · Nsight Compute scheduler statistics

HFuse changes the set of work represented in the resident block. It assigns an integral group of warps to one operator and another group to the second operator. Because the boundary falls between warps, a warp in a straight-line section can perform one operator’s work for all its active lanes. The two groups appear in the same block and therefore the same SM, although their warps can belong to different warp schedulers within that SM. If an Im2Col warp waits for a memory operand and a resize warp is ready to issue useful work, the SM has an opportunity to make progress through the second operator. This is thread-level parallelism (TLP). The scheduler remains free to select eligible warps, and the pair may still bottleneck on the same load/store, issue or memory resource. HFuse, §III

Local worker numbering determines which image elements are written

The experiment uses a workload shape from the HFuse authors’ artifact. Im2Col takes a single-channel FP32 image with 2,512 by 2,048 entries. At each of 2,500 by 2,048 valid positions it extracts a vertical window of thirteen inputs, writing one value to each of thirteen output planes. The second operator independently enlarges an eight-channel image from 256 by 100 positions to 2,000 by 2,560 using bilinear interpolation with aligned corners. Each output position therefore calls for eight channel results. Both grids happen to contain 5,120,000 spatial positions. The common count makes a grid-stride mapping easy to inspect. Synchronization belongs to the logical group that exchanges data

Thread indices are only part of the semantics a horizontal fuser inherits. Imagine a neighboring operator, unlike these barrier-free image kernels, in which each warp fills part of a shared tile and then reads values supplied by other warps. In its original standalone block, a block-wide barrier ensures every participating writer has arrived before the reads begin. After fusion, half the physical threads might belong to an unrelated resize branch whose code never executes that barrier. A barrier that still expects the entire physical block can wait indefinitely or have undefined behavior under an invalid control-flow pattern. Simply deleting the barrier leaves a different bug. A fast warp could read a shared tile before its slower peers have written the needed entries.

HFuse rewrites applicable synchronization points into named barriers for the logical groups, with separate identifiers and participant counts. The count must cover the threads whose progress is actually required. Reusing one identifier for two independent loops can let arrivals from the wrong group satisfy a generation of a barrier. Substituting a warp-only primitive for a barrier that coordinates four warps can leave three groups of writes unordered. A sound mapping must also preserve the group shape required by the algorithm, disjoint shared-memory regions where the original kernels had distinct ones, and valid participation on every relevant control path. The Im2Col and resize timing below comes from a barrier-free pair. A GEMM–stencil implementation later in the chapter provides a concrete instance with distinct 128-thread barriers. A paired measurement of Im2Col and bilinear resize

The number of warps assigned to each side is a performance parameter once the mapping is correct. Half the warps on each side need not mean half the time. One group gathers thirteen values per position and the other interpolates eight channels. Either group can outlive its partner, leaving an end interval in which there is no second operator to hide its stalls. An even split could nevertheless win if it gives the two groups enough workers and the right mix of ready instructions. HFuse profiles candidate partitions and register choices because predicting that mixture from two standalone durations is difficult. The local port implements the warp partition by hand. A pilot compared seven partitions at three grid sizes and chose 16 warps per group at 1,080 blocks before the final timing runs. The standalone launches each used 360 blocks of 1,024 threads.

GoPTX weaves independent instructions into one warp’s program

The Im2Col example supplied a different warp when the first warp was waiting. There is another place to look for work. Consider a warp executing a kernel that loads an integer and then increments it. The increment depends on the value returned by the load. The warp cannot issue that increment until the value is available. A second kernel increments a float at an independent address. Its load needs its own address, but none of the integer data. If the program executed by each logical thread includes both operations, it can place the float load between the integer load and the dependent integer addition. This exposes instruction-level parallelism (ILP) within the same warp. Other warps can still be selected during either wait.

The GoPTX authors publish the two standalone entries and the generated merged entry in a small worked example. The integer and float pointer arguments have separate names and the two operations are assumed to access distinct storage here. These four consecutive instructions come from the merged entry. Within the register names, _saf identifies the integer computation and _sbs identifies the floating-point computation. The surrounding code loads parameters, forms the addresses and stores both results. The authors’ minimal example names one location per pointer. A direct race-free example can use one active thread. To apply the same dependency pattern to an array with a full warp, give each lane its own element in each array. The hexadecimal floating-point literal in the last line represents the FP32 value one. GoPTX authors’ generated PTX at revision 37f9e0b

ld.global.u32 %r_saf1,[ %rd_saf2];
ld.global.f32 %f_sbs1,[ %rd_sbs2];
add.s32 %r_saf2, %r_saf1, 1;
add.f32 %f_sbs2, %f_sbs1, 0f3F800000;

Put the logical dependencies in words. The first addition reads the result of the first load and supplies the first store. The second addition reads the second load and supplies the second store. If the two pointer values alias bytes modified by the other operation, the operations might not be independent and the reordering needs different justification. With disjoint inputs and outputs, neither chain needs an intermediate result from its neighbor. In the authors’ merged entry, the loads from the two chains occur consecutively and so do the adds and the stores. Seeing both original entries in a PTX file would only establish that both had been linked. Seeing a single entry with this interleaving, and a launcher that actually invokes it with both argument lists, establishes the structural transformation under discussion.

The issue opportunity is quite specific. After the integer load has issued, the next instruction is the float load. The warp need not wait for the integer value before issuing the float load if that second instruction’s own dependencies are ready and the issue and load/store resources can accept it. The next instruction after the two loads consumes the integer. If the integer has still not arrived, this warp waits at that point. The scheduler does not discover an arbitrarily later source-level instruction and skip the unresolved addition on the programmer’s behalf. The changed instruction stream puts an independent operation at the place where the original program would have encountered its dependency. The physical memory latency of the first load need not change by a single cycle.

Consider an illustrative schedule in which the integer load issues first and would become ready twelve cycles later. If the second load becomes issuable one cycle after the first, the two requests can spend part of that interval outstanding together. The first addition still cannot consume its result earlier than data readiness permits. The potential saving is that by the time execution reaches the float addition, some of the service time of its own load has already elapsed. A cache miss on the float and a cache hit on the integer would change the exposed tail. A saturated memory interface can turn the extra outstanding request into another customer of the same bottleneck. The numbers in this timeline describe dependencies, not a claim about an actual NVIDIA load latency. PTX is a virtual instruction representation, so the final native program and its measurements determine how much of that opportunity survived compilation and execution.

Merging control-flow graphs while preserving synchronization

Two single-block examples can be interleaved by inspection. Real kernels bring loops, predicates, indirect uses of identifiers, multiple exits and collective operations. If one program exits after a short branch while the other still owes several iterations, returning from the fused entry at the first exit drops work. If a compiler makes both sides take the same branch to simplify merging, it can change the address or result of one operator. GoPTX parses each kernel into basic blocks, which are straight sequences with explicit control-flow successors. A location in the merged control flow can represent a location in the first graph together with a location in the second. Progress in one component can advance while the other component remains at its own pending location. GoPTX, §III and Figures 6–9

For example, suppose the first kernel chooses one of two branches based on image coordinates and the second chooses one of two branches based on its own bounds. These decisions can be independent, giving up to four combinations of next paths. A combined branch that allowed only “both take the first path” and “both take the second path” would be wrong for one interior pixel paired with a boundary pixel. The merged graph must permit the combinations that the inputs can reach. Within resulting blocks GoPTX weaves instructions while retaining the order needed by each input stream and using estimated latencies to choose opportunities for alternation. It can split long basic blocks to create additional weaving opportunities. The input identifiers are renamed so that two originally unrelated registers, labels or parameters do not accidentally refer to one another. Renaming alone says nothing about whether pointers refer to the same memory at runtime.

Synchronization adds a dependence between threads, which a purely per-thread data-flow picture misses. A branch containing a synchronization operation from the first program and another containing a different operation from the second can leave participants reaching the two rendezvous in inconsistent orders. The GoPTX paper shows a case in which naïvely merging the control-flow graphs can deadlock. Its transformation delays synchronization at selected locations using auxiliary graph nodes so that the groups retain a viable order. The opportunity to interleave around such a point depends on what the operation requires all its participants to do. It cannot be inferred from the fact that two numerical outputs live in different arrays. GoPTX graph implementation and weaving

A compatible launch is another precondition. If one standalone kernel implicitly requires a particular block geometry to address shared memory or execute a collective instruction, a common launch must preserve those assumptions or provide a verified remapping. In the paper’s A100 PCIe evaluation the authors standardized the workload launch geometry, using 256 threads per block and 1,048,576 blocks for the GoPTX runs. They evaluated seven source kernels, pairing each with others including itself. Against their concurrent-stream baseline they report an average speedup of 11.2%, with outcomes ranging from a 23% improvement for STMS with LUD to a small decline for WMMA with GELU. This is a paper result on an A100 and a different workload from the laptop’s Im2Col and resize. Its range is informative in its own right. Valid weaving makes independent instructions available to the compiler. The pair’s existing stalls and the costs introduced by the merge determine whether that structure buys time. GoPTX, §§IV–V

Register lifetimes, resident blocks and spill traffic

Return to the two loads. A common source of confusion is what happens to the integer result when the float instruction is allowed to issue. A PTX register is a virtual name with a type or bit width. A 64-bit name such as %rd_saf2 in the example holds an address. It is not an instruction to fetch a particular physical register from device memory. When ptxas compiles the merged program to native code, it chooses where values will live across their uses. The integer and float values may now have overlapping lifetimes. If a value is needed later, the compiler has to preserve enough information to supply that later use. This is a compile-time register allocation problem. The dynamic warp scheduler executes the resulting program on resources already assigned to the block.

Once admitted to an SM, a block occupies register capacity for its resident warps. The scheduler can issue instructions from another resident warp without first writing the waiting warp’s architectural registers to global memory. Otherwise the very act of hiding a short arithmetic or memory wait behind a neighboring warp would incur a large save-and-restore operation. The original warp can be temporarily ineligible yet remain resident with its execution state. Removing or preempting a kernel to free the machine for a different request, as REEF later considers, is a different operation. The distinction between issuing another resident warp and evicting an executing workload becomes crucial when interpreting both performance counters and service latency. CUDA hardware multithreading

Static allocation can change how many blocks fit

Imagine a simplified SM with 65,536 registers and a candidate block containing 256 threads. Ignoring allocation granularity for the moment, 64 registers per thread require 16,384 registers for the block. Four such blocks would exactly exhaust the pool. At 65 registers per thread a block needs 16,640 and four would require 66,560, which exceeds the assumed capacity. The register limit alone would then allow at most three. This arithmetic illustrates the step at a resource boundary. Real architectures allocate in hardware-specific units, and the register file can be partitioned within the SM. Thread slots, shared memory, warp limits and the maximum active block count also restrict admission. The actual block limit is set by whichever restriction binds for the given device and binary. CUDA Programming Guide, hardware implementation

The raw register counts of two standalone kernels are poor predictors of that step. If two computations use a temporary at disjoint times, the native compiler might assign the same physical location to both. If weaving lengthens their lifetimes, the old results may have to coexist with a second operator’s operands or address calculations. The compiler may also rematerialize a cheap value rather than preserve it. The transformation creates a new program whose maximum simultaneous demand can differ from the sum of two standalone reports. A reduction in resident warps might be worth accepting if the survivors now have substantially more independent work to issue. An increase in residency could be unhelpful if it came at a high cost in additional memory instructions.

A spill occurs when the compiler generates an alternative storage path for a value that it cannot profitably keep in a register across its needed lifetime. The conventional path uses thread-local memory, backed by device memory and served where possible by caches. A spill store and later reload can add instructions and latency even when the requests hit cache. Conversely, seeing local memory in a profile does not establish that all of it was introduced by register spilling. An explicitly indexed local array, for instance, can also occupy local memory. Inspecting the compiled resource report and native instructions helps identify the source. Runtime memory counters and a matched timing establish how expensive the resulting path was for these data. CUDA Programming Guide, local memory

CUDA 13 adds an explicit opt-in option for spilling to shared memory first under the conditions documented by NVIDIA. That option can reduce the latency and cache traffic associated with a local-memory spill. Its cost appears in the block’s shared-memory reservation, which can in turn reduce the capacity available for another block. A compiler report showing fewer local spill accesses therefore has to be read together with shared-memory allocation and observed execution time. The underlying scheduling question is unchanged. Does the alternative store for a live value release the resource that is currently limiting progress, or does it take away the space that made a complementary partner possible? NVIDIA, shared-memory register spilling in CUDA 13

These distinctions give “the GPU is underutilized” a more useful set of meanings. Blocks may be ready to launch yet unable to fit, resident warps may be waiting for operands, or eligible warps may compete for an already saturated pipeline. The first points toward changing resource demand or block placement. The second can motivate an independent warp or an independent instruction stream. The third can make adding more work harmful even when the reported occupancy is below its theoretical maximum. A profiler showing more eligible warps after GoPTX supplies evidence that more warps could issue at the sampled times. By itself that counter cannot prove which instruction dependence was shortened or how much of the wall-clock change came from it. The generated instruction stream, resource usage and like-for-like timing provide the complementary evidence.

Persistent and elastic blocks change the amount of resident work

Suppose the original launch contains twelve independent logical blocks. Each logical block owns a tile and uses the same thread arrangement to process that tile. A persistent-thread-block transformation could launch four physical blocks and give block zero logical tiles zero, four and eight. Block one gets one, five and nine, and the other two physical blocks cover the remaining residues modulo four. Provided the iteration bounds and logical block indices are translated correctly, the same twelve tiles reach their outputs. The physical blocks stay alive across multiple pieces of work, so the program can limit the grid admitted on behalf of this kernel while still completing its original problem. This is the principle of a persistent thread block, usually abbreviated PTB. Plasticine, persistent and elastic blocks

The loop is serial for one physical block’s successive tiles. That does not imply serial memory access for the whole GPU. The resident blocks work concurrently and each block contains warps that can have multiple requests outstanding. Reducing twelve physical blocks to four can reduce the number of available warps and expose memory latency. It can also free block slots and aggregate register or shared-memory capacity for a partner. Whether a second kernel fills that capacity matters. If no partner is ready, deliberately reducing the first kernel’s parallelism can simply extend its finish time. If the first kernel already saturates DRAM with four blocks, launching the partner may add contention without increasing total memory service. These are claims about simultaneous requests and achieved bandwidth, which cannot be derived from how many tiles one block visits over its whole lifetime.

Persistence also changes what must be reset between iterations. A standalone logical block starts with its own shared storage, local indexing and barrier generations. A persistent block that reuses storage for another tile has to complete all required reads and writes to the old tile before overwriting it. A reduction that once initialized an accumulator once per physical block may now need to initialize it once per logical tile. Otherwise later tiles inherit earlier totals. The resident allocation of the physical block lasts through the loop. Running an already compiled binary with fewer physical blocks does not change its compiled register count, whereas rewriting the body to add loop state and recompiling it can change liveness and spill decisions.

Plasticine goes further for Tensor Core matrix multiplication. An output tile of shape MbM_bMb​ by NbN_bNb​ needs parts of the two inputs along an inner dimension KbK_bKb​. A simple single-stage shared-memory budget for FP16 inputs is 2(MbKb+NbKb)2(M_bK_b+N_bK_b)2(Mb​Kb​+Nb​Kb​) bytes before padding and extra buffers. A smaller output tile can thus reduce the number of input values resident in each block, even when the total GEMM and its output are unchanged. The authors adjust both the thread-block size and the work it performs. In their reported case the elastic variant decreases shared memory from 64 KB to 36 KB per block. That can make a different coexistence pattern possible. On its own, changing the launch syntax to halve the thread count would not implement those altered tile shapes. Plasticine, §V-B

There is a price on the opposite side of that calculation. Adjacent matrix tiles may load some inputs that a larger tile could reuse internally. The transformation can spend more total memory traffic to reduce the simultaneous allocation of a single block. Conversely, a carefully chosen tile that shortens accumulator lifetimes could give a later instruction-weaving pass enough registers to accommodate an independent chain. Those are compatible mechanisms, but their benefits do not add automatically. To identify such an interaction, one would compare the original and retiled body alone and compare both with the same partner under a common completion boundary. A smaller per-block footprint establishes feasibility of residency. Timing is needed to show that the useful work admitted by that change outweighed the reuse or parallelism that the original kernel gave up.

μShare shapes block placement and checks the partner before launch

A different option is to keep two kernels as separate launches and use the block-size limit to rule out undesirable placements. The μShare paper describes cases in which the hardware scheduler places several blocks from the same kernel on one SM. Such stacking can leave another kind of execution resource underused even with many threads present. Making one type of block too large to stack with another identical block changes the set of legal placements. It does not name the destination SM or the identity of the block that will eventually fit beside it. The method works through ordinary launch geometry and profiled resource requirements, so it needs a block-size-adjustable kernel whose indexing remains correct after shaping. A library call that hides its internal launch or a kernel with a fixed collective layout may not offer that freedom. μShare, shaper and device analysis

On the A40 used in the paper, an SM can have 1,536 resident threads. Half is 768. The minimum warp-aligned block size strictly above half is 800, so two such blocks would require 1,600 slots and cannot reside together. One 800-thread block leaves at most 736 thread slots. A 512-thread partner fits under that particular limit. It may still lack the registers, shared memory, remaining block slots or other required resources. An additional question is whether the two grids are deep enough for their blocks to meet in time. A single large block on an otherwise empty GPU cannot cause other SMs to become active just because a second identical block could not stack beside it.

On a device such as the A800 with a capacity of 2,048 threads per SM and a maximum of 1,024 threads per block, a strictly larger-than-half block is impossible. The paper instead describes one-third-plus shaping. The first warp-aligned size above 2,048/32{,}048/32,048/3 is 704. Two 704-thread blocks occupy 1,408 slots, leaving 640. A third would require 2,112, which is too many. The arithmetic now excludes a third large block rather than a second. These examples give meaning to the fractions. Half-plus and one-third-plus describe how many large blocks of like type the target SM can stack while leaving possible room for a smaller partner. They do not prescribe 800 threads for every device, promise a particular small partner or enforce a global limit on the threads in the entire launch.

μShare also distinguishes the kernels it shapes immediately from candidates that retain their default block size. Its runtime ranks intercepted kernels using launch slack relative to profiled timing. From the tighter-slack part of that ordering it selects a set of large blocks intended to spread across the available SMs. The other candidates can be launched with their normal smaller blocks if they meet the admission tests. In the positive-slack A40 example the selected large kernel starts at the minimum half-plus size. When launch slack is negative, the paper lets the shaper increase that size by warps. This policy has a time component as well as a geometric one. Static arithmetic establishes a placement that is impossible, while the runtime still has to contend with the actual kernels that are ready at a particular instant.

The time-shifted launch policy uses profiles on six resource dimensions: FP32, FP64, integer, load/store, special-function and Tensor Core use. For a candidate partner, the estimated combined utilization on each dimension must stay at or below 100 percent, and the available registers and shared memory must suffice. For illustration, if the two profiled load/store utilizations sum to 110 percent, spare Tensor Core capacity cannot make the load/store test pass. If all six sums fit but the physical shared-memory reservation is too large, the capacity check still fails. Profiles guide admission and can differ from actual concurrent behavior because cache traffic and instruction issue change under competition. They provide a decision rule, not a hardware guarantee of a particular overlap.

Only when the conditions fail does the waiting candidate delay and recheck. In the paper’s evaluated policy the interval is β=10\beta=10β=10 microseconds. At the next check the runtime updates the kernel’s slack, reorders candidates and may admit it or promote it into the tighter-slack set. If the checks pass immediately, there is no mandatory ten-microsecond gap. Delaying every small kernel by ten microseconds would implement a different policy and could miss a useful interval that existed at first check. Delaying the start of a launch also does not suspend its blocks after launch. It changes which other work is likely to be in flight when the kernel is offered to the hardware scheduler. μShare, time-shifted launch and experimental parameters

Tacker pairs Tensor Core and CUDA core work under a foreground deadline

The shape of a block settles only part of the decision. Return to the VGG16 convolution at the beginning of the chapter, this time with a background stencil ready to update an unrelated grid. A convolution implementation can send its matrix multiply-accumulate instructions to Tensor Cores. The stencil reads neighboring grid entries and combines them using ordinary arithmetic. A busy matrix multiplication can therefore coexist with useful scalar instructions. The convolution still needs to form addresses, load tiles, synchronize and write results. The stencil still consumes instruction issue bandwidth, cache capacity and the path to memory. Knowing that one operation uses Tensor Cores is a reason to examine this pair, not sufficient information to predict its joint duration. Tacker, §§III–VI

In the public Tacker implementation there is a concrete mixed entry for the Tensor Core matrix multiplication and stencil. Physical threads zero through 127 enter the matrix branch. They cooperatively stage data and invoke wmma::mma_sync. Physical threads 128 through 255 enter the stencil branch, using an offset of 128 to recover their local worker numbers. The matrix code uses barrier identifier one with 128 participants. The stencil uses identifier two, also with 128 participants. The two identifiers express which threads are intended to wait together. In two independently advancing loops, equal group sizes alone cannot justify sharing an identifier, since an arrival from the wrong branch would not establish that a required tile had been loaded. There is also an ISA constraint here. The current PTX specification gives the legacy bar.sync spelling aligned-barrier semantics and places conditions on its use in conditional control flow. The intended grouping in this historical source does not establish portability to every target. A port must validate the emitted barrier and participation rules for its own architecture. PTX barrier semantics · Mixed entry and its two thread ranges · Matrix and stencil synchronization

HFuse and this Tacker entry both use groups within a block. Their callers seek different outcomes. For the two images, the caller could wait for the last output and compare complete-pair times. Here the next foreground layer depends on the convolution result. If the stencil makes a mixed launch run longer than the foreground convolution alone, the foreground chain may be held up even if the background completed much sooner than it would have under serial execution. The service contract specifies a request latency or deadline, so the scheduler needs an explicit way to decide how much of that additional foreground time it can afford. The chain of required VGG16 layers still comes from the model. The scheduling decision is whether to accompany an eligible step with some other ready work.

Offline fusion and online admission use different information

The Tacker paper generates the code for candidate combinations offline. It transforms eligible kernels to a persistent-block form, considers block setup and resource demand, characterizes the resulting kernel and makes its callable entry available to the runtime. The fixed repository contains the generator and CUDA source for mixed entry points. Its build compiles these sources before the experiment runs. The presence of such an entry establishes that a pair can run together for its supported contract. It says nothing about whether the stencil is ready when a particular request reaches this convolution, or about the amount of time the request has already spent waiting in a queue. Compiling on every foreground launch would make the cost of producing code part of the very latency the scheduler is trying to protect. Selecting a previously built entry is a much smaller and distinct operation. Tacker source generator · Tacker, implementation and evaluation

A useful prediction for a mixed kernel cannot generally be obtained by taking either the maximum or sum of its standalone durations. During the shared portion the components may make progress at different rates from their solo rates. After one component ends, the other can leave a tail that receives none of the intended overlap. Tacker models fused duration using profiling and two-stage linear regression. Its GEMM and FFT example varies the load ratio, the ratio of the standalone durations of the CUDA-core and Tensor-Core work. Past a point, adding more background work primarily extends the tail. The slope in that regime can differ from the slope while most of the new work runs beside the foreground. This model uses prior characterization of the relevant candidates. It does not require reading live utilization counters before each kernel launch.

The runtime has information the offline generator cannot have. If a query arrives at time aaa and its service target is a duration TqosT_{\rm qos}Tqos​, its absolute deadline is a+Tqosa+T_{\rm qos}a+Tqos​. At current time ttt, suppose the predicted remaining foreground work by itself takes RRR. The approximate room for additional interference is H=a+Tqos−t−RH=a+T_{\rm qos}-t-RH=a+Tqos​−t−R. In particular, queueing time already spent has reduced HHH just as surely as GPU time already consumed. With multiple active latency-critical queries, the paper also reserves time for the remaining foreground work of earlier queries. Reusing a schedule that was feasible when no one was queued can therefore be harmful for two requests with exactly the same tensor shapes.

The paper’s rule for one candidate can be checked with arithmetic. Call the solo foreground duration FFF, the solo background duration BBB, and the predicted mixed duration MMM. First, M<F+BM<F+BM<F+B asks whether doing these two pieces together saves device time. Second, M−F<HM-F<HM−F<H asks whether the predicted extra time on the foreground path fits the available headroom. Suppose the two solo durations are 2.0 and 1.5 ms and the candidate is predicted to finish in 2.6 ms. It saves 0.9 ms of combined work and adds 0.6 ms to the foreground path. A headroom of 0.8 ms permits it under both tests. With only 0.3 ms left, the same fused binary and same predicted saving fail the latency test. These numbers illustrate the two strict inequalities in the paper. A machine that merely picks the fastest combined kernel would make the same choice for both requests and lose the distinction that matters to the client. Tacker, Equations 7–9

The runtime can consider several eligible background kernels and compare the predicted work saved among candidates that fit. It can sometimes use spare time to run a standalone background kernel when no suitable mixed candidate exists. The choice concerns ready kernels and a known foreground schedule, not arbitrary substitution of a different layer for a VGG16 layer. Nor does it require an entire GPU schedule to be frozen at request arrival. Known portions could be prebuilt as ordinary execution graphs, but a fixed sequence that always takes the same mixed branch would have no place for a late background arrival or reduced headroom. Preparing the candidate code ahead of time and deferring the admission choice give the system both a predictable code-launch cost and a response to runtime conditions.

What the published scheduler and request measurements establish

The repository’s experimental foreground loop makes the difference between profiling and launch selection easy to inspect. It records standalone foreground durations and makes a suffix sum for the remaining layers. The loop begins its budget accounting at 50 ms, and one branch takes the original foreground kernel when the remaining budget falls below the estimated suffix plus a 4 ms margin. Other branches use eligibility flags for matrix multiplication or convolution and can invoke a prepared mixed implementation. The repository also includes the later Aker mode, with additional rules for choosing a background block quota. The specific constants and branches belong to this revision of the implementation. They illustrate the service decision without serving as universal values for every model or arriving request. Foreground profiling and suffix sum · Runtime choice and bookkeeping

An important reading detail appears after the launch. The code synchronizes and observes a duration, but its model can charge the solo foreground time when a mixed attempt offers no throughput improvement relative to the estimated separate work. That accounting decision does not undo elapsed time. A recorded model budget might therefore look healthy in an individual iteration even if the actual request experienced extra delay. To measure service quality, record when a request arrived and when the dependent result reached its caller. Use the distribution of those intervals to calculate a percentile or the fraction that missed the deadline, and state the offered load. A table of mixed kernel durations or a trace of the budget variable cannot recover those queueing and response intervals after the fact.

In the paper’s principal RTX 2080 Ti study, foreground requests arrived according to a Poisson process at 80 percent of each service’s peak load that met a 50 ms target. Six foreground services and twelve background applications formed 72 pairings. The authors report foreground mean and 99th-percentile latency. Figure 14 reports an average 18.6 percent background throughput improvement over Baymax, with a maximum of 41.1 percent. In Equation 10 the authors call the underlying TTT quantities background processing times and use (TTacker−TBaymax)/TBaymax(T_{\rm Tacker}-T_{\rm Baymax})/T_{\rm Baymax}(TTacker​−TBaymax​)/TBaymax​. The expression is positive when the paper’s background processing time is larger under Tacker. The paper supplies neither a definition of TTT as the completion time of a fixed batch nor a raw count of completed jobs for this figure. Converting the reported percentage to jobs per second would require the completed work and the observation interval. The 18.6 percent value belongs to the authors’ metric and offered workload. RT/BE scheduling in REEF handles work already in flight

Tacker can choose an original or mixed foreground kernel at a launch boundary. Consider a foreground request that arrives while a standalone background kernel is already executing. The scheduler may be able to withhold everything still in its own queues, but the GPU has accepted some work and may already have resident blocks. Even an ideal choice for the foreground’s first kernel cannot erase an interval during which no suitable resources are available to start it. This is a particularly consequential wait for a high-percentile latency objective. A small fraction of requests that happen to arrive behind long background work can move the tail while scarcely changing the mean. REEF addresses both how to make room for arriving real-time (RT) work and how to use remaining capacity for best-effort (BE) work after the foreground has been admitted. REEF, §§3–5

Reset-based preemption depends on safe replay

The full REEF implementation on AMD coordinates work at several stages. Kernels can remain in the host-side submission queue, wait in a device queue or already execute on compute units (CUs). Clearing a host queue stops future dispatch from that queue but leaves the other two stages intact. A buffer management policy can limit how much background work is outstanding beyond the host. It cannot by itself make resident work disappear. REEF’s AMD implementation adds a reset path to remove executing work while preserving device memory, allowing the real-time request to start and the interrupted best-effort kernel to be replayed later. This avoids the cost of saving and restoring a complete running kernel context. It relies on knowing what a partial execution may already have written. REEF, reset-based preemption

For a concrete safe case, give each logical index one output location and let a kernel compute y[i] = f(x[i]) from an unchanged input, using disjoint buffers. Suppose 400 locations have already been written when the kernel is killed. A restart recomputes those 400 values and writes exactly the values that would have been present after one uninterrupted execution. It also completes the previously unwritten locations. This reasoning assumes nobody observes the partial output as a completed tensor and the function has no externally visible side effects. The property required for restart is that after any permitted partial execution, retrying with the available state yields the intended observable result. Looking only at the result of two full executions on freshly reinitialized inputs would miss the important failure mode.

Change the update to atomicAdd(counter, 1) on an existing shared counter. Each individual increment can be perfectly atomic and still be unsafe to replay. If some increments have completed, retrying the kernel adds those contributions a second time. An in-place update that reads the old value it has already overwritten has a similar problem. Random-number state, metadata queues and writes seen by another stream can also be observable effects. An application can sometimes make work replayable by changing its representation or publication protocol, but the claimed safety must hold for the actual input and output state. Idempotence is a semantic requirement for this preemption technique. It does not follow from the fact that a kernel belongs to a neural network or happens to use a particular arithmetic pipeline. REEF, §8 discussion of idempotence

The hardware and driver path matters. REEF evaluated its full reset mechanism on an AMD Instinct MI50 platform with the relevant queue and compute-unit control. Its restricted design for a closed NVIDIA stack, REEF-N, can hold unsubmitted work in virtual host queues, limit outstanding work and evict queued commands through its supported mechanisms. It must still wait for kernels that are already running to complete. Reducing the backlog can substantially shorten the wait even without killing a running kernel. It cannot provide the same bound on the residual duration of a long in-flight kernel as a supported reset. When comparing preemption measurements, the device, the affected pipeline stage and the meaning of “preempted” belong beside the reported time. REEF, §§4.4 and 7.5

Dynamic kernel padding admits a partner before the RT launch

Once REEF has a foreground kernel ready to launch, it uses offline profiles to reserve enough CUs for that foreground work and looks for background blocks to fill the remainder. It selects suitable BE candidates before launching a combined dynamic kernel padding entry. That entry routes blocks to the chosen RT and BE functions according to CU assignment. It does not inject a new function into the middle of an already running RT kernel. This form of composition differs from the HFuse image example even though both can appear as one launch. HFuse partitions warps of one block so the two branches can use the same SM. REEF can assign the foreground and background functions to different CUs in a combined entry, prioritizing the foreground’s allocation.

The selection policy in the paper has two concrete restrictions. A BE candidate’s profiled standalone duration must be shorter than the RT kernel’s duration, because a long-running background tail could delay completion of the combined launch. Its CU occupancy, defined here as the number of blocks that can reside concurrently on one CU, must be higher than the RT kernel’s. The combined launch is subject to its more restrictive residency demand. An accompanying candidate with worse occupancy could reduce the foreground’s ability to run enough blocks. REEF also uses proxy kernels sized to cover ranges of register demand, so that preparing a dynamic combination does not force every launch to reserve the worst possible register budget. Selecting too large a proxy would recreate the same residency problem that register allocation exposed earlier in the chapter. REEF, Figure 9 and §§5.1–5.2

For illustration, suppose that a standalone RT kernel takes 30 time units and permits two resident blocks per CU. A candidate BE kernel taking 20 units with three blocks per CU satisfies these two comparisons. Another taking 40 units with three blocks per CU fails the time condition. One taking 20 units but allowing only one block per CU fails the occupancy condition. These checks narrow the candidates before launch. They do not make all interference disappear. Distinct CUs still use resources such as the memory system, and a measured joint duration can differ from standalone predictions. The published policy is deliberately conservative about the background work it admits because the response required by the RT caller determines the acceptable tail.

Choosing a completion boundary for a fusion or co-location result

Look again at the program from its caller’s point of view. To eliminate a tensor transfer, trace one value beyond the proposed fusion region. If every required consumer can obtain it on chip, a store and a later read may vanish. If a separate branch still requires the full value in global memory, retain the write in the accounting. For independent images, establish who writes each output and verify that the grid covers every requested position. A joint completion event can then show whether the chosen mapping delivers both sooner. Inspecting the actual mix of eligible warps, instruction dependencies and residency constraints explains what sort of work could have filled the interval. It can also explain why a theoretically permissible overlap failed to help.

For a service, follow the same reasoning one boundary farther. The arrival of an RT or latency-critical request starts a clock that includes queueing and any delay behind already submitted work. Its relevant stop event is delivery of the result required by that client. A scheduler can improve complete-pair throughput yet harm that response, or preserve the deadline while completing substantially more BE work. The portable way to demonstrate the latter is to fix the offered foreground load, collect complete response times and deadline misses, and identify the background metric and its denominator. Which kernel to combine, and even whether combination is the right action, follows from that contract. The choice of consumer is what connects an intermediate store, a stalled warp and a request deadline.
