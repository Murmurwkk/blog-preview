When to Retire a Navigation Correction and How to Roll It Back

One translation fixed the early trajectory but damaged the late one. This post discusses how long a navigation correction should stay active, how to detect that it is outdated, and why undoing it requires a fallback that keeps updating.

Suppose a navigation system has accepted a long-lived correction and has kept running since then, with more position observations, more pressure updates and more inertial propagation. Half an hour later, the correction turns out to be wrong and must be undone. What should the system actually do?

The two obvious answers both lose something:

  • Restore the snapshot from before the correction. This throws away every legitimate update since that time.
  • Subtract the original correction vector from the current state. This ignores how the later updates interacted with the corrected state through correlation.

What is really needed is a third object: a fallback posterior that has absorbed every legitimate new observation all along, but without the long-lived model that is now rejected. Undoing then means switching branches, not doing arithmetic on the present state.

One walking log, called the main walk (T33) in this post, shows that this question is practical. A single translation reduced the early error by 10 m and then pushed a good late trajectory 8 m off course. The post first examines this case, states precisely what a correction claims, and works out the three undo strategies on a small Gaussian example. It then shows how the implementation keeps two branches synchronized, what happens when a correction is replaced instead of undone, and why cumulative scores are slow to notice that a correction has become outdated.

The case: a correction that outlived its usefulness

In the main walk, one total translation enters the offline counterfactual scoring from 131.5 s:

teffective=131.5 s,ΔpEN=(−2.705369, 9.976063) m.t_{\mathrm{effective}}=131.5\ \mathrm{s},\qquad \Delta p_{EN}=(-2.705369,\ 9.976063)\ \mathrm{m}.teffective​=131.5 s,ΔpEN​=(−2.705369, 9.976063) m.

“Total” means that the translation replaces the full amount of the current action instead of being added again in every update. Its recorded expiry is 101210^{12}1012 s, so in practice it never expires within the log.

The action was built from observations, and the surveyed reference points were used only for scoring, after the action table was frozen. The action was never applied to the production output. The table below is therefore a counterfactual: it shows what the error would be if this fixed translation were applied to the saved trajectory.

At first, the translation is an almost perfect correction, reducing the error from 10.308 m to 0.201 m. By 217 s, however, the baseline had drifted back on its own to within about one meter of the truth, and the translation that was still active pulled it almost 10 m away.

Over all 10 reference points, including the startup reference, the 75th/90th-percentile error (P75/P90) goes from 8.864/10.265 m for the baseline to 9.619/10.766 m for the counterfactual. Over the last quarter of the route by length (only 3 reference points), the original report shows P75/P90 going from 5.038/5.860 m to 10.887/11.310 m. This boundary of the last quarter comes from the original report, not from an inspection of the errors afterwards.

For comparison, the stairs walk (T25), recorded in the same period, produced no action at all and stayed at P75/P90 1.625/2.567 m. This walk is a useful control, because it shows that the routing rules do not always fire. However, “does not fire without reason” and “exits in time after firing” are two different requirements, and the main walk fails the second.

What a correction actually claims

Let the baseline position be p(t)p(t)p(t) and the action a fixed translation aaa. Within the local segment where the action applies, its claim is

p∗(t)≈p(t)+a.p^{\ast}(t)\approx p(t)+a.p∗(t)≈p(t)+a.

This claim silently asserts that one translation explains the main error of the segment. It does not promise that the inertial error keeps this direction and size forever, or that later WiFi stays in the same position mode.

If the baseline gradually converges toward the true path, as it did in the main walk, keeping the old translation pushes a good trajectory away. Conversely, if the error depends on the direction, or comes from a floor binding or a wrong map component, adding an expiry time alone does not make the model correct. The lifetime of a correction should depend on physical and statistical conditions, not only on elapsed seconds.

In code, the state of the action must therefore cover more than the vector:

ObjectThe question it answers
Model and coordinate identityWhich position hypothesis, which coordinate frame and origin version?
Raw observations usedWhich scans were already used for construction, confirmation or later updates?
Full candidate and fallback state at acceptanceWhich two numerical models were being compared?
Subsequent observation updatesWhat legitimate information was fused after acceptance?
Prediction model for ongoing checksWhat did the model predict before each new observation arrived?
Replacement and exit rulesWhich changes need a new candidate, and which allow undoing?

In the code, an owner represents the current correction model and its full state. The coordinate and source identities decide what is undone, the consumption records decide which observations can still be used afterwards, and the candidate and fallback posteriors decide the actual numbers after the undo.

Three ways to undo, worked out

In a linear-Gaussian model, the differences between the three undo strategies can be computed exactly. Take a 2D state (E,U)(E,U)(E,U). The candidate and the fallback start at the means (10,1)(10,1)(10,1) and (0,0)(0,0)(0,0) with the common covariance

P0=(41.21.21).P_0=\begin{pmatrix}4&1.2\\1.2&1\end{pmatrix}.P0​=(41.2​1.21​).

Both branches then receive two independent observations: first E=2E=2E=2 with RE=1R_E=1RE​=1, then U=0.4U=0.4U=0.4 with RU=0.25R_U=0.25RU​=0.25. (The U observation only imitates the statistical role of a height update; it is not a real barometer model.) Each step is standard conditioning:

K=PH⊤(HPH⊤+R)−1,m+=m+K(z−Hm),P+=P−KHP.K=PH^\top(HPH^\top+R)^{-1},\quad m^+=m+K(z-Hm),\quad P^+=P-KHP.K=PH⊤(HPH⊤+R)−1,m+=m+K(z−Hm),P+=P−KHP.

Because of the correlation, the E observation moves U and the U observation moves E. The gap between the branches started at (10,1)(10,1)(10,1) and is now about (2.349272,−0.363825)(2.349272,-0.363825)(2.349272,−0.363825). The three undo strategies give the following results:

  • Restore the old snapshot: (0,0)(0,0)(0,0). Both new observations are lost.
  • Subtract the old gap from the candidate: (−6.070686,−0.943035)(-6.070686,-0.943035)(−6.070686,−0.943035). This result is far from any reasonable value.
  • Switch to the live fallback: (1.580042,0.420790)(1.580042,0.420790)(1.580042,0.420790). Both observations are kept, and the old correction is removed.

The gap changed for a simple reason. In this example, both branches have the same covariance, the same linear HHH and the same RRR, so they share the same KKK, and the gap propagates as

Δm+=(I−KH)Δm\Delta m^+=(I-KH)\Delta mΔm+=(I−KH)Δm

So every update transforms the gap, and the gap does not stay equal to the starting vector. With different linearization points, models or covariances, KKK itself differs between the branches, and “undo” is even further from a subtraction. If old nodes have been marginalized, removing old information also depends on what joint information was kept during the marginalization (see the post on sliding-window marginalization).

How the implementation keeps two branches alive

In my implementation, a transaction object called NativePosteriorFamilyTransaction keeps both branches and switches between them. Its prepare_rollback simply selects the fallback branch that it has updated all along, and it never reloads an old file from the time of acceptance.

Its test file runs 12 test cases, and all of them pass. The longest test walks through a full sequence on two branches. It commits a pressure reference, applies an EN (east–north position) update, propagates forward and releases an old state, applies the next pressure update, rolls back, and finally applies one more new EN observation. A separate recorded run exported the state after every step:

The count includes only the EN position observations, and pressure has its own index. The retained target moves from native:0.0 to native:0.5 when the older state is released.

Several details show that the semantics are correct:

  • Each branch keeps a 36-dimensional matrix. After the first EN, the trace of the covariance drops from 36.54 to about 32.76047, and this information remains after the old target is released.
  • The rollback leaves the numerical bridge identity of the fallback unchanged, keeps the pressure index at 1 and does not disturb the existing C scoring contexts.
  • Updates are transactional. Each update is prepared on each separate full view, and only if every branch succeeds are the global consumption records written and the new family adopted. The tests cover stale contexts, modified pending objects, a failure to prepare one branch, and an observation already consumed elsewhere. So it is impossible to update the branch that succeeded while the other branch stays at an old state.
  • Consuming the same raw EN twice is rejected. A covariance query across branches is also rejected when the branches are separate local noise coordinates without a common-source representation, because keeping two candidates does not mean that their joint noise model is built correctly.

Replacing a correction: when the reference component changes

Undoing is not the only way a correction ends; a successor can also replace it. The main walk contains one change of reference component that connects replacement, source consumption and the budget for repeated attempts.

The old candidate was built from observations at 171.5 and 174.0 s (its A and B segments, in the sense of the post on held-out prediction), and all of them came from one reference component. At 195.5 s, an observation from a different component arrived. The corrected rule first retires the old candidate, without letting it consume the incompatible new data. Only after that can the still unclaimed observation at 195.5 s start a new candidate, with 198.0 s as its second segment.

The new candidate gets

anew=(−0.216514, 3.500225) m,R=0.890372I m2.a_{\mathrm{new}}=(-0.216514,\ 3.500225)\ \mathrm m, \qquad R=0.890372I\ \mathrm m^2.anew​=(−0.216514, 3.500225) m,R=0.890372I m2.

Two new test observations at 200.0 and 202.5 s give a cumulative score of 9.106831 in favor of applying the correction instead of applying none. The bound for the 6th candidate of this run is 9.274176, so the score falls short by 0.167345. The decision therefore stays deferred, and the candidate is retired later, when yet another component appears at 210.0 s.

It is tempting to reset the candidate index to 2, because the bound would then drop to 7.076952, and this score would easily exceed it. But such a reset changes how the whole run spends its risk budget for repeated attempts. Fixing the data routing does not erase the attempts that were already made, and a new candidate that looks useful does not earn a looser budget.

This implementation also assigns each scan one final attribution. A scan that served as the C of one candidate is therefore not reassigned to the A/B of another candidate. This single-use routing rule keeps the observation ledger unambiguous; a procedure that reuses past data to construct later candidates would need an explicit conditional model and evidence accounting. (The division of construction, confirmation and availability is covered in A/B/C and frozen prediction.)

The saved structural checks show that in the main walk, each of the 55 observation blocks and 1,521 raw events completed exactly one final attribution, with 5 reprocessings after component changes; the stairs walk has 16 blocks, 725 events and 2 reprocessings. So the routing bookkeeping is now consistent. This result is a separate question from whether the scores are well calibrated on natural logs, and the bookkeeping fix does not undo the damage in the late segment of the error table above.

When to undo: cumulative scores remember old wins

Knowing how to undo is half of the problem; the other half is noticing when to undo. The common approach is to keep accumulating, after acceptance, the predictive log-likelihood ratio between the fallback and the current action:

Ln=∑i=1nlog⁡p(zi∣Mrollback,Fi−1)p(zi∣Mkeep,Fi−1).L_n=\sum_{i=1}^{n} \log\frac{p(z_i\mid M_{\mathrm{rollback}},\mathcal F_{i-1})} {p(z_i\mid M_{\mathrm{keep}},\mathcal F_{i-1})}.Ln​=i=1∑n​logp(zi​∣Mkeep​,Fi−1​)p(zi​∣Mrollback​,Fi−1​)​.

The correction is undone once LnL_nLn​ is large enough. The problem is memory. If the action was genuinely good early on, the sum has built up a large negative balance, and when the action becomes bad later, the monitor must first use up this “old advantage”. So this statistic really answers the question “which fixed model has done better since the beginning?”, not the question “has the current model just stopped working?”

An older historical report with three models actually recorded this effect. Its cumulative log score for keeping the original model instead of the correction was about −900 before the late change and still about −707.486 at the end, so it never crossed its upper bound of 3.483382. That report used a slightly different action vector, and its step-by-step inputs were not kept, so it cannot be rerun; it illustrates the effect but does not measure it.

To isolate the mechanism, I built a small reproducible example. The first 225 observations are drawn from N(0,1)\mathcal N(0,1)N(0,1) and the next 100 from N(2,1)\mathcal N(2,1)N(2,1), with the fixed seed 17. When two distributions fixed in advance are compared, the log likelihood ratio of each step is

ℓt=log⁡ϕ(yt−2)ϕ(yt)=2yt−2.\ell_t=\log\frac{\phi(y_t-2)}{\phi(y_t)}=2y_t-2.ℓt​=logϕ(yt​)ϕ(yt​−2)​=2yt​−2.

When the sum starts from the first sample, the expected step is −2 before the change and +2 after it. With a post-change segment of finite length, the running sum may never return above zero.

The change happens after sample 225, so the last two methods need 4 and 11 observations after the change. These values come from one constructed sequence, not from an average detection delay.

Resetting looks fastest, but the error probability of a single test does not apply to it, because every new starting point gives the algorithm another chance to fire. In this example with known distributions, weights can be assigned in advance to a start at τ\tauτ,

wτ=1τ(τ+1),∑τ=1∞wτ=1,w_\tau=\frac1{\tau(\tau+1)},\qquad \sum_{\tau=1}^{\infty}w_\tau=1,wτ​=τ(τ+1)1​,τ=1∑∞​wτ​=1,

and the following statistic can be formed:

Mt=∑τ=1twτexp⁡(∑i=τtℓi).M_t=\sum_{\tau=1}^{t}w_\tau \exp\left(\sum_{i=\tau}^{t}\ell_i\right).Mt​=τ=1∑t​wτ​exp(i=τ∑t​ℓi​).

Under the fixed Gaussian null hypothesis, the likelihood ratio of each start has the required property of the conditional expectation. For rigorous crossing control that is valid at any time, the weight of the starts that have not begun yet must be added:

Since Mt≤M~tM_t\leq\widetilde M_tMt​≤Mt​, the same threshold on MtM_tMt​ is still controlled by the corresponding bound. A new start does not have to repay all the old negative score, but it carries only its own small weight, so the delay is not free.

📝 Further reading: PITMonitor uses a similar start-point mixture to monitor distribution shifts in probability integral transforms. It assumes stable, independent PIT values and is evaluated on synthetic regression streams, so using it for navigation would need its own checks (paper, §3.1, §4.2–4.3, §5–6).

Before such a method can be used in navigation, the observations, the conditional predictions, the correlations and the candidate selection must meet its assumptions, because the guarantee against false alarms comes from these assumptions, not from the formula alone.

How fair is the fallback comparison?

With a live fallback branch, it is tempting to read the difference between the branches as “the effect of the correction”. NativeOwnerEffectRecorder does record this difference, after it checks that both branches refer to the same physical time, target, coordinate frame and gauge epoch. The source code, however, carefully calls this difference “the actual fallback policy that keeps later local updates” and notes that it is not an unconditional causal effect.

The reason is that the set of observations absorbed by the counterfactual fallback may itself depend on decisions made in the actual run. Under a different long-lived model, the later candidates, the observation routing and the map choices might all have changed. So the comparison of the two branches answers how the two state interpretations differ, given the update policy and the data history that actually happened. It cannot show what a different complete system would have produced from the beginning.

To show that a rollback strategy improves navigation, a comparable run protocol is necessary. Such a protocol saves the actual availability times, freezes the candidates and the undo rules, and compares complete continuous runs at the same reference times. It also records whether and when actions were executed, whether the fallback stayed current and how many replacements occurred, instead of reporting the error right after one successful switch.

Conclusion

A correction makes a claim, namely that one transform explains the current error, and this claim has a lifetime that should depend on conditions, not on a clock. Noticing that the claim is outdated is a monitoring problem, and cumulative scores are slow at this task because they remember old wins. Undoing the correction is a state problem: once later observations have been fused, the right way to undo is to switch to a fallback posterior that kept absorbing them, not to restore or subtract. Replacing a correction has its own rules: the old candidate must be retired before the new data is used, and the risk budget must not be reset.

Monitoring and state are separate requirements, and both must hold. When this chain runs end to end on a natural log, it should record the lifetimes of the actions, the replacement times, the monitoring delay and every reference point that can be scored, together with controls without actions such as the stairs walk.

Undoing a correction is not going back in time; it is choosing the version of the present that never believed the correction.

Appendix: historical records and recomputation

There are several similar but different historical action tables. The main table uses the saved results of 20260901-v18-phase1-frozen-association-greedy-r1. That version freezes the position reference component used by A/B, retires the old candidate when the component identity changes, and hands unconsumed new observations to the next candidate. It produced only the single T33 total translation discussed above.

Recomputation entry points in the working repository:

py -3.13 bench_mur/navigation/owner_rollback_evidence.py
py -3.13 bench_mur/navigation/owner_rollback_evidence.py --source-root O:/IPIN --component

The first reads only locally saved evidence, re-aggregates errors and generates the constructed experiments and figures. The second reads the historical store read-only, additionally runs the current component tests and records hashes of the imported source, writing test output into the working repository. Evidence is in rep_mur/blog-rewrite/navigation/owner-rollback/, with historical reports, current components and constructed computations stored separately. No new natural navigation replay was run, and none of these actions were executed on production output.
