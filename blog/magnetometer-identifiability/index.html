Why Magnetometer Calibration Cannot Determine Heading by Itself

Ellipsoid calibration fixes the length of each reading, so any rotation of a valid calibration fits equally well. This post explains this rotation freedom, shows when planar motion removes heading information and describes a real column-order bug in the logs.

The standard procedure for magnetometer calibration is as follows. The user waves the phone around and collects readings, and the software fits an ellipsoid and then removes the offset and the direction-dependent stretch, so that in a constant field every reading lies on the same sphere. When the residuals reach zero, the magnetometer is considered calibrated.

This condition, however, constrains only the length of each vector. It says nothing about how the sphere is oriented relative to the axes of the device. If CCC is a calibration matrix that satisfies the condition, then QCQCQC for any rotation QQQ gives exactly the same residuals, so ellipsoid fitting has a built-in rotational degree of freedom. Even if the data covers the entire sphere and the fit error drops to floating-point precision, the magnitudes still cannot show which direction is correct.

This problem is different from having too few samples, and it is also different from reading the file incorrectly. This post separates all three problems. It first splits “calibration” into the three questions that the word usually combines, derives the rotation freedom, demonstrates it on constructed data, and shows what planar motion does to the fit. It then discusses which extra information determines the axes and the absolute yaw. The last part describes two implementation bugs found in the historical pipeline, one of which affected how real MAGU log lines were parsed.

Three questions people lump together

Let RWDR_{WD}RWD​ rotate vectors from the device frame into the world frame. A convenient model is

y=ARWDTmW(p,t)+b+ϵ.y=A R_{WD}^{T}m_W(p,t)+b+\epsilon.y=ARWDT​mW​(p,t)+b+ϵ.

Here mWm_WmW​ is the magnetic field in the world frame and depends on position and time; bbb is an additive bias; and AAA combines scale, non-orthogonality, linear distortion and the relationships between the axes. The model holds only within its valid range, because changes in the device state, moving accessories or changes in the environment can all invalidate a fixed A,bA,bA,b.

“Calibrating the magnetometer” can mean three different things:

  1. Magnitude and shape. After the bias and the direction-dependent stretch are removed, readings in a constant field should lie near a sphere.
  2. Alignment between sensor axes and device axes. Is a vector on that sphere expressed in the same device frame that the gyroscope and the accelerometer use?
  3. Orientation of the device relative to the world. How is the device frame related to the chosen world reference? In addition, “magnetic north”, “geographic north” and “the x-axis of the indoor map” are three different references.

Solving the first problem does not solve the other two. Even a known axis alignment under one fixed mounting does not guarantee that the same field model still holds in an environment with magnetic disturbances.

Fundamentals: magnitude fixes the quadratic form, not the direction

Assume a locally constant field, normalized to length 1. Write y=Au+by=Au+by=Au+b with ∥u∥=1\|u\|=1∥u∥=1 and an invertible AAA. Then

(y−b)TH(y−b)=1,H=A−TA−1.(y-b)^T H(y-b)=1, \qquad H=A^{-T}A^{-1}.(y−b)TH(y−b)=1,H=A−TA−1.

Fitting an ellipsoid estimates the center bbb and the symmetric positive-definite matrix HHH. Choose any CCC with CTC=HC^TC=HCTC=H. Then, for every rotation QQQ,

∥QC(y−b)∥2=(y−b)TCTQTQC(y−b)=(y−b)TH(y−b).\|QC(y-b)\|^2 =(y-b)^TC^TQ^TQC(y-b) =(y-b)^TH(y-b).∥QC(y−b)∥2=(y−b)TCTQTQC(y−b)=(y−b)TH(y−b).

So CCC and QCQCQC explain every magnitude observation in exactly the same way. Requiring a positive determinant rules out reflections, but it still leaves the full 3D rotation free. Choosing the symmetric square root C=H1/2C=H^{1/2}C=H1/2 is a unique numerical convention, but a unique convention is not a unique physical relationship between the axes.

The polar decomposition makes this point even clearer. For an AAA that preserves handedness, write A=SUA=SUA=SU, with SSS symmetric positive definite and UUU a rotation. Then H=S−2H=S^{-2}H=S−2, symmetric whitening gives C=S−1C=S^{-1}C=S−1, and

C(y−b)=S−1SUu=Uu.C(y-b)=S^{-1}SUu=Uu.C(y−b)=S−1SUu=Uu.

The stretch is removed, but the unknown rotation UUU remains completely unchanged. So the magnitude residuals can approach zero while the direction of every vector is systematically wrong by UUU.

If the true field strength is also unknown, the absolute scale is one more convention, because the unit sphere is only a normalization and cannot recover a scale in µT. If the field strength varies along an indoor route, the assumption that all points come from one ellipsoid must be checked again: absorbing the field variation into AAA can produce a very good fit and destroy the physical interpretation at the same time.

Seeing it: three equally good calibrations

The following experiment shows this freedom directly. The constructed data uses 1000 Fibonacci sphere directions, without noise and without units, transformed by A=SRz(35∘)A=S R_z(35^\circ)A=SRz​(35∘) with

S=[1.40.20.10.20.8−0.050.1−0.051.1],b=[0.4−0.250.2].S=\begin{bmatrix} 1.4&0.2&0.1\\ 0.2&0.8&-0.05\\ 0.1&-0.05&1.1 \end{bmatrix}, \qquad b=\begin{bmatrix}0.4\\-0.25\\0.2\end{bmatrix}.S=​1.40.20.1​0.20.8−0.05​0.1−0.051.1​​,b=​0.4−0.250.2​​.

The fitting code sees only the transformed yyy. It subtracts the mean of the point set, solves an algebraic least-squares problem over nine quadratic, cross and linear terms, recovers the center and the quadratic form, and takes the positive-definite square root. The true uuu is used only afterwards to measure the error, never as supervision.

The fitted center is about (0.4,−0.25,0.2)(0.4,-0.25,0.2)(0.4,−0.25,0.2). The experiment then takes this single fitted result, multiplies it from the left by three different rotations, and evaluates all 1000 points again:

Then left-multiply by Rz(25∘)R_z(25^\circ)Rz​(25∘)2.22×10−152.22\times10^{-15}2.22×10−1560°
Then left-multiply by Rz(−35∘)R_z(-35^\circ)Rz​(−35∘)2.22×10−152.22\times10^{-15}2.22×10−15about 0°

The three calibrations have identical magnitude residuals, but their directions differ by up to 60°. The last row uses the constructed ground truth, so it shows only that the correct direction is one of the equivalent solutions, not that the algorithm found it, and no magnitude metric could select it. The direction error here is the angle of the horizontal projection of the field vector; it is not the heading error of the device after tilt compensation and frame verification.

When excitation is planar

The rotation freedom exists even with perfect data, and poor excitation adds a second, separate problem. A second construction also has 1000 points, but all true vectors lie on one horizontal circle, and the same A,bA,bA,b are applied. An SVD of the centered design matrix with nine columns gives a numerical rank of 9 for input that covers the full sphere and 5 for planar input. In the planar case, the sixth singular value is about 5.13×10−155.13\times10^{-15}5.13×10−15, compared with a largest value of 65.42, so it is floating-point noise.

The cause is not that 1000 points are too few. More points in the same plane cannot provide the missing third dimension of excitation. Noise can turn exact zero singular values into small positive values, but such values do not form a reliable constraint. Regularizing the inverse keeps the arithmetic running, but the direction that the regularizer chooses should be labeled as prior knowledge, not counted as information from the data.

What it takes to determine direction

If magnitudes cannot determine direction, other information must do it, and the kind of information depends on which of the three questions is being asked.

Axis alignment: inertial data

Kok and Schön’s Magnetometer calibration using inertial sensors (IEEE Sensors Journal, 2016, 16(14):5679–5689) uses inertial data for axis alignment and for an offline maximum-likelihood calibration, and it uses ellipsoid fitting only for initialization. Their experiments require slow rotations and use relative 90° turns of a rectangular block for validation; such turns are not an absolute geographic heading reference (paper v3 and experiments).

The general rule is as follows. Residuals on the unit sphere check the shape of the observations. Checking the axis alignment requires motion constraints that agree with an inertial reference. Checking the absolute orientation of the device requires a direction reference that does not take its answer from the magnetometer under test. If both training and checking come from one magnetometer fit, no residual is small enough to replace this last reference.

Absolute yaw: you need a horizontal reference

Even when AAA and bbb are known perfectly, a second freedom exists at the world level. For any rotation GGG about the vertical axis of the world, set

RWD′=GRWD,mW′=GmW.R'_{WD}=G R_{WD},\qquad m'_W=Gm_W.RWD′​=GRWD​,mW′​=GmW​.

Then RWD′TmW′=RWDTmWR_{WD}'^{T}m'_W=R_{WD}^{T}m_WRWD′T​mW′​=RWDT​mW​, so the magnetic reading does not change, and gravity does not change either. In a model without a known horizontal reference, the absolute yaw of the device and the horizontal orientation of the field therefore cannot be determined separately.

Gyroscopes provide relative rotation. They constrain the change of attitude over time and the relationships between the sensor axes, but integrating them does not produce geographic north. Defining some magnetic direction as the x-axis of the world is a choice of convention, and proving that this axis is the x-axis of the building map requires an external direction relationship. The walking direction is not the yaw of the device either, because a person walking in a straight line can hold the phone sideways or rotate it.

How much a magnetometer tells you about yaw

Now assume much stronger conditions: the local field vector is known, the tilt of the device relative to gravity (roll and pitch) is known, only a small yaw perturbation remains, and each axis has independent zero-mean Gaussian noise with variance σ2\sigma^2σ2. With eze_zez​ as the vertical unit vector in the device frame and uuu as the predicted field in the device frame, the local Jacobian and the Fisher information are

Hψ=−ez×u,Iψ=HψT(σ2I)−1Hψ=∥uh∥2σ2.H_\psi=-e_z\times u, \qquad \mathcal I_\psi =H_\psi^T(\sigma^2I)^{-1}H_\psi =\frac{\|u_h\|^2}{\sigma^2}.Hψ​=−ez​×u,Iψ​=HψT​(σ2I)−1Hψ​=σ2∥uh​∥2​.

The sign depends on the rotation convention, but the information does not. Only the horizontal component uhu_huh​ appears in the result. However strong the field is, if it is nearly vertical, small yaw changes hardly affect the reading, and when the horizontal component is zero, the yaw information is exactly zero.

The right panel of Figure 3 uses a demonstration value of σ=1\sigma=1σ=1 µT. Horizontal components of 5 and 20 µT give information of 25 and 400 rad⁻². Under the usual regularity conditions, the Cramér–Rao bound on the variance of a local unbiased estimator from a single sample is 1/Iψ1/\mathcal I_\psi1/Iψ​, so the lower bounds on the standard deviation are about 11.46° and 2.86°. These values are theoretical bounds under this model, not measurements from real phones. They also assume a known field, so they do not address the problem of the unknown field from the previous section.

If the frames share calibration error or environmental change, the information does not simply grow with the number of samples. Correlated error belongs in the joint covariance, the same issue that the post on how common-source observations update the state discusses.

Short-window dynamics

Short-term dynamics can also add constraints, but only if the environmental change is modeled. For a debiased and axis-aligned vector u=RTm(p,t)u=R^Tm(p,t)u=RTm(p,t),

u˙=−ωD×u+RT∇m p˙+RT∂m∂t.\dot u=-\omega_D\times u +R^T\nabla m\,\dot p +R^T\frac{\partial m}{\partial t}.u˙=−ωD​×u+RT∇mp˙​+RT∂t∂m​.

The field vector can change because the device rotates, because the device moves through a spatial gradient, or because the field itself changes over time. If the residual r=u˙+ωgyro×ur=\dot u+\omega_{gyro}\times ur=u˙+ωgyro​×u is built, it contains the gyro bias and the last two terms, and without constraints on the local stability of the field, these explanations can replace each other.

A fixed additive bias cancels in a plain difference, but inserting the raw y=u+by=u+by=u+b into the whole residual leaves an ωgyro×b\omega_{gyro}\times bωgyro​×b term. Differencing each sample also amplifies high-frequency noise. So “we used differences” does not remove the need to check the bias and the axes, and the mixed residual is not pure gyro error.

Attitude invariants also have limits. When the calibration and gravity are reliable, the magnitude, the vertical projection and the horizontal magnitude are good checks of field consistency. These invariants, however, do not respond to pure yaw, and for exactly this reason they cannot recover yaw. Passing a consistency check means that a hypothesis survives, not that the other explanations are excluded.

In summary, magnitude fitting recovers the quadratic form of the ellipsoid, inertial motion constraints connect the sensor axes one step further, and absolute heading needs a known horizontal reference. The three goals need three kinds of information, so one plot of unit-sphere residuals cannot confirm all three.

Two implementation bugs worth knowing about

The rest of the post concerns the historical pipeline, in which two concrete bugs appeared.

The constant term after shifting an ellipsoid

An older calibration report on 72 logs recorded an error in recovering the constant term of the ellipsoid. This post recomputes the algebraic counterexample from that report.

In coordinates xxx from which the fitting origin has already been subtracted, the fit is

xTQx+2vTx=1,c=−Q−1v.x^TQx+2v^Tx=1, \qquad c=-Q^{-1}v.xTQx+2vTx=1,c=−Q−1v.

Completing the square should give

(x−c)TQ(x−c)=1−vTc.(x-c)^TQ(x-c)=1-v^Tc.(x−c)TQ(x−c)=1−vTc.

Here ccc must still be in the local fitting coordinates, because a center that has already been mapped back to the raw coordinates cannot be inserted into this constant. Take (x−1)2=4(x-1)^2=4(x−1)2=4, written as x2/3−2x/3=1x^2/3-2x/3=1x2/3−2x/3=1. Then Q=1/3Q=1/3Q=1/3, v=−1/3v=-1/3v=−1/3 and c=1c=1c=1, and the correct right-hand side is 4/34/34/3, so the recovered radius is 2. If the sign is flipped to 1+vTc1+v^Tc1+vTc, the recovered radius becomes 2\sqrt{2}2​.

So one sign changes the recovered scale, even though the quadratic fit itself did not fail. The fitting code explicitly checks the rank, the positive definiteness, the recovered center and the error, but it is an implementation for a noise-free counterexample, not a production calibrator for natural data.

MAGU’s interleaved columns

The field semantics were checked on the IPIN training log Trial21 / session01 / SG24, after the full SHA-256 of the raw file was verified. The two kinds of magnetometer lines in this file have different field orders:

MAGN;AppTimestamp;SensorTimestamp;Mag_X;Mag_Y;Mag_Z;Accuracy
MAGU;AppTimestamp;SensorTimestamp;Mag_X;bias_X;Mag_Y;bias_Y;Mag_Z;bias_Z;Accuracy

MAGU interleaves the field and the bias for each axis. For an array p split at semicolons, with p[0] holding the record type, the correct read is:

field = np.array([float(p[3]), float(p[5]), float(p[7])])
bias  = np.array([float(p[4]), float(p[6]), float(p[8])])
device_debiased = field - bias

The same report says that an even earlier analysis read the MAGU field as p[3:6] and the bias as p[6:9]. This is the natural guess for anyone who assumes the layout of MAGN. The formula described in the report was reproduced on the raw lines. The module src/ipin/frontends/magnetic/raw.py in the current repository handles MAGN, so this historical problem does not affect that module.

Line 61780 of the raw log gives an arithmetic counterexample that does not depend on any model. The values are in µT:

The Android API and the on-disk format are easy to confuse here. The official interface for the uncalibrated magnetometer puts the three field values and the three biases in separate array positions, while this capture app chose to interleave them for each axis, so a file reader must follow the header of the file itself. The official documentation also notes that “uncalibrated” does not mean unprocessed: the output may still include factory calibration and temperature compensation, and the regular magnetic field output is roughly the uncalibrated field minus the estimated bias (Android: Position sensors).

Checking all of the first 256 lines, not just one

To avoid choosing only a favorable line, I took the first 256 MAGU lines in the file (AppTimestamp 0.024–5.114 s), and for each line I found the MAGN line with exactly the same SensorTimestamp. All 256 lines matched, without nearest-neighbor pairing, interpolation or time shifting.

Both streams come from the same device and may share the same calibration, so they are not two independent instruments, and the small differences between them are not the noise level of the magnetometer.

The timestamps need the same care. Lines 61780 and 61786 have SensorTimestamps of 25950.082 and 25950.102 s, but their values in all six field and bias columns are identical, so different timestamps do not always mean different values. Two lines, however, cannot show whether the cause is sample-and-hold, quantization or a stable input. A de-duplication rule should therefore not be built on them, because deleting real samples that happen to share values would also change the noise statistics.

Conclusion

“Magnetometer calibration” consists of three problems: magnitude and shape, the axes from sensor to device, and the orientation from device to world. Ellipsoid fitting solves only the first problem, and it provably leaves a rotation free; planar motion removes even part of the first problem. The axes need inertial constraints, the absolute yaw needs an independent horizontal reference, and the amount of yaw information depends on the horizontal field strength. Below all of these issues, a parser that assumes the wrong column order can create a field anomaly out of nothing.

A perfect sphere shows the length of every vector and nothing about the direction of any of them.

Appendix: missing natural data and how to reproduce

📝 Note: Paths in this appendix such as bench_mur/ and rep_mur/ are in my private research repository, so they aren’t public; they’re listed so each result can be traced.

The surviving historical qualification file concludes ABSTAIN. It records missing evidence for a certified device-to-magnetometer-axis rotation, an independent device yaw reference, a calibration validity interval, and strict three-axis magnetic maps with time-validity evidence. It also lists engineering gaps such as map position support and common-source covariance. That’s the historical file’s conclusion; the qualification wasn’t rerun.

The T152 report also describes a 72-log, 316-revisit magnitude comparison. Its per-log outputs, full pairing records and execution scripts weren’t recovered, so its improvement numbers aren’t carried over, and the constructed spheres here don’t substitute for that experiment. Evaluating real gains would need those historical identities plus an independent direction reference. Similar magnitudes on repeated visits to one place support repeatable field features, but they don’t certify device heading.

The recomputation script is bench_mur/navigation/rebuild_magnetometer_article.py, with instructions in MAGNETOMETER_README.md in the same directory. From the working repository root:

D:/python/python.exe bench_mur/navigation/rebuild_magnetometer_article.py

Environment: Python 3.13.5, NumPy 2.4.4, Matplotlib 3.11.0. The raw log’s SHA-256 is 02afc8292a2985356ed7f936b7bb9d902dc9f6a60a8a9df1e9d8907916fbceb8.

rep_mur/blog-rewrite/magnetometer/ holds source identities, a minimal snapshot, result JSON and the constructed point sets. The snapshot keeps only magnetometer headers and selected records, with no WiFi identifiers, geographic coordinates or full trajectories. The first capture checks the raw file’s SHA; later runs read only the local snapshot and check its hashes, without touching the raw data drive. SHAs of the historical report and the current read-only module are recorded separately, and old code commits mentioned in the report aren’t treated as this round’s code.

The base figures are generated directly by the script and marked as real log, constructed data or conditional theory. The direction-gauge figure comes from bench_mur/editorial/style-v2/navigation_figures.py; it illustrates the rotation equivalence class and adds no natural heading validation.
