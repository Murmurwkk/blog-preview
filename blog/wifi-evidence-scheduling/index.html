Sharing One WiFi Observation Between Two Navigation Estimators

When the heading estimator chose WiFi fixes first, the position filter accepted 7 fixes instead of 42, and the heading estimator never produced a correction. Shared evidence needs ownership rules, not just an order.

Our indoor navigation system has one WiFi positioning provider and two parts of the estimator that use its output. The position filter takes each WiFi fix when it arrives, checks it against the current prediction and, if the fix fits, adds a position constraint. The heading estimator collects a stretch of walking and several WiFi fixes, fits how the whole trajectory should be rotated, and only then decides whether to correct the heading.

The heading estimator needs time to collect enough evidence, while the position filter uses every fix it can get. So we tried a change that sounded reasonable: the heading estimator would choose first from each fix, and the position filter would receive only the fixes that the heading estimator did not take.

On the first walk we tested, the WiFi provider produced the same 90 fixes as always. The position filter, however, accepted 7 of them instead of 42, and its first accepted fix came at 233.5 s instead of 85.0 s. The change was meant to help the heading estimator, but the heading estimator never issued a single heading correction. Reverting the order brought back exactly the old results. A later version went to the opposite extreme: once the position filter had committed a fix, the heading estimator stopped working completely.

Both failures are wrong answers to one design question, and this question is the subject of the post: once one consumer has reserved or used an observation, when may another consumer still use it?

The post goes through the three versions in order and uses a small toy filter to reproduce the first failure. It then examines what goes wrong statistically when both consumers simply share every observation, and it describes the bookkeeping that would make sharing safe.

Two consumers, one stream of fixes

A WiFi fix passes through several stages before it changes the state, and each consumer has its own stages:

  • Position filter: routed to it → gated against the prediction → accepted → committed to the graph.
  • Heading estimator: routed to it → used to build a rotation hypothesis → used to confirm it → authorized → applied.

Any stage can stop a fix. So two runs with the same 90 fixes can end with very different numbers of constraints in the graph, and counts from different stages cannot be compared directly: “56 fixes reached the position gate” and “7 fixes were accepted” do not contradict each other.

The gate is the standard one. A fix ztz_tzt​ with noise covariance RtR_tRt​ is compared with the predicted state x^t−\hat x_t^-x^t−​:

νt=zt−Htx^t−,St=HtPt−HtT+Rt,dt2=νtTSt−1νt.\nu_t=z_t-H_t\hat x_t^-,\qquad S_t=H_tP_t^-H_t^T+R_t,\qquad d_t^2=\nu_t^TS_t^{-1}\nu_t .νt​=zt​−Ht​x^t−​,St​=Ht​Pt−​HtT​+Rt​,dt2​=νtT​St−1​νt​.

The position filter accepts the fix when the normalized innovation squared (NIS) dt2d_t^2dt2​ is at most 9.21, the 99% chi-square threshold for a 2D Gaussian innovation. Note what the gate compares against: the current prediction, not the truth. This detail drives everything in the next section.

Why losing early fixes costs more than the fixes themselves

The numbers do not add up in the expected way. On walk A, the heading estimator took 34 fixes and the accepted position fixes fell by 35, while on walk B it also took 34 fixes but the accepted fixes fell by only 18. Even the rejections changed: under heading-first, walk A had 49 rejections instead of 48, although 34 fewer fixes reached the gate.

The early fixes explain these numbers. On walk A, the fix at 85.0 s had an NIS of 7.085, well inside the gate, and heading-first routed it away. On walk B, the fix at 76.0 s, with an NIS of 6.260, was routed away in the same way. Without these early corrections, the prediction x^t−\hat x_t^-x^t−​ drifts further from the truth, so the next fix can be identical bit for bit and still fail the gate, because its innovation is now measured against a worse prediction.

A 1D toy model shows this feedback. The truth and every observation are 0, but the motion model of the filter pushes the prediction forward by 0.8 per step. The initial variance is 0.25, the process variance is 0.1 per step, the observation variance is 1, and the gate stays at 9.21. (In 1D this number has no chi-square meaning; it is only the same threshold.) The observations contain no noise, so each run is deterministic.

Two rules are compared over 20 steps. The first rule checks position in every step. The second rule reserves the first 6 steps for a heading estimator that never delivers a result, and only then lets the position checks resume.

When the second rule opens the gate at step 7, the NIS is already 16.08, and the gate rejects every later observation, so six withheld observations turn into twenty lost ones. The first rule still ends 2.16 away from the truth, because its motion model is wrong; checking every fix does not repair a bad model.

The toy model does not reproduce the map, the optimizer or the noise of walk A, and it cannot divide the error of walk A among its causes. It does show that the mechanism exists: the same fixes and the same threshold do not guarantee the same acceptances, because the reference point of the gate depends on which fixes came before.

On walk A, heading-first is as bad overall as not using WiFi at all. Its few late fixes reduced the error in the tail to about 9.6 m, but the early reference points had already been scored, and a late correction cannot revise positions that were already reported. Walk B is milder: heading-first is worse than position only but still better than no WiFi, and its tail is even slightly better.

Walk A alone would suggest the conclusion “heading-first breaks positioning”. The two walks together support a narrower conclusion. If a slow consumer is placed in front of a fast consumer on the same provider, the change can break timing that the fast consumer depended on, and the size of the damage depends on the trajectory and on which fixes come later.

Version 2: position-first restores the old behavior, failures included

The fix put the position filter back in first place. The position filter gates every fix with its original NIS, and only the fixes that it rejects go to the heading estimator. When the position filter accepts a fix, any heading correction in the same window that has not been applied yet is cancelled.

This change restored the old outputs exactly. Across four walks (581, 416, 1,085 and 896 output rows), the position-first and position-only trajectories differ by at most about 1.2×10−71.2\times10^{-7}1.2×10−7 m, and the floor sequences are identical.

Exactly the old behavior, however, also means exactly the old failures. On a harder walk, both runs accepted only 9 position fixes, the first at 415.0 s, and the error at the last reference point rose from 12.3 m without WiFi to 29.6 m with WiFi. Restoring the order removed the regression, but it did not fix the walks that the position filter had never handled well.

This fix is narrow. “The position filter sees each fix first” is one decision, while “the heading estimator is blocked for the rest of the walk” is a much broader decision, and the next version made exactly this mistake.

Version 3: position locks out heading

The next version changed how the heading estimator built and confirmed its hypotheses. Under this version, the heading estimator stopped working once the position filter had committed a fix. On a long, difficult walk, the provider produced 194 fixes, and 25 of them became position constraints. After the position filter committed, the heading estimator took zero further steps: no hypothesis, no confirmation and no correction.

The overall error became worse than without WiFi: P75 / P90 rose from 76.3 / 103.6 m to 93.3 / 120.8 m. This result is the mirror image of version 1, because the position filter received its early fixes, while the slow path that could have recovered the heading never got another chance.

Two cautions apply to this result. First, this version changed the strategy of the heading estimator together with the priority behavior, and no ablation separated the two changes, so not all of the regression comes from the lock-out. Second, the error at the last reference point improved, from 6.7 m to 2.5 m. By choosing whichever metric looks best, the endpoint, the tail or the overall score, one could tell opposite success stories about the same run.

So priority needs a scope: one transaction, one stage that can be undone, or a state condition that can be justified statistically. Shutting a consumer out permanently is a modeling decision, and this decision needs its own test of whether recovery is still possible.

The tempting fix: let both consumers see everything

If reserving fixes starves one consumer and locking out starves the other, a natural idea is to give every fix to both consumers. Computationally, two readers of the same data cause no problem. Statistically, however, the path of the information must be followed.

The simplest case shows why. The prior is x∼N(0,4)x\sim\mathcal N(0,4)x∼N(0,4), and one measurement z=2z=2z=2 has noise variance 1. Using the measurement once gives:

P+=(14+1)−1=0.8,x^+=0.8×2=1.6.P^+=\left(\tfrac14+1\right)^{-1}=0.8,\qquad \hat x^+=0.8\times2=1.6 .P+=(41​+1)−1=0.8,x^+=0.8×2=1.6.

Now copy the measurement and treat the copy as independent:

P~+=(14+1+1)−1=49,x~+=49 (2+2)=169.\tilde P^+=\left(\tfrac14+1+1\right)^{-1}=\tfrac49, \qquad \tilde x^+=\tfrac49\,(2+2)=\tfrac{16}{9}.P~+=(41​+1+1)−1=94​,x~+=94​(2+2)=916​.

No new information arrived, but the reported variance fell from 0.8 to 0.44. The estimate also moved, from 1.6 to 1.78, toward a measurement that it has effectively counted twice.

In navigation, the copy is much better hidden. A WiFi fix first corrects the trajectory of the position filter. The heading estimator then fits a rotation to this corrected trajectory, against the same WiFi fixes, and sends the result back as an independent heading measurement. No duplicate measurement IDs appear anywhere, because the duplication travels through the updated state, the shared fingerprint map and the common reference data.

So the question “can both consumers use this fix?” is really three questions:

  • Do the raw sources overlap? Do two derived measurements use the same scan or the same reference sample?
  • Does one estimate already contain the information of the other? Was the trajectory that the heading estimator fits already corrected by fixes that the position filter used?
  • Are the errors independent? Even with disjoint scans, the errors of the fingerprint map, multipath and device bias are shared.

Disjoint raw sources answer the first question but say nothing about the third. Routing only the fixes rejected by the position filter to the heading estimator is also a selection on the data, so any test that the heading estimator runs later must take this selection into account.

📝 Further reading: Cossette et al. (IJRR 2024, §3.2–3.3 and §4) treat the related problem of several estimators that represent the same physical state. Cross-correlation doesn’t vanish because the implementations are separate, and unknown correlation can be handled conservatively at the cost of using less information (paper).

In the example with an exact copy, giving each copy half of the information weight recovers the answer for a single measurement. This works only because the two copies are known to be the same measurement. The real overlap between the two consumers is partial and unknown, so it cannot justify a general rule such as “halve everything”.

Ownership: reserve, commit, release

If fixes are shared, the sharing needs bookkeeping, not a boolean flag for each consumer. Our ownership module had the right structure. A claim binds to the derived measurement and also to its lineage, its episode and the raw evidence that it came from. A consumer can reserve several bindings together, commit them when they change the state, and release them if its attempt is cancelled.

The states have different meanings, and the scheduler must respect these differences:

  • Reserved: a consumer is holding the fix while it works.
  • Committed: the fix has changed the state.
  • Released: a cancelled attempt gives its unused reservations back before they go stale.

The observation time, the processing time, the reservation time and the commit time should also be recorded separately. Only these separate records can distinguish a late correction from the state that was actually available when a decision was made.

Version 1 showed the cost of reservations that never bring any benefit, while version 3 showed the cost of permanent exclusivity. A policy that avoids both problems needs reservation deadlines and release conditions for the heading estimator, together with a position priority that is limited to a clear transaction or stage.

What a fair test of the next policy looks like

A fair test freezes the fix sequence, the provider outputs, the error model, the thresholds and the scoring code, and changes only the ownership policy. For every fix, the test records its raw source, whether the position filter gated it and with what NIS, any reservation and the reason for its release, which consumer finally used the fix, and when this use was committed. If the measurements or the model change together with the policy, the result belongs to the whole combination, not to the scheduling.

To count as “solved”, three conditions must hold at the same time:

  1. Early position fixes are preserved.
  2. A heading estimator that needs to recover can keep collecting.
  3. A harmful heading correction is still refused.

Bringing walk A back to 42 accepted fixes does not show any of these conditions on its own.

Conclusion

Putting the heading estimator first took the early and fully acceptable WiFi fixes of walk A away from the position filter. As a result, the prediction drifted, the gate rejected the later fixes, and 42 accepted fixes became 7, while the heading estimator still delivered nothing. Putting the position filter back first restored the old behavior exactly, including the old failures, and making the position priority permanent starved the heading estimator instead.

All three versions are one problem. Two consumers of one observation need explicit ownership (reserve, commit, release), a priority with a limited scope, and tracking of the information that flows through the updated state instead of through measurement IDs.

Scheduling evidence is part of the statistical model: a wrong schedule changes what the estimator believes, not only when it receives the information.

Code is in bench_mur/wifi-scheduling/: audit.py rescores the saved outputs, demonstrate.py runs the two toy examples and plot.py draws the figures. The rescoring covers 16 saved runs; none are new replays. Scoring details that change results:

  • Each reference point is scored against the last output committed before it (with the evaluator’s 0.01 s tolerance), never interpolated from later outputs.
  • “Last quarter” is the last 25% of the reference path’s length, not of recording time or of reference points. An early rescoring by time didn’t match the original reports until this was fixed.
  • Eight of the 16 runs still have their original per-commit logs. For the other eight, output times are reconstructed as 0.5i0.5i0.5i s from the fixed 0.5 s output protocol, which is weaker evidence than an original log.
  • The fingerprint map excludes the walk being scored but may include other sessions of the same route, so these scores aren’t held-out-route generalization.
