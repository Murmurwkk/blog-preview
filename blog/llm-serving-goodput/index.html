DistServe: Serving Prefill and Decode on Separate GPUs

This note explains how DistServe serves prefill and decode on separate GPU pools, from goodput and pool sizing to KV transfer. With it, a reader can judge when splitting the two phases pays off.

DistServe (OSDI 2024) serves the two phases of LLM inference on separate groups of GPUs. Prefill processes the whole prompt at once, while decode generates one token at a time, and the two phases share the weights but not the shapes of their matrices. When they run on the same GPUs, they interfere: a long prefill inserted between two decode steps stretches the token interval of requests that are already generating, and if those requests get priority instead, new requests wait a long time for their first token. DistServe gives each phase its own pool of GPUs. The model computation does not change, but the split creates a job that did not exist before: moving the computed KV cache from one pool to the other.

This note goes through the DistServe paper and its public implementation at a pinned commit. It covers:

  • what makes prefill and decode different;
  • how the paper defines good serving as a number, and how it sizes the two pools;
  • what moving KV between the pools costs, and how the public code performs the handoff;
  • what the paper measured;
  • how multi-turn conversations change the routing problem.

All throughput and latency numbers come from the authors. I recomputed only byte counts, sums of squared lengths and table errors, and these numbers are marked (computed).

Fundamentals: one set of weights, two matrix shapes

For a prompt of length ℓ\ellℓ, the linear transform of one layer is XWXWXW with X∈Rℓ×hX\in\mathbb R^{\ell\times h}X∈Rℓ×h. All ℓ\ellℓ positions are known, and causality is expressed through the visibility mask of attention, so the whole model does not need to run token by token from the start. Every layer produces the K/V of this input at once, and the output at the last position is the first generated token.

The new token then goes back into the model. For one sequence, the input of the linear transform in each layer is now a single new position; attention uses the query of this position to read the history K/V and appends the new K/V. Repeating this step is decode. The cache means that old positions do not run through the whole model again, but the current position still has to read their keys and values.

For the linear layers, the many tokens of prefill share one read of the weights and form a large matrix multiplication, while decode for a single sequence is closer to a matrix-vector product with little weight reuse. Batching several sequences for decode recovers some of this reuse. The common saying “prefill is compute-bound, decode is bandwidth-bound” is a useful rule of thumb, but batch size, length, model structure and hardware can all move the bottleneck, so the name of the phase alone does not decide it.

Long inputs carry a separate attention cost. For a prefill batch with request lengths l1,…,lbl_1,\ldots,l_bl1​,…,lb​, the linear layers process

t=∑ilit=\sum_i l_it=i∑​li​

tokens, while the pairing of positions within each request scales with

t2=∑ili2.t_2=\sum_i l_i^2.t2​=i∑​li2​.

Four requests of 256 tokens and one request of 1024 tokens both contain 1024 tokens, but their sums of squared lengths are 262144 and 1048576 (computed), four times apart. The total prefill time does not quadruple, because linear layers, attention kernels, parallel communication and fixed overhead all combine. For this reason, Appendix A of DistServe keeps both ttt and t2t_2t2​ and fits a latency model by profiling, instead of assigning a fixed cost to each token.

When both shapes run in one execution instance, interference follows. Decode needs a short and punctual slot in every iteration, while a long prefill wants to process enough input at once to spread its overhead. So one long prefill between two decode steps immediately stretches the token interval.

Figure 1: Rectangle widths are illustrative, not measured, and the two schemes aren’t assumed to use the same number of GPUs. The decode appearing first below belongs to an existing request; the new request still has to go through prefill and KV handoff before it can generate.

Chunked prefill cuts long inputs into slices and interleaves them with decode. This limits the stall from any single interruption, at the cost of more iterations and lower efficiency per iteration. PD disaggregation isolates execution resources at a larger scale, so the P pool and the D pool can choose their own parallelism and scale independently. The two methods do not exclude each other, because the P pool can still use chunking internally.

What “good” means: TTFT, TPOT and joint attainment

A service must manage two kinds of waiting. Request iii arrives at aia_iai​, its first token returns at ti,1t_{i,1}ti,1​ and its last token at ti,mit_{i,m_i}ti,mi​​. For mi>1m_i>1mi​>1,

TTFTi=ti,1−ai,TPOTi=ti,mi−ti,1mi−1.\mathrm{TTFT}_i=t_{i,1}-a_i,\qquad \mathrm{TPOT}_i=\frac{t_{i,m_i}-t_{i,1}}{m_i-1}.TTFTi​=ti,1​−ai​,TPOTi​=mi​−1ti,mi​​−ti,1​​.

TTFT is the time to the first token, and TPOT is the average interval between the following tokens. TPOT compresses a whole generation into one average, so it is neither the worst stall nor a high percentile of the token intervals, and requests with a single output token need their own rule for TPOT.

Given the thresholds TF,TOT_F,T_OTF​,TO​, a request must pass both. At the arrival rate λ\lambdaλ and the full configuration ccc, the joint attainment is

A(λ,c)=1n∑i=1n1{TTFTi≤TF ∧ TPOTi≤TO}.A(\lambda,c)=\frac1n\sum_{i=1}^n \mathbf1\{\mathrm{TTFT}_i\le T_F\ \land\ \mathrm{TPOT}_i\le T_O\}.A(λ,c)=n1​i=1∑n​1{TTFTi​≤TF​ ∧ TPOTi​≤TO​}.

The configuration covers the number of GPUs, the split between the pools, the parallelism of each pool and the routing of requests. If at least a fraction qqq of the requests must meet both targets, the goodput of DistServe is the highest arrival rate per GPU that the system can sustain:

Goodput⁡(c;q)=sup⁡λ:A(λ,c)≥qλG(c).\operatorname{Goodput}(c;q)= \sup_{\lambda:A(\lambda,c)\ge q}\frac{\lambda}{G(c)}.Goodput(c;q)=λ:A(λ,c)≥qsup​G(c)λ​.

This metric selects different configurations than the goal “keep the GPUs as full as possible”. Bigger batches raise throughput, while requests that wait to be batched miss their deadline for the first token; giving everything to P makes the output intervals of D exceed the threshold. So capacity must be counted over complete requests, and failed, timed-out or rejected requests cannot be dropped from the denominator.

Two separate percentiles can also hide a problem. Suppose that out of 100 requests, 80 pass both targets, 10 fail only TTFT and 10 fail only TPOT. Each metric then shows 90%, while the joint attainment is 80%.

Figure 2: Constructed data showing why one request’s two times have to be evaluated together.

Whether the change concerns the P:D ratio or the transfer path, the fairest comparison uses the same joint requirement throughout, instead of a loose threshold for one phase and a strict threshold for the other.

Sizing two pools

Fix the model, the length distribution and the SLO. Suppose one P instance sustains μP\mu_PμP​ requests per second and one D instance sustains μD\mu_DμD​. With nP,nDn_P,n_DnP​,nD​ instances, and without communication and queueing tails, a stable arrival rate requires at least

λ≤min⁡(nPμP,nDμD).\lambda\le\min(n_P\mu_P,n_D\mu_D).λ≤min(nP​μP​,nD​μD​).

The minimum makes a simple point: adding GPUs to the side that is already idle does nothing for the backlog on the other side. This is an idealized capacity model. The real μ\muμ varies with batch size, length distribution and parallelism, and near saturation, queueing breaks the SLO first.

Figure 1 of DistServe gives a concrete motivating experiment: OPT-13B, 512 input tokens, 64 output tokens and an A100 80 GB. Mixed execution handles about 1.6 requests/s. When the phases run separately, P handles about 5.6 requests/s and D about 10. So 2P+1D has an ideal bottleneck of about min⁡(11.2,10)=10\min(11.2,10)=10min(11.2,10)=10 requests/s, or about 3.3 requests/s per GPU across three GPUs. This value of 3.3 is a ratio estimate that ignores the handoff and real queueing, not a measured system capacity.

An “instance” is also not the same as one GPU. A model can spread the compute within a layer with tensor parallelism (TP), or split into layer segments with pipeline parallelism (PP). TP shortens some compute while it increases the communication within a layer, and PP lets several batches advance in different segments at the same time, with pipeline waits and bubbles. P wants to shorten the execution of long inputs, while D also cares about a sustained generation batch size and KV capacity, so the two pools may need different TP/PP settings.

The actual choices of the authors from Appendix B:

Model and workloadP’s TP / PPD’s TP / PP
OPT-13B, ShareGPT2 / 11 / 1
OPT-66B, three workloads4 / 12 / 2
OPT-175B, ShareGPT3 / 34 / 3

This table shows the choice of the authors for their setup, not a general recipe. What it shows is that disaggregation really does give each phase room to make its own choice. The results depend on the hardware, the length distribution and the latency targets of the authors, and a larger decode batch or a model with fewer KV heads would move the bottleneck.

Memory is also a constraint. The active sequences on D keep growing, and the KV usage decides how many requests fit at the same time; requests that P has finished but not yet handed off still occupy the cache of P. So the first limit that the system reaches is not necessarily compute.

The price of separation: moving KV

Once P and D are separate, the state of each request must be migrated. For ordinary dense KV, without padding and metadata, the payload per request is

MKV=2LNKVdhℓs.M_{\rm KV}=2L N_{\rm KV}d_h\ell s.MKV​=2LNKV​dh​ℓs.

The factor 2 stands for K and V, LLL is the number of layers, NKVN_{\rm KV}NKV​ the number of KV heads, dhd_hdh​ the head dimension, ℓ\ellℓ the context length and sss the bytes per element. With GQA, several query heads share each KV head, so this formula must use the number of KV heads, not the number of query heads.

Take 40 layers, 40 KV heads, a head dimension of 128, FP16 and 512 tokens:

MKV=2×40×40×128×512×2=419430400 bytes=400 MiB.M_{\rm KV}=2\times40\times40\times128\times512\times2 =419430400\ \text{bytes}=400\ \text{MiB}.MKV​=2×40×40×128×512×2=419430400 bytes=400 MiB.

Sent serially over one 25 Gbit/s link, with an ideal 3.125 GB/s, this payload takes about 134.218 ms without any protocol or queueing overhead (computed). With 8 KV heads instead, the payload drops to 80 MiB, about 26.844 ms (computed). At 2048 tokens, the two cases become 1600 MiB / 536.871 ms and 320 MiB / 107.374 ms.

Figure 4: Byte accounting, not NIC measurements; GB/s is decimal and MiB binary.

Once a model is split by TP/PP, the full payload is divided among ranks and links, and it does not necessarily go through one port. Several GPUs that send at the same time also do not each receive independent bandwidth, because NICs, PCIe uplinks or switch ports may be shared.

So a deployment must answer more than whether the network is fast enough: it must also ask which data needs to cross the network at all. The placement of DistServe for low cross-node bandwidth puts the P and D of each layer segment on the same node. With the model in two segments, node 1 holds the P and D of segment one, and node 2 holds those of segment two. The intermediate activations of P flow to the next segment, while the KV of each segment stays on its node and goes to the matching D. Real TP ranks still need a layout, but activations and KV now travel on different physical paths.

This placement reduces the freedom of the configuration, because a P/D parallelism that is ideal for compute may not satisfy the requirement to share a node. DistServe therefore searches separate placement spaces for the cases of high and low cross-node bandwidth. A fast P instance that forces hundreds of MiB of state over a slow link every time does not necessarily give good request capacity.

A single transfer that looks acceptable does not settle the question either. At the arrival rate λ\lambdaλ with the mean KV size Mˉ\bar MMˉ, the system needs about λMˉ\lambda\bar MλMˉ of sustained effective bandwidth. Under full load, queueing makes a few requests wait a long time, so the uncontended value M/BM/BM/B cannot represent the tail latency. In Section 4.3 of the paper, D pulls KV on demand, and P holds the cache temporarily to absorb some backlog; a finite cache can buffer bursts but cannot absorb sustained overload.

How the public code hands off a request

In the public implementation, the handoff is an explicit chain of calls. DistServe calls prefill the context stage. When ContextStageLLMEngine._step receives results, it first delivers the generated token through the output callback. It then builds a MigratingRequest for unfinished requests and puts it on the queue that connects the two stages. The request carries the block table and the parallel configuration of P. The blocks of P cannot be freed yet, because D does not have their contents.

On the receiving side, DecodingStageLLMEngine._migrate_blocks first allocates destination blocks to obtain the block table of D, and then calls each worker to migrate the data. Below are the migration and reclamation steps, with lifecycle logging omitted, from single_stage_engine.py at the pinned commit (Apache-2.0):

await asyncio.wait(self._remote_call_all_workers_async(
    "migrate_blocks",
    migrating_req.block_indexes,
    migrating_req.context_parallel_config,
    target_block_indexes
))
# ... lifetime logging ...
self.clear_migrated_blocks_callback(migrating_req)

The callback then makes P free the resources of the request. migrate_blocks in worker.py passes the TP/PP configurations of both sides, the source and destination block indices and the K/V buffers to torch.ops.block_migration_ops.migrate_blocks. This operation does more than copy a contiguous byte range, because the same logical KV slice of the same layer must be mapped onto a different set of parallel ranks (worker implementation).

This Python code shows only the order of the handoff at the control level. asyncio.wait alone does not establish that low-level exceptions and GPU visibility are handled correctly, because this depends on the completion semantics of the workers and of the native migration operation.

The code does explain one thing that appears on a client timeline: prefill can return the first token before it hands off the KV. So the transfer latency is not fully counted in TTFT, and it may appear between the first and the second generated token instead. Recording only the time of P and the time of D makes it easy to miss this wait. A measurement should therefore keep the token times on the client side and connect the preparation, transfer and availability of the KV to the same request.

Resource usage should be traced along the same chain. When P finishes its compute, this is one state change, and it does not mean that the memory of P is reclaimed immediately. If the target D cannot accept the request, completed requests accumulate on P, and if the source cache is freed too early, the next prefill may overwrite it.

What the paper actually measured

The main experiments use 4 nodes with 32 A100 SXM 80 GB GPUs, NVLink within the nodes and 25 Gbps between them, and they run FP16 OPT-13B, 66B and 175B. The workloads provide input and output lengths but no arrival timestamps, so the authors generate arrivals as Poisson processes at varying rates. What the experiments measure is therefore the capacity under this controlled traffic.

WorkloadModelTTFT thresholdTPOT thresholdMean input / output length
ShareGPTOPT-13B0.25 s0.10 s755.5 / 200.3

HumanEvalOPT-66B0.125 s0.20 s171.3 / 98.2
LongBenchOPT-66B15 s0.15 s1738.3 / 90.7

The authors set these SLOs from the goals of the applications, and the LongBench inputs are truncated to the maximum length of OPT. HumanEval has a strict requirement for the first token, and LongBench has long inputs, and these properties affect the queueing and execution shares of the two pools differently. So the gains on different workloads are not a fixed multiple of one mechanism.

At an attainment target of 90%, ShareGPT sustains 2.0–4.6× the request rate of vLLM and 1.6–7.4× that of DeepSpeed-MII, while HumanEval reaches 5.7× vLLM and LongBench 4.3×. A second set of experiments uses a fixed request rate and tightens the TTFT and TPOT thresholds together. In this set, ShareGPT tolerates SLOs that are 1.8–3.2× stricter than vLLM and 1.7–1.8× stricter than MII, while HumanEval reaches 1.4× and LongBench 12.6×. The two sets measure different things: 7.4× concerns the request rate and 12.6× concerns how strict the SLO can be, so a threshold that is 12.6× tighter is not the same as a latency that is 12.6× lower (DistServe §6).

The conditions of the baselines also matter. The TP of vLLM is 1, 4 or 8, depending on the model. The DeepSpeed-MII implementation used in the paper is limited by vocabulary partitioning and memory and has no configuration for OPT-175B. These limits belong to the measured versions and configurations, and they say nothing about other versions.

The estimate above gave about 134 ms for 400 MiB over 25 Gbps. Yet the authors report that for OPT-175B/ShareGPT, the transfer takes less than 0.1% of the total phase time, and more than 95% of the requests migrate in less than 30 ms. The key is that the KV does not all go over the 25 Gbps link: the placement for low bandwidth keeps most of the handoff of each layer segment within the node, over NVLink. The denominator also matters. The value of 0.1% is a share computed by summing the phase times of all requests, while the distribution per request comes from the transfer CDF, and the two cannot replace each other.

Figures 8–10 are real end-to-end results. Figure 11 studies higher cross-node bandwidth and placement schemes with simulation, because the testbed lacked the bandwidth and the baselines did not support every configuration. Table 2 compares real and simulated results at seven arrival rates, and a recomputation item by item gives a maximum absolute difference of 1.8 percentage points. At the arrival rate 2.0, for example, vLLM reaches 52.8% / 51.0% and DistServe-Low 99.3% / 99.3%. This agreement supports the use of simulation for those configurations, but it is not an error bound for all bursty traffic. Appendix C also reports an attainment target of 99%, within the same controlled experiments.

Together, these results make the statement “separate pools help” concrete. The benefit is not only less interference between the phases: disaggregation also allows a different parallelism for each pool, and a suitable placement prevents the KV handoff from cancelling out the gain. If any one of these three factors is removed, the capacity result changes.

When history is already in place: routing multi-turn requests

The main line of DistServe starts from new requests. In a real conversation, however, the next turn changes the choice: the history KV already lives on some D machine, and the new message is short. Sending every new input to P would move a large existing state for a small amount of additional compute.

With the history length hhh and the new input length uuu, reusing the history means that the linear transforms of each layer only process the new positions, while attention still reads the history K/V. This computation is neither a prefill of length h+uh+uh+u from the beginning nor an ordinary decode that adds one position per request. This append-prefill needs its own model of compute and interference.

PPD v1 studies how to keep some later turns on D and execute the appended input there, with choices based on offline measurement tables and weights for TTFT and TPOT. This approach saves the transfer and the P queue, but the appended compute still blocks other decodes; the TPOT degradation in its Figure 5 shows that keeping the state in place does not avoid compute contention. That experiment uses a single node with 4 H100 80 GB GPUs, mainly with Llama-3.1-8B, with runs of 10 seconds per synthetic point and ZeroMQ transport in the appendix, so the trade-offs of cross-machine RDMA need separate measurements.

Prefix reuse across requests adds another conflict: the machine that holds the cache may be busy, while the idle machine has no cache. Mooncake uses a shared KV store that includes host memory. It schedules cache hits, cache movement and compute load together, and it can replicate hot caches to spread concentrated access. So routing is no longer just a choice of the shortest queue; it compares the total cost of waiting, fetching state and recomputing.

The numbers of Mooncake cannot be compared directly with those of DistServe. Its relevant experiments use a dummy model shaped like Llama3-70B, 8 A800 GPUs and 4 × 200 Gbps NICs per node, and 16 nodes per side in Figure 1. TBT is defined as the mean of the longest 10% of the token intervals, and the TTFT threshold is 30 seconds, and both definitions differ from the mean TPOT and the thresholds above. What this post takes from Mooncake is the mechanism of cache-driven routing, not the multipliers.

So, should you split?

No answer holds independently of the workload. Long inputs, strict output requirements and enough devices make an independent P pool directly valuable, while short appends to history KV that is already resident are simpler to keep on D. With few GPUs, two pools that each hold a copy of the weights may use up the KV capacity first, and offline jobs without strict requirements for the first token and the intervals may do better with mixed execution and full batches. Section 7 of DistServe discusses settings with limited resources and offline throughput, and it leaves advanced preemption and fault tolerance to future work.

Conclusion

Prefill and decode use the same weights in two matrix shapes, so running them together forces each phase to wait for the other. “Good” serving is the arrival rate per GPU at which enough requests meet both latency targets. Disaggregation gives each phase its own pool size and parallelism, at the price of moving KV, and the placement decides whether this price is negligible or dominant. Once conversations have a history, the question changes again, to where the state already lives.

The thing worth keeping is the path of one complete request: where it queued, which compute decided its first token, which path its KV took, and what each later token waited for. When this path is recorded together with the GPUs, memory and links that it occupied, PD disaggregation is no longer just the name of an architecture but a deployment that can be compared with others.

Disaggregation does not make the work smaller; it decides where each piece of the work waits.
