Producer–Consumer Operator Fusion: From Tensor Reuse to Tile Scheduling

Two adjacent convolution tiles share two input columns. Following those columns through a VGG16-shaped producer shows where fusion saves a read, when it saves the write, and what the local storage costs.

Place two 8×88\times88×8 tiles side by side in the output of a convolution. Each CUDA block is responsible for a different tile. Can we fuse the producer into both blocks, keep its values on chip and cross a global-memory write off the budget? To answer, first color the producer positions that both blocks need. Then look for any other operator that still needs the producer’s tensor after those blocks finish.

Welder starts with the consumer’s output tile and propagates its indices backward to infer the shape required from each producer. Two small calculations expose the tradeoff the planner sees. The first is about overlapping tiles. The second is about a tensor with another consumer. Welder, §§3.1–3.2

Overlapping inputs and recomputation for adjacent convolution tiles

Take two interior output tiles of a stride-one, undilated 3×33\times33×3 convolution. Start numbering input columns at the first column needed by the left tile. Its eight output columns touch input columns 0 through 9. The right tile starts eight columns later and touches columns 8 through 17. Both need the same ten input rows.

Figure 1. One cell is one input position in one channel. The dark cells in columns 8 and 9 contribute to outputs owned by both blocks. The outer rows and columns needed around the output tile form its halo.

Each block asks the producer for 100 positions. Lay the two footprints on top of each other and there are only 10×18=18010\times18=18010×18=180 distinct positions. If each block regenerates just what it needs, they generate 200 positions altogether. Twenty are second copies of values already computed by the other block. The duplication costs 10% of the generated positions in this two-tile example.

A larger output tile reduces the fraction of work spent on the shared edge. For side length bbb, the two full footprints contain 2(b+2)22(b+2)^22(b+2)2 positions and their intersection contains 2(b+2)2(b+2)2(b+2). At b=16b=16b=16, 36 of 648 generated positions are duplicates, about 5.6%. Larger tiles also need more space. Holding all 256 FP16 channels for one complete input footprint takes 50 KiB at b=8b=8b=8 and 162 KiB at b=16b=16b=16. Processing channels in smaller groups changes that calculation. A candidate therefore needs both a count of duplicated work and a capacity check at the memory level where the producer and consumer meet.

Intermediate reads and writes with a second convolution consumer

Follow the same dependency in the simpler case of a pointwise ReLU. ReLU at (y,x)(y,x)(y,x) needs precisely the producer’s value at (y,x)(y,x)(y,x). If ReLU is the only consumer, a convolution block can compute that value, apply ReLU, and write the final answer. The separate kernels would have written a full intermediate and read it back. Both transfers can be removed while the final output write remains.

Now give the convolution output to a second, separately launched operator as well. The fused ReLU still gets a local value, but the separate operator needs a global address from which to read. Cross out one read. Leave the producer’s write in the budget.

With nnn external consumers initially, the logical cost is (1+n)A(1+n)A(1+n)A for one shared materialization and one read per consumer. Move kkk of the consumers on chip. While k<nk<nk<n, the cost is (1+n−k)A(1+n-k)A(1+n−k)A. Moving the last one removes its read and the write. The distinction matters most at a branch, where it is easy to count the write as a saving twice.

Input region propagation and traffic estimates in Welder’s tile planner

The default policy visits consumers before producers. One short excerpt from _compute_memory_traffic shows where the geometry enters. The method name propogate_inputs [sic] appears exactly this way in Welder’s source. Welder default GPU policy, pinned source

for node in reversed(self.ordered_nodes):
    tile = op_tile_map[node]
    input_shapes = node.propogate_inputs(tile)

For the convolution in Figure 1, that backward step turns the consumer’s 8×88\times88×8 tile into a 10×1010\times1010×10 producer footprint. For the ReLU in Figure 2 the shape stays unchanged. The policy carries the inferred shape back along each edge and estimates transfers across the boundary of the fused group using tile shapes and transaction sizes. Its shared-memory allocation logic tracks downstream users of a temporary before freeing its storage. The scheduling algorithm checks capacity and compares estimated traffic, then profiles selected candidates. Welder memory traffic and temporary lifetimes · Welder, Figure 7

When sketching a fusion, I would mark the two shared columns first, write down where their values will live, and trace the last consumer of that storage. That gives three different quantities to check against a proposed schedule: repeated producer work, live bytes, and the reads and writes that actually disappear. The same reasoning about what stays local applies to block and register tiling inside a GEMM.

Coordinate enumeration, byte counts and figure reproduction

This standard-library Python example enumerates every position touched by the nine taps of each output. The second and third printed counts independently check the union and intersection in Figure 1.

def footprint(b, first_col):
    return {(row + dy, col + dx)
            for row in range(b) for col in range(first_col, first_col + b)
            for dy in range(3) for dx in range(3)}

a, b = footprint(8, 0), footprint(8, 8)
print(len(a) + len(b), len(a | b), len(a & b))  # 200, 180, 20

The duplicate fraction is 1/(b+2)1/(b+2)1/(b+2) for these two horizontally adjacent interior tiles. Padding boundaries, dilation or a different stride change the set of positions.
