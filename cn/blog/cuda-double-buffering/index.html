CUDA GEMM 的共享内存优化：XOR 重排与双缓冲的性能比较

在 RTX 5070 Laptop 上，XOR 重排消除了目标共享内存读取的额外 wavefront，但在 1024³ FP32 GEMM 上，这个单缓冲版本比原布局慢约 27%。每个线程占用的寄存器增多，限制了可同时驻留的线程块数。在相同 XOR 双缓冲布局下，异步复制又缩短了两个测试尺寸的耗时。

我在一版 FP32 GEMM 里发现，共享内存同一个 bank 要服务八个不同地址。改用 XOR 布局后，历史 Nsight Compute 报告中目标读取多出的 4,194,304 个 wavefront 全部消失，整颗 kernel 的共享内存读冲突计数也从 6,297,071 降到 7,399。可等我把两个单缓冲实现在同一进程里交替测量，1024³ 上 XOR 版反而慢了 26.6%。局部冲突确实解决了，整颗核函数的耗时还受另外几项变化影响。

四种实现都在 RTX 5070 Laptop 上计算相同的 GEMM。每个线程块有 128 个线程，负责 128×64 个输出，每个线程累加其中的 8×8 个元素，K 方向每轮推进 32 项。保持这套分工后，相邻实现只改 A 的共享内存布局、缓冲槽数或复制指令，边界矩阵也走各自的完整实现。另一篇讲 GEMM 数据复用的文章使用另一种分块，计时只在各自文章的实现之间比较。

早先我看到冲突计数下降，就以为每个线程也能更早完成计算。可同一个线程在 XOR 版本里还要计算新的地址，而且会占用更多寄存器。理解完整耗时，需要知道省下了哪些读取，以及一个 SM 还能同时容纳多少线程块。

这也区分了后面两次改动的作用。XOR 重排改变同一条读指令中的地址分布，两个缓冲槽则让当前 K 块与下一块可以同时留在共享内存。两种改动最终对耗时的影响都要在完整 kernel 中测量。

128 个线程对 128×64 GEMM 输出块的分工

对于连续行主序的输入 A[M,K]A[M,K]A[M,K] 和 B[K,N]B[K,N]B[K,N]，一个线程块只计算 C[M,N]=ABC[M,N]=ABC[M,N]=AB 中的 128×64 个输出。K 方向每推进一段，块内四个 warp 共同读入 A 的 128×32 子块和 B 的 32×64 子块，合计 6,144 个 float、24 KiB。每个线程将自己 64 个输出的部分和留在寄存器里，继续处理下一段 K。

int warp = threadIdx.x / 32;
int lane = threadIdx.x % 32;
int mr = (warp / 2) * 64 + (lane / 4) * 8;
int nc = (warp % 2) * 32 + (lane % 4) * 8;

每个线程负责块内 [mr:mr+8,nc:nc+8]。看 warp 0：lane 0–3 做相同的八行、不同的四组八列，合起来是 8×32；lane 4–7 接下一条。一个 warp 覆盖 64×32，四个 warp 按 2×2 拼成 128×64。固定 k 后，同四个线程共享八个 A，却取不同的 B。A 在计算上适合复用，麻烦出在把它直接按 row*32+k 放入共享内存。

XOR 布局对共享内存标量读取 bank 冲突的影响

要由前面的线程映射算出冲突，需要把每个线程读的字地址换成 bank 编号。这里访问的是 32 位字，共享内存分成 32 个 bank，字地址对 32 取模便得到编号。落在不同 bank 的访问可以并行，同 bank 的不同字要分批服务。如果几个 lane 读的是同一个字，硬件可以广播一次。数冲突时，应先把这些广播合并。CUDA 共享内存说明

固定线程内的行偏移 iii，把上面的线程编号代入 A 的地址：

r=64⌊warp/2⌋+8⌊lane/4⌋+i,word=32r+k,bank=k mod 32.\begin{aligned} r&=64\lfloor warp/2\rfloor+8\lfloor lane/4\rfloor+i,\\ word&=32r+k,\\ bank&=k\bmod32. \end{aligned}rwordbank​=64⌊warp/2⌋+8⌊lane/4⌋+i,=32r+k,=kmod32.​

当相邻两行相距 32 个字时，跨一行恰好又回到原来的 bank。一个 warp 的 32 个 lane 因此全落在同一 bank。每四个相邻 lane 读同一个字，可以广播，但八组仍要分别读八个不同的字。

最容易想到的处理是在行尾垫一个元素。我还希望把相邻四个 float 作为连续的 16 字节一起复制，于是保留每组的内部顺序，只重排一行里的八个组：

int a_index(int row, int col) {
    int group = (col / 4) ^ ((row / 8) % 8);
    return row * 32 + group * 4 + col % 4;
}

拿 col=0 检查：第 0–7 行留在组 0，第 8–15 行换到组 1，第 16–23 行换到组 2。沿原先冲突的八组行去读，组起始 bank 变成 0、4、8、…、28；相邻四个 lane 的广播仍然成立。

图 1　普通行布局把八个不同地址都映射到同一 bank，XOR 重排把它们分散到八个 bank。四个 lane 对同一地址的读取在两种布局中都可广播。

固定一行，XOR 是对八组位置的一一置换，同组四个 float 保持连续。写入 shared 的生产者、从中读取的消费者必须共用 a_index。如果只改读端，线程拿到的是另一个矩阵元素。以下实验只重排 A，B 沿用原布局。

我枚举了四个 warp、32 个 k 和八个行偏移。按每个 lane 加载一个标量计算，同一 bank 在普通布局中最多收到八个不同的字地址，XOR 重排后只收到一个。编译器可以把标量读合为宽指令，共享内存流水线也可以拆分请求，因此下面还要对照实际指令与硬件记录的服务次数。

共享内存双缓冲的搬运、同步与计算顺序

XOR 改变的是一个 K 块内部的读地址，缓冲策略则决定何时能装入下一个 K 块。若共享内存中只有一份 A、B 子块，所有线程必须按以下次序生产和读取它。

load K chunk t
block barrier: all inputs written
compute every multiply-add for this chunk
block barrier: all consumers done reading
overwrite the same storage with chunk t+1

同一线程块的四个 warp 可以各自推进。第一道屏障让它们等所有线程写完当前块才开始读，第二道屏障让已经算完的 warp 等待读者离开，才允许覆盖当前块。

只有一个槽时，哪怕下一块地址已经算出来，也不能提前覆盖还在用的数据。第二个槽允许分块 ttt 和 t+1t+1t+1 短暂共存：先装入第 0 块，消费当前槽，同时准备另一个。等新数据到齐、旧数据读完，两个槽交换角色。

图 2　箭头表示写入、读取和复用之间的依赖。线程读取一个槽时，搬运指令可以写另一个槽，横向距离不代表耗时。

异步版本用 cp.async.cg.shared.global 直接从全局内存搬到 shared，绕过程序可见的中转寄存器。线程发出复制后可以继续计算，临用数据前再等。commit_group 将本线程发出的复制组成一组，wait_group 0 等到本线程此前的组全部完成。PTX 的 cp.async 语义

循环中的 current_slot 和 other_slot 交替指向两块共享内存，等待和块级屏障位于每次交换之前。

if (tiles > 0) {
    load_tile(0, slot0);   // each thread handles its own piece of input
    commit_group();
    wait_group_0();
    __syncthreads();
}
for (int t = 0; t < tiles; ++t) {
    if (t + 1 < tiles) {
        load_tile(t + 1, other_slot);
        commit_group();
    }
    compute_tile(current_slot);
    wait_group_0();
    __syncthreads();
    swap(current_slot, other_slot);
}

每个线程的 wait 只等待自己提交的复制。即使它已经写好下一块，其他线程仍可能在写新槽，也可能还有 warp 在读旧槽。块级屏障要求所有线程完成各自的等待与本轮计算，跨过屏障后才能读新槽、覆写旧槽。

理想情形下，稳态每块接近 max⁡(Tload,Tcompute)\max(T_{\rm load},T_{\rm compute})max(Tload​,Tcompute​)，串行则是两者之和。这个估算略去了首块装入、末块计算、同步和资源竞争。K 只有一块时压根没有稳态，哪怕测到时差，也不能归给跨块重叠。

寄存器双缓冲的首组预加载

每个 k 上，一个线程从共享内存读八个 A 元素和八个 B 元素，用它们更新寄存器中的 64 个累加器。操作数也可以分两组寄存器交替存放，这样计算本组 FMA 时就有位置预取下一组。第一次进入循环前必须装好第 0 组，否则第一条 FMA 就会读到初值未定的寄存器。

load_fragment(/* k */ 0, /* register slot */ 0);
for (int k = 0; k < 32; ++k) {
    int cur = k & 1;
    if (k + 1 < 32) load_fragment(k + 1, cur ^ 1);
    fma_fragment(cur);
}

图 3　第一次 FMA 读取的是槽 0，图中循环前的装入不能省。

去掉预装，第一轮会填槽 1，却拿槽 0 去做 FMA。把槽 0 清零也会漏掉当前分块 k=0 的贡献。除非专门设计跨分块预载，每次换 shared 分块，都要重新装好首组寄存器。

这项预加载遗漏在一次实际运行中造成了数值错误。在 M=128,N=512,K=64 的那次错误运行里，65,536 个输出全部超出误差预算，最大绝对误差约 0.993。值都是有限数，保护区完好，memcheck 也报零错。读到未初始化的操作数，完全可能没有任何非法地址访问。 当时还同时改过其他代码，不能把全部数值误差都精确摊给这一处。

比多抽几组随机数更直接的测试，是让 A 每 32 个 K 元素中只有第一个为 1，其余都为 0，B 任取。整个乘积只靠 k=0、32、64……这些项；逐块漏掉第一项便一目了然。

非整块矩阵的补零、地址对齐与写回边界

K=33 时，第二块只有一个有效 k。M=129 或 N=65 时，边缘输出也只占完整 tile 的一部分。线程仍按原 tile 协作，只在读入阶段给越界的位置补零，在写回阶段检查输出的行列边界。

越界元素对 GEMM 乘积的贡献可以补零，负责这些位置的线程仍需和其他线程一起通过屏障。比如一个四元素组只剩一个有效元素时，16 字节宽读已经越界，必须缩小读取范围。

因此每组先检查完整范围和实际指针对齐。四个数全有效且源地址 16 字节对齐，才走宽异步复制；否则逐个读取有效元素，其余补零。K=33 时行间距 132 字节，同一矩阵的不同行对齐情况不同，单次 kernel 内就可能混用异步复制和普通 shared 写。

宽复制和逐元素补零都写入同一套 XOR 布局，各自负责的目标范围互不重叠。若只有回退路径按普通行布局写入，整块测试仍可能通过，碰到边界时消费者却会读到错误的元素。消费者还必须等异步复制和块级屏障完成，才能使用这批数据。

输出网格直接取二维 ceil(N/64) × ceil(M/128)。我试过以八个列块为一组重排：

tile_row = blockIdx.x >> 3
tile_col = blockIdx.y * 8 + (blockIdx.x & 7)

旧实现没有排除重排产生的填充块。比如 N=64 只需一列块，多出的块却仍去读 B、写 C。128×64×64 报了 82 次 memcheck 错误，第一处就是 16 字节异步读越界。按列分组可以研究块间缓存局部性，前提是每一块确实映到有效输出。这里退回直接网格。

四个正式变体加一份兼容入口，通过了 240 项 FP64 数值检查，覆盖 K=0、尾块、0–3 个 float 的指针偏移及每块只有首项非零的输入。四个正式变体各跑了 48 次 memcheck 和 48 次 racecheck，均为零错误、零危险。误差预算和形状清单放在文末。

从普通单缓冲到 XOR 布局与异步双缓冲

下表的四个版本使用同一套线程映射、8×8 寄存器外积和首组预加载，相邻两行只改变 A 的共享内存布局、缓冲槽数或复制方式中的一项。

简称A 的 shared 布局槽数global→shared
raw single普通行布局1同步 float4，边界用标量
swizzle single四元素组 XOR1同上
swizzle double四元素组 XOR2同步预装下一槽

例如，异步双缓冲与同步双缓冲共用 XOR 布局和两个槽，二者的差值才对应这次复制路径的改写。若直接与普通单缓冲相比，布局和槽数的影响也会计入。

异步复制的机器指令与寄存器开销

异步版本的 PTX 保留了 cp.async.cg.shared.global、cp.async.commit_group、cp.async.wait_group 0 和 bar.sync 0。在 SM120 的 SASS 里，它们对应：

LDGSTS.E.BYPASS.128 ...
LDGDEPBAR
... compute and other instructions ...
DEPBAR.LE SB0, 0x0

从机器码可以确认，全局内存到共享内存的异步复制、提交与等待都出现在这个模板实例中。反汇编里跨预装、循环和分支共有五处 LDGSTS、两处提交和两处等待。静态出现几处，不能读成每块恰好执行几次，更量不出被计算盖住了多少搬运时间。

普通单缓冲改为 XOR 单缓冲后，每个线程多占 40 个寄存器。重排同时改变地址表达式、值的活跃区间和指令调度，无法把这 40 个寄存器都算在执行 XOR 的那条指令上。改用双槽后，共享内存翻倍，寄存器用量增至每线程 211 个。即使编译器没有将寄存器内容溢出到局部内存，一个 SM 能同时容纳的线程块仍会受寄存器总量限制。

一次共享内存读请求可能需要流水线分批服务，每一批称为一个 wavefront。即使访问没有冲突，一条宽读取也可能需要分几次服务。报告根据指令宽度和参与线程给出理想次数，实测超过它的部分才算额外 wavefront。这里最常见的是 LDS.128，每个 lane 读四个 float，读宽已经不同于上面的标量模型。

我从 raw 版本的 Source 页逐个导出 SASS 地址，发现额外服务集中在 64 处 LDS.128。例如 LDS.128 R20,[R4] 实际 131,072 次，理想 65,536 次；64 处差值之和恰为 4,194,304。对这条真正执行的宽读，实际与理想之比是 2。

三个 XOR 实现的目标读额外 wavefront 都归零。另一个硬件计数 l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum 从 raw 的 6,297,071 降到 XOR 单槽的 7,399，两项指标并不相等，整个 kernel 仍有少量读冲突。

同一份报告里有两种与驻留有关的量。按寄存器容量推算，每个 SM 可同时容纳的线程块上限从 4 块降到 3 块、再降到 2 块；单看共享内存容量，上限从 4 块降到 2 块。表中实测的是 SM 在活动周期里平均驻留的活跃 warp 数占硬件上限的比例，这个比例也随之降低。驻留的 warp 较少时，调度器可选来掩盖等待的工作也较少，实际能否发射还取决于指令的就绪情况。

两个同函数 A/A 的区间都落入预定的 ±2% 校准带，八组比较均达到了区间半宽 2% 的目标。在两个测试形状上，把普通单缓冲改成 XOR 单缓冲都会变慢。随后加上同步双缓冲，1024³ 变快、2048³ 变慢。保留双槽并把同步复制换成异步之后，两种尺寸的耗时才都缩短。每一步是一次独立配对，不能将相邻比连乘当作 raw 与 async 的直接配对结果。

笔记本未锁频。每个进程只在开始和结束时记录功耗、温度与时钟，期间的电源状态查询还显示软件功率限制曾生效，因此无法还原每次执行的频率。编译器分配的寄存器数则可以直接从构建产物读取，也可以给它设置上限，检验普通布局与 XOR 布局的排名是否会改变。

寄存器上限改变了普通布局与 XOR 布局的耗时排序

为了判断名次对寄存器约束有多敏感，我先在编译命令里统一设置 -maxrregcount=128。结果 raw 仍分到 128 个寄存器，XOR 仍有 168 个。原有 __launch_bounds__ 使这个选项没有约束到目标 kernel。我保留这次失败的编译日志，另生成两份头文件，只把注解换为 __maxnreg__(128) 或 __maxnreg__(168)，内核主体与原二进制不动；构建时检查实际分配确实没超过上限。CUDA 对寄存器限定符的说明

两个派生配置各自用 3 个进程试测，8 个独立确认进程、每进程 20 个平衡块。以下是 1024³：

寄存器上限真正生效的两个单缓冲实例均无 spill。两列绝对时间是保存的计时块中位数，比值按进程对数比汇总。不同编译配置之间没有直接配对，不能用它们的绝对时间差单独估计改上限的收益。

两种派生约束下原排名都翻转。它说明编译与资源配置能左右结果，却还不能锁定唯一原因。举例说，上限 168 时 raw 自己就从 128 变成了 167 个实际寄存器。换注解还可能改变调度和活跃区间，同一上限不保证同一分配，无 spill 也不保证指令相同。零额外 wavefront 的采样来自历史原生二进制，派生版本没有重做那项采样。

1024³ 历史批次里 XOR 单槽慢约 19.5%；raw 的三轮范围 0.30325–0.30822 ms，swizzle 为 0.36302–0.36312 ms。早期结论是额外 wavefront 的消失没抵销完整改写的成本。寄存器、驻留数、地址计算和调度当时都还是候选原因，因此后续才要检查寄存器约束究竟有没有生效。

2048³ 时加同步槽使耗时从 2.47729 升至 2.82787 ms；换异步搬运后降到 2.25238 ms。以同布局同步双槽为分母，约省 20.4%；以原始 raw 单槽 2.33407 ms 为分母，约省 3.5%。一个比较复制机制，另一个比较整套设计。

短 K 提供了一个可以排除跨块重叠的对照。128×64×32 只有一个输出块和一个 K 分块，没有下一块可预取；async 仍测到 11.78 µs，raw 为 12.54 µs。此处只能归到整个复制路径与编译调度的差异。K=64 时两者为 12.71 和 12.66 µs，三轮范围相交。

硬件参数与 Roofline 对 GEMM 方案选择的局限

这次最难预判的是两种真实变化谁会主导耗时：共享内存读得更顺畅，同时每个线程要用更多寄存器。我后来尝试先用 Roofline 缩小候选范围，但计算强度对假定的流量很敏感，硬件峰值也无法直接给出编译后的寄存器用量。

我仍想知道，在第一版 GEMM 写好之前，哪些硬件参数足以淘汰不合适的分块，哪些选择只能等有了基准实现，再借助 Nsight 的指令和资源记录判断。如果你在实际设计中用过这样的筛选方法，我很愿意交流。

源码接口、正确性与复现实验

附录里的 bench_mur/、rep_mur/ 是私有研究仓库中的定位信息。可公开查看相关 CUDA 内核。cuda-operators

历史环境与计时口径

RTX 5070 Laptop GPU，8 GB，SM120；构建用 CUDA Toolkit 13.1.115、MSVC 2022，驱动 610.88。另一次环境查询得到运行时 API 13.3。自 CUDA 13 起，Windows 运行时可随显示驱动提供，版本可以不同于构建工具包。原 GEMM 环境取的是 nvcc 与驱动版本，运行时来自另一次核验。CUDA Runtime 版本说明

设备端先预热 20 次，再用 10 次试跑估计每批重复数，目标每批约 20 ms，重复限制在 1–2,000 次。每轮次序打乱跑 30 批，共三轮，复用数据、不清 L2。主机往返单独计入 pageable H2D(A、B)、kernel、D2H(C) 和同步，排除分配、编译与 cuBLAS handle。历史误差棒是三个轮中位数的最小到最大值。

早期四种实现分别编译为独立的可执行文件，互不链接旧 solve。GPU 任务串行执行，记录起止温度和时钟；未锁频，机器整体功耗状态也未固定。

接口与正确性覆盖

输入是连续行主序的 FP32 A[M,K]、B[K,N]，输出 C[M,N]。普通 FP32 FMA，不使用 Tensor Core 或 TF32。验证覆盖这个布局契约，未考察任意 stride、输入输出别名及 NaN/Inf 的特殊语义。

共享实现放在 gemm/gemm_pipeline.cuh。两个独立兼容入口各自可编译：

文件保留的参数顺序用途
mulmatrix_let_merged.cusolve(A,B,C,M,N,K)保留 merged 调用顺序，另有接受 stream 的异步入口
mulmatrix_let2.cusolve(A,B,C,M,K,N)保留旧实现实际解释的维度顺序；旧函数内部曾交换最后两维

兼容接口 solve 在返回前同步，设备计时则向指定流提交工作，以免每次启动都同步主机。两种入口的尺寸参数排列不同，测试封装分别按各自签名传入 M、N、K，否则类型检查通过也可能算错矩阵。

旧源码按原样归档并记录 SHA-256，再抽出公共 tile 和消费映射，建立可分步比较的新实现。新代码同时修正边界、寄存器初值、stage 协议并撤掉八列重排。因此旧版与修复版的差不能归给单项优化。

在 CPU FP64 上逐元素核对了以下 12 组形状，顺序为 M、N、K：

1×1×0, 1×1×1, 7×13×3, 15×17×15,
63×65×31, 64×64×32, 65×63×33, 127×129×17,
128×128×32 (one aligned, one offset), 129×131×65, 256×256×129

每个指针取 0、1、2、3 个 float 偏移；每种形状测随机、全零、正负交替及每个 K 块仅首项非零四种输入。四个性能版本加 let2 兼容入口，共 240 项通过。输出先填 NaN，前后放哨兵，分别发现漏写、非有限值和越界破坏。

CPU 参考逐项用 double 累加，预算为 1e-6 + 16*FLT_EPSILON*sum(abs(Aik*Bkj))。这是本实验的验收预算。性能实验的大矩阵额外采 257 个固定位置查 FP64，全矩阵与 pedantic FP32 cuBLAS 对比，阈值 3e-4 + 3e-4*abs(reference)。大矩阵完整对照是 GPU 参考，高精度对照是采样。

四种性能实现各有 48 次 memcheck、48 次 racecheck，均为零错误、零危险，覆盖短 K、多 K 块、偏移及尾块。gemm_8 的两类检测都复跑了一次，也通过。

旧 mulmatrix_let2.cu 有一条被截断的循环语句，原样编译报 10 个错误，无法作为旧性能基线。原始编译日志、只补类型别名的 merged 失败记录和修复结果分开保存。

重跑命令与数据位置

配对修订在 bench_mur/revision_20261115_gemm/，入口 run.py pilot/confirm --suite pipeline；对上限先用 build_caps.py 128 或 168，再按对应 --cap 计时。原生确认共 120 个进程、2,400 个配对块，每个上限配置 16 个进程、320 块。verify.py 独立检查预先列出的条件、正确性结果和进程级区间；派生头文件、编译日志、资源、二进制哈希与结果导出在 results/revision-20261115/。原生二进制另做过带偏移尾块的 memcheck、racecheck 和 synccheck。

历史脚本在 bench_mur/gemm/，原始失败样本、快照、哈希、环境、逐批 CSV 和反汇编在 rep_mur/blog-rewrite/gemm/。本篇用独立的 pipeline/ 子目录存放计时。

./bench_mur/gemm/build.ps1 -Variants 8,9,10,11,12
python bench_mur/gemm/run.py --phase check --suite pipeline --variants 8,9,10,11,12
python bench_mur/gemm/run.py --phase bench --suite pipeline --variants 8,9,10,11
python bench_mur/gemm/plot_pipeline.py

编号 8 是异步双槽，9 是 XOR 单槽，10 是原始单槽，11 是 XOR 同步双槽，12 只验证旧 let2 接口。换环境要调整工具链并重新构建、验证。

两篇 GEMM 文章共享的第二批实验包含 10 个变体、240 项计时前正确性检查和 14,400 条计时记录，仍是原始二进制、三轮各 30 批。数据在 rep_mur/blog-rewrite/style-v2/gemm/，独立于第一批汇总。

从 NCU 报告可以按 SASS 地址定位额外 wavefront，核对 bank 冲突计数和实测活跃 warp 占比。每个 SM 可容纳的线程块数上限则按寄存器、共享内存等资源推算。本实验没有分别计量复制、等待和计算各占多少周期，所得耗时也只覆盖这张未锁频显卡上的独立 GEMM，未涉及 TMA、其他 GPU 或生产模型。

汇编、NCU 报告和 CSV 在 rep_mur/blog-rewrite/style-v3/profiling/。profile_static.py 从计时二进制取 PTX/SASS，collect_ncu.ps1 串行采集，read_ncu.py 保留原指标名及单位，plot_profile.py 从导出数据出图，二进制和导出报告均记录哈希。
