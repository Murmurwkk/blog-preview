大语言模型推理的连续批处理：迭代调度与 KV 缓存分配

同批请求生成的词元数不同，先完成的请求会留下空位。连续批处理调度器可以在下一轮接纳新请求，但还要为它分配 KV 缓存、安排提示词计算，否则一段长提示就可能拖长其他请求的输出间隔。

假设同一批里的四条请求分别生成 20、100、150 和 220 个 token。如果整个批次必须等最后一条请求结束，四个槽位在 220 步中本可生成 880 个 token，实际只生成 490 个，槽位利用率约为 55.7%。对第 30 步到达的新用户，这意味着第一个槽位已经空了，他却还得等 190 步。连续批处理把重新组批的时点提前到每次前向结束，新请求便有机会用上这些空位。

Orca 的逐迭代调度与请求补位

Orca 每次只为一批请求执行一轮。调度器按请求到达的先后顺序选取当前未在运行的请求，每批最多接纳 max_bs 条。请求首次入选时，系统还要按该请求允许的最大总词元数 max_tokens 预留 KV 缓存槽位；如果剩余槽位不够，这一轮就停止继续选取。新请求需要先处理整段提示（prefill），已开始生成的请求则只解码一个新位置（decode）。在线性层和层归一化中，Orca 把这些请求的输入沿词元维拼接起来。到了注意力计算，它按请求拆开，分别读取各自的历史 KV，再把结果拼回去供后续算子使用。这就是论文所说的选择性批处理。Orca，第 3 节、算法 1

逐迭代调度也意味着，主机在每一步都要花时间准入请求、重新组批。按 7B 模型、批大小为 1 的示例，解码一步的理想下界约 7.4 ms。如果主机每步还需 1 ms 决策，单是决策就相当于这一下界的约七分之一。队列再长也不能保证输出平稳。如果调度器将一段很长的提示一次放入本轮，所有正在解码的请求都要等这次迭代结束，才能生成下一个词元。把预填充和解码拆到不同 GPU，正是同一问题的另一种解法。预填充与解码的算术 · DistServe 的分离式服务

PagedAttention 的 KV 块表与按需分配

调度器即使找到了空闲计算槽位，也要给新请求分配 KV 缓存。设允许的最大序列长度为 2,048，平均完成长度只有 500，每个 token 的 KV 占 512 KiB。若按上限给每条请求预留一整块连续空间，每条先占 1 GiB，实际平均只用 250 MiB。按同样的 66 GB 可用容量估算，预留最长序列时大约只能容纳 61 条请求；如果只为实际使用的位置分配空间，则约能容纳 251 条。这是对容量的估算，还没有计入调度或执行时间。

PagedAttention 将 KV 分装在固定大小的物理块中。每条序列维护一张块表，把该序列依次使用的逻辑块号映射到显存里可以不连续的物理块。序列增长时只追加所需的块，未使用的空间因此集中在最后一个块。每块 16 token 时最多浪费 15 个位置；在尾块占用近似均匀、序列平均 500 token 的例子中，平均浪费约 1.5%，最坏约 3%。一条 2,048 token 序列有 128 个表项，32 位块号只占 512 B。这部分空间节省也有代价：注意力核函数读取 KV 时需要查块表，物理块过小还可能降低读取效率。

如果多个请求共享同一段提示，它们的块表最初可以指向同一组物理块。只有当新增词元使序列开始分歧时，系统才复制需要分别写入的末块，让各条后缀独立增长。对同一 2K 提示采样 nnn 次，容量于是接近一份公共提示加 nnn 份独立后缀。PagedAttention 作者在 A100 上运行了 13B 至 175B 的 OPT 和 LLaMA 模型。在论文所用的负载和相同延迟水平下，采用该机制的服务系统相对 FasterTransformer、Orca 报告了约 2–4 倍吞吐。PagedAttention，§4

分块预填充的 token 预算与解码间隔

显存能够容纳一条新请求，仍不意味着适合把它的整段提示立即放入当前批次。对 7B 参考模型，2K 提示的投影约需 28.7 TFLOP。在 A100 的稠密峰值下约 92 ms，以峰值的 30% 估算则约 306 ms。将整段预填充插入解码循环，一次相邻 token 间隔（TBT）就可能变成平常的十倍。用户会直接感到这次停顿，但平均输出词元间隔（TPOT）把它摊到了整条回答上：一次额外停顿 Δ\DeltaΔ 对输出 mmm 个 token 的请求只增加 Δ/(m−1)\Delta/(m-1)Δ/(m−1)。因此平均 TPOT 很接近平时的水平，也可能掩盖一次明显的停顿。

为了限制这次等待，调度器可以给每轮迭代设定 token 预算，先安排已有请求解码，再用剩余预算处理一段新提示。若把 2K 提示拆为四个 512 token 的分块，按上述假设，每块的投影约用 76 ms。已有请求可以在分块之间继续解码，但新请求必须等四块都处理完，才能返回首个词元。给每轮分配的预算越小，这两种等待之间的差别就越明显。前面分块写出的 KV 还要被后面分块读取：后三块分别重读 512、1,024、1,536 个历史位置，按 512 KiB/token 合计约 1.5 GiB。注意力核函数因此要处理两部分计算：当前块中各查询对既有前缀的访问形成一个矩形，块内的因果掩码则留下一个三角形。

Sarathi-Serve 将这种安排用于持续推进解码的混合批，论文评估包括单张 A100 的 Mistral-7B、两张 A100 的 Yi-34B 和流水并行的 Falcon-180B。Sarathi-Serve

RadixAttention 按最长公共前缀复用 KV

分块能限制一次预填充延迟，跨请求复用还能直接省去一部分预填充。多个请求若使用同一系统提示、同一组示例或同一篇长文档，就可能具有完全一致的 token 前缀。SGLang 的 RadixAttention 把 token ID 组织成基数树，新请求沿树找最长匹配，在本请求的块表中登记已有 KV 块，只计算余下后缀。缓存空间不足时，RadixAttention 可以移除最近最少使用的叶节点。vLLM 的自动前缀缓存则用当前完整块的 token 和父块的哈希标识缓存块，同样按最近使用情况决定淘汰顺序。RadixAttention · vLLM 的块哈希与淘汰

如果同一模型复用了长度为 LprefixL_{\rm prefix}Lprefix​ 的前缀，便可省去约 2PLprefix2P L_{\rm prefix}2PLprefix​ 的投影 FLOP，以及相应的 KV 写入。不过，维护块表、追加记录和保留暂时无人访问的缓存也会消耗资源。因此，一段提示即使计算昂贵，只要后续请求始终没有命中它，缓存这段提示就不会节省第二次预填充。

KV 抢占的恢复成本：重新预填充与主机换入换出

如果连续增长的序列用完了 KV 块，调度器就要暂时抢占某个请求。选择重算时，调度器丢弃该请求的 KV，恢复时再对提示和已经生成的所有 token 做一次预填充。按 7B、312 TFLOP/s，每 token 仅投影就需约 45 µs，达到峰值的 30% 时约 150 µs。换出则要把 KV 向主机送一次、取回一次。在 PCIe 4.0 ×16 有效带宽取 32 GB/s、每 token 512 KiB 的条件下，双向传输项约 33 µs/token。上述两个数只比较了理想计算时间与链路传输时间。选择实际恢复策略时，还须计入主机内存管理、链路争用和重新调度、分配资源所需的时间。

vLLM v0.6.3 的 V0 调度器默认重算，代码给出的理由是其开销通常更低；重算不支持含多条序列的组，像 beam search 这类组走换出。换出保存精确状态，重算在不同批形状下能否位级一致取决于数值实现。对被抢占的请求，两者最终都表现为某一次 TBT 拉长。调度器的抢占分支

一次调度迭代中的块回收、请求准入与组批

  1. 调度器先回收上一轮已完成请求的 KV 块，使这些块可以分给排队的请求。
  2. 如果现有空间无法容纳待接纳的请求，它还要决定暂时中止哪条序列，以及稍后怎样恢复。
  3. 对能继续运行的请求扣除已缓存的前缀，再按本轮 token 预算安排解码和剩余的预填充分块。
  4. 调度器将各请求的投影输入合批，同时把对应的历史块表交给注意力核函数。
  5. 前向结束后，服务程序追加本轮生成的 KV 并对输出采样，再把每条请求是否完成及其时间记录交给下一轮调度。

衡量这次调度可以从三处读数。实际分配的 KV 块数决定剩余容量，每步完成的有效 token 数决定吞吐，而相邻输出 token 的最长间隔则能反映用户经历的停顿。比如给一段长提示腾出更多预算，可以让它更早完成，却会延迟同批中正在解码的请求。

调度机制的适用条件与资料来源

当瓶颈是显存时，分页和前缀共享可以让更多请求入场；当用户等得太久时，则要查清等待来自组批、长提示还是被抢占后的恢复。下表列出了每种机制适用的条件。

能改动的机制直接收益同时付出的成本与适用条件
按迭代调度提前归还槽位并在下一步补位每步都要组批、提交，批次需能摊薄开销
选择性批处理投影行可以合并Orca 将注意力计算按请求拆开，再合并输出供后续算子使用
分页 KV物理存储随生成的 token 增长读块表和 gather 有成本，块大小权衡尾部浪费与寻址效率
前缀缓存精确匹配的前缀可复用占用缓存并增加查找与维护，负载要有实际重复
分块预填充限制解码单次被拖长的幅度长提示经过更多轮，后续块需要读先前的 KV
抢占临时腾出 KV 预算，接纳更需要运行的序列恢复时需要重算或搬运，发生在 KV 池已紧张的时候
