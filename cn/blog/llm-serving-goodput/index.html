DistServe 的预填充与解码分离：按延迟目标配置 GPU

一条长提示占用 GPU 时，其他请求可能迟迟等不到下一个词元。DistServe 把预填充和解码分给两组 GPU，让两个阶段分别排队；分开后能多服务多少请求，还要看两池的配比，以及历史键值要经过哪条链路交接。

语言模型处理提示时，所有输入 token 的位置都已知，同一层可以并行计算这些位置。开始生成输出后，每一步却必须先得到前一个 token，才能确定下一个位置的输入。前者叫 prefill，后者叫 decode，两者共用同一份权重，但矩阵形状与数据复用方式并不相同。

当两个阶段共用一组 GPU 时，调度器每轮都要在已有请求和新请求之间分配时间。如果两次 decode 之间加入一段很长的 prefill，已有请求就要更久才能收到下一个 token。反过来，如果调度器一直优先运行 decode，新请求收到首个 token 的时间就会推迟。DistServe 把两种计算分给两组 GPU，模型计算本身不变，改的是两个阶段怎样争用资源，并因此多出一件原先没有的工作：把算好的 KV 从一个池搬到另一个池。

把两个阶段分开，还要算一笔成本。如果两个池可以各自扩容，却要把几百 MiB 的 KV 缓存送过一条慢链路，同一批 GPU 最终能否多服务一些请求？要回答这个问题，除了比较两个阶段的计算量，还得看请求何时过池、缓存走哪条链路。下文的服务吞吐与延迟取自 DistServe 作者的实验。本地复算了载荷、请求长度平方和与表格误差。

预填充与解码的矩阵形状及权重复用

对长度为 ℓ\ellℓ 的提示，每一层的线性变换可以写成 XWXWXW，其中 X∈Rℓ×hX\in\mathbb R^{\ell\times h}X∈Rℓ×h。由于全部 ℓ\ellℓ 个位置都已知，模型逐层处理整段输入时，每层都可以并行计算各个位置的 K/V，再通过因果掩码限制注意力的可见范围。最后一层的末位置隐状态经输出投影得到各词元的分数（logits），解码规则据此选出首个输出词元。

生成首个 token 后，模型把它作为下一次前向的输入。此时每条序列只增加一个位置：线性层处理这一行，注意力用它的 query 访问历史 K/V，并将新的 K/V 追加到缓存。此后每生成一个 token，都要重复这一解码过程。缓存让旧位置不必重走整个模型，但它们的 key 和 value 仍然要被当前位置读到。

对线性层来说，prefill 可以把多个位置合成一次矩阵乘法，读来的同一份权重可以反复使用。单条请求进入 decode 后，每次只有一个新位置，运算更接近矩阵与向量相乘；如果将多条请求组成同一批，权重又可以在请求之间复用。因此，大批量预填充常先受算力限制，小批量解码常先受带宽限制。判断某次执行的瓶颈，还得知道批量、序列长度、模型结构和设备。

长输入的 Attention 另有成本。设一个 prefill batch 里请求长度为 l1,…,lbl_1,\ldots,l_bl1​,…,lb​，线性层要处理的 token 总数是

t=∑ili,t=\sum_i l_i,t=i∑​li​,

而请求内部的位置配对工作量与

t2=∑ili2t_2=\sum_i l_i^2t2​=i∑​li2​

相关。四条 256-token 请求和一条 1024-token 请求都是 1024 个 token，长度平方和分别是 262144 和 1048576，后一个是前一个的四倍。整轮 prefill 的时间不会跟着变成四倍：线性层、Attention kernel、并行通信和固定开销还要合起来。DistServe 附录 A 因此同时保留 ttt 和 t2t_2t2​，再用 profiling 拟合延迟模型，没有给每个 token 标一个固定成本。

如果两个阶段共用一个执行实例，同一批任务就会对执行时间提出不同要求。解码需要频繁运行，以缩短相邻输出之间的等待；长提示的预填充则需要处理足够多的输入，才能摊薄单次提交的开销。一段很长的 prefill 插进两次 decode 中间，token 间隔当场被拉长。

上图用矩形表示执行先后，矩形的宽度不代表实测耗时，两种部署的 GPU 数量也可以不同。下图最先执行 decode 的是已经收到首个 token 的旧请求；新请求则要等自己的 prefill 和 KV 交接完成，才能继续生成。

如果希望两个阶段继续共用 GPU，可以把长提示切成较小的块，在相邻的 decode 之间分次处理。这种分块预填充（chunked prefill）缩短了单次停顿，但会增加迭代次数，有时也会降低每次计算的效率。DistServe 则把预填充池（P 池）和解码池（D 池）部署在不同设备上，让两个池分别选择并行度和 GPU 数量。P 池内部仍然可以分块处理长提示。

首 token 延迟、逐 token 延迟与联合达标率

分开执行是否改善了用户体验，需要分别观察首个 token 与后续 token 的等待时间。设请求 iii 在 aia_iai​ 到达，第一个 token 在 ti,1t_{i,1}ti,1​ 返回，最后一个在 ti,mit_{i,m_i}ti,mi​​ 返回。mi>1m_i>1mi​>1 时，

TTFTi=ti,1−ai,TPOTi=ti,mi−ti,1mi−1.\mathrm{TTFT}_i=t_{i,1}-a_i,\qquad \mathrm{TPOT}_i=\frac{t_{i,m_i}-t_{i,1}}{m_i-1}.TTFTi​=ti,1​−ai​,TPOTi​=mi​−1ti,mi​​−ti,1​​.

TTFT 衡量请求到达后等待首个 token 的时间，TPOT 则把首个 token 之后的等待平均分配到各个输出间隔。读到相同的 TPOT 时，两条请求中最长的停顿仍可能相差很大，这个平均值也不能替代输出间隔的高分位数。只有一个输出 token 时没有可供求平均的间隔，需要另外约定这类请求的统计方法。

给定阈值 TF,TOT_F,T_OTF​,TO​，一条请求只有同时满足这两个延迟目标才算达标。到达率 λ\lambdaλ、完整配置 ccc 下，联合达标率是

A(λ,c)=1n∑i=1n1{TTFTi≤TF ∧ TPOTi≤TO}.A(\lambda,c)=\frac1n\sum_{i=1}^n \mathbf1\{\mathrm{TTFT}_i\le T_F\ \land\ \mathrm{TPOT}_i\le T_O\}.A(λ,c)=n1​i=1∑n​1{TTFTi​≤TF​ ∧ TPOTi​≤TO​}.

这里的配置包括 GPU 数量、两池配比、并行方式和路由策略。要求至少 qqq 比例的请求达标时，DistServe 用每张 GPU 在该约束下可持续承载的最大请求到达率衡量 goodput：

Goodput⁡(c;q)=sup⁡λ:A(λ,c)≥qλG(c).\operatorname{Goodput}(c;q)= \sup_{\lambda:A(\lambda,c)\ge q}\frac{\lambda}{G(c)}.Goodput(c;q)=λ:A(λ,c)≥qsup​G(c)λ​.

这个定义解释了为什么最高吞吐配置可能无法满足延迟目标。加大批次虽然能提高吞吐，排队等候组批的请求却可能错过首 token 时限；把过多资源分给 P 池，又会使 D 池的输出间隔超标。容量得按完整请求统计，失败、超时、被拒绝的请求不能从分母里删掉。

如果分别报告两个指标的达标率，也可能高估真正合格的请求数。举例说，100 条请求中有 80 条同时达标，另有 10 条只在 TTFT 上失败，剩下 10 条只在 TPOT 上失败。单看每项指标都能得到 90% 达标，而两项都满足的请求只有 80%。

图中标出的是这组构造数据，每个点保留同一条请求的两个时间。比较 P:D 配比或 KV 传输路径时，两套配置需要沿用相同的首 token 和后续 token 时限，再数有多少完整请求同时通过。

预填充池和解码池的容量与并行策略

固定模型、长度分布和 SLO，一个 P 实例每秒持续处理 μP\mu_PμP​ 个请求，一个 D 实例处理 μD\mu_DμD​ 个。分别配备 nP,nDn_P,n_DnP​,nD​ 个实例后，即使忽略通信和长尾排队，能够持续承载的请求到达率也以两池中较小的总服务速率为上限，即

λ≤min⁡(nPμP,nDμD).\lambda\le\min(n_P\mu_P,n_D\mu_D).λ≤min(nP​μP​,nD​μD​).

取最小值是因为每条请求都要经过两池。一侧已有余量时，继续给它增加 GPU 无法处理另一侧积压的请求。这个上限假定两池服务速率已知。实际的 μ\muμ 会随批量、长度分布和并行策略改变，而且池还没有完全饱和时，请求就可能因排队过久而错过延迟目标。

DistServe Figure 1 给出了一个具体的动机实验：OPT-13B、512 输入 token、64 输出 token、A100 80 GB。混合执行约 1.6 请求/s；单独跑时 P 约 5.6 请求/s，D 约 10 请求/s。于是 2P+1D 的理想瓶颈约 min⁡(11.2,10)=10\min(11.2,10)=10min(11.2,10)=10 请求/s，除以三张 GPU 约 3.3 请求/s/GPU。3.3 是忽略交接与真实排队后的配比估算，不是测出来的完整系统容量。

一个服务实例可以用多张卡。采用张量并行（TP）时，一层内的计算由多张卡分担，但卡间要交换部分结果；采用流水线并行（PP）时，不同批次可以同时占用不同层段，不过前后两段相互等待会留下流水线空隙。P 池需要尽快处理长输入，D 池还要兼顾持续生成的批量与 KV 缓存容量，因此两个池未必适合相同的 TP/PP 设置。

两个池还要分别预留显存。D 池中的序列不断生成新 token，所以可用的 KV 缓存决定了它最多能同时容纳多少条序列。P 池也会保留已经算完但尚未交接的 KV，因此计算单元尚有余量时，两个池都可能因显存不足而无法接纳新请求。

图里的 Pending KV 是 P 已算好、还没迁完的缓存，Active KV 是 D 正在生成的序列状态，两处都可能先耗尽空间。λE[BKV]\lambda E[B_{\rm KV}]λE[BKV​] 是每秒要交接的字节数，得跟有效带宽比，不能直接与每秒请求数相加。

从模型形状计算每条请求的 KV 迁移量

两池在不同设备上运行时，D 还需要拿到 P 为该请求计算的各层 K/V，才能生成后续 token。对于稠密 KV 缓存，忽略填充和元数据后，每条请求要传输的有效载荷为

MKV=2LNKVdhℓs.M_{\rm KV}=2L N_{\rm KV}d_h\ell s.MKV​=2LNKV​dh​ℓs.

2 对应 K 和 V，LLL 是层数，NKVN_{\rm KV}NKV​ 是 KV head 数，dhd_hdh​ 是 head 维度，ℓ\ellℓ 是上下文长度，sss 是单元素字节数。GQA 里多个 query head 共用 KV head，所以这里不能填 query head 数。

取 40 层、40 个 KV head、head 维度 128、FP16、512 token：

MKV=2×40×40×128×512×2=419430400 bytes=400 MiB.M_{\rm KV}=2\times40\times40\times128\times512\times2 =419430400\ \text{bytes}=400\ \text{MiB}.MKV​=2×40×40×128×512×2=419430400 bytes=400 MiB.

全量串行走一条 25 Gbit/s 链路，理想速率 3.125 GB/s，没有任何协议和排队开销也要约 134.218 ms。只把 KV head 改成 8 个，载荷降到 80 MiB，理想时间约 26.844 ms。上下文涨到 2048 token，两者变成 1600 MiB / 536.871 ms 和 320 MiB / 107.374 ms。

图中的传输时间由载荷和标称链路速率计算，GB/s 采用十进制，MiB 采用二进制。部署时若用 TP/PP 把模型分给多个进程，每个进程只发送自己持有的部分，完整载荷可能有多个出口。即使多张卡同时发送，它们也可能共享网卡、PCIe 上行链路或交换机出口，实际带宽仍需测量。

部署要回答的不只是网络够不够快，还有哪些数据有必要过网络。DistServe 的低跨机带宽放置方案按层段把对应的 P 和 D 共置到同一节点：模型分两段，节点 1 放第一段的 P、D，节点 2 放第二段。P 的中间激活往下一段走，每段产生的 KV 留在本节点交给对应 D。真实 TP rank 还要展开，但激活和 KV 已经能走不同的物理路径。

按层段共置也会限制并行配置。某种组合即使能让 P 和 D 分别跑得更快，两侧的层段也不一定能放进同一节点。DistServe 因此针对跨节点带宽充足和受限的两种网络分别搜索放置方式。只比较 P 的计算速度，会低估每个请求将几百 MiB 状态送过慢链路的代价。

除了单次传输延迟，还要比较所有到达请求的总传输需求与链路带宽。到达率 λ\lambdaλ、平均 KV 为 Mˉ\bar MMˉ 时，系统持续需要约 λMˉ\lambda\bar MλMˉ 的有效带宽。满负载下的队列会让少数请求等很久，无争用的 M/BM/BM/B 代替不了尾延迟。论文 §4.3 让 D 按需拉取 KV，P 暂时留着缓存吸收一部分积压；有限的缓存能缓冲突发，不能无限消化过载。

DistServe 源码中的请求移交与 KV 块迁移

从客户端看，KV 传输究竟发生在首个 token 之前还是之后，要看服务实际怎样交接。DistServe 把 prefill 叫 context stage，ContextStageLLMEngine._step 拿到计算结果后先通过输出回调交付生成 token，再为没结束的请求构造 MigratingRequest，放进连接两阶段的队列。迁移请求保存了 P 侧的缓存块表和并行配置。由于 D 此时还没有读到这些数据，P 必须暂时保留源缓存块。

接收侧 DecodingStageLLMEngine._migrate_blocks 先分配目标块，拿到 D 的 block 表，再调各 worker 迁移。下面节选迁移和回收两段，中间省了生命周期日志；代码来自 固定 commit 的 single_stage_engine.py，项目用 Apache-2.0 许可。

await asyncio.wait(self._remote_call_all_workers_async(
    "migrate_blocks",
    migrating_req.block_indexes,
    migrating_req.context_parallel_config,
    target_block_indexes
))
# ... lifetime logging ...
self.clear_migrated_blocks_callback(migrating_req)

回调再让 P 释放对应请求的资源。worker.py 里的 migrate_blocks 把两端 TP/PP 配置、源和目标 block 索引、K/V 缓冲交给 torch.ops.block_migration_ops.migrate_blocks。这不只是搬一段连续字节，还要把同一层、同一逻辑 KV 片映射到另一组并行 rank。worker 实现

这段 Python 可以确定控制层按什么顺序发起交接。要判断异常是否会传回、目标 GPU 何时可以读取 KV，还需要查看工作进程和原生迁移操作在什么条件下报告完成，仅凭 asyncio.wait 无从判定。本文没有运行这套多卡系统，也没有验证它的故障路径。

这组调用的先后顺序解释了客户端时间线上的一个现象：prefill 可以先返回首 token，再交接 KV。搬运延迟因此不全算进 TTFT，而可能落在第一、第二个生成 token 之间。只记 P 耗时和 D 耗时很容易漏掉这段等待；测量得保留客户端 token 时间，把 KV 准备、传输、可消费时间关联回同一请求。

P 完成计算后，源缓存仍然占着显存，直到 D 接收完毕才能回收。若 D 来不及接收，已完成的请求便会在 P 越积越多；若 P 提前释放缓存，下一次 prefill 又可能把仍待传输的数据覆盖。

90% 达标目标下，ShareGPT 的请求率相对 vLLM 提高 2.0–4.6 倍，相对 DeepSpeed-MII 提高 1.6–7.4 倍；HumanEval 相对 vLLM 是 5.7 倍，LongBench 是 4.3 倍。另一组固定请求率、同步收紧 TTFT/TPOT 阈值，ShareGPT 相对 vLLM 能承受的严格程度是 1.8–3.2 倍，相对 MII 是 1.7–1.8 倍；HumanEval 是 1.4 倍，LongBench 是 12.6 倍。两组数沿不同坐标方向比较：7.4 倍请求率和 12.6 倍 SLO 严格程度不在同一个运行点上，SLO 阈值收严 12.6 倍，也不表示实际延迟降了 12.6 倍。DistServe §6

对照实现的条件同样要算进去：vLLM 的 TP 随模型取 1、4、8；论文用的 DeepSpeed-MII 实现受词表分割和显存限制，没有对应的 OPT-175B 配置。这是所测版本和配置的限制，不能说其它版本都支持不了。

若完整的 400 MiB 都要经过 25Gbps 链路，前面的估算给出了百毫秒级延迟。作者在另一组配置中却报告 OPT-175B/ShareGPT 的传输耗时不到总阶段耗时的 0.1%，95% 以上的请求迁移低于 30 ms。该配置的放置方式解释了这一差别：低带宽放置让对应层段主要在节点内经 NVLink 交接。另一个细节是分母，0.1% 是把各请求的阶段时间分别累加后算的占比，传输 CDF 才能看单请求分布，两者不能互换。

Figure 8–10 是实机端到端结果。Figure 11 研究更高跨节点带宽和放置方案时用模拟，因为 testbed 没有所需带宽，基线也不支持全部待比配置。Table 2 给出七个到达率的实机/模拟校验，逐项重算最大绝对差 1.8 个百分点；比如到达率 2.0 时 vLLM 是 52.8% / 51.0%，DistServe-Low 是 99.3% / 99.3%。这个一致性支持对应配置的模拟用途，推不出所有突发流量下的误差上界。附录 C 还报了 99% 达标目标，仍在同一套受控实验里。

从这些结果可以看出，分开两池减轻了阶段间的阻塞，也让两个阶段可以独立选择并行配置；再配合合理放置，才有机会缩短 KV 迁移时间。最终服务容量取决于计算干扰、并行配置和迁移开销三者。

多轮对话中的 KV 局部性与请求路由

前面的分析假定输入来自一条新请求。对话进入下一轮时，请求路由还要考虑数据目前的位置：历史 KV 已经在某台 D 机器上，新消息只有一小段。这时固定把新输入全送 P，就可能为少量增量计算搬动一大份已有状态。

设已有历史长度 hhh、新增输入长度 uuu。复用历史时，新增 token 的各层线性变换只处理新位置，Attention 仍要读历史 K/V；它不等于从零处理长度 h+uh+uh+u 的整段 prefill，也不是每请求只新增一个位置的普通 decode。这类 append-prefill 的计算量和干扰程度得单独建模。

PPD v1 研究让部分后续轮次留在 D 执行追加输入，用离线测量表和 TTFT/TPOT 权重做选择。让请求留在 D 可以省去传输和在 P 排队的时间，但处理新增输入仍会推迟同池其他请求的解码。论文 Figure 5 记录的 TPOT 上升就反映了这种竞争。该实验是单节点 4 张 H100 80 GB、主模型 Llama-3.1-8B，每个合成负载条件运行 10 秒，附录配置用 ZeroMQ 传输。换为跨机器的 RDMA 网络后，传输与计算之间的取舍需要另行测量。

跨请求前缀复用又加一层冲突：有缓存的机器可能很忙，空闲的机器没有缓存。Mooncake 用包含主存在内的共享 KV 存储，把命中、缓存搬运和计算负载一起纳入调度，还能靠复制热门缓存缓和集中访问。路由于是不再只是挑最短队列，比较的是等待、取回状态和重新计算的总成本。

Mooncake 还改变了硬件、模型和延迟指标，因此其吞吐提升与 DistServe 的结果不能直接比较。它的相关实验用仿照 Llama3-70B 结构的 dummy 模型，每节点 8 张 A800、4 张 200Gbps NIC，Figure 1 的比较各用 16 个节点；TBT 定义成最长 10% token 间隔的平均值，TTFT 阈值 30 秒，和前面的平均 TPOT、阈值都不同。这个实验能说明缓存位置为何影响路由选择。

当输入较长、输出间隔要求严格且 GPU 充足时，独立的 P 池可以把长预填充移出解码队列。如果一轮对话只追加少量输入，而且历史 KV 已经在 D，留在当地计算往往能省去迁移。GPU 少的时候，两个池重复保存权重还会减少可用于 KV 的显存；离线任务没有严格的首 token 和输出间隔要求，混合执行把 batch 填满也可能更合算。DistServe §7 讨论过资源紧张和离线吞吐，高级抢占与容错留作后续工作。

评估一种放置方案时，可以从一条完整请求入手：先确定它在哪个池排队、何时返回首 token，再跟踪 KV 的迁移路径和后续 token 的生成间隔。把这些时间同实际占用的 GPU 数、缓存和链路带宽对应起来，就能比较两种配置在相同延迟目标下各自能承载多少请求。
