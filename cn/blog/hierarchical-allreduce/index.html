分层 AllReduce：节点内梯度归约与跨节点网卡带宽

三个节点先在各自内部归约梯度，再把同一位置的分片跨节点求和。这样能减少单张 GPU 的跨机发送量，但同一节点的分片仍可能共用一张网卡。计算通信时间下界时，要把各卡经过这个出口的字节加在一起。

在有 HHH 个节点、每节点有 GGG 张 GPU 的数据并行训练中，每张卡都用不同样本计算梯度。因此，同一参数的更新要汇总 G×HG\times HG×H 份贡献。若节点内通过 NVLink 连接，节点间通过带宽较低的 InfiniBand 连接，可以先在节点内求部分和，再跨节点合并，最后将完整结果分发回各卡。

在每节点八张卡的配置下，每张卡负责八分之一的梯度分片。跨节点归约时，各张卡还要分轮收发这些分片，八张卡的数据也可能共用同一张网卡。为了估算分片能节省多少时间，我们先用一组具体的梯度检查每个位置是否恰好收齐所有贡献，再分别计算每张卡和整个节点的跨机发送量。

三节点上梯度分片的机内归约与跨机合并

设集群有 HHH 个节点，每个节点运行 GGG 个参与通信的进程（rank），每个进程管理一张 GPU。节点 hhh、本地编号 ggg 的输入记为 xh,g∈RNx_{h,g}\in\mathbb R^Nxh,g​∈RN，同一个位置 iii 始终是同一个参数。目标是

第二步，各节点负责同一分片的 GPU 组成一个跨节点通信组。各节点的 0 号卡归为一组，1 号卡归为另一组，其他编号以此类推。每组独立做一次 AllReduce，

这样，位置 5 的三个节点内部分和都进入同一个跨机通信组（1 号组）。跨机阶段结束，每个节点的 1 号卡都有了 1128；另外三张卡还没拿到这个位置，但它们各自持有别的正确片。

第三步，各节点在本地做 AllGather，将四张卡各自持有的结果分片分发给其他卡，并按位置拼回完整向量：

图中只画两个节点的第 0 片，以便看清这个分片的局部和怎样各自进入全局和一次。每个其他分片都需要经历相同的过程。图中的求和节点表示归约操作，具体实现可以将收发工作分给多张 GPU。

三个阶段合起来是 RS–AR–AG：机内 ReduceScatter、跨机 AllReduce、机内 AllGather。正确性来自两个独立条件：每片收齐全部贡献，所有片覆盖完整位置范围。它不要求节点数是二的幂，也不看哪层网络更快。

按贡献来源检查梯度分片的遗漏与重复

1 号卡收到的是第 1 片上所有本地 GPU 的贡献，它仍然缺少其他分片位置的数据。假如在 ReduceScatter 之后只让 0 号卡与其他节点通信，它可以归约本地持有的第 0 片，但位置 5 在第 1 片上，三个节点的部分和便没有机会相加。

单代理方案本身可以是对的：先把完整机内和归约到代理，代理之间做全局 AllReduce，最后机内广播。它和分片方案的区别只在各片由谁持有、走哪些路径，求和目标完全一样。

反过来，若先做机内 AllReduce，本节点四张卡都会保存同一份完整的局部和。这时如果将所有副本放进同一次全局求和，就会得到

∑h∑g=0G−1sh=G∑hsh=Gy.\sum_h\sum_{g=0}^{G-1}s_h=G\sum_hs_h=Gy.h∑​g=0∑G−1​sh​=Gh∑​sh​=Gy.

这样，正确值 1128 就会被重复计算成 4512。即使每张卡最后拿到的值完全一致，也要检查其中是否重复累加了相同来源。

如果机内 AllReduce 后建立四个彼此独立的同号卡组，结果又会不同。每个跨机组从每个节点只取一份局部和，因此四组都能得到正确的 1128。代价在于四组都要发送完整向量，产生了重复通信；由于副本没有进入同一次加法，求和本身不会出错。

为了区分遗漏、重复求和与单纯的数据复制，可以给每个输出位置附一行来源计数：有多少原始 rank 就有多少列，每份输入被加一次就加一。正确结果里每个真实位置都该是全 1；漏片出现 0，重复求和出现大于 1 的数。

图中结果来自一个 CPU 整数模型，它模拟三个节点，每个节点四张卡，输入长度为 13。程序先补零到 16，按四片处理，最后裁掉补齐部分。正确结果的前 13 行应各有 12 个 1，补齐位置没有原始贡献。若只有 0 号片跨机，只有前四个真实位置收齐全部来源；若机内副本一起再次相加，每格的计数就变成 4。

用不溢出的 int64，是为了把归约结构和浮点舍入分开。换成真实梯度后，贡献仍然该各出现一次，可分层改变了加法结合顺序，结果未必和串行求和逐位相同。高精度参考、非有限值检查、合适容差都还得留着，容差不能大到把漏片也放过去。

训练的最后那步 AllGather 未必总要跑。每张 GPU 只拥有一片优化器状态时，它只要对应的全局梯度片就能更新参数。FSDP hybrid sharding 的梯度归约就是分片组内 ReduceScatter、复制组间对同号片 AllReduce（见 FSDP 与 Megatron）；等前向需要完整参数时再做参数 AllGather。那是另一种张量、另一段生命周期，和「立刻复制完整梯度」不是一件事。FSDP §3.2.2

分层环形归约的每卡流量与共享网卡出口

确认每个分片都收齐了贡献后，再计算这些分片在各段链路上产生的流量。令每个 rank 的完整输入为 SSS 字节，先假设标准分块 ring：PPP 个参与者排一圈，每轮只发下一位一片。

ReduceScatter 有 P−1P-1P−1 轮，每轮 S/PS/PS/P；AllGather 再来 P−1P-1P−1 轮。每个 rank 总发送

Vrank=2P−1PS.V_{\rm rank}=2\frac{P-1}{P}S.Vrank​=2PP−1​S.

公式按各进程发送的有效载荷计数。它已经反映了数据在环中的传递，再加上对端的接收量就会把同一次传输计算两遍。换用不同的 NCCL 算法时，轮数可能改变，实际链路的利用率也不由这个公式决定。

分层方案的机内 RS 加 AG，每张卡发送

Vlocal,rank=2G−1GS.V_{\rm local,rank}=2\frac{G-1}{G}S.Vlocal,rank​=2GG−1​S.

中间有 GGG 个跨机组，每组只处理 S/GS/GS/G 大小的片，各有 HHH 个参与者。每卡跨机发送

Vcross,rank=2H−1HSG.V_{\rm cross,rank}=2\frac{H-1}{H}\frac SG.Vcross,rank​=2HH−1​GS​.

与每张卡发送完整向量相比，单卡的跨机发送量确实缩小到了 1/G1/G1/G。同一节点有 GGG 张卡发送数据，把所有卡的发送量相加，节点出口的总量为

Vcross,node=2H−1HS.V_{\rm cross,node}=2\frac{H-1}{H}S.Vcross,node​=2HH−1​S.

如果先将完整的机内和归约到一张代理卡，再由各节点的代理卡运行 ring AllReduce，算出的节点总载荷相同。分片让多张卡有机会并行发送，但节点总计需要交换的数据不会因此再减少 GGG 倍。

扁平 ring 也得按实际路径算。把 HGHGHG 个 rank 放进同一个环、同节点 rank 连续排列，每节点只有一条环出边跨到下一个节点。每轮那条边发 S/(HG)S/(HG)S/(HG)，共 2(HG−1)2(HG-1)2(HG−1) 轮，节点跨边界发送

Vflat,cross,node=2HG−1HGS.V_{\rm flat,cross,node}=2\frac{HG-1}{HG}S.Vflat,cross,node​=2HGHG−1​S.

同节点内部的环边不过网卡，所以不能拿每 rank 发送量乘 GGG 当跨机流量。交错排列 rank 会增加跨机边数；如果使用多个通道、双向环或其他拓扑，就要按实际路径重新统计每条跨机边的发送字节数。

短消息的启动延迟与分层通信的执行顺序

前面的估算关注大消息占用的链路时间。消息较小时，每轮固定的启动延迟也会在总耗时中占较大比重。用 α\alphaα 表示 ring 单步延迟、忽略归约计算，一个简单模型是

TAR(P,S)≈2(P−1)α+2P−1PSB.T_{\rm AR}(P,S)\approx2(P-1)\alpha+2\frac{P-1}{P}\frac SB.TAR​(P,S)≈2(P−1)α+2PP−1​BS​.

如果按顺序执行机内 RS/AG 和跨机 AR，并假设各跨机分片都能使用独立、等速的路径，三个阶段的估算时间可写成：

Thier≈2(G−1)αlocal+2G−1GSBlocal+2(H−1)αcross+2H−1HSGBcross.\begin{aligned} T_{\rm hier}\approx{}&2(G-1)\alpha_{\rm local} +2\frac{G-1}{G}\frac{S}{B_{\rm local}}\\ &+2(H-1)\alpha_{\rm cross} +2\frac{H-1}{H}\frac{S}{G B_{\rm cross}}. \end{aligned}Thier​≈​2(G−1)αlocal​+2GG−1​Blocal​S​+2(H−1)αcross​+2HH−1​GBcross​S​.​

节点带宽共享时，最后一项的分母换成节点总有效带宽。多个组的启动与排队时间还可能互相串行，因此仅替换带宽分母不足以预测实际耗时。这个式子把「减少慢链路步数」「更充分地用并发路径」和「新增机内阶段」放进同一次比较。

BlueConnect 把这种分解推到多层网络。rank 写成三轴坐标 (a,b,c)(a,b,c)(a,b,c)，轴大小 p0,p1,p2p_0,p_1,p_2p0​,p1​,p2​：先沿 ccc 做 ReduceScatter，再沿 bbb 对所得片做 ReduceScatter，最后沿 aaa 再做一次。一个拥有者的载荷依次变成

S⟶Sp2⟶Sp2p1⟶Sp2p1p0.S\longrightarrow\frac S{p_2}\longrightarrow\frac S{p_2p_1} \longrightarrow\frac S{p_2p_1p_0}.S⟶p2​S​⟶p2​p1​S​⟶p2​p1​p0​S​.

至此，每个分片都收齐所有进程的贡献，但仅由一个进程持有。接着沿 a,b,ca,b,ca,b,c 逆序执行各层的 AllGather，逐层恢复各进程持有的向量范围。前面 RS–AR–AG 方案中的跨机 AR 也可以拆成 RS+AG，因此两者沿用了同一种归约与分发的分解。BlueConnect §3（条件与局限在 §3.4）

按层次分解后，前期较大的载荷可以优先在快链路上交换，较慢的链路只处理已经缩小的分片。实际加速仍取决于参与者的分组与物理出口是否对应。即使某一层每张卡只传一个很小的分片，所有分片仍可能在同一条上行链路排队。

作者的训练实验用了 48 台 IBM S822LC，每台四张 P100-SXM2、机内 NVLink、单端口 100 Gbit/s InfiniBand。ResNet-50/ImageNet-1K，每卡 batch 32，192 卡总 batch 6144，梯度 FP32，数据预装 RAM disk。正文以单卡 163 ms 为基线，192 卡时以 GLOO 作对照，它的额外开销约 58 ms，BlueConnect 约 31 ms。

TACCL 的归约融合与 Trivance 的多端口假设

按通信路径估算时，我们把一次分片发送和归约算作一个步骤。实际 GPU 后端可能把它拆成接收、求和、写临时缓冲区、重新读取和发送；如果这些动作无法融合，即使规划出的路径更短，额外的访存与同步也可能抵消收益。

TACCL（NSDI 2023）按用户给的 communication sketch 综合通信计划。在两台 DGX-2、消息不小于 512 MB 的 AllReduce 上，它曾最多比 NCCL 2.8.4-1 慢 9%。作者把这个负结果归到后端缺少接收、归约、复制、发送的融合操作：路径层省下的工作，可能被新增的指令和同步开销抵消。TACCL Figure 8(i)

同一论文最高 6.7 倍的结果来自两台 DGX-2、32 GPU 的小到中等消息 AllGather，不是这组 AllReduce。§7.2 还显示增加执行实例会拉高小消息延迟；作者用发送开始时同步访存调度来解释，属于原因推测。对于更大的消息，额外并行带宽才更有机会抵偿新增的启动成本。

多端口算法则改变了另一个条件，即每个参与者同时可以向多少条独立路径发送数据。Trivance 面向双向 ring 和多维 torus，用多个方向并发减少逻辑步数。它的 §6 是 SST 包级仿真，Appendix E 默认链路 800 Gb/s，并且没有额外加「所有接口共享一个节点总注入上限」的约束；Appendix D 也要求这些路径能同时使用。Trivance

若物理机器上的两个方向最终共享一条拥挤的上行链路，数值归约仍然正确，仿真所需的并发条件却不再成立。这与八张卡共用一张网卡受到的限制相同。BlueConnect 研究怎样按网络层次分解通信，TACCL 检验后端执行通信计划的成本，Trivance 依赖多端口并发；三组实验因而不能用各自报告的最高倍率直接排序。

将归约接入训练时，还要把各通信阶段与梯度产生及使用的顺序对应起来。反向在计算 stream 上写出梯度，通信 stream 得等这片梯度就绪才能读；跨机归约要等机内 ReduceScatter 的结果；优化器也得等它要的那片完成。NCCL 普通调用返回只表示操作已提交到 CUDA stream，不表示数据已经能被任意消费者用，跨流依赖要用 stream/event 语义建。NCCL CUDA Stream Semantics

位置 5 的数学归属落到实现里，对应的是 buffer offset、片长度、dtype 和 communicator 的 rank 映射。各节点必须用同一套规则解释「第 1 片」，补齐和裁剪也得一致。CPU 来源模型没验证真实网络的偏移、包序和故障恢复，更没实现 GPUDirect RDMA 的完成与可见性协议。重试若把同一份贡献再加一次，来源次数又大于 1，光靠重发解决不了。

对整次参数更新而言，决定等待时间的是关键路径上最后一份可用的梯度。某段通信即使明显加速，早已被反向计算盖住时，整步收益就很小；相反，即使归约很短，只要优化器仍在等待它，就可能决定整步的完成时间。因此实测应分别记录机内阶段、跨机阶段、完整归约和整个训练步，再用单卡与节点的字节数、链路 GB/s 和整步时间解释瓶颈出现在哪一段。
