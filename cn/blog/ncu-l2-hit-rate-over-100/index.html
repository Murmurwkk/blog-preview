Nsight Compute 的 L2 命中率越界：原始计数与跨轮采样核查

Nsight Compute 在两个 kernel 上报出了超过 100% 的 L2 命中率。保留底层计数的后续采样表明，异常报告里的命中扇区数确实多于查询总数。GB206 后端生成的离线计划把两者安排在不同采样轮次，实卡上究竟是什么活动改变了计数，现有报告还无法确定。

我用 Nsight Compute 分析一个 Softmax kernel 时，报告里的 L2 命中次数竟是查询总数的约 102%，换成另一个注意力 kernel，命中率仍有约 101%。两个程序都算对了，工具也正常退出，因此我从最早能读到的原始报告开始，检查这些额外的命中究竟在哪一步出现。两条记录分别来自 INT8 KV 缓存实验和在线 Softmax Attention 实验。

我从原始报告追到计数器后端，又分两批各采了 60 份报告。在保留底层计数的越界样本里，命中扇区数确实超过了查询扇区总数。同一批扇区查询中，命中数不可能多于查询总数。为查明两项计数能否来自不同轮次，我把它们的底层依赖一起交给 GB206 后端。它生成的离线计划把两组依赖安排在不同的隔离轮次。

原始 NCU 报告中的越界 L2 命中率

我用 NVIDIA 的 Python Report Interface 直接读取 .ncu-rep，两项原生指标在导出 CSV 之前就已经超过 100%。CSV 的变化只有小数位数，因而可以排除导出、单位换算和绘图这三道处理。

两条记录都用了应用重放（application replay）：工具为每一轮重新运行整个应用，并在各轮采集不同的计数器。前一个 kernel 约 5 µs，后一个却接近 250 µs，明显超过约 20 µs 的稳态参考时长。既然后者同样越界，就不能只用工作过短来解释这两条记录。表中的时长只描述当次带 profiler 的采集，正式性能比较有另外的无插桩计时。

Softmax 会原地覆盖输入，我因此查了一遍应用重放时各个 kernel 的调用顺序。如果第二轮把第一轮写出的概率当成分数，输入便会改变。实际的 KV 入口每次先做 QK，重新生成分数，再运行 Softmax 和 PV。在线注意力则每轮读取固定的 Q、K、V。两条路径都没有读回上轮的概率作为本轮输入。

命中扇区数超过总扇区数

NVIDIA 工程师给出了全局 L2 命中率的定义。这个定义指明了下一轮需要一起保留哪些计数，才能把工具报出的百分比逐项复算。

r=100lts__t_sectors_lookup_hit.avglts__t_sectors.avg.r=100\frac{\texttt{lts\_\_t\_sectors\_lookup\_hit.avg}} {\texttt{lts\_\_t\_sectors.avg}}.r=100lts__t_sectors.avglts__t_sectors_lookup_hit.avg​.

L2 用 32 字节的扇区（sector）计数。上式覆盖全局 L2 扇区查询，来源包括 SM 的 L1TEX 单元以及其他请求方。如果两项指标来自不同的重放轮次，它们观测的就可能是不同执行；GPU 上其他引擎的活动也可能影响共享资源上的计数。NVIDIA 工程师对该指标的说明

原始报告只记录了总共重放三轮，既没有这两个底层数，也没有说明各自在哪一轮采集。因此第一批诊断仍使用原二进制、原输入和相同的完整入口，应用仍预热 20 次，只改变所请求的指标组合。新配置加入全局命中数 H、未命中数 M 和总数 T 的 .sum 与 .avg，也加入限定 L1TEX 来源的对应计数。以下两行取自全局 .sum。

按公式代入全局 .sum，计算值与原生百分比在导出精度内一致，改用 .avg 得到的比率相同。第一行的命中扇区就比总数多了 41,022 个。如果分子和分母来自同一批查询，命中数至多等于总数。因此需要解释的是两项计数各自来自哪一次执行。

若改用 H+M 作分母，第一行几乎为 100%，第二行恰好是 100%。因为 H、M 非负，这样构造的百分比必定落在 0～100% 之内，也就无法检验独立采到的 T 是否与 H 一致。按 L1TEX 来源筛选可以缩小流量范围，但仍需核对分量是否描述同一组查询。

GB206 计数器的分轮采集与实机重放

我对两种原始算例分别使用六种指标配置，每轮随机打乱这 12 个组合的顺序，每个组合用五个独立进程各采一次，合计 60 份报告。KV 入口会捕获三个 kernel，在线入口捕获一个，因此留下 120 条 kernel 记录。这五次是定位问题的重复观测，不能据此推算整个 GPU 上越界的发生概率。

在线注意力只请求百分比时，五次里有四次超过 100%。关闭附加后缀的一次采集甚至到了约 121%；那组配置没有请求 H、M、T，已无法还原这个样本的分量。只保留一个派生指标，依然可能需要多轮底层采集。

我将 H 和 T 一起提交，后端仍为它们分配了不同的采样轮次。这次查询是离线进行的，没有加载 CUDA 驱动或创建 GPU 上下文，也拿不到实卡当时可用的计数器，因此表中能够确认的是这个版本的后端怎样为 GB206 排程。现场的 pct-only 报告实际用了三轮，目前的报告接口还给不出“某个依赖在哪一轮采到”的映射。报告列出的 profiler 预热轮次为零，单凭总轮数仍无法确定额外一轮实际执行了什么。

512 个线程块下仍出现越界命中率

原 KV 算例只有八个线程块。若越界只出现在 GPU 工作量过小的时候，扩大同一 Softmax 的网格后就应看不到它。我为此做了第二批实验，在独立程序里固定 N=4096N=4096N=4096，把注意力头数 HHH 依次设为 8、36、144、512。每个头仍由一个 CUDA 线程块（CTA）处理。

在采集前，我先核对独立程序里跑的还是同一段机器代码。去掉地址与编码注释、统一空格以后，新旧 Softmax 的 504 条 SASS 指令逐条相同。主扫描和额外的边界样例 H=3,N=257H=3,N=257H=3,N=257 在六个进程中产生七个输出，全都通过独立 FP64 参考、逐行求和、输入位模式和越界保护检查。正式采集时，每次重放也会记录 GPU 输入指纹和校验输出。

第二批使用 pct-only、global、tex 三种配置，每格五次，共 60 份报告。重放导致的 220 次应用启动全部通过输入、输出与边界保护检查。

图 2　每个头由一个线程块处理，因此横向比较的也是网格大小。每个点来自一次带 profiler 的采集，图中只列出请求了原生全局命中率的两种配置。

144 个块和 512 个块的报告都再次记录了越界。即使在 512 个块时，带 profiler 的 Softmax 已运行约 46～65 µs，远超过约 20 µs 的参考时长，采到的命中率仍可能高于 100%。

增加头数也增加了工作量和数据占用，并延长了执行时间。独立程序在进入 Softmax 前还会做一次设备内拷贝来恢复 logits，再将输入拷回主机校验。因此它的缓存访问历史与原来先算 QK 再运行 Softmax 的入口不同。独立程序的部分报告测得 70%～80% 的全局 L2 命中率。两种程序在进入 Softmax 时的缓存条件不同，这组数值无法替换原图中接近 100% 的读数，也不足以说明原算子的缓存表现变差。

重复采样的局限与尚未定位的跨轮差异

如果条件稳定、随机误差无偏，增加独立重复可以降低均值的不确定性。遇到运行中缓慢漂移，博客的正式计时用交错配对、A/A 对照和独立进程复核。这次需要检验的却是分子和分母是否对应于同一批查询。即使将几次超过 100% 的读数平均后得到 99%，也不能由此恢复那一批查询的命中数和总数。

我能直接核实的是原生报告已经越界，保存了分量的异常报告中有 H>T，工具用 100H/T 得出了那个百分比。算子本身通过正确性检查，且保留同样 SASS 的独立程序可以再次观察到异常。另一层证据来自调度：同版 GB206 后端把 H、T 分到两个隔离轮次，实卡仅请求百分比也实际重放了三轮。这表明跨次执行组合计数是一个可能的解释。

KV 缓存文章和在线 Softmax 文章保留最初的读数并标为无效。独立的数值校验和无 profiler 的配对计时仍可使用。今后要由命中率推算未命中量或 DRAM 流量，我会先留下匹配的原始计数、单位、实际重放轮次以及重复观测的分布。NVIDIA Profiling Guide 对取值范围和精度的说明

目前还缺少实卡报告里每个原始计数器和采样轮次的对应关系。有了它，才能继续查两轮之间发生了什么。GPU 上其他引擎的活动、缓存状态、采集边界和工具本身的行为都可能影响计数，现有数据还不足以区分它们。

采样环境、精确读数与原始报告位置

测试用 RTX 5070 Laptop GPU，GB206，计算能力 sm_120。软件是 CUDA 13.1 和 Nsight Compute 2026.2.1。全部采集采用应用重放，设置 --cache-control none 和 --clock-control none，应用先预热 20 次。两批实验都按事先冻结的计划串行执行，期间沿用原有的显示、驱动和电源设置。实验前后保存了功率与频率快照，运行过程没有连续轨迹。计数器采集与正式计时分开。

在 H=512H=512H=512 时，带 profiler 的 Softmax 运行了 45.760～65.344 µs。对第一批的任务 19，改用有界公式 100H/(H+M) 得到 99.999017%。两份原始报告的完整百分比见首表。

私有研究工作区的 bench_mur/l2_hit_rate_investigation/README.md 记录了源文件、命令、编译与 SASS 校验、120 份 CSV 导出及逐次检查、离线调度查询和绘图入口。完整 .ncu-rep 保存在本地归档中，另存 SHA-256。小型证据包保留了原始导出字节和清单。
