HFuse 的水平融合：用线程束分区并行执行 Im2Col 与双线性缩放

HFuse 把一个 CUDA 线程块分成两组，一组做 Im2Col，另一组做双线性缩放。以 512 个线程为界时，物理编号 512 的线程要从缩放组的 0 号开始算，否则就会漏掉输出。在本机选定的网格上，等两张结果图都算完，融合约用 1.50 ms，串行约用 1.52 ms。

把 Im2Col 和双线性缩放放进同一个 CUDA 线程块后，两个算子仍然使用各自的输入和输出。困难在于原来的索引公式默认整个块只做一个算子。如果沿用 threadIdx.x 直接计算输出位置，分到后半个块的算子就会从错误的编号开始。

HFuse 沿着两个线程束（warp）的边界切分线程块，让每组都从自己的 0 号线程算起。在这组 Im2Col 与双线性缩放（bilinear resize）实验中，选定的方案把 1,024 个线程对半分。分界处相邻的两个线程很适合用来验算，第 15 号 warp 的最后一个线程编号为 511，第 16 号 warp 的第一个线程编号为 512。它们的物理编号相邻，写入的却是两张不同的图。

Im2Col 与双线性缩放的输出索引

形状取自 HFuse 作者在 V100 上扫描 Im2Col 与缩放工作量时的第一组配置。Im2Col 输入一张 2,512×2,0482{,}512\times2{,}0482,512×2,048 的单通道 FP32 图。一个竖直的 13×113\times113×1 窗口以步幅 1 滑动，输出位置 (y,x)(y,x)(y,x) 在第 rrr 个平面上存输入像素 (y+r,x)(y+r,x)(y+r,x)，其中 r=0,…,12r=0,\ldots,12r=0,…,12。对每一列，窗口顶部有 2,500 个合法位置。

缩放算子读另一张图，八个通道，每通道从 256×100256\times100256×100 放大为 2,000×2,5602{,}000\times2{,}5602,000×2,560。采用角点对齐时，输出坐标 (y,x)(y,x)(y,x) 对应输入坐标 (255y/1999,99x/2559)(255y/1999,99x/2559)(255y/1999,99x/2559)，根据附近四个点计算插值。每个通道的最后一个输出像素恰好对应输入的 (255,99)(255,99)(255,99)。HFuse 作者的 V100 测试用例和包装函数

因为两种输出都有 5,120,000 个空间位置，它们的跨网格步进循环可以使用同一个终点。每处理一个位置，Im2Col 要向 13 个平面各写一个数，而缩放要为八个通道分别插值。因此两边实际写出的 FP32 值分别有 66,560,000 和 40,960,000 个。

按线程束分区的局部线程编号与跨网格步长

在本地 deep_split 的 Im2Col–resize 分支中，cut=512 同时给出 Im2Col 的线程数和缩放组的起始物理编号。下面展开索引表达式，省略了跟踪计时的部分。

if (threadIdx.x < cut) {
    int worker = blockIdx.x * cut + threadIdx.x;
    im2col(w, worker, gridDim.x * cut);
} else {
    int width = blockDim.x - cut;
    int worker = blockIdx.x * width + threadIdx.x - cut;
    bilinear(w, worker, gridDim.x * width);
}

取 blockIdx.x = 1，第 15 号 warp 的最后一个线程在块内编号为 511，在 Im2Col 组里也排第 511 号，所以它第一次写的是 Im2Col 的第 1×512+511=10231\times512+511=10231×512+511=1023 号输出位置。紧挨着的线程在块内编号为 512，却是缩放组的 0 号，它第一次要写的是缩放图的第 1×512+0=5121\times512+0=5121×512+0=512 号位置。

块 1 中的线程第一个空间序号实际写入的位置
warp 15，lane 31，物理线程 511Im2Col 的 1,023遍历 rrr，从 input[1023 + r*2048] 读取，写到 im2col_out[r*5120000 + 1023]。
warp 16，lane 0，物理线程 512缩放图的 512输出坐标为 (0,512)(0,512)(0,512)，落在输入第 0 行的第 19、20 列之间；每个通道的结果写到 resize_out[ch*5120000 + 512]。

整个网格有 1,080 个块，每侧各有 1,080×512=552,9601{,}080\times512=552{,}9601,080×512=552,960 个逻辑 worker。下一轮，刚才那两个线程分别走到各自输出的第 553,983 和 553,472 个位置。对一个算子而言，每个空间序号除以 552,960 的余数唯一，所有余数在第一轮又恰好各分到一个 worker。因此每个位置都有且只有一个写入者。实际校验时，Im2Col 的全部输出与独立 CPU gather 完全一致，缩放结果与 CPU 插值参考的最大绝对误差为 4.42×10−74.42\times10^{-7}4.42×10−7。

HFuse 还要处理那些用到块级屏障的算子，为参与同步的组调整屏障编号和参与线程数。本例的两个算子在作者配置中都标为无需块级屏障。把 warp 放到一起，调度器便有机会在一侧等待访存时发射另一侧已经就绪的 warp。本地 CUDA 移植手写了同样的编号规则；正式测量前，先在三种网格大小下分别试了七种 warp 切分，最终选定 1,080 个块、每侧 16 个 warp。HFuse 论文 §III、图 5～6 · 作者工件

串行、双流与融合执行的双输出完成时间

原论文用两条并发 CUDA stream 作为原生基线。对实际调用者，还应比较顺序跑完同一对算子的时间。在 RTX 5070 Laptop GPU 上复用输入和输出缓冲，融合实现约用 1.50 ms，串行约用 1.52 ms，双流约用 1.73 ms。两个独立 kernel 各启动 360 个块，每块 1,024 个线程；融合 kernel 用预选的 1,080 块。所以计时评估的是网格选择和 warp 划分合起来的效果。HFuse 论文 §IV、图 7

图 2　菱形是 160 对计时比值的几何平均，误差线为分层自助抽样的 95% 区间，浅色点为八个进程各自的平均比值。竖线表示两种方案等时。

相对论文采用的双流基线，这组融合的加速比约为 1.15。如果调用者也可以让两个算子顺序执行，就该看串行这一列。融合只比串行少用约 25 µs（按几何平均耗时计算），配对加速比区间的下界已接近 1。双流计时尤其容易低估：如果停止事件只等其中一条流，即使另一张图还没写完，计时也会结束。只有两路输出都就绪，下游才可以同时使用它们。CUDA Graph 与推理运行时的计时边界

另有三次插桩启动，用设备全局时钟记录每个 warp 的起止。第一次以最早进入的 warp 为时间原点，最后一个缩放 warp 在 1,446.176 µs 时结束，最后一个 Im2Col warp 在 1,454.176 µs 时结束，相差 8 µs。三次记录的差距为 7.296～8.000 µs。这些跨度也包含等待调度的时间。表中的性能数取自另一组没有插桩的 event 计时。

图 3　1,080 个线程块中，每个算子各占 17,280 个 warp。每条线从该组最早一次进入画到最后一次退出。warp 内同步后，由 lane 0 记录结束时刻。

写这个融合核函数时，把块内编号 511 和 512 分别代入，就能查出分界两侧的索引有没有错位。要证明整张图没有漏写或重复写，还得检查每一组线程在一个步长内是否恰好覆盖所有余数，再将两张完整输出与各自的参考实现逐项核对。计时也要按同样的任务来比，两张图中较晚完成的那一张，决定下游什么时候能开始。

计时协议、正确性与复算入口

本地 FP32 移植使用 CUDA 13.1.115、目标 sm_120、驱动 610.88，GPU 为 36 个 SM 的 RTX 5070 Laptop，系统使用 Windows WDDM。输入生成器以 20261130 为种子生成标准正态 FP32 样本。每次记录前，先在同一批地址上以相同方案运行一次。相邻计时组采用随机打乱的方法顺序及其逆序。event 区间涵盖 GPU 等待以及起止事件之间的空隙，分配、主机到设备的拷贝和校验在区间以外。

八个独立进程各有 20 组配对观测。耗时列取每个方案 160 次完整运行的几何平均，加速比先逐对相除，再取几何平均。区间先重采样进程，再在入选进程内重采样完整配对计时组，取 10,000 次估计的第 2.5 与 97.5 百分位。
