MPI 点对点通信：消息匹配、发送模式与缓冲区复用

两个 MPI 进程都先发送、再接收时，短数组有时能顺利交换，因为 MPI 库可以暂存数据，让双方的发送调用先返回。换成长数组后，如果两边的发送都要等对方开始接收，两个进程就都走不到接收这一步，程序也就死锁了。

假设进程 0 要把数组发给进程 1，进程 1 也有一个数组要发回来。两边都把 MPI_Send 写在 MPI_Recv 前面。用几个整数测试，程序可能每次都跑通，但这只能说明这几次发送都顺利返回了。换成长数组以后，即使进程编号和消息标签（tag）原封不动，程序也可能卡在第一次发送。

进程 0 从 MPI_Send 返回时，可以改写自己的发送数组，可它凭什么知道进程 1 收到了数据？如果库只是把数组复制到临时缓冲区，进程 1 此刻甚至可能还没调用 MPI_Recv。正因为发送完成和接收完成可以发生在不同的时刻，我们得先弄清哪一次接收能取走这条消息，再决定代码在哪里等待。文中的条款号对应 MPI 4.1 正式版 PDF。多个进程沿环交换梯度时也会遇到同样的问题。环形 AllReduce 的收发过程

MPI 通信域、进程编号与上下文隔离

两个进程可以运行同一份程序。调用 MPI_Init 初始化 MPI 后，每个进程用 MPI_Comm_rank 查询自己在通信域内的编号（rank），用 MPI_Comm_size 查询域内共有多少个进程，于是同一段代码就能按编号选出不同的收发对象。程序退出前，各进程调用 MPI_Finalize 结束 MPI 通信。这种写法叫作单程序多数据（SPMD），MPI 也允许各进程运行不同的程序。

这里用的是组内通信域（communicator）。它把一组进程和私有的通信上下文关联起来，所以进程 0 指的是这个组里的第一个进程。假设一个库也要在这批进程之间传消息，它可以调用 MPI_Comm_dup，沿用原来的进程组并取得独立的上下文。如果还需要把进程分组，则可以调用 MPI_Comm_split。这样即使库与应用用了一样的 rank 和 tag，它们的消息也不会混在一起。同一个通信域中的集合操作仍要由成员按一致的顺序调用，如果部分进程跳过了一次集合操作，其余进程也可能一直等下去。

消息匹配与顺序保证：通信域、来源和标签

通信域确定以后，接收方还要按消息来源和标签选择消息。MPI 把这些匹配信息称为消息的“信封”。接收端可以要求某个来源，也可以指定 MPI_ANY_SOURCE；可以要求特定 tag，也可以用 MPI_ANY_TAG。同名变量、相同的数组地址、双方看似对称的循环，都不参与匹配。匹配成功后，类型和接收容量还要符合要求。

如果接收方事先提交了接收请求，MPI 就知道该把到来的数据写到哪里。发送也可以先发生，这时实现通常会暂存较小的消息，较大的消息则可能要等接收方就绪才开始传，具体阈值由实现决定。接收方如果还不知道数组有多长，可以先用 MPI_Probe 查询消息，从返回的状态中取得元素数，分配好缓冲区，再按刚查到的来源和标签接收（§3.8）。这期间要避免另一条接收取走同一条消息，尤其是在多个线程共用一个通信域时。

两条消息都满足同一个接收的条件时，发送顺序才会限制这个接收可以取走哪一条。 假设同一进程先发 tag 为 1 的消息，再向同一个目的地发 tag 为 2 的消息。如果接收方明确指定 tag 为 2，它可以先收到后发的那条。如果它使用 MPI_ANY_TAG，两条消息都符合条件，它就不能越过仍在等待匹配的第一条，直接取走第二条（§3.5）。换成不同的发送方，MPI 就没有规定两条消息之间的全局顺序。不同通信域里的消息也互不影响。

四种发送模式的完成条件与缓冲区复用

发送模式完成后能确定的事程序承担的条件
MPI_Send，标准发送缓冲区可复用；实现可能已缓存，也可能等过接收端正确性要覆盖有缓冲和无缓冲两种情况
MPI_Ssend，同步匹配接收已经提交并开始接收，发送缓冲可复用仍允许实现内部使用缓冲
MPI_Bsend，缓冲源缓冲区可复用，完成不依赖匹配接收；需要时使用附加缓冲区配置足够的缓冲空间，MPI 4.1 也允许显式启用 MPI_BUFFER_AUTOMATIC（§3.6）
MPI_Rsend，就绪合法调用完成后可复用发送缓冲区发起前匹配接收必须已经提交，否则程序有错

回到开头的数组交换，短消息可以采用 eager 协议。只要库有地方存放数据，两个进程就有机会先从发送调用返回，接着执行接收。长消息如果采用 rendezvous 协议，发送方就要等对端提交接收才能继续。两边都把接收写在发送后面，因而谁也等不到对方。四种发送模式对调用何时可以完成有不同约定（§3.4）。对接收方而言，能够读取收到的数组，还得以自己的接收请求完成为准。

用 Sendrecv 或非阻塞收发避免环形死锁

要解除这条循环依赖，可以把两个进程各自的收发写进同一次 MPI_Sendrecv 调用（§3.2.7）。把这个例子扩展成环时，每个进程向右邻发送，同时从左邻接收。只要收发对象和标签配对，MPI 就可以推进传输。另一种写法是先用 MPI_Irecv 提交接收，再用 MPI_Isend 提交发送。这两个调用各自返回一个请求句柄，进程可以用 MPI_Waitall 等待两项操作全部结束，也可以用 MPI_Test 分别检查。发送请求完成后可以改写发送数组，接收请求完成后才可以读取或改写接收数组（§3.7）。

操作可以在什么时候使用缓冲区？
MPI_Recv返回即可读取接收到的数据
MPI_Isend发送请求完成后才可覆盖原发送区域
MPI_Irecv接收请求完成后才能访问对应区域的数据
MPI_Sendrecv返回时该调用的发送和接收均已完成

MPI_Test 返回 false 表示请求尚未完成。即使调用了 MPI_Cancel，请求也还得用 MPI_Wait 或 MPI_Test 完成，再从状态调用 MPI_Test_cancelled，分清是取消成功，还是操作已经正常完成。MPI 4.1 已弃用对发送请求执行取消（§3.8.4）。

派生数据类型的内存布局与类型签名匹配

消息能够配对之后，还要确认数据类型相容。假设发送方要传出矩阵的一列，可以用 MPI_Type_vector 描述带步长的元素，接收方把这些元素紧密地收到一维数组里。MPI 比较的是基本类型的序列，也就是类型签名；类型描述中的位移可以不同（§3.3.1）。可用 MPI_Type_contiguous、MPI_Type_indexed 或 MPI_Type_create_struct 构造其他布局，通过 MPI_Type_commit 启用，MPI_Type_free 释放的是类型句柄。

例如，发送方发了 10 个 MPI_INT，接收方为 20 个 MPI_INT 留出了空间，这次接收就装得下，之后用 MPI_Get_count 查询实际收到的元素数，结果是 10（§3.2.4）。如果接收方要求的是 10 个浮点数，哪怕两边恰好都是 40 字节，类型签名仍然不匹配。接收操作的 count 给出容量上限，消息过长可能报 MPI_ERR_TRUNCATE。如果要用 MPI_BOTTOM 和绝对地址把分散的变量拼成一个布局，还得确认每个位移指向哪个变量，以及传输期间该变量是否一直有效。

经典接口的 count 是 int。传入的元素数超过 231−12^{31}-1231−1 时应使用 MPI 4.0 引入的 _c 大计数接口，例如接收 MPI_Count 的 MPI_Send_c。2 GiB 的 MPI_BYTE 已越过这个边界，直接把 size_t 转成 int 可能溢出。

边界进程、线程支持与非阻塞通信的进展条件

假设进程排成一列，每个进程都要交换相邻网格的边界数据。最左和最右的进程各缺一个邻居，把那个方向的收发对象设成 MPI_PROC_NULL，发送和接收就都能立即完成，所有进程仍可共用同一段循环（§3.10）。如果程序还用不同的标签区分这些交换，可以从通信域属性 MPI_TAG_UB 查询标签上限，标准保证它至少是 32,767（§9.1）。

用了非阻塞收发，线程可以在提交请求后继续计算，但这段时间里数据能传多远，还取决于 MPI 实现。有些实现把传输交给网卡或单独的通信线程，有些则要等应用再次调用 MPI 才能继续推进。要知道能否在目标机器上把通信时间隐藏在计算中，可以在计算间隙调用 MPI_Test 检查请求是否完成，给依赖这类调用的实现一个推进通信的机会，再测量收发和计算全部完成的时间（§2.9）。

多线程程序用 MPI_Init_thread 协商级别（§11.6），必须查看实际返回值。SINGLE 假定只有一个线程；FUNNELED 要求只有初始化 MPI 的线程调用 MPI；SERIALIZED 允许多线程轮流调用；MULTIPLE 允许并发调用。这四个名字的完整前缀均为 MPI_THREAD_。错误处理也取决于通信域。通常默认处理器 MPI_ERRORS_ARE_FATAL 会终止作业；换作 MPI_ERRORS_RETURN 后，应用要逐次检查错误码。标准不要求实现检测出所有非法匹配（§9.3）。

环形 AllReduce 中 MPI 与 NCCL 的收发约定

把这些规则用于环形 AllReduce 时，归约分散和全收集都可以写成相邻 rank 的收发。为这两个阶段的协议建立独立通信域，可以避免库外消息意外参与匹配。阶段可能重叠时，使用不同 tag 有助于核对匹配；如果阶段串行、对端固定、调用顺序正确，也可以复用一个 tag。遇到挂起，先找是否有某个 rank 走进了不同的集合调用，再找是否所有进程都在等第一次发送。

NCCL 的 ncclSend 和 ncclRecv 不使用 tag，收发双方要约定相同的元素数和数据类型。通信提交到指定的 CUDA 流后，GPU 异步执行传输，同一条流上的后续工作要等传输完成。以环上的一个 rank 为例，它要同时向右邻发送、从左邻接收，就把这两次调用放在 ncclGroupStart 与 ncclGroupEnd 之间，让收发都能向前推进。组内调用返回时，通信甚至可能还没入队。要判断缓冲区何时可以复用，可以在整组成功提交后，在同一条流上记录 CUDA 事件并等待事件完成。NCCL 的 CUDA 流语义 · 点对点收发分组
