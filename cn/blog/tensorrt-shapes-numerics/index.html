TensorRT 线性层推理：动态形状、FP16 溢出与执行上下文复用

TensorRT 可以分别接受两个输入的形状，却在执行时发现它们无法逐元素相加。输入形状即使合法，FP16 的残差线性层仍可能因输出超出数值范围而产生无穷大。用六个 FP32 与 FP16 引擎进行对照时，64 行与 65 行请求交替到达，按形状复用上下文还可以省去反复切换优化配置的时间。

一个请求从 64 行增至 65 行，只增加一行数据，却可能跨过 TensorRT 的优化配置边界。继续用同一执行上下文切换配置，还是把请求交给已准备好的另一个上下文，会改变这批请求的耗时。比较这两种策略之前，我们先确认引擎能接受哪些输入组合，再检查合法输入在 FP16 下会不会溢出：调用成功和输出数值可用，是部署时要分别验证的两件事。

残差线性层的 TensorRT 建图、ONNX 导入与引擎加载

实验选取一个带残差连接的线性层，输出由下面的式子给出：

Y=ReLU⁡(XW+R),X,R∈RM×64,W∈R64×64.Y=\operatorname{ReLU}(XW+R),\qquad X,R\in\mathbb R^{M\times64},\quad W\in\mathbb R^{64\times64}.Y=ReLU(XW+R),X,R∈RM×64,W∈R64×64.

其中 MMM 表示随请求变化的行数，特征宽度固定为 64。因为 RRR 要与矩阵乘积逐元素相加，每行都得提供自己的 64 个残差值。输入和输出均按行连续存储。

权重大部分列由固定种子的正态分布生成，标准差 1/81/81/8；第一列全置 1，第二列交替 +1,−1+1,-1+1,−1。第一列方便手算累加范围，第二列方便看近似相等输入相减时的误差。六个引擎共用同一份原始 FP32 权重，FP16 构建时才转换存储类型。

下面的建图代码依次创建矩阵乘、残差加法和 ReLU。dt 取 trt.float32 或 trt.float16，常量权重 weight 是相应类型的 NumPy 数组。这里省略了节点名称和日志。

flags = 1 << int(trt.NetworkDefinitionCreationFlag.STRONGLY_TYPED)
network = builder.create_network(flags)
x = network.add_input("x", dt, (-1, 64))
r = network.add_input("residual", dt, (-1, 64))
x.set_dimension_name(0, "rows")
r.set_dimension_name(0, "rows")

w = network.add_constant(weight.shape, weight).get_output(0)
z = network.add_matrix_multiply(
    x, trt.MatrixOperation.NONE, w, trt.MatrixOperation.NONE).get_output(0)
u = network.add_elementwise(z, r, trt.ElementWiseOperation.SUM).get_output(0)
y = network.add_activation(u, trt.ActivationType.RELU).get_output(0)
y.name = "y"
network.mark_output(y)

图中的 -1 允许请求在运行时指定行数。两个输入的这一维都命名为 rows，表示行数必须相等。为了给这些形状选取实现，构建器还需要一份优化配置（optimization profile），分别指定允许的最小尺寸、用来优化的目标尺寸和最大尺寸。下面取 M=1/64/512M=1/64/512M=1/64/512，下文叫 wide：

profile = builder.create_optimization_profile()
profile.set_shape("x", (1, 64), (64, 64), (512, 64))
profile.set_shape("residual", (1, 64), (64, 64), (512, 64))
config.add_optimization_profile(profile)
config.clear_flag(trt.BuilderFlag.TF32)
serialized = builder.build_serialized_network(network, config)

构建器把选定的实现写入序列化引擎，加载后再由执行上下文保存每次调用的动态状态。对动态形状请求而言，这一区分很重要：同一份网络和权重可以反复用，请求行数、绑定地址和执行资源必须落到具体上下文里。

执行上下文还需要知道这一次请求的具体形状和存储地址。程序先选择 profile，设置两个输入的形状，再查询输出形状，绑定设备地址并提交执行。代码中的 tx,tr,ty 是提前分配好的 CUDA Tensor，stream 是执行流。

assert context.set_optimization_profile_async(profile_id, stream.cuda_stream)
assert context.set_input_shape("x", tuple(tx.shape))
assert context.set_input_shape("residual", tuple(tr.shape))
assert not context.infer_shapes()
assert tuple(context.get_tensor_shape("y")) == tuple(ty.shape)

for name, tensor in [("x", tx), ("residual", tr), ("y", ty)]:
    assert context.set_tensor_address(name, tensor.data_ptr())
assert context.execute_async_v3(stream.cuda_stream)
stream.synchronize()

脚本用 PyTorch 管理 CUDA 缓冲区、流和事件，由 TensorRT 执行计算。设备指针只给出地址，因此绑定前还要核对张量的数据类型、步长和缓冲区长度，并在设备操作结束前保留张量。直接把 FP32 数据的地址传给 FP16 引擎，TensorRT 会按 FP16 读取该地址，不会自动把数据转换为 FP16。

部署已有模型时，也可以先用 ONNX 解析器导入图，再由调用方构建引擎并提交请求。为了检验这条路径，实验用 ONNX 1.19.1 另存了同一张 MatMul → Add → Relu 图，权重放 initializer，输入声明 ['rows',64]，opset 18、IR version 9。模型文件通过 ONNX 校验后，再交给 TensorRT 解析并构建 FP32 wide 引擎。

这里直接生成并校验了 ONNX 文件。因为没有调用 torch.onnx，以下结果只覆盖从既有 ONNX 模型到 TensorRT 执行的过程。七个行数 1,3,17,64,65,257,5121,3,17,64,65,257,5121,3,17,64,65,257,512 的完整输出同时与 ONNX CPU ReferenceEvaluator、独立 FP64 公式比较：对 FP64 的最大误差 4.242×10−74.242\times10^{-7}4.242×10−7 到 7.585×10−67.585\times10^{-6}7.585×10−6，对 ONNX CPU 的最大差 7.629×10−67.629\times10^{-6}7.629×10−6，全部有限且在 FP32 预算内。

解析器接受 ONNX 文件之后，我们继续比较完整输出，才能确认导入后的计算与原来的数学表达式一致。

构建器以 opt 尺寸作为选择实现的一个目标点，范围内的其他尺寸不会因此获得逐个调优。部分实现还要求 min、opt、max 三者相同，这使 fixed 和 wide 的候选集合都可能不同。选择 profile 时还得考虑真实请求集中在哪些尺寸，单凭范围宽窄无法判断快慢。动态形状文档

即使两个输入的形状分别落在 profile 范围内，它们仍须满足图中的跨输入约束。在这个残差层中， MX=MRM_X=M_RMX​=MR​。选中 profile ppp 时，真正的接纳域是

Dp={(X,R):Mmin⁡,p≤MX=MR≤Mmax⁡,p,KX=KR=64}.\mathcal D_p=\left\{(X,R): M_{\min,p}\le M_X=M_R\le M_{\max,p},\quad K_X=K_R=64 \right\}.Dp​={(X,R):Mmin,p​≤MX​=MR​≤Mmax,p​,KX​=KR​=64}.

以 split profile 0 为例，矩形包含两个输入各自落在允许范围内的所有组合。再考虑两者行数必须相等，网络能够执行的组合就只剩对角线上的点。(7,9)(7,9)(7,9) 落在矩形内，落在对角线外。实验实际提交了这一组并观察到拒绝，其他整数点的分布由形状约束推得。

实测把 XXX 设成 7 行、RRR 设成 9 行，两次 set_input_shape 都返回 true；一直到 execute_async_v3，同名维度关系不满足，执行返回 false。调用层如果只看 setter 就认定成功，接下来可能读到复用输出缓冲里上一次留下的内容。

对于直接超出范围的输入，执行上下文在设置形状时就能发现。wide/split 的 0 或 513 行、任何方案的 63 列、fixed 的 63 或 65 行，均在这一步被拒绝。六个引擎合计完成 22 项形状拒绝检查。由于业务入口已经掌握两个 Tensor 的形状，调用方可以先比较输入是否匹配，随后仍应检查后端最终返回的执行状态。

两套 API 的返回约定也不能混。这个版本里，构建期 IOptimizationProfile.set_shape 成功返回 None，发现不一致抛异常；运行期 IExecutionContext.set_input_shape 返回布尔值。写一句统一的 assert set_shape(...)，会把成功的构建误判成失败。Profile API

FP16 输入舍入、执行误差与输出溢出

六个引擎的两种精度都是强类型图。FP32 版的输入、权重、残差、输出全是 FP32，FP16 版全是 FP16，同时显式关掉 TF32。因此存储类型在建图时已经确定，可以直接研究将整条路径存为 FP16 所产生的误差与范围限制。

存储类型不等于内部每一步都按同类型单独舍入。矩阵乘会换累加方式，残差和激活也会融进乘法之后。保存下来的 engine inspector 显示，wide FP32 保留独立 GEMM，接着融合残差加法和 ReLU；wide FP16 把 GEMM、残差、ReLU 融在一起。两者还带形状逻辑，inspector 条目数不能直接当成 kernel launch 数。Engine Inspector

FP16 tactic 名里有 f16f16 和 tensor16x8x16，FP32 GEMM 名里有 ffma。这些名字记录了构建器的实现选择。实际设备为 SM120，名称中的 sm80 不能用来判定本机架构。要进一步判断执行了多少条相关指令、Tensor Core 利用率如何，还需要动态计数，本次实验未采集这两项。

输出范围可以直接由数学表达式检验：让 XXX 每个元素都是 2000，R=0R=0R=0，权重第一列全为 1，那么

Yi0=ReLU⁡(∑k=0632000×1)=128000.Y_{i0}=\operatorname{ReLU}\left(\sum_{k=0}^{63}2000\times1\right)=128000.Yi0​=ReLU(k=0∑63​2000×1)=128000.

2000、0、1 都能被 FP16 精确表示，128000 却大于 FP16 最大有限值 65504。内部累加精度再高，最后也没法把它存成有限 FP16。调 profile 的最大行数没有用，每行独立累加 64 项，MMM 再小都不改变结果。数值范围说明

实跑时，wide、split、fixed 三个 FP16 引擎都成功提交，但输出的第一列全是正无穷；512 行时就有 512 个非有限输出。另三个 FP32 引擎能保留 128000。六个直接构建的引擎覆盖四种输入模式和各自合法的测试形状，共 120 个案例：105 个有限结果通过诊断预算，15 个 FP16 溢出记为数值范围失败。

如果实际请求可能达到这种输入幅值，应给相应的中间值和输出选择更宽的数据类型，或者在模型允许的情况下先做缩放。选类型时既要判断输入能否表示，也要推算每个输出在累加之后可能达到的范围。

排除非有限输出之后，还要解释其余结果的误差来自哪里。为此需要两份参考：FP16 引擎读到的输入和权重已经舍入过，直接与原始 FP32 模型比较，会把表示变化和执行误差混在一起。令 ϕ\phiϕ 为 ReLU，定义

Y0=ϕ(XW+R),Ys=ϕ(XsWs+Rs),Y_0=\phi(XW+R),\qquad Y_s=\phi(X_sW_s+R_s),Y0​=ϕ(XW+R),Ys​=ϕ(Xs​Ws​+Rs​),

两份都用 FP64 计算；Y0Y_0Y0​ 用原始 FP32 存储值，YsY_sYs​ 先舍到引擎实际存储类型再提到 FP64。引擎输出记 Y^\widehat YY，逐元素有

Erepr=Ys−Y0,Eexec=Y^−Ys,Etotal=Erepr+Eexec.E_{repr}=Y_s-Y_0,\quad E_{exec}=\widehat Y-Y_s,\quad E_{total}=E_{repr}+E_{exec}.Erepr​=Ys​−Y0​,Eexec​=Y−Ys​,Etotal​=Erepr​+Eexec​.

第一项来自输入、权重和残差写入目标类型时的舍入。第二项固定这些存储值，衡量执行算术和最终写出又引入多少差异。由于同一元素上的两项误差可能叠加，也可能相互抵消，直接相加两个 RMSE 的平方通常得不到总 RMSE 的平方。

把表示变化在激活前展开，还能写成

ΔZ=XΔW+ΔXW+ΔXΔW+ΔR.\Delta Z=X\Delta W+\Delta XW+\Delta X\Delta W+\Delta R.ΔZ=XΔW+ΔXW+ΔXΔW+ΔR.

同样的权重舍入会随输入幅值放大；第二列交替正负的构造让相近输入相消，更容易看见舍入对小结果的影响。ReLU 的绝对差满足 1-Lipschitz，却会把负数全压到零，盖掉一部分前激活差异，所以只看最终输出定位不到每一层。

六个 FP32 和 FP16 引擎的构建与稳态计时

稳态计时要求各进程加载完全相同的引擎。原实验的六份 plan 已无法取得，因此本轮为 wide、split、fixed 三种 profile 各建 FP32 和 FP16 引擎。每份只构建一次，使用空 timing cache、64 MiB 工作区上限、优化级别 3、每个 tactic 一次计时。记录这六份新 plan 的散列后，所有确认进程都加载同一批字节。这样可以比较固定引擎的运行表现，旧批次的绝对计时另行保存；每个配置只有一次构建，也无法估计构建器选择的波动。

单次构建耗时在 3.20–10.56 s 之间。plan 除权重外还保存实现选择，因此 FP16 的文件完全可能更大；每个配置只构建一次，也不足以据此给构建耗时排次序。导入、CUDA 初始化、反序列化、创建上下文、绑定地址、第一次执行和稳态调用，各自支付的成本不同。TensorRT 构建可复现性与精度控制
