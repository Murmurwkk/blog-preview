GPU 算子开发入门：并行分工、内存层级与数据复用

面向非 GPU 方向读者梳理算子开发的核心概念，依次说明框架调度、线程与内存层级、算术强度，以及分块复用、合并访存、算子融合与 Tensor Core 四类基础优化机制。

在 PyTorch 里写下一行 C = A @ B 或 y = torch.relu(x + b) 只需要一秒，但模型训练和推理的绝大多数时间，都消耗在调用背后执行的底层算子（Operator / Kernel）上。计算结果完全相同的两份 GPU 算子实现，耗时可能相差数倍甚至一个数量级，决定快慢的关键往往不是数学公式，而是线程怎样分工、数据怎样在各级存储之间搬运。这篇导读不假定读者具备 CUDA 编程经验，从“算子在框架中处于什么位置”讲起，依次介绍 GPU 的线程组织与存储层级、算术强度直觉，以及分块复用、访存对齐、算子融合和 Tensor Core 四类核心优化思路。

算子在深度学习框架中的位置

一个神经网络在执行时可以拆解为一系列基础计算节点：矩阵乘法、卷积、归一化、激活函数、Softmax 与注意力计算。每个节点背后对应的底层实现函数就是算子，它同时负责前向输出计算与（训练阶段的）反向梯度计算。

当 Python 执行 C = A @ B 时，真正做乘加运算的并不是 Python 解释器。框架的调度器（Dispatcher）先检查张量所在设备（CPU 或 GPU）、数值类型（如 FP32、BF16、FP16）和内存步长，再把计算派发给底层编译好的高性能库（如 cuBLAS、cuDNN）或自定义算子。当模型引入标准库未覆盖的新运算、需要合并多个零散小算子以减少显存读写，或特定输入形状在通用库中利用率偏低时，就需要人工编写或借助编译器生成专门的 GPU 算子。

CPU 与 GPU 的硬件分工逻辑

CPU 把大量芯片面积留给大容量缓存、分支预测与乱序执行控制逻辑，目标是让少数几条线程尽可能快地跑完复杂逻辑；GPU 则把面积集中投入到成千上万个相对简单的计算单元上，用高吞吐并发来掩盖单次访存延迟。

在 CUDA 编程模型中，GPU 的并行任务按三层结构组织：

flowchart TB
    G[Grid 网格：一次算子启动，覆盖整个输出张量]
    B1[Thread Block 线程块 0：调度到单个 SM，块内共享高速 Shared Memory]
    B2[Thread Block 线程块 1：与其他块相互独立，可自由调度]
    W1[Warp 线程束：32 个线程按同一指令步调执行]
    T1[Thread 线程：拥有私有寄存器与坐标编号]
    G --> B1
    G --> B2
    B1 --> W1
    W1 --> T1
  • 线程（Thread）：最基本的执行单元，拥有私有寄存器，通过自身编号确定要计算输出张量的哪个位置。
  • 线程束（Warp）：在 NVIDIA GPU 上，硬件按每组 32 个线程（一个 Warp）统一调度。如果同一 Warp 内的线程在 if/else 分支上走向不同路径，硬件只能串行执行两个分支并屏蔽不需要执行的线程，这称为分支发散（Warp Divergence）。
  • 线程块（Thread Block）：由若干 Warp 组成，整体分配到同一个流式多处理器（SM）上运行。同一线程块内的线程可以同步（__syncthreads()），并通过片上高速共享内存（Shared Memory）交换数据；不同线程块之间彼此独立，保证同一份代码能够无缝扩展到不同规模的 GPU 上。

存储层级与算术强度：为什么“搬数据”比“做乘法”更贵

初学者常以为优化算子就是减少加减乘除次数。但在现代 GPU 上，计算单元的峰值算力极高，真正的瓶颈往往在于把数据从显存搬进计算单元的带宽有限。

存储层级可见范围容量量级访问速度算子中的典型用途
寄存器（Registers）单个线程私有最小（每 SM 数十至数百 KB）最快（时钟周期级）存放当前累加值与活跃操作数
共享内存 / L1单个线程块共享小（每 SM 数十至约 200 KB）很快（片上 SRAM）程序员手动管理的高速中转区，用于块内数据复用
L2 缓存全芯片所有 SM 共享中等（MB 级）较快（片上）硬件自动缓存，吸收跨块重复访问
全局内存（显存 HBM / GDDR）全部线程块与主机可见最大（GB 级）最慢（数百时钟周期）存放输入与输出张量

衡量一个算子受限于算力还是受限于显存带宽，最直观的指标是算术强度（Arithmetic Intensity）——每从全局内存搬运 1 字节数据，能完成多少次浮点运算：

对比两个 FP32（每个数占 4 字节）算子，差距一目了然：

  • 逐元素向量加法（ci=ai+bic_i = a_i + b_ici​=ai​+bi​）：每个元素只做 1 次加法，却要读入 a[i]、b[i]（8 字节）并写出 c[i]（4 字节），共搬运 12 字节，算术强度仅 1/12≈0.083 FLOP/B1 / 12 \approx 0.083\text{ FLOP/B}1/12≈0.083 FLOP/B（计算值）。哪怕算力无限大，耗时也完全卡在显存带宽上，属于典型的访存受限（Memory-Bound）算子。
  • 稠密矩阵乘法（1024×10241024 \times 10241024×1024 的 FP32 矩阵 C=ABC = ABC=AB）：总浮点运算量为 2×10243=2,147,483,6482 \times 1024^3 = 2{,}147{,}483{,}6482×10243=2,147,483,648 次（计算值）。若 AAA、BBB 仅各读一次、CCC 仅写一次，最少只需搬运 3×10242×4=12,582,9123 \times 1024^2 \times 4 = 12{,}582{,}9123×10242×4=12,582,912 字节（12 MiB，计算值），理论算术强度达到 1024/6≈170.7 FLOP/B1024 / 6 \approx 170.7\text{ FLOP/B}1024/6≈170.7 FLOP/B（计算值）。只要做好数据复用，就能让计算单元满负荷运转，属于计算受限（Compute-Bound）算子。

算子开发的四类核心优化机制

看懂线程与存储层级之后，日常算子优化中反复出现的四种手段都顺理成章。

1. 分块与数据复用（Tiling）

如果写一份最直白的矩阵乘法：让每个线程直接去全局内存读一整行 AAA 和一整列 BBB 来算一个输出元素，那么 102421024^210242 个线程总共会向全局内存发起 2×10243×4=8 GiB2 \times 1024^3 \times 4 = 8\text{ GiB}2×10243×4=8 GiB 的逻辑读取（计算值）——而 AAA 和 BBB 加起来本身只有 8 MiB8\text{ MiB}8 MiB，同一批数字被重复搬了上千遍。

分块（Tiling）的做法是：让一个线程块负责输出矩阵的一块子区域（例如 32×3232 \times 3232×32）。块内线程先协作把对应的 32×3232 \times 3232×32 块 AAA 和 BBB 搬进片上共享内存，同步后各自在寄存器里完成局部乘加，再滑向下一块。这样每个从全局内存搬上来的元素都会被块内 32 个线程复用，逻辑全局读取量直接下降 32 倍，从 8 GiB8\text{ GiB}8 GiB 降到 256 MiB256\text{ MiB}256 MiB（计算值）。进一步让每个线程在寄存器里同时负责一小块输出（如 4×44 \times 44×4），还能同步压缩对共享内存的重复读取。

2. 合并访存与消除 Bank 冲突

全局内存按连续缓存行（32 字节扇区）批量传输。如果同一 Warp 里的 32 个线程正好读取内存中相邻的 32 个 FP32 数值，内存控制器会把它们合并成一次 128 字节的高效读取（合并访存 / Coalescing）；如果线程按大步长跨列跳跃读取，硬件不得不拆分出大量零碎事务，大部分带宽都浪费在用不上的相邻字节上。

在共享内存内部，NVIDIA GPU 把空间均分为 32 个存储体（Bank），每个 Bank 宽 4 字节。同一 Warp 的 32 个线程如果恰好落在 32 个不同 Bank，可以一拍同时读出；但如果多个线程落到了同一个 Bank 的不同地址（例如按步长 32 竖着读矩阵），硬件就必须排队串行响应，形成 Bank 冲突（Bank Conflict）。工程上通过给行宽加填充（Padding）或使用异或索引重排（XOR Swizzle），把不同列错开到不同 Bank 上。

3. 算子融合（Kernel Fusion）

对于访存受限的轻量操作（加偏置、激活函数、残差相加、归一化），如果每个操作都单独启动一次算子，就会反复把中间结果写回显存、再从显存读回来。

以 FP32 下的 y = relu(x + b) 为例：

  • 不融合（两次算子调用）：第一个算子读 x、b 并写出临时结果 t（12 B/元素）；第二个算子再读 t 并写出 y（8 B/元素），全局内存总流量为 20 B/元素（计算值）。
  • 融合（一次算子调用）：线程读入 x[i] 与 b[i] 后，在寄存器里顺手完成加法和 ReLU，直接写出 y[i]，全局内存流量降至 12 B/元素，直接省掉 40% 的显存搬运（计算值），同时少了一次内核启动开销。

大模型中广为人知的 FlashAttention 本质上也是更彻底的融合：它不把巨大的 N×NN \times NN×N 注意力分数矩阵写回显存，而是在片上按块流式计算并在线更新归一化系数，相关推导可见Online Softmax与注意力分块实现。

4. Tensor Core 与低精度计算

传统标量计算单元每拍每个线程只能做一次标量乘加。从 Volta 架构起，NVIDIA GPU 引入了专门面向矩阵乘加的硬件单元 Tensor Core，单条指令即可在 Warp 或 Warp 组粒度上完成小型矩阵块（如 16×8×1616 \times 8 \times 1616×8×16）的乘加运算。Tensor Core 主要面向低精度输入（FP16、BF16、TF32、FP8 等），同时在内部用更高精度（通常为 FP32）做累加，兼顾速度与数值稳定性。要真正跑出 Tensor Core 的高吞吐，不仅需要矩阵维度对齐硬件块大小，还需要配合异步搬运指令让数据供给跟上计算节奏。

输入形状如何决定实现选择

没有哪一种并行切分方式能在所有输入形状下都最快。当批量大小（Batch Size）很大时，把并行度分配给不同样本和通道就能填满所有 SM；但当批量退化为 1、序列很长时，原有切分会让大部分 SM 闲置，此时改为沿时间步或归约维度切分（例如分块并行扫描或 Split-K 矩阵乘）反而能获得数量级的加速——具体形状对照可以参考站内的选择性扫描并行设计。

因此，规范的算子开发总是遵循“先验证数值正确性 → 再用性能分析工具（如 Nsight Compute）定位当前卡在带宽、延迟还是算力 → 针对瓶颈实施一项改动 → 在目标形状上重新计时验证”的闭环，而不是凭直觉盲目套用模板。
