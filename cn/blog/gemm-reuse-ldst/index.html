CUDA GEMM 优化：线程块分块、寄存器复用与向量化访存

一个线程块计算 64×64 个输出，让多个线程共用同一批 A、B 元素；每个线程计算其中的 4×4 子块，又能在寄存器中复用操作数。在同一 RTX 5070 Laptop 上，分块和输入地址相同时，float4 加载使 1024³ 和 4096³ GEMM 的耗时分别缩短约 22% 和 16%，CUB DIRECT 与标量加载的耗时差异则未能分辨。

整理早期的 GEMM 记录时，我发现标量加载器和 CUB 加载器编出了相同的指令文本，旧计时却相差约三成。要判断这样的差距来自加载器还是测量条件，得先分清分块究竟复用了什么，再把两种实现放在同一批数据上比较。

矩阵乘法 C=ABC=ABC=AB 中，A∈RM×KA\in\mathbb R^{M\times K}A∈RM×K、B∈RK×NB\in\mathbb R^{K\times N}B∈RK×N，大约需要 2MNK2MNK2MNK 次浮点运算。如果每次乘加都要重新从显存读取 A 和 B 的元素，显存带宽便可能限制运算速度。在我写的第一版 GEMM 中，每个线程只算一个输出元素，1024³ 方阵耗时 3.2601 ms；同一台机器上，cuBLAS 用同样的 FP32 输入只需 0.6164 ms。

减少访存有三种着手点。相邻输出需要同一批 A、B 元素，负责一个 64×64 输出块的线程因此可以共用一份输入。当单个线程也计算多个输出时，进了寄存器的操作数又能参加多次乘加。float4 改变的则是每条指令搬运的数据量，只有固定前两种分工，才能把它与标量加载、CUB 加载在 RTX 5070 Laptop 上比较。

我把三个加载器编进同一份可执行文件，让它们在同一进程交替读写完全相同的地址。对 1024³ 和 4096³ 方阵，宽读比标量分别省下约 22% 和 16% 的时间。标量和 CUB 逐条相同的指令在配对复测中也没有显示出旧实验所报的速度差距。

朴素 GEMM 的线程映射与全局内存访问

A、B、C 都按行连续存储，地址 A[i*K+k] 对应 AikA_{ik}Aik​，B[k*N+j] 对应 BkjB_{kj}Bkj​。计算第 i 行、第 j 列的一个输出，就是对 A 的这一行与 B 的这一列求点积。

Cij=∑k=0K−1AikBkj.C_{ij}=\sum_{k=0}^{K-1}A_{ik}B_{kj}.Cij​=k=0∑K−1​Aik​Bkj​.

一个线程负责一个输出，沿 K 循环累加，就是最直接的写法：

// 教学版：A[M,K]、B[K,N]、C[M,N]，均为连续行主序。
__global__ void gemm_naive(const float* A, const float* B, float* C,
                           int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= M || col >= N) return;
    float sum = 0.0f;
    for (int k = 0; k < K; ++k)
        sum = fmaf(A[row * K + k], B[k * N + col], sum);
    C[row * N + col] = sum;
}

fmaf(a,b,c) 算 ab+cab+cab+c，乘积和加法只舍入一次。K=0 时循环不执行，输出自然是 0。这个 kernel 没有线程间通信，边界上的线程可以直接返回。

用 16×16 的线程块（block）启动，256 个线程盖住 16×16 个输出。CUDA 按线程束（warp）分组，每 32 个线程一组，组内编号叫 lane。二维 block 里 x 下标变得快，所以一个 warp 跨两行，每行负责 16 个输出。

固定 k 时，同一输出行的 16 个线程都读取同一个 A 元素，读取 B 的列号则连续递增。即使 warp 合并了对相同或相邻地址的访问，这次加载得到的操作数仍只在当前线程的一个输出上使用。

例如，计算 Ci,jC_{i,j}Ci,j​ 与 Ci,j+1C_{i,j+1}Ci,j+1​ 的线程都需要 AikA_{ik}Aik​，计算 Ci,jC_{i,j}Ci,j​ 与 Ci+1,jC_{i+1,j}Ci+1,j​ 的线程都需要 BkjB_{kj}Bkj​。缓存命中能减少抵达显存的请求，却不会自动删去程序里的加载指令、地址计算和依赖等待。若显式分块，线程便可以约好由谁搬运输入，再共同读取它。

全局内存（global memory）放整张矩阵。块内的线程用共享内存（shared memory）交换一小块输入，每个线程的累加器则放在自己的寄存器里。一个 block 驻留在一个流式多处理器（SM）上，同一个 SM 能同时容纳几个 block，取决于寄存器、共享内存用量与线程数。

用共享内存分块复用 A、B 的输入

当一个线程块负责 C 中 64×64 个输出时，它需要 A 的 64 行和 B 的 64 列。沿 K 每 32 项分成一段，线程只需把 A 的 64×32 个元素和 B 的 32×64 个元素搬到共享内存，就能更新全部 4096 个输出。处理下一段时，部分和仍保留在原线程的寄存器里。

把各段对同一输出的贡献相加，得到的就是原来的点积。

Ctile=∑tAtile,tBt,tile.C_{\rm tile}=\sum_{t}A_{\rm tile,t}B_{t,\rm tile}.Ctile​=t∑​Atile,t​Bt,tile​.

每段输入是 64×32+32×64=409664\times32+32\times64=409664×32+32×64=4096 个 float，16 KiB；它能完成 64×64×3264\times64\times3264×64×32 次 FMA，262144 FLOP。忽略写回 C 的成本，这一级的逻辑输入算术强度是 16 FLOP/B。一般的 BM×BN×BKB_M\times B_N\times B_KBM​×BN​×BK​ 分块对应

Itile=2BMBNBK4(BMBK+BKBN)=BMBN2(BM+BN).I_{\rm tile} =\frac{2B_MB_NB_K}{4(B_MB_K+B_KB_N)} =\frac{B_MB_N}{2(B_M+B_N)}.Itile​=4(BM​BK​+BK​BN​)2BM​BN​BK​​=2(BM​+BN​)BM​BN​​.

分子、分母中都有 BKB_KBK​，约去后，逻辑输入复用比就只取决于输出块的两个维度。加大 K 分块可以减少循环和同步次数，也会占用更多共享内存；扩大输出块则能让同一输入真正参与更多个输出的计算。

这个式子按线程块需要哪些输入计数。相邻块可以命中 L2 缓存，朴素实现的重复读取也可能由缓存满足，因此不能把式中的字节数直接代入显存带宽来预测耗时。

寄存器外积与每线程 4×4 输出分块

共享内存已经把输入送到线程块，下一步是让每个线程复用取出的操作数。64×64 的块有 4096 个输出，若仍由 256 个线程承担，正好能将每个线程分配到一个 4×4 子块。

int local_m = (threadIdx.x / 16) * 4;
int local_n = (threadIdx.x % 16) * 4;
float acc[4][4] = {};

线程 0 算行 0–3、列 0–3；线程 1 算行 0–3、列 4–7；线程 16 算行 4–7、列 0–3。16×16 个这样的小块正好铺满整个输出，不重叠也没有空洞。

线程负责一整个输出子块时，可以把同一 k 上的更新写成外积。固定 k，线程只需要 4 个 A 元素和 4 个 B 元素，8 个数就能更新 16 个输出：

for (int kk = 0; kk < 32; ++kk) {
    float a[4], b[4];
    for (int i = 0; i < 4; ++i)
        a[i] = shared_a[(local_m + i) * 32 + kk];
    for (int j = 0; j < 4; ++j)
        b[j] = shared_b[kk * 64 + local_n + j];
    for (int i = 0; i < 4; ++i)
        for (int j = 0; j < 4; ++j)
            acc[i][j] = fmaf(a[i], b[j], acc[i][j]);
}

图 1　左图中，一个线程块把输入分给多个线程；右图中，同一个线程取出四行上的 A 元素和四列上的 B 元素，完成 16 个输出的累加。

一份输入从全局内存搬进共享内存后，块内的多个线程都能用它。每个线程再将一个操作数读入寄存器，利用外积让它参加四次乘加。展开循环还能交错更新彼此独立的累加器，在一条乘加依赖尚未解除时执行另一条。

协作加载需要两道块级屏障。第一道保证各线程读到完整的 A、B 子块。第二道设在外积累加之后，防止较快的 warp 用下一段 K 覆盖仍在读取的共享内存。只有全部 K 段处理完毕，各线程才把寄存器里的部分和一次写回 C。

还可以进一步扩大块内和线程内的复用范围。128×128 输出块、每线程 8×8 累加，逻辑输入强度升到 32 FLOP/B，但每线程也要存 64 个输出。下文叫它 128² 寄存器分块版：256 线程、BK=16、A 在 shared 中转置并加 padding、整齐内部块和边界块分开处理。它同时改了好几个设计参数，所以后面它的成绩只能说明更大复用范围的整体效果，不能算成对 64² 版只改一个参数。

用 float4 加载连续的四个元素

要单独比较加载宽度，先固定 64² 输出块、BK=32 和每线程 4×4 的分工。A、B 子块各有 2048 个元素，256 个线程各搬八个。让线程 t 负责逻辑下标 8*t 到 8*t+7，这叫 blocked 分配：每个线程拿一段连续下标，而不是按 lane 交替。

一个线程的八个元素连续，并不意味着同一条加载指令访问的地址也连续。标量循环在第 i 次发出读取时，lane 0、1、2 依次读取下标 i、8+i、16+i，相邻 lane 相隔八个 float，即 32 字节。

同一个线程负责的八个元素在内存中相邻，因此可以用两次 float4 宽读将它们搬完。三个加载器读的是相同输入，使用相同的共享内存布局和后续乘加，下面比较的差别集中在如何发出读取。

加载方式每线程取得的元素shared 布局与计算
手写标量八次标量读，逻辑下标 8*t+i相同
手写 float4两个完整对齐组宽读，其余标量回退相同
CUB DIRECT用 BlockLoad 表达同一 blocked 分配相同

加载器用二维迭代器把子块内的逻辑下标还原为矩阵中的地址，越界位置返回零。A 子块每行只取 32 项，下一行在原矩阵里的起点却要跨过 K 项。B 子块同样必须保留 N 的行步长，直接把整个子块当成一串连续数据会从错误的行取数。

int row = index / TileCols;
int col = index % TileCols;
return row < valid_rows && col < valid_cols
     ? base[row * stride + col] : 0.0f;

CUB 版就是把这个迭代器交给 cub::BlockLoad<..., BLOCK_LOAD_DIRECT>。DIRECT 保持 blocked 的元素归属，不会自动换成按 lane 连续的 striped 加载；换加载策略时还得核对每线程收到的元素顺序，再改写 shared 的索引。库能把加载方法表达清楚，但不会替 GEMM 决定整套数据布局。BlockLoad 实现

16 字节对齐、矩阵尾部与标量回退

一次宽读覆盖四个 float，也就是 16 字节。只有实际起始地址满足对齐条件，并且四个元素都在矩阵范围内时，才可以走这条分支。

if (row_valid && col + 3 < valid_cols && aligned_16(ptr)) {
    float4 value = *reinterpret_cast<const float4*>(ptr);
    // value 的四个分量归入本线程的四个连续位置。
} else {
    // 逐元素判断；有效则读取，否则写零。
}

图 2　比较分配基址与偏移一个 float 的视图，后者使一次 16 字节宽读失去对齐。

分配基址对齐时，传 A_allocation+1 就让起点偏了四字节。就算 M、N、K 都是整齐的 tile 倍数，也不能继续无条件宽读。K=33 时 A 的行距是 132 字节，每行起点的对齐状态都不一样。CUDA 自然对齐要求

128² 版一开始只按形状判断走不走快路径，在 M=N=128,K=32,offset=1 上就发出了 16 字节错位读，memcheck 直接报 misaligned。修好以后，快路径额外检查 A/B/C 的实际基址，边界路径逐组检查宽读与宽写，包含这个反例的 36 项 memcheck 零错误。条件很具体：矩阵尺寸没变，变的是传进来的数组视图地址。

M、N 的尾块只写有效输出，K 的尾块则把越界的输入补零。在协作加载中，一个没有有效输出的线程仍可能负责搬运其他线程要用的输入，也必须参加块级屏障，因此不能按自己的输出坐标提前返回。

PTX、SASS 与 L1TEX 计数中的宽加载

源码写成 float4 只给出了类型，要确认这次编译是否产生了对应的宽指令，还得检查实际模板实例的反汇编。PTX 是面向 GPU 的虚拟指令表示，SASS 才是目标架构执行的机器指令。用 CUDA 13.1、-O3 -lineinfo -arch=sm_120 编译，沿实际加载模板把两层都取出来。

float4 分支的 PTX 节选如下，寄存器编号是编译器分的：

@%p5 bra $L__BB2_5;
shl.b64 %rd28, %rd2, 2;
add.s64 %rd29, %rd4, %rd28;
ld.global.v4.b32 {%r1084, %r1083, %r1082, %r1081}, [%rd29];
bra.uni $L__BB2_13;

下标左移两位得到字节偏移，加到基址后执行 v4.b32，一次加载四个 32 位分量。SASS 里对应 LDG.E.128。条件不满足就跳到标量回退路径，所以在同一个函数里同时看到标量和向量指令并不矛盾。

图 3　纵轴分别统计对 L1TEX 的请求数和访问的 32 字节扇区数。对齐的 1024³ 上，float4 使两项都降到标量的四分之一。

blocked 分配让一个 warp 里相邻 lane 隔 32 字节，一条标量指令就碰 32 个 sector；一个线程接着读相邻那三个 float，三次指令碰的还是那批 sector。换成 float4，四个元素落在一次宽读里，warp 还是碰 32 个 sector，但请求数和 sector 访问计数都降到四分之一。

寄存器变多也不必然按比例压低驻留。occupancy 是实际驻留 warp 数相对硬件容量的比例；SM 按整个 block 分配资源，资源限制有离散阈值。这份输入下 NCU 给出的 register block limit 对两版都是 3，实际 occupancy 只从 45.14% 走到 44.12%，运行时 local/shared spilling 都是零。这里还没跨过新的驻留门槛，换线程数或累加块就得重新判断。

形状一不整齐，这个四倍关系就不成立了。129×131×65,offset=1 的 float4 模板是 2220 个请求、41484 个 sector：部分 lane 无效，某些行又正好满足对齐，宽读和标量混着走。模板叫 float4，只说明它有这条路径；分支实际走了多少次，需要动态计数。

标量、float4 与 CUB 加载器的同进程配对计时

旧的 4096³ 测量把标量与 CUB 放在不同的可执行文件中运行。虽然归一化后的 SASS 逐条相同，两种加载器的耗时却相差约三成。两份可执行文件的散列不同，温度和频率也在变化。要把实现的影响分出来，我让两版共享同一可执行文件和同一组 A、B、C 地址，并在每个进程里交替执行 ABBA、BAAB。再把同一个标量函数放在 A、B 两个位置，先看测量自身会不会凭空给出差距。

两组 A/A 的整个区间都落在预定的 ±2% 校准带内，八个区间也都达到半宽 2% 的精度目标。宽读在两个方阵上都缩短了耗时，CUB 与标量的耗时比区间则都包含 1。 这轮测量足以排除旧报告中 1.32 倍的差距，但旧批次同时存在环境与可执行文件差异，无法判定是哪一项造成了旧结果。cuBLAS 在两个尺寸上均快于手写 128² 分块，在 1024³ 上与历史批次的排序相反。

这台笔记本没有锁频，测试期间曾查到软件限功率生效，进程首尾的读数不能还原每一个计时窗口。用 Nsight Systems 另外抓取，1024³ 的库 kernel 是 cutlass_80_simt_sgemm_128x64_8x5_nn_align1，4096³ 是 cutlass_80_simt_sgemm_128x128_8x4_nn_align1，都封装在 cutlass::Kernel2 中。这里测的是 CUBLAS_PEDANTIC_MATH 下的 cublasSgemm；库版本、数学模式或算法选项变化，都可能改变它选的内核。

按输入复用、加载宽度与矩阵形状选择 GEMM 实现

在这两个大方阵上，线程块分块先让相邻输出共用 A、B，线程分块又让寄存器中的操作数参加多次乘加。在同一分工、同一地址下，每条指令从四字节读扩大到十六字节仍然缩短了耗时。换成 CUB DIRECT 后，编译器生成的加载指令却与标量版相同，配对结果也没有显示出稳定优势。换矩阵形状时，可以直接从三个量判断同样的优化还有多少机会：输出块总数、尾块中有效的行列数，以及输入在连续调用之间是否常驻设备。

双缓冲实验沿用寄存器外积累加，但调整了线程分工。这里比较加载方式时，每个线程块计算 64×64 个输出，每线程负责 4×4 个。双缓冲实验把它们分别改为 128×64 和 8×8，再固定这套映射，测量共享内存的 bank 冲突，并检验下一块输入的搬运能否与当前块的计算重叠。共享内存布局与双缓冲

想看 Hopper 上的 TMA、WGMMA 和 persistent 调度怎么把搬运与计算交给不同的硬件路径，可以读 Aleksa Gordić 的 matmul 长文。那套机制下分块和同步都要跟着改；这里的 FP32 SIMT 测量只描述这里的 SM120 实现。

实验环境与测量方法、正确性检查、复现入口

附录中的 bench_mur/、rep_mur/ 指向作者私有实验仓库，供对应实现和数据归档时检索。

实验环境与测量方法

测试设备为 RTX 5070 Laptop GPU、SM120、约 8 GB 显存；编译 Toolkit 13.1.115，MSVC 2022 14.44，驱动 610.88，选项为 -O3 -arch=sm_120 -lineinfo。环境交叉核验记录到运行时 API 版本 13.3。CUDA 13 起 Windows 运行时可随显示驱动分发，因此这个值可能不同于构建 Toolkit，见 Runtime API 版本说明。原始 GEMM CSV 未查询该字段。消费级 SM120 与 B200/SM100 的资源和指令能力也应分别考虑。

所有实现都用普通 FP32 乘加，cuBLAS 对照也采用 pedantic FP32，不启用 TF32。这项约束排除了用更低精度换取速度的因素。数据布局、编译器生成的指令与寄存器分配都可能改变耗时，笔记本未锁定的频率也会影响测量。

设备计时采用 CUDA events：20 次预热，估计单次时间后把每批调整到约 20 ms，每批重复数限制在 1–2000。较慢 kernel 一次已超过 20 ms，极短 kernel 达到重复上限后可能不足 20 ms，原始记录保留实际重复数。每轮 30 批，共三轮，固定种子打乱轮内任务顺序。输入重复使用，不清 L2，因此测的是缓存热态的重复调用。笔记本未锁频，三轮波动如实展示。

端到端计时包含从可分页主机内存上传 A、B，执行一次 GEMM，下载 C 并等待完成。内存分配、编译及创建 handle 均在计时之外。每轮预热五次后测 30 次，每个样本只发起一次调用，这样主机传输开销不会被多次复用设备输入摊薄。

正确性检查

先运行六变体、12 形状、三种输入，共 216 项：均匀随机、全零、正负交替的消减输入；形状覆盖 K=0、单元素、63/64/65 和 127/128/129 附近尾块、不对称矩阵，以及 1/2/3 个 float 偏移。输出预填 NaN，并检查前后哨兵，防止漏算和越界写入被初始化掩盖。

小形状逐元素对照 CPU FP64。每个输出点的工程误差预算为：

∣Cij−Cij64∣≤10−6+16ϵ32∑k∣AikBkj∣.|C_{ij}-C^{64}_{ij}|\le 10^{-6}+16\epsilon_{32}\sum_k|A_{ik}B_{kj}|.∣Cij​−Cij64​∣≤10−6+16ϵ32​k∑​∣Aik​Bkj​∣.

这是本实验的验收阈值，不是任意输入、任意 K 的浮点证明。216 项全部通过，最大绝对误差 6.6622e-6，最大“实际误差/阈值”为 0.1123。四种修正版自写 kernel 的 memcheck 均为零错误。

大矩阵做全量 cuBLAS FP32 对照，阈值 atol=3e-4,rtol=3e-4；另选 257 个确定位置对照 CPU FP64，包含首尾和分散位置。这同时提供全量 GPU 对照和部分独立高精度参考，不能称为全量 FP64 验证。每个性能任务先通过对应正确性检查。

复现入口与数据位置

配对复测使用 bench_mur/revision_20261115_gemm/{paired.cu,run.py,verify.py,plot.py}。先运行 build 和 accuracy，每个对照用三个预试进程确定固定样本量，再执行 pilot --suite gemm 和 confirm --suite gemm。预试数据从确认统计中排除。每个对照 24 个全新进程、每进程 20 个平衡块，共 192 个进程和 3,840 个配对块。先取各进程内平均对数时间比，再用跨进程的 Student-t 区间并取指数还原。每进程都检查数值有限、输出哨兵、全量 cuBLAS 与 CPU FP64 抽样。时间窗内只保留重复调用和可能的设备供给间隙，分配、H2D 和构造参考值都在窗外，复用地址且不主动清 L2。另存从提交到完成的墙钟均值。数据、散列、功率记录在 rep_mur/experiment-revision-20261115/gemm/，复跑另用 --output，内核源改变需要重建。

兼容入口 solve(A,B,C,M,K,N) 仍在返回前同步；计时使用新增的 stream launch。各变体独立编译，避免多个同名 solve 相互链接。脚本位于 bench_mur/gemm/{build.ps1,run.py,plot.py}，逐批数据、原始失败、源码哈希、SASS 与 sanitizer 日志保存在 rep_mur/blog-rewrite/gemm/。地址图和外积图是依据源码绘制的示意，不是 profiler 截图。

两篇 GEMM 共用的第二批实验包含 10 个变体、240 次计时前正确性检查和 14,400 条设备/端到端时间记录。乘积项数达到 3000 万以上的形状采用全量 cuBLAS pedantic FP32 加 257 点 CPU FP64，其余较小案例完整对照 CPU FP64。第二批原始文件与独立聚合在 rep_mur/blog-rewrite/style-v2/gemm/，未与第一批时间混合统计。

PTX/SASS、NCU 原始报告、CSV 和 Nsight Systems 事件保存在 rep_mur/blog-rewrite/style-v3/profiling/。bench_mur/editorial/style-v3/profile_static.py 从计时二进制提取汇编；collect_ncu.ps1 串行采样；read_ncu.py 保留原指标名与单位；plot_profile.py 从原始导出作图。二进制和报告均记录哈希。
