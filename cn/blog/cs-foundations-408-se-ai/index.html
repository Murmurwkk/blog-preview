视频播放器停在一帧画面上。放大左上角的一点，它的红、绿、蓝三个分量分别是 210、231、236。我们可以写程序把这一帧存成图片，也可以让程序去一千段视频里找出画面模糊的片段。两件事都从像素开始，难处却落在不同地方。保存帧时，程序必须知道文件怎样编码、这一帧在哪里。判断模糊时，我们还得说明什么样的画面算模糊，并让程序在从未见过的视频上接受检验。

我们就做一个这样的视频资料库。用户交来一段短片，服务抽取预览图、标出值得复查的画面，必要时还能解释它用了哪一种解码工具。先在一台机器上处理一个文件，再把这项功能交给浏览器里的其他用户，最后用收集到的样本训练模型。沿这个顺序走，每次都会遇到上一层尚未解决的问题。图中的五层自上而下画出依赖，正文从最下面一个字节开始。例中的像素、矩阵、回归和注意力都可以手算，服务则是一个用来推演接口和故障的教学例子。

图像的字节表示与帧时间索引

字节的解释与 RGB 图像的内存布局

一张画面首先要有读法。一个字节含八个二进制位，把 01000001 当无符号整数，从右往左给各位配上 1、2、4 到 128 的权重，其中只有 64 和 1 两位被置上，结果就是 65。按照 ASCII 编码，编号 65 分给了大写字母 A。ASCII 定义的是七位字符码，早期网络规范把它放进八位字节时规定最高位为零。图像程序也能把这同一个字节读成一个通道强度 65。究竟看到字母还是颜色，取决于读它的位置和格式约定。RFC 20 的 ASCII 码表

挑一张最容易读懂的图片，假设解码器已经给出每个通道八位的 RGB 数据，像素依次存放，行尾没有填充。示例像素的字节顺序就是十六进制的 D2 E7 EC。如果另一段程序沿用蓝、绿、红的通道顺序，它会把 210 交给蓝色、236 交给红色。两段程序都能顺利读到缓冲区末尾，颜色却会有偏差。再考虑一行有两个这样的像素，总共需要六个字节。若某个接口出于对齐需要把下一行的起点放在距本行起点八字节处，逐行前进就要跨八字节。行的可见宽度和行起点之间的距离是两项分别要写清的约定。

沿这个例子算一笔大小。宽 1,920、高 1,080 的同类图像共有 2,073,600 个像素，紧密排布的 RGB 数据占 6,220,800 字节，约 5.93 MiB。一张用单精度浮点数承载相同三个通道的张量会占四倍空间，约 23.73 MiB。相机保存的 JPEG 或视频中的压缩画面又有各自的编码，文件大小还受场景与编码参数影响。这里从宽、高、通道数算出的是给定内存布局下一帧的数据量。用它可以为解码后的缓存估算容量，不能据此预报视频上传会传多少字节。

图像一旦进入数组，坐标也要有读法。以左上角为原点，列号为 xxx、行号为 yyy，两者从零开始。宽度为 WWW 的紧密 RGB 图中，第 yyy 行第 xxx 列的绿色分量位于距首字节 3(yW+x)+13(yW+x)+13(yW+x)+1 的位置。取宽为四的图，第二行第三列的绿色就在偏移 19 处。若一行实际占 sss 个字节，式子要改成 ys+3x+1ys+3x+1ys+3x+1。这个看似琐碎的修改同样适用于从大图中裁出的小矩形。视图可以保留原图的行距，只移动左上角的起点，因而看上去同宽的两张图也可能需要不同的寻址公式。

视频还多了一层时间。MP4 是容器，容器可以把用 H.264 编码的视频、用 AAC 编码的音频以及对应的时间信息放在同一个文件中。FFmpeg 读取文件时先由解复用器分出各条流，再由所选视频解码器把压缩包还原为帧。很多视频帧会引用其他帧，定位到某个时刻的文件位置，往往还要从能恢复解码状态的位置开始向前解码。连续三字节的 RGB 像素是其中一种解码结果，直接在 MP4 文件里按像素公式查找颜色没有意义。FFmpeg 对解复用、解码与筛选的说明

以下命令选择输入文件中的第一条视频流，取一帧，明确把输出像素格式定为 rgb24。裸数据里没有宽、高和颜色顺序，接收方还需要从视频信息或双方约定中取得它们。若改用 PNG 作为输出，接收方可以从文件头取得尺寸，但还得先解码 PNG。这里换了交付格式，所保存的画面可以是同一张。

ffmpeg -i clip.mp4 -map 0:v:0 -frames:v 1 -pix_fmt rgb24 -f rawvideo frame.rgb

为了检验读出的是哪一组字节，用 FFmpeg 8.0.1 把一张四列两行、首像素为 (210, 231, 236) 的小图经过 libx264rgb 的无损设置装入单帧 MP4，再按上述参数解码。读回的 RGB 数据长 24 字节，与八个输入像素逐字节相同。普通有损编码会量化画面，颜色转换也可能引入误差，逐字节相等是这个无损 RGB 样例可以检验的属性。

根据时间戳寻找应当显示的帧

要做播放器的拖动预览，首先得定义“第 95 毫秒的画面”。设六帧的显示时刻依次为 0、40、80、120、160、200 毫秒，每帧持续到下一帧开始。第 95 毫秒应显示 80 毫秒那一帧。如果问从现在往后下一次何时开始显示新帧，答案则是 120 毫秒。在同一张索引里，两个问题要取边界的不同一侧。若只查找完全相等的时间戳，会错过绝大多数用户选择的位置。如果视频允许可变帧率，试图用“时间乘平均帧率”计算数组下标也没有这个保证。这就把解码工具中的一个界面动作，变成了一个边界查找问题。

有序数组适合这个问题。用两个下标圈住仍可能含有答案的范围，每次读中点，把至少一半候选排除。Python 的 bisect_right 返回把目标插到所有相等值右侧的位置，95 的插入点是下标 3，往前退一格便得到下标 2，对应时间 80。选择刚好等于 120 的时刻时，返回位置 4，退一格仍然得到 120。若目标早于第一帧，要单独定义是显示空画面还是钳到首帧，不能把 Python 的负下标误用成最后一帧。Python 有序序列的二分查找

from bisect import bisect_right

def frame_at(starts, time_ms):
    index = bisect_right(starts, time_ms) - 1
    return None if index < 0 else index

搜索一百万个已经排好序的起始时刻，二分大约经过二十次区间折半就能定位。这个计算说的是查找阶段。如果原始记录没有排序，要先付出建索引的代价。若每追加一项都得插入数组中部，找到位置虽快，后面的大量元素仍然要让位。视频帧通常按一条明确的时间线提供，批量构建后反复查询有利于把这份成本摊开。对乱序到达、随时要增删的任务记录，能维护顺序的平衡树或数据库索引会更合适。

换一种需求，用户手上已经有任务编号，只想知道任务是否完成。哈希表按编号的哈希值寻找候选槽位，碰到冲突时再检查键，在合理负载和分布下平均能很快回答精确匹配。它缺少按时间相邻的次序，用来找 95 毫秒之前最近一帧就费力得多。链表可以在已知节点附近插入新元素，然而要得到中间编号的那一帧仍需沿指针逐个走。数组、树和哈希表之间的选择，来自程序实际要做的查询和更新。MIT 算法课的搜索树、哈希与图讲义

同一个资料库里还会出现图。压缩视频中的参考帧关系、工程中的构建依赖、训练时产生梯度的计算图，都是在记“谁依赖谁”。一张时间表只记录先后，依赖图还能表示某个结果被多个消费者共用。因此当一个模型改了预处理规则，几批旧预览需要重算，可以沿依赖关系找受影响的输出。到这里，我们已经用到了计算机基础 408 中的数据结构与算法。衡量算法时关心工作量怎样随输入增长，接下来要看这些动作落到机器上，每一次读写究竟要走多远。

CPU 指令、缓存与进程中的图像缓冲区

从一个像素加法进入寄存器与缓存

设我们想让画面更亮，把每个通道增加 10，并把结果限制在 255 以内。示例像素会变成 220、241、246。对原值 250，先用能容纳 260 的整数做加法，再把它钳到 255。如果先写回八位无符号数，260 会按模 256 变成 4，之后再取最小值也救不回来。一次像素处理至少包含取数、运算、选择合法结果、写回以及推进循环位置。同一个数学式放进不同宽度的机器类型，截断发生的位置就可能改变画面。

计算机组成原理研究处理器怎样完成这些动作。指令集架构规定机器指令的语义、可见寄存器和寻址规则。比如在常见的 AArch64 调用约定下，传入一个整型参数并返回整数，参数与返回值可复用寄存器 w0。一个简单的“加一后返回”函数在优化后可能只需 add w0, w0, #1 和 ret。实际生成哪些指令由类型、编译目标和优化决定。C 源文件里没有寄存器名，汇编里也没有“调亮图片”的指令，这层转换由编译工具完成。CS:APP 的 hello.c 更短，然而连它的一行输出也要经历预处理、编译、汇编、链接和加载，才有处理器真正执行的程序。CS:APP 的原始 hello 示例

对写程序的人，理解指令的可见效果往往已经足够。处理器内部可以把一条指令分解为多个动作，同时预取后续指令，提前执行不依赖当前结果的运算，再按架构规则交付结果。同一套指令集可以有不同内部设计，有的控制步骤由微程序实现。若给一个 RGB 缓冲区调亮，连续若干像素之间相互独立，编译器还有机会用向量指令一次计算多个通道。无论硬件用多少条内部路径，边界像素有没有越界、溢出后应得到什么值，最后都得按程序约定核对。

CPU 能同时做很多加法，读到下一个像素却未必同样快。寄存器直接供指令取操作数，缓存把附近用过的部分内存留在处理器附近，主存才容纳整个大数组。顺着行扫描时，载入的一块相邻字节能服务随后的多次迭代。若先固定列号、逐行向下，在紧密的全高清 RGB 图中相邻两次会跳过 5,760 字节，同一块缓存数据中相邻的其他像素要等好久才会再用。两个循环处理的像素个数相同，时间差完全可能来自访问顺序。SSD 上的压缩文件还要经过系统与解码器才成为这块内存，磁盘读量和 CPU 缓存流量也分属不同环节。

CS:APP 的“存储器山”给了一个可以自己检查的对照。作者的代码改变数组工作集的大小和访问步长，定时读取，观察有效吞吐怎样变化。缩小工作集相当于让重复访问更可能留在近处，减小步长相当于利用一次取来的相邻元素。这两个因素可以分别改变，正好解释为什么缩小预览分辨率和调整遍历顺序都可能见效。实验中的具体速率取决于处理器、编译方式及计时条件。分析一个确定的像素循环时，可以用每次从内存读写的数据量和每次完成的运算数估算它更可能受哪一侧限制。再估算整个抽帧流程，还要计入解码、颜色转换和输出编码的时间。用算术强度比较计算和带宽上界CS:APP 存储器山源程序

文件、进程、线程与虚拟地址

存放在磁盘上的 ffmpeg 是程序。启动它处理文件后，系统建立进程，里面有代码、数据、动态分配的缓冲区以及执行线程的状态。同一份可执行文件可以同时处理两段视频。两个进程都可能声称自己的图像起始地址是同一个数，因为它们看到的是各自的虚拟地址空间。内存映射给出当前进程的地址对应哪里的物理存储，并规定是否可读、可写或可执行。只有双方显式建立共享映射等关系时，两个虚拟地址才可能有意引用同一份可写数据。OSTEP 的进程与地址空间 地址空间的构成

设页大小为 4 KiB。缓冲区的虚拟地址 0x2010 可以拆成虚拟页号 2 和页内偏移 16。地址转换找到这一页的物理位置后保留偏移，才能定位到具体字节。向程序提供一段连续的虚拟地址，并不要求物理内存中所有物理页首尾相连。首次访问按需分配或尚未装入的页时，处理器可能触发缺页异常，系统建立映射后让指令继续。越权限的访问则可能终止进程。观察到一次缺页，并不能只凭这个事件断定进程刚从交换文件读回了一页。

如果把图片划成上下两半交给同一进程的两个线程，它们共享像素缓冲区，但各自保有当前指令位置、寄存器和调用栈。把输出行范围明确分开，可以防止两个线程改写同一元素。反过来，让两者直接执行共享的“已完成行数加一”，如果操作需要分别读取、加一和写回，就可能一起读到旧值，最后只记了一行。应当让每个线程记录局部数量、等它们结束再相加，或选用合适的原子操作或锁。调度器在任意允许的位置换出线程，偶然跑出一次正确结果并不能证明这些交错都安全。

当解码器等磁盘数据或网络包时，操作系统可以把 CPU 时间交给准备就绪的线程。程序通过文件接口申请打开、读写与关闭，系统维护文件位置、权限和已打开对象等状态。一次库函数调用未必对应一次系统调用，系统的文件缓存也可能意味着一次读取无需访问物理磁盘。反过来，库函数只是把输出交给缓冲区时，应用想让内容经受重启还要使用符合目标系统的持久化保证。后面把任务标记为完成时，就会遇到这个区别。

从本机解码程序到浏览器的任务请求

编译器、解释器和依赖环境怎样协作

现在用 Python 把资料库串起来。可以在脚本里启动 FFmpeg 子进程，把文件名、视频流和目标格式作为参数交给它，读它的退出状态与输出。也可以让一个 Python 扩展在当前进程内调用编解码库。两条路径的接口不同。前者跨进程传文件、管道或共享内存，子进程正常退出后才能据此判断这一步完成。后者能把当前进程中的数据直接交给库，不过双方对内存布局、对象寿命和二进制版本的约定也要相容。说“项目用 Python 写”，没有指明实际逐像素计算运行在哪一段代码里。

在常见的 CPython 实现中，源程序被编译成解释器能执行的字节码，函数调用可以进入由 C 等语言实现的扩展。字节码属于这个解释器的实现，它与 AArch64 或 x86-64 的机器码不同。Python 源码中同样一个加号，可以按运行时对象的类型做数字相加，也可以拼接字符串。给函数附上类型注解并不会让普通调用自动执行静态检查。把整张图交给数组库的一次操作可以在本机循环中处理许多元素，而写一层 Python 循环逐个取出像素，就可能重复支付解释器分派、构造对象和检查类型的成本。Python 术语表对字节码的定义

Java 给出另一种分工。源码通常编译成含字节码与类型信息的类文件，Java 虚拟机负责装载并执行。实现可以解释执行，也可以把经常运行的部分即时编译为目标机器的指令。虚拟机规范描述每个线程的栈与程序计数器、所有线程共享的堆等运行时区域，把具体内存布局和即时编译策略留给实现。C++ 的本机程序则可借对象作用域管理图像缓冲区和文件句柄。Rust 在编译期用所有权和借用规则限制某些不安全访问，Go 常见工具链生成本机可执行文件并由运行时管理堆对象。采用本机编译和使用垃圾回收完全可以出现在同一种语言中。Java SE 21 虚拟机规范第 2 章

在浏览器一侧，用 JavaScript 注册点击事件、显示预览图，具体引擎还可结合解释和即时编译。若用 TypeScript 开发，类型检查能在构建时发现一批前后端字段不匹配的问题，但网页从网络实际收到的仍是字节。后端如果把原先的数字帧号换成字符串，即使前端源码通过了检查，也必须在读入响应时核对格式。从高级语言到 CPU，从客户端声明到实际输入，每个边界都有各自能保证的事。比起给语言排快慢顺序，先找到真正读写大块像素的循环，常常更容易解释程序的表现。

讲义里的 Notebook 还藏着一个常见的故障。编辑器能找到并给某个库补全，运行单元格时却说找不到模块。代码实际由选定的 Notebook 内核执行，终端里安装依赖的解释器可能是另一份。在出错的环境查看 sys.executable，再核对同一解释器下 python -m pip 查到的包，就能沿执行路径检验这种可能。虚拟环境主要隔开解释器相关的包和工具，不能同时保证操作系统的设备驱动或外部 FFmpeg 可执行文件也匹配。记录解释器、依赖和外部工具的版本，别人才有机会重建同一条路径。Python 虚拟环境说明

这些区别还能说明编辑器插件、库和 API 各管哪件事。给编辑器安装语言插件可以增加补全、语法诊断和调试入口。FFmpeg 编解码库提供可调用代码，调用方按函数参数、返回值与对象生命周期组成的接口使用它。另一个进程也能提供 API，例如浏览器稍后要调用上传接口，接口不要求客户端直接加载服务器的动态库。遇到缺少功能时，先看调用发生在哪个进程中，再决定该查编辑器、解释器、加载的库还是远端服务。

一次 HTTP 上传怎样抵达服务端

本机脚本已经能够从文件中取出图片。现在把上传入口放到网页上，浏览器要取得远端服务的地址。以新建的 HTTPS 上的 HTTP/1.1 连接为例，如果没有可复用的连接或地址缓存，浏览器先通过名字解析取得候选 IP 地址，再与其中一个地址和指定端口建立 TCP 连接，进行 TLS 握手并检查服务身份，随后发送 HTTP 请求。已有连接可以被复用，HTTP/3 则把 HTTP 语义映射到 QUIC，不经过同一套 TCP 建连流程。教程中画出的单条路径，必须说明适用的是哪一种连接。HTTP 语义与连接 HTTP/3 的 QUIC 映射

现在只看请求里的四个字节。发端应用可以一次把它们写进连接，对端应用可能先读到一个再读到三个，也可能把它们连同后面的数据一起读到。链路上按帧传送，路由器按 IP 数据包转发，TCP 在两个端点之间用序号、确认和重传等机制向应用交付有序字节流。TCP 不保存各次写调用的消息边界，因此接收端必须按应用协议定义的边界解析请求。在集群程序里，发送方可以重新使用内存和接收方已经处理完消息也常是两个时刻，MPI 把不同完成条件写进各自的调用语义。MPI 发送的完成条件

UDP 交付数据报，保留每个数据报的边界，基础协议自身不负责按序和丢失重传。选择传输协议会改变应用要承担的工作。TCP 的字节流与分段 UDP 数据报的定义

服务器返回 HTTP 202 Accepted，在 HTTP 语义里表示请求已被接受处理，处理尚未完成。服务可以另外约定，先完整保存上传数据并登记任务，然后返回任务编号与查询地址。用户界面此时应显示“已接收”，等读到完成状态才展示预览。接收端的 TCP 先收到相关字节，才可能把它们交给应用解析。发送方看到的 TCP 确认至多说明对端收到了相应字节，应用是否已经接受请求、工人是否写出了图片，各有另外的证据。关掉浏览器再重新打开，如果页面仍能凭编号查回结果，就还需要状态存储。TCP 本身留不住这个业务事实。RFC 9110 对 202 的定义

再考虑一次超时。请求可能还没到达服务器，也可能已经登记任务，只是返回编号的响应没能传回。客户端从“没收到”推不出服务器究竟做没做。如果用户点击重试，每次都直接新建一条任务，最后可能出现两个解码工人处理同一份视频。可以让客户端对同一次提交使用稳定的标识，让服务端在登记时对标识施加唯一性约束，重复请求返回同一任务编号。这里由应用定义哪些两次提交代表同一件事。仅仅让 TCP 更可靠，解决不了对端已经处理、应答途中断开造成的不确定性。

视频服务中的模块、部署与事务边界

单体程序里的接口与数据库提交

一开始，浏览器只需要“提交视频”“查询任务”“读取预览”三个动作。服务器可以用一个可部署的程序提供这三个接口，内部把媒体处理、任务状态和页面呈现分别组织成模块。这已经同时具有客户端与服务端的分工、分层调用和单体部署三种特点。它们描述的维度不同。用户界面也可以把任务状态交给模型对象、把控件交给视图、把点击后的操作交给控制器。界面如此分工，并不会自动决定解码器运行在本机还是服务器，也不会决定后端要拆成几个服务。

设计接口时，先约定哪一方对结果负责。解码模块输入视频标识和时间，输出帧的宽、高、像素格式、行距以及缓冲区的有效期。模型模块要单精度 RGB 张量，就由明确的一处做格式转换。若模块间只写“传一张图片”，新版本的解码器把图改成 BGR 排列后，程序可能照常返回成功，只是特征和颜色都变了。把宽高极小、每个颜色均可人工识别的图加入接口测试，可以捕捉这类错误。单元测试能准确定位像素转换，集成测试还能验证从解码、推理到写结果之间传的确实是同样的布局。

任务状态可取“已接收、处理中、已完成”。设预览的元数据和任务状态都放在同一份 SQLite 数据库里，希望读者看到“已完成”时，也一定能查到对应的结果记录。把这两个数据库改动放在一个事务里，提交的目标是在该数据库、给定日志和持久化条件下，让读者看到一致的前后状态。SQLite 对回滚日志的解释很直观，修改数据库页之前保留足以恢复的旧内容，依照规定次序写入并完成提交。若供电中断，重新打开时可以据恢复信息判断该保留哪一边。WAL 模式另有自己的机制，不能把回滚日志的逐步过程照搬过去。SQLite 对原子提交和回滚日志的说明

现在把预览图片本身另存为文件。即使两个数据库修改能原子提交，普通文件写入也没有因此自动加入事务。如果先标完成再写图片，中途崩溃会留下一个打不开的预览。可以先把内容写到临时位置，在约定的文件系统和持久化条件下发布为可读结果，最后在数据库里关联这个结果并标完成。若崩溃点落在发布和数据库提交之间，重试能检查已有文件的身份和内容，复用正确结果，另行清理没有引用的临时文件。顺序的选择来自读者要看到的保证，而非事务这一名词本身。

异步队列与独立部署改变了哪些故障

一段很长的视频不适合让浏览器连接一直等到处理结束。把接收和处理解耦，接收请求的服务返回任务编号，后台工作进程从队列取出任务，解码、推理、写结果，再向队列确认。生产者和消费者于是可以按不同速率运行。若工人处理一条任务平均需要两秒，单个工人在忽略额外开销的理想条件下每秒只能完成半条。一秒持续到来一条时，队列会积压。队列给突发流量提供等待空间，提高不了长期处理能力。还要增加足以独立工作的工人、减轻单次工作，或限制接受的负载。

如果工人已经写好图片、还没确认消息就退出了，队列可能再次交付这条任务。给每个结果分配由任务、目标时刻和处理版本共同确定的标识，可以让再次处理找到已有结果。只用文件名当标识会遇到同名视频，忽略处理版本则会把新算法的结果误判成旧缓存。数据库提交和消息发布之间也可能中断。在需要两者一致时，一种设计是在同一事务里登记状态和一条待发布记录，由独立步骤重试发送，消费者仍按这个稳定标识识别重复。服务能恢复到哪一步，取决于哪些信息已被可靠保存。

等到解码和推理的扩容需求真的分开，才有理由把它们做成能够独立发布和扩容的服务。微服务带来的方便是可以只给推理增加机器、按各自节奏升级。代价是进程内调用变成了跨网络的请求，一次业务完成可能要跨多个持久化边界。传递已压缩的视频引用，只需让工人取得正确版本的对象。跨网络搬运许多解码后的全高清浮点帧，则会受前面算过的每帧大小约束。Fowler 与 Lewis 讨论微服务时强调按业务能力组织以及独立部署。把每个函数都搬到网络另一端并不会自动获得这些性质。Fowler 与 Lewis 对微服务的说明

团队协作也沿着这些接口留下记录。保存一小段可公开复现的输入、它的预期尺寸与输出、解码命令和工具版本，比只说“有一帧是黑的”更能帮助开发者排查。源码仓库记录哪个版本改了转换或边界判断，测试确认这个修改对其他格式仍然成立。FFmpeg 项目将媒体容器和流的处理放在 libavformat，编解码器放在 libavcodec。界面程序可以调用库，命令行工具也可以组合它们。阅读开源项目时，顺着实际功能找到负责的库，再查接口文档、实现与该版本的许可，比在所有目录里漫无目的地搜索更省力。FFmpeg 对 libavformat 的说明 libavcodec 的职责

程序已经能抽出任何指定时刻的图像。现在要标出值得人工复查的片段。格式宽度、通道顺序和时间边界都能写成确定的程序，画面是否模糊则很难只用一句规则说清。可以先收集不同视频中的画面，给出一致的标注规则，并分开保存后面用来检验的样本。机器学习在这里负责从已标记的数据估计一组参数，让它们对新输入也有预测能力。任务登记、解码和存图仍用原来的程序执行。一个含模型的应用里，确定规则与统计推断会长期并存。Goodfellow 等《深度学习》第 5 章

小学习率、振荡与凸二次损失的收敛

再单独看学习率。挑一个参数、一个样本，固定截距为零，输入取 1、目标取 2，那么 L(a)=(a−2)2/2L(a)=(a-2)^2/2L(a)=(a−2)2/2。沿横轴画出它，只有 a=2a=2a=2 一个谷底。梯度下降的更新为 at+1=at−η(at−2)a_{t+1}=a_t-\eta(a_t-2)at+1​=at​−η(at​−2)，整理后得到 at+1−2=(1−η)(at−2)a_{t+1}-2=(1-\eta)(a_t-2)at+1​−2=(1−η)(at​−2)。离最优位置的误差每一步都会乘上同一个系数。观察这个系数，就能判断什么时候向谷底靠拢，什么时候会越走越远。

设初值为零，学习率取 0.1，前两步是 0.2、0.38，始终从左侧接近 2。若减到 0.01，两步只有 0.02、0.0398，走得慢，却没有另一个局部最低点能把它困住。学习率取 1.5，前两步变成 3、1.5，跨过谷底又跨回来，但误差的绝对值每次缩小一半，仍会收敛。取 2 时则在 0 和 4 之间往复，继续增大会使误差放大。小步长、越过谷底和不能收敛是三个不同的判断，在这个凸二次函数上可以分别验证。高维、非凸、带抽样噪声的训练需要重新分析，不能仅凭这幅抛物线断定任何神经网络的结局。

这也解释了“梯度指向哪里”容易引起的混淆。在当前位置，梯度是函数局部上升最陡的方向，负梯度给出在足够小步长下的下降方向。它提供附近的变化率，不能直接给出某个遥远的全局最优点。在图像特征取值范围差很多时，某些方向上损失变化很快、另一些方向很慢，同一个全局学习率会受到较陡方向限制。规范输入尺度、使用合适的参数化或换用带自适应步长的优化器，处理的是这种更新困难。它们都无法把标错的画面变成正确监督。

一批张量怎样经历前向、反向和更新

实际训练的一批图片有多个轴。以 PyTorch 常见的二维卷积接口为例，可以把批次整理成 N × C × H × W，依次表示多少张图、每张几个通道、高和宽。把先前的 RGB 字节变成模型输入，既要从整数转到预期的浮点范围，也要安排通道维。如果训练时把 0 到 255 映射到 0 到 1，部署时漏掉这一步，即使元素总数和各层权重都相同，第一层看到的数值也会整体放大。检查输入时看一张图的几个已知像素，比只打印形状更能发现这种故障。

批数据就绪后，框架用当前参数完成前向计算，保存反向所需的中间关系。以平方误差为例，先从预测与标签的差求出损失对预测的导数，再乘上预测对权重的导数，这就是链式法则。深层网络将相同的规则沿实际运算图反向应用。PyTorch 的 backward() 把叶参数的梯度累加到相应字段。普通的一批一更新循环会在新一批求导前清理旧梯度。若刻意想累计几小批来模拟大批，才会保留它们，并让损失缩放与预期批量对应。参数的改变发生在优化器执行更新时，单独做一次前向或反向不会替代这一步。PyTorch 自动求导教程

卷积网络怎样利用邻域，怎样检验泛化

一块小图上的互相关、池化与感受野

单一特征值丢掉了画面的空间结构。模糊常常表现为相邻区域的强度变化变缓，算局部差异比把所有像素随便打乱再交给模型更有意义。卷积神经网络把一组权重放在小窗口里，让它在整张图上移动。某种边缘出现在左上角或右下角，负责比较相邻像素的权重都可以复用。输出仍按位置排列，所以后续层还能判断哪些局部响应彼此相邻。

用一块单通道的三行三列数字演算，左边为输入，右边为两行两列的权重。将权重覆盖在左上角，逐项相乘再求和。向右、向下各移动一格，就能算完四个合法位置。

X=[124013120],W=[−11−11],Y=[2420].X=\begin{bmatrix}1&2&4\\0&1&3\\1&2&0\end{bmatrix},\qquad W=\begin{bmatrix}-1&1\\-1&1\end{bmatrix},\qquad Y=\begin{bmatrix}2&4\\2&0\end{bmatrix}.X=​101​212​430​​,W=[−1−1​11​],Y=[22​40​].

第一个响应等于 (2−1)+(1−0)=2(2-1)+(1-0)=2(2−1)+(1−0)=2。向右移动后得到 (4−2)+(3−1)=4(4-2)+(3-1)=4(4−2)+(3−1)=4，因为两行的相邻列变化都更明显。这一计算让权重保持原方向，正是 PyTorch Conv2d 文档给出的二维互相关。数学定义中的卷积要把权重沿两个空间方向翻转，这个具体窗口翻转后会得到相反的符号。网络能从训练中学出适合任务的方向，所以人们把这层简称为卷积并不会妨碍训练，但逐个数字与传统滤波器对照时，翻不翻转必须说清。PyTorch 2.9 的二维卷积定义

现在换回 RGB 图。一个输出通道通常要在所有相连的输入通道上分别做窗口乘加，再把结果相加。普通稠密卷积用大小为三乘三的核，从三个输入通道产生十六个输出通道，需要 16×3×3×3=43216\times3\times3\times3=43216×3×3×3=432 个权重。若每个输出通道带偏置，再加十六个。图再宽一倍，能放窗口的位置变多，却不需要为右半边另学这 432 个权重。课程讲义用七乘七小图与五乘五窗口，默认不补边、步长为一、膨胀率为一，就只剩三个横向、三个纵向的合法放置位置。改变图像尺寸后，是否补边和窗口的实际跨度都会进入输出形状的账本。

步长决定相邻输出的起点隔了多远，膨胀率决定同一组权重在输入中隔几个位置采样。相邻叠两层三乘三、步长为一的普通卷积，第二层的一个输出会受到原图最多五乘五区域的影响，这叫理论感受野。第一层传播每个位置附近一格的消息，第二层再向外扩一格。若中间加入降采样，后续同样大小的窗口会跨过更大的原图距离。感受野覆盖某个像素只代表存在传播路径，最终预测有多依赖它，还要看训练出的权重和具体输入。

在上面的四个响应上做两乘二最大池化，最后只留下 4。局部亮边略微移动，只要最大值还留在同一池化窗口，输出就可能相同。这会减弱某些小位移的影响，同时也丢掉了“最大响应在窗口哪个角”的信息。如果目标要逐像素画出边界，就得认真考虑这种位置损失。带步长的采样在窗口边缘也可能对一格移动十分敏感，不能从这一个漂亮的例子推断任意平移都保持不变。

每层还需要能表达非线性。两层纯仿射变换总能合并成一次新的矩阵乘法加偏置，因此单靠堆层数，函数形状仍受同样的限制。ReLU 把负响应截成零、正响应原样通过，可以让后续计算随输入所在区域而变。如果将所有系数和每个空间位置都连接，得到的是全连接层。把相同窗口拿到各位置复用，则把图像的局部结构写进模型。矩阵乘法和卷积有许多相似且彼此独立的乘加，适合让 GPU 并行计算。设一次串行处理的原耗时中，卷积占比为 fff，现在把卷积加速到原来的 sss 倍，其余时间都不变，总耗时减少的比例就是 f(1−1/s)f(1-1/s)f(1−1/s)。例如卷积占一半、卷积用时减半，整次处理只少用四分之一的时间。若实际等待来自排队或并行阶段，还得回到这次请求的时间线上找出哪些阶段真的缩短。深度学习教材的卷积网络一章

训练模式、评估模式与不同来源的视频

同一组参数在训练和部署时可能产生不同结果，这里有两个常见的原因。二维批量归一化在训练时，按通道汇集一批样本和空间位置上的统计量，先从数据中减去均值，再除以这批方差与小正数 ϵ\epsilonϵ 之和的平方根。随后还有可学习的缩放与偏移，所以最终输出不必恰好零均值、单位方差。默认配置还会积累均值和方差的运行估计。切到评估模式后用积累的统计量，这样一张上传图片的结果才不会随同批其他图片随意变化。若专门关闭 track_running_stats，评估也会使用当前批统计，这个配置应随权重一起记下。PyTorch 2.9 的 BatchNorm2d 训练与评估

暂退法则在训练时随机把一部分激活置零。例如保留概率为二分之一时，PyTorch 的标准 Dropout 会把保留下来的值扩大两倍，单个值在随机掩码下的期望仍与原来相同。评估模式使用确定的恒等变换。model.eval() 负责切换这类层的行为，torch.no_grad() 负责让相应作用域不记录梯度运算。只关闭梯度记录，不能把训练中的随机暂退或批统计自动切换成评估方式。出现“同一张预览反复预测结果不稳”时，两种设置需要分开核对。PyTorch 2.9 的 Dropout 说明

接下来才有资格评价训练出来的系统。一段三十秒的视频可以贡献许多相邻帧，但它们拍的是同一场景，有相近的光照和压缩特征。把所有帧打散，随机拿一部分做测试，训练集里可能就有测试帧前后几毫秒的画面。模型只需要认出这个场景，就可能取得好成绩。若想估计对新视频的效果，应先按视频来源分组，再把整组分去训练、验证和测试。若部署面向以前没有见过的摄像设备，甚至要把设备或采集场次作为更高一级的分组单位。划分方法取决于要向谁承诺泛化。

验证集帮助挑学习率、窗口大小和模型版本，测试集在选择结束后用于独立评估。训练样本较少时，可以在用于开发的数据上做 KKK 折交叉验证。将独立视频组划成 KKK 份，每次保留一份用于验证，用其余组从头训练，轮流覆盖各份。归一化参数等从训练数据估计的变换也要在每一折各自拟合。平均验证表现给出同一选择流程下的参考，若用它在很多方案之间反复挑最好的一项，这个最好看的分数本身会带选择偏差。仍保留一份从未参加选择的测试数据，或者在条件允许时使用嵌套验证，可以回答另一个独立问题。

聚合指标时也要保留样本单位。短片甲有十个已标注画面、短片乙有一千个，逐帧平均会把乙的影响放大一百倍。若用户购买的是按视频给出的复核报告，除了逐帧错误率，还应该检查多少段视频漏报，或者每段平均增加多少次无意义的人工复核。同一个模型的两种分数都能算对，却回答不同问题。从这里回看前面的损失，训练集上的损失降低、独立数据上的预测改善、用户少看几段误报的视频，任何一项都不能单凭另一项自动推出。

从视频说明到语言模型的注意力与检索

词元、隐藏状态与带掩码的注意力

资料库现在能显示某段视频的预览和预测。用户还希望用自然语言问：“这张图是怎样从视频里取出来的？”模型要先把问题变成数。分词器按与模型约定的词表把文本切成词元，再转成整数编号。词元可能是完整词、词的一部分、标点或带前导空格的片段。一段中文的字符数既不等于 UTF-8 字节数，也不一定等于模型消耗的词元数。编号只是词表中的位置。把两个编号相减，得不到它们在语义上有多相似。模型通过嵌入表取得每个编号对应的一组浮点表示，才开始做后续计算。

一种处理序列的方式是让循环神经网络维持一个隐藏状态。读入当前词元时，把它的向量和上一步留下的状态一起变换，再把新状态向后传递。这样前面的信息有路可走，但位置隔得越远，就要经过越多次状态变换。训练时沿着这条链反传梯度，跨越许多步可能变得困难。注意力增加了另一类路径。某个位置可以直接根据相关程度，从允许访问的一批其他位置取回信息，不必只从相邻位置的单一状态接力。

在缩放点积注意力里，每个位置的表示经过学得的投影产生查询 qqq、键 kkk 和值 vvv。查询与各键做点积，再除以键维度的平方根，得到一排打分。分数经 softmax 转成总和为一的一组权重，随后这些权重作用在对应的值上。键参与决定从哪一个位置取多少，值决定从那个位置取回什么。一个多维的值向量能带回许多特征，某个键得到最高分也不等于最终只保留对应的一个词。Vaswani 等的缩放点积注意力与多头注意力

取一个只为手算而设的例子，键的维度是一，查询取 1，两把键取 0 与 ln⁡3\ln 3ln3，对应的两个值取 2 与 6。点积后的两个分数仍为 0 与 ln⁡3\ln 3ln3，指数分别为 1 与 3，归一化后权重就是四分之一与四分之三，输出为 2/4+3×6/4=52/4+3\times6/4=52/4+3×6/4=5。保持查询与键不变，只将第二个值改成 10，权重完全相同，输出却变成 8。若当前位置使用因果掩码，第二把键来自未来而不可用，归一化时就要把它排除，此时只留下第一个值，输出为 2。训练时即使把整句话一次送入计算，也能用这个掩码保证早先位置不会看到后文。推理生成则要等上一步选出的词元，才知道下一次把什么输入模型。

“小明背起装满书的书包，准备把它带到教室”提供了可理解的语义。预测或解释“它”时，前面的“书包”提供了有用上下文。上面的两个数值权重是人为构造的算例，没有测过任何模型在这句汉语上的注意力。真实 Transformer 还包含多个注意力头、位置表示、前馈层与残差连接等结构，词元最终经输出层得到词表上的打分。注意力里的归一化比较一个查询可见的输入位置，语言模型输出层里的归一化比较词表中的候选词元。两处都用了 softmax，参与比较的对象完全不同。

常见的自回归预训练让模型根据已有前缀预测下一词元，不断调整参数，使训练文本中的后继词元获得更高概率。模型因此能利用大量语言形式与内容之间的统计联系。部署时要一起使用相匹配的模型结构、参数和分词器，同一个整数编号若对应不同词元，形状完全正确的程序仍可能读错全部输入。提示词和参考材料占用当前可用的上下文，模型生成的回答再由分词器还原成文字。实践中，读入已有提示的预填充阶段可以同时计算许多已知位置，逐步解码阶段则要等待刚选出的词元，两个阶段对设备算力与带宽的需求也会不同。大模型预填充与解码的计算和访存

材料写进一次上下文可以改变这一次输出，训练才会把改变写入可用于后续调用的参数。

用 FFmpeg 文档回答一个可核对的问题

回到用户这次查询。问题是“FFmpeg 中哪个库负责音视频解码，哪个库先读懂 MP4 容器？”资料库可以把官方文档分成有出处的短段，一段记录 libavformat 对容器和媒体流的职责，另一段记录 libavcodec 对编解码器的职责。检索程序用问题去找这些段落，把找到的材料连同问题送入生成模型，要求给出能回溯到原文的回答。这样回答“先由 libavformat 解复用，再由 libavcodec 相应的解码器产出帧”时，每一项职责都有可以打开的出处。FFmpeg 的格式库 FFmpeg 的编解码库

这种把外部材料接入生成过程的做法叫检索增强生成（RAG）。Lewis 等人的原模型把存入生成模型参数的知识与外部文档索引结合，检索器根据输入取候选文档，生成器在相应条件下生成输出。原论文的训练设置固定文档编码器与索引，联合微调了查询编码器和生成器。工程里也常见先检索、再把片段拼入提示词的实现。用户提问时从已建好的索引取回一段刚更新的项目文档，可以影响这一次回答，单次检索不会重写当前语言模型的权重。原论文的训练方法与这里一次在线请求所做的事，发生在系统的不同阶段。Lewis 等的检索增强生成论文

若回答把两个库的职责恰好颠倒，检验时先保存它实际取回的段落。候选里压根没有容器文档，优先查文档是否入库、切分是否保留了标题、检索词怎样表达。如果正确片段已经出现，再看生成器有没有按引用理解主语和动作。让模型返回一个看起来像官方文档的网址，不足以证明该页真支持那句话。分别检验“候选是否包含证据”和“给定证据能否回答正确”，能把一个笼统的语言模型错误拆成可单独修复的环节。若库版本发生变化，文档片段也要记录它描述的版本。

微调适合另一个目标。假如收集了大量视频工单，希望模型稳定地区分“音频中断、画面失真、文件丢失”，包含这些标签的训练样本能够更新模型的一部分或全部参数，随后要在未用于训练的工单上检验分类。若只是今天换了部署中的 FFmpeg 版本，在请求时提供正确的版本文档通常更直接。模型还可以提出“读取当前任务的解码日志”之类的工具调用，外层程序核对调用者是否有权读取这条任务，查到记录后再交给模型解释。日志是否存在、查询是否成功、回答是否符合记录，各自可以独立核对。

同一项预览功能的四种验证

现在重新看左上角那个像素。原始数据读出 210、231、236，给三个通道各加十，得到 220、241、246。如果实际画面却偏红，先比较解码后与模型前的那三个数，查看通道顺序、行距和整数截断。若数值正确而抽取的是前一幕，转去检查显示时间戳、参考帧和“当前帧”的边界定义。这类故障有很强的确定性，几像素的小图或六条时间记录，经常比一份几小时的视频更适合定位。

到了网页上，还得区分服务端已接收、已排队、已生成可读文件。诊断依据是请求编号、状态变更和实际结果对象。到了模型上，要问的则是哪个版本在哪批独立视频上预测更好，依据换成标注、分组和评价指标。最后，让模型解释处理流程时，举证的是它实际拿到的 FFmpeg 文档及回答所指向的原句。计算机组成和操作系统能解释一次读写，网络与软件工程能解释一次交付，学习算法能解释参数怎样改变。把这几种可验证的结果接在一起，才解释得清用户为什么能在指定的时刻看到这张图，为什么应当或不应当相信它旁边的判断。
