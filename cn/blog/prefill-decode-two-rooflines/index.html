大语言模型推理的 Roofline 分析：预填充与解码的算术强度

同一个 7B 模型处理 2K 提示时，许多输入位置可以共用一次权重读取；生成下一个词元时，每条请求却要重新读取自己的历史键值。因此扩大解码批次能提高总吞吐，但每条请求的下一次输出未必更早。

假设一个 7B 模型读入长度为 2,048 token 的提示，先返回第一个输出 token，然后再生成一个。两次前向使用同一套权重，第二次只增加一个位置，耗时却不能简单按第一次的 1/20481/20481/2048 估算。处理提示时，一次读取的权重能用于许多输入行；生成下一个 token 时，模型既要读取这套权重，还要访问整段历史的 KV 缓存。两个阶段的计算量与内存访问量因此按不同的比例变化。

为了分别估算计算与访存，下文以稠密模型为例。记模型参数量为 PPP，提示长度为 LLL。进入解码阶段后，SSS 表示每条请求已缓存的上下文长度，bbb 表示共同解码的序列数。以下把一次乘法和一次加法计为两次浮点运算，权重与缓存中的每个元素都占两字节。

预填充与解码的计算量和 KV 缓存读写量

在预填充（prefill）阶段，提示里的所有词元都已知。线性层因此能把多个位置的输入排成一个矩阵，一次前向就为每层生成并缓存各位置的键和值（K/V）。进入解码（decode）阶段后，每条序列每步只增加一个位置。此前的 K/V 不必再算，但新位置的查询向量仍要和全部可见历史匹配，所以这部分注意力计算随 SSS 线性增长。

前向的稠密投影约需每个 token 2P2P2P FLOP，嵌入查表和分数矩阵另计。单条提示约需 2PL2PL2PL，一轮批解码约需 2Pb2Pb2Pb。预填充中每层还要做 QK⊤QK^\topQK⊤ 和概率矩阵乘 VVV，完整矩阵约为 4L2d4L^2d4L2d FLOP，因果掩码大约减半。对下面的 7B 形状，以投影计算为分母，因果注意力在 2K 时多出约 4%，8K 时多出约 15%。例如，四条 512 token 提示和一条 2K 提示的投影输入行数相同，但短提示之间不做注意力计算。四个短提示各自的因果三角形合起来，包含的位置对就少于单条长提示形成的一个大三角形。

预填充写下的 K/V 要一直保留到解码结束。每新增一个词元，各层合计需要的缓存字节数为

Mkv=2nlayersnkvdhc.M_{\rm kv}=2n_{\rm layers} n_{\rm kv} d_h c .Mkv​=2nlayers​nkv​dh​c.

式中的系数 2 对应每个位置的 K 和 V 两份存储，nkvn_{\rm kv}nkv​ 是 KV 头数，dhd_hdh​ 是头宽，ccc 是每元素字节数。分组查询注意力（GQA）可以让一组 query 头共享一份 KV。例如 64 个 query 头只对应 8 个 KV 头时，缓存大小就是每个查询头都拥有一份 K/V 时的八分之一。

以 32 层、32 个 KV 头、头宽 128 的 FP16 模型为例，每个 token 跨全部层需要 524,288 B，也就是 512 KiB 的 KV 缓存。7B 权重约占 14 GB，80 GB 卡的剩余 66 GB 在理想条件下约容纳 12.6 万个缓存 token，或者 61 条长 2,048 的序列。这个上限把剩余显存全部算给了 KV，实际运行还要为激活、运行时和分配碎片留出空间。另一个 175B 例子有 96 层，隐藏维 12,288，每 token 约用 4.5 MiB，单条 2K 历史就要约 9 GiB。

两阶段的算术强度与 GPU 屋顶线

有了两阶段的 FLOP 数和访存字节数，就可以用屋顶线模型估算它们各自的理想时间下界，写作 t≥max⁡(F/Fpeak,M/Bpeak)t\ge\max(F/F_{\rm peak},M/B_{\rm peak})t≥max(F/Fpeak​,M/Bpeak​)。I=F/MI=F/MI=F/M 称为算术强度，单位 FLOP/B。脊点 I∗=Fpeak/BpeakI^*=F_{\rm peak}/B_{\rm peak}I∗=Fpeak​/Bpeak​ 表示计算和传输耗时相等的位置。这里比较规格中的稠密峰值和 HBM 带宽，实际执行还受利用率、访问方式和频率影响。

H100 SXM，BF16989 TFLOP/s3.35 TB/s约 295

H100 两项分别取规格所列结构化稀疏峰值 1,979 和 3,958 的一半。较低精度可以提高标称矩阵吞吐，却不会同时使芯片的显存带宽翻倍。因此每种精度应使用自己的脊点。屋顶线如何估算与测量

当激活读写远小于权重读写时，预填充的 I≈2PL/(2P+activations)≈LI\approx 2PL/(2P+\text{activations})\approx LI≈2PL/(2P+activations)≈L。2K 提示约为 2,048 FLOP/B，已超过 A100 的脊点，计算时间因此决定这组假设下的下界。解码时，一个批次仍能共用一次权重读取，每条序列却必须读取自己的历史 KV：

Idecode≈2Pb2P+bSMkv,lim⁡b→∞Idecode=2PSMkv.I_{\rm decode}\approx\frac{2Pb}{2P+b S M_{\rm kv}}, \qquad \lim_{b\to\infty} I_{\rm decode}=\frac{2P}{S M_{\rm kv}} .Idecode​≈2P+bSMkv​2Pb​,b→∞lim​Idecode​=SMkv​2P​.

小批、短历史时，b=1b=1b=1 对应的算术强度约为 1 FLOP/B。加大批次可以让多个请求分摊一次权重读取，但每条请求仍须读取自己的历史 KV。对 7B 模型、S=2048S=2048S=2048，若分子只计稠密投影的浮点运算量，这一估算的上限约为 13 FLOP/B，距离 153 的脊点仍很远。缩短历史或通过 GQA、KV 量化减少每个 token 的缓存量，可以抬高这个上限。反过来，极短的单条提示也未必能充分复用权重，因此判断实际瓶颈还要结合提示长度、批大小与单个 token 的缓存量。

首 token 延迟与逐 token 延迟的构成

首 token 延迟（TTFT）从请求发出计到第一个输出出现。若请求无需排队，这段时间主要花在预填充上。再将调度、排队和传输计入，便可近似写成

TTFT≈max⁡(2PLFpeak,2PBpeak)+tqueue+ttransfer.{\rm TTFT}\approx\max\left(\frac{2PL}{F_{\rm peak}},\frac{2P}{B_{\rm peak}}\right)+t_{\rm queue}+t_{\rm transfer}.TTFT≈max(Fpeak​2PL​,Bpeak​2P​)+tqueue​+ttransfer​.

上述 2K 提示的稠密投影约需 28.7 TFLOP。只算这些投影，按 A100 的 312 TFLOP/s 峰值折算约为 92 ms，按峰值的 30% 折算则约为 306 ms。计入因果注意力后，运算量还要增加约 4%，合计约 29.8 TFLOP。一次 14 GB 权重读取约 6.9 ms。在这个例子中，投影计算所需的时间远高于单次权重读取，缩短长提示的处理时间就要优先考虑计算并行度；如果目的是缩短同批解码请求的等待，则可以把预填充分块穿插执行。

首个 token 返回以后，用户等待的是下一个输出。对于已经开始生成且始终留在同一稳定批次里的请求，平均输出 token 间隔（TPOT）等于相邻解码步的平均耗时：

TPOT≈max⁡(2PbFpeak,2P+bSMkvBpeak)+toverhead.{\rm TPOT}\approx\max\left(\frac{2Pb}{F_{\rm peak}},\frac{2P+b S M_{\rm kv}}{B_{\rm peak}}\right)+t_{\rm overhead}.TPOT≈max(Fpeak​2Pb​,Bpeak​2P+bSMkv​​)+toverhead​.

同一个解码批在一步中总共产出 bbb 个 token，但每条请求只得到一个。如果调度器在相邻两次解码之间插入长提示的预填充，这段工作便直接延长已有请求的输出间隔。两类工作可以在同一张 GPU 上交错调度，也可以放在不同 GPU 池中执行，分别见连续批处理和DistServe 的分离式服务。
