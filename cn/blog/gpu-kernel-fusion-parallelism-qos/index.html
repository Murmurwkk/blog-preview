GPU 算子融合与共置：数据复用、指令级并行与前台延迟约束

卷积与 ReLU 融合能省掉中间张量读写。对独立的两个算子，HFuse 借不同线程束（warp）的就绪工作掩盖等待，GoPTX 在同一 warp 里交错指令，两者都受寄存器和访存资源限制。到了有截止时间的推理服务，融合的取舍还取决于前台尾延迟和后台实际完成的工作量。

一次 GPU 启动既可以完成 VGG16 的卷积和 ReLU，也可以在两张互不相关的图上分别运行 Im2Col 和双线性缩放。我更看重的是合并之后，究竟哪一步工作消失了，或者哪一段等待能被别的工作填上。卷积写出的值本来就要交给 ReLU，合并可以省掉把中间值写到全局内存、再由 ReLU 读回的两次访问。Im2Col 和缩放各有自己的输出，这种传值机会并不存在。在 HFuse 的块内划分里，一种可能的收益来自同一个流式多处理器（SM）上的两类线程束：一侧等待时，另一侧仍有工作可以发射。启动次数、网格规模和缓存行为也会改变整对算子的完成时间。

还要辨认谁在等结果。一个调用者要拿到两张图才开始下一步，它关心两份输出中较晚的完成时刻。推理服务的用户只等自己的那份结果，缩短前后台的总完工时间，仍有可能拖慢他的响应。把数据依赖、硬件上的等待和调用方的交付条件分清之后，才能为不同层级的融合选对实现和衡量标准。

卷积接 ReLU 的数据复用与独立算子的双输出

以 VGG16 的 conv3_1 为例。单张图的卷积输出有 56×56×25656\times56\times25656×56×256 个 FP16 元素，全张共 1,605,632 字节。分开运行时，卷积把这些值写进全局内存，ReLU 随后读出，计算 max⁡(x,0)\max(x,0)max(x,0)，再写最终输出。如果只有 ReLU 用到中间值，卷积线程算出 xxx 后便可直接激活，前面的一写一读合计省去约 3.21 MB 的逻辑访问。如果另一条分支在独立启动的核函数里运行，而且必须从全局内存读到完整的激活前张量，卷积仍得写回原值，此时只省去 ReLU 的一次读，约 1.61 MB。最终的激活结果在两种方案中都要写。缓存可以接住全局地址上的访问，所以这笔账不能直接换算成显存总线上的流量。Welder 的融合规划正需要沿计算图追踪这样的消费者，并根据它们的输出分块反推所需的输入范围。Welder 论文 · VGG16 的分块与逻辑字节推导

从输出块反推读写范围与重算量

ReLU 按元素消费中间值，所以知道哪个线程写出了卷积结果，通常也就知道谁可以继续处理该元素。若消费者变成另一个卷积，相邻输出会使用互相重叠的输入区域。假设下游采用步幅一、无膨胀的 3×33\times33×3 卷积，图像内部相邻的两个 8×88\times88×8 输出块各需上游 10×1010\times1010×10 个空间位置。把左块需要的输入列编号为 0 到 9，右块需要第 8 到 17 列。两块共用的正是十行中的两列，总计二十个位置。若两个块各在自己的片内重新计算这些上游值，虽然省了读中间张量的全局访问，它们实际上生成了两百个位置的结果，其中只有一百八十个不同。这一算例只计算空间位置，若有多个通道，还得按具体通道切分和算术重复量换算代价。Welder 的输出块到输入区间推导

因此查看计算图时，需要沿两个方向追踪同一条边。顺着边看，有几个消费者需要完整原值，它们是否能在同一块内得到。逆着边看，想要的输出块需要生产者计算哪些坐标，有多少坐标会被邻块重新生成。若能让需要相同输入的线程以合适的粒度共享它们，片上交接可能同时消除写回和重复读取。若扩大分块以后一次工作占去过多寄存器或共享内存，能同时驻留的块又会变少。Welder 的规划之所以要把输出分块作为参数，正是因为只看图上的算子相邻关系，无法判断一条边的读写收益是否值得这些新增成本。

即使数学公式相邻，实际接口也可能要求保存中间态。调试时若上层会导出激活前特征，或另一条独立启动的支路会读取它而且需要原值，删除写回就改变了程序能观察到的输出。另一方面，两个核函数分开时的全局内存请求可能在 L2 命中，省掉一次逻辑读的字节数未必逐字节反映在 DRAM 读取计数上。可靠的比较先固定程序对外提供的结果，再分开记录逻辑读写、片上复用和到达显存的流量。若这三项混为一个“节省了多少带宽”的数字，换一种输入大小或缓存状态就很难解释差异。

Im2Col 和缩放没有这条可以消掉的依赖边。本机用例中的 Im2Col 把每个空间位置及其下方相邻的像素写进 13 个输出平面。缩放读取的是另一张图，根据四邻点的距离为八个通道分别插值。把它们放进不同的 CUDA 流（stream），GPU 就可以在资源允许时重叠执行两个核函数。这称为共置。另一种做法是改写代码，让同一核函数中的不同线程完成两路独立工作，这称为水平融合。两种做法都得交付完整的两张结果图。

两部分都要处理 5,120,000 个空间位置，但相同的位置数并不意味着同样的工作量。Im2Col 每处理一个位置，就向 13 个平面各写一个 FP32 数。缩放每处理一个位置，既要把输出坐标换成输入坐标，又要在八个通道分别组合四个邻点，最后写八个数。只数两张输出的逻辑写入，就分别有 66,560,000 和 40,960,000 个元素，合计 430,080,000 字节。再怎么重新编排线程，这些指定地址上的输出都要产生。缩放的一组邻点还可能被相邻输出重复利用，发出四次取数也不等于显存为每个输出提供四笔独立传输。比较独立算子的调度，首先得确定写了多少结果，以及哪些读请求有可能由缓存满足。

CUDA 流在这里建立的是顺序关系。同一流中先提交 Im2Col、再提交缩放，后一核函数会在前面的命令完成之后执行。若把它们提交到不同的普通工作流，又没有事件或其他依赖把两者串起来，这两个网格才有同时运行的机会。设备是否支持并行发射、两个网格需要多少寄存器与共享内存、当前还有哪些工作已经驻留，决定了这种机会是否兑现。主机线程从一次异步启动调用返回，只能说明这项工作已经提交，不能说明某个 SM 上已经出现两套来自不同核函数的线程。CUDA Best Practices Guide，并发核函数

HFuse 的线程级并行（TLP）：让同一个 SM 上的 warp 分做两张图

跟踪一次 Im2Col 加载可以看到更细的时序。启动一个网格后，GPU 把其中的线程块分批分配到 SM。一个线程块完整地落在一个 SM 上，32 个线程组成一个线程束（warp）。块获得驻留位置才有自己的 warp 和寄存器状态。一个已驻留的 warp 运行到读取 input[i + r * width]，先要算出有效地址，才可能发出访问。读回的数据在后面作为写出指令的输入，消费者必须等到数据就绪。与此同时，工作组内另一束已经有了数据，或者另一个算子的 warp 正要执行不依赖该地址的插值算术，调度器就可能先发射它。只有地址、输入和相应发射资源都可用的指令才提供掩盖等待的机会。

因此，占用率、就绪线程束数和发射情况是三个不同的观测量。占用率说明同时容纳了多少 warp，就绪线程束数说明调度器当前有多少候选可以发射，已经发射的指令才代表某项工作获得执行机会。一个高占用率的 SM，如果所有驻留 warp 都在等同一批长延迟加载，仍可能有空闲发射周期。另一台设备即便每个 SM 驻留的 warp 较少，只要其中有足够多的独立操作，也可能持续发射。Nsight Compute 的 Scheduler Statistics 将 active、eligible 和 issued 分开报告，在这里能直接用于检验“缺的是并行工作，还是已有工作都在等数据”。Nsight Compute，Scheduler Statistics

从物理线程号映射到两份完整输出

从多个独立 warp 中寻找下一束就绪工作，利用的是线程级并行（thread-level parallelism，TLP）。原生双流由设备决定把两种块放到哪里，某个 SM 上可能有多束同类线程一起等待。HFuse 把两类 warp 显式安排在同一物理块中，改变了每个接到这种块的 SM 能获得哪些可选工作。CUDA 的 warp 调度与驻留 · HFuse 论文

本机移植在三种网格大小、七种 warp 切分中选出的配置，每块有 1,024 个线程，前 16 个 warp 做 Im2Col，后 16 个做缩放。两个算子都按各自组内的线程号计算输出位置。以第 1 号块为例，物理线程 511 第一次写 Im2Col 的第 1×512+511=10231\times512+511=10231×512+511=1023 个空间位置，相邻的线程 512 则是缩放组的第 0 号，第一次写另一张图的第 1×512+0=5121\times512+0=5121×512+0=512 个位置。由于边界落在两个完整 warp 之间，分组也保留了各束线程内部一致的算子路径。HFuse 作者工件 · 本机索引、代码与正确性核对

用跨网格步进的代码来核对这个分工，可以把物理线程与实际输出位置一一对应。下面展开本机 deep_split 的索引，只保留本例的两个分支。gridDim.x 是融合网格的物理块数。两条循环各自要覆盖的是所属算子的完整输出。

int tid = threadIdx.x;
if (tid < cut) {
    int first = blockIdx.x * cut + tid;
    int stride = gridDim.x * cut;
    im2col(w, first, stride);
} else {
    int width = blockDim.x - cut;
    int first = blockIdx.x * width + (tid - cut);
    int stride = gridDim.x * width;
    bilinear(w, first, stride);
}

在选定的 1,080 块网格里，每侧共有 552,960 个 worker。任取一个合法空间序号，将它除以 552,960 的余数，就是第一轮负责它的那个 worker。商则告诉这个 worker 要向后跨多少步。因而所有序号都有唯一写入者，哪一侧先做完也不影响另一张图的数据。若只改分支入口，仍把步长写成 gridDim.x * blockDim.x，每一侧便会跳过另一半余数，明明启动了足够多线程也会留下未写的区域。将两个输出分别与 CPU 参考核对，是选择划分之前就能完成的正确性检查。本机的 Im2Col 完整输出与 CPU 收集结果一致，缩放与独立插值参考的最大绝对误差约为 4.42×10−74.42\times10^{-7}4.42×10−7。本地双输出的正确性与工作划分

确定工作都没丢，才轮到选每组多少 warp。多给缩放一组线程，可能让它的插值更快完成，也会从 Im2Col 一侧拿走吞吐位置。均分只是本机在这对输入采用的方案，不能从两个算子各出一张图推出“每侧正好需要一半线程”。HFuse 原论文本身生成多个线程划分，通过实际运行候选来选择。其输入核函数的索引和同步约束会限制能试哪些划分。本机程序手写相同的分工规则，并先做网格与块内切分的试选，所以正式比较中的数字同时包含了这两个选择。HFuse，第 III 节的候选生成与测量

完整双输出的计时区间与基线选择

实验在 36 个 SM 的 RTX 5070 Laptop 上进行，系统为 Windows WDDM，每次计时都复用同一组已分配的 FP32 设备缓冲区，把两份结果都可用的时刻设为共同的计时终点。双流方案中，计时流等待两条工作流各自的结束事件。

并发实验常见的计时偏差出在末尾。如果开始事件放在一条计时流中，两条工作流都要等它，使两边的设备工作都在共同起点之后开始。停止时则要倒过来，让各工作流各记录一次结束事件，计时流都等到了才记录停止。假如只等待缩放，先结束的缩放已经能交出一张图，Im2Col 仍可能在写最后几个平面，所报“整体时长”就比真实的双输出完成时间短。串行版要等一条流的两次启动，融合版要等一次启动内所有块退出，三种方案才有相同的交付条件。

表中的时间和图中的比值来自同一批设备事件计时。所有方案都反复使用同一组缓冲区，内存分配、主机到设备拷贝以及输出校验都在计时区间之外。不同方案在每组内成对测量，先对每对取耗时比，再汇总跨进程和轮次的结果。用两列经过舍入的绝对时间算出的近似差，可以回答典型一次少用了多少微秒。用配对区间则能看出同一次实验条件下两种方法的比值有多稳定。相对双流的区间与相对串行的区间离一的距离很不相同，这是保留两条基线最有用的地方。一项工作能稳定跑赢原生双流，仍可能只比更快的原生串行方式省下一小段时间。

在这组数据里，独立流更慢有几种待检验的解释。原生并发调度无法指定两类线程块以什么比例驻留，相同设备缓冲区也意味着缓存可能在两个算子之间产生竞争，分流还增加了一组事件和提交关系。完整配对计时把这些效果都纳入调用方实际等待的区间，却不能把 230 多微秒的差逐项分解。要归因到某条加载管线或某种放置策略，就得增加能够区分候选原因的对照或剖析数据。对于已经测好的结果，能下的判断是所选一次启动最早交付了这两张图。

GoPTX 的指令级并行（ILP）：让第二笔加载不必等第一笔返回

HFuse 给正在等数据的 warp 找了另一组 warp。GoPTX 改的是同一条指令流。论文先把两个输入核函数调整到共同的发射配置。换一对算子时，必须核对新网格里的每个线程仍然处理正确的数据，原有屏障要求的线程也都能到齐。在此基础上，GoPTX 解析两份 PTX，构建并合并控制流图，在可以交错的基本块中，根据指令延迟选择下一条从哪一路取，同时保留原计算的数据依赖和同步次序。PTX 还要交给 ptxas 生成目标 GPU 执行的机器码。因此读生成的 PTX 可以检验编译器有没有交错两路工作，实际能发出哪些机器指令、等了多久，则要看编译结果和运行表现。GoPTX 论文 · 作者实现与生成示例

作者给了一个很小的例子，一路将整数加一，另一路将浮点数加一。下表用 AAA 和 BBB 代指两片独立地址，只画出同一线程的依赖关系。表中上下顺序表示先后，行高没有时间含义。

读整数 AAA读整数 AAA
用 AAA 的结果做整数加法读浮点数 BBB
写回整数结果用 AAA 的结果做整数加法
读浮点数 BBB用 BBB 的结果做浮点加法
用 BBB 的结果做浮点加法写回整数结果

左栏发出第一条加载后，下一条就是它的消费者。只要数据还没到，这个 warp 的整数加法就得等。右栏把读 BBB 放到了中间，读 BBB 的地址不依赖 AAA 的值，因此只要发射和访存资源允许，这个 warp 就可以提前把第二笔请求送出去。两次加载都可能尚未完成，另一个就绪 warp 此时也仍有机会被选中。前一种机会来自指令级并行（instruction-level parallelism，ILP），后一种仍是 TLP。这样的安排能拉开生产者与消费者的距离，并没有消除整数加法对 AAA 的依赖。如果原先的瓶颈已经是加载管线或显存带宽，再往里送一条加载也可能只会延长排队。GoPTX 的控制流合并与指令编排

作者生成的 PTX 如何保留两条指令链

GoPTX 作者的最小示例可以逐条查出两路操作。参数区加载和地址转换之后，整型指针存于 %rd_saf2，浮点指针存于 %rd_sbs2。下面六条保留了作者合并后入口中的寄存器名与类型，省略了参数读取、分支标签和最后的返回。它用一个有效线程访问两个独立标量即可说明编排。示例本身没有按线程号计算数组下标，不能把这个片段直接当作大量线程更新不同数组元素的带宽实验。GoPTX 作者生成的合并入口

ld.global.u32 %r_saf1, [%rd_saf2];
ld.global.f32 %f_sbs1, [%rd_sbs2];
add.s32 %r_saf2, %r_saf1, 1;
add.f32 %f_sbs2, %f_sbs1, 0f3F800000;
st.global.u32 [%rd_saf2], %r_saf2;
st.global.f32 [%rd_sbs2], %f_sbs2;

两条加载各自有一个消费者。整数加法要等 %r_saf1，浮点加法要等 %f_sbs1，常量 0f3F800000 是单精度的一。两个数组指针本身还得先从参数区取得，通用地址转换到全局地址以后，才有合法的加载地址。把第一路参数名和寄存器名同第二路区分开，避免了拼接 PTX 时把独立值误当成同一个变量，但寄存器名称不同不能证明两片实际地址不重叠。若第二路本来就需要读取第一路新写回的结果，那么两路之间已经出现了内存依赖，图中这次提前加载便会改变它读取的值。是否可以交错，要由调用合同和实际访问范围来决定。

这里最直观的风险是先写后读的真正数据依赖。第一条加载发出，硬件会追踪目标寄存器是否可用，后面的加法碰到未就绪的输入就必须等待。GoPTX 增加了一条不依赖这个输入的加载，使得同一 warp 在抵达等待点前能做更多工作。它没有把一个 warp 的指令队列变成可以随意选取任意后续指令的队列。若列表中的下一条恰好是等待旧值的加法，后面再有互不相关的指令，也需编译时搬到可用的位置或依靠其他就绪 warp。即便在 PTX 里两次加载相邻，最终机器码仍可能由汇编器调整顺序，两次访存之间能重叠多少、是否刚好落在同一个时钟周期，都必须在目标架构上另行观察。

从两条控制流图合成一份仍可执行的程序

直线程序只有两个加载、两个加法，编排的直觉很容易建立。实际核函数的一路可能有循环，另一路可能因边界条件提前退出。若把两个返回指令都照抄，一个输入走到结尾时就会把另一份还没写出的结果一起截断。GoPTX 分析每个输入的基本块和控制流边，在合成的控制流中记录两路各进行到哪里。可以配对的部分再按延迟作指令交错。作者给控制流长度不相称的情形增加了进一步拆分基本块的处理，使较长的一段有机会与另一侧更多工作相配。这里所谓“延迟感知”是用预测辅助选择静态次序，真实的缓存命中与争用仍会让单次运行的等待不同。

同步比普通寄存器依赖更难处理。假设某一路要求一组线程在同一轮屏障汇合，另一路先按输入走上不同分支。如果合并之后让某些线程先进入这一轮屏障，余下线程却还在另一条路径上等待后续阶段，就可能再也凑不齐参与者。因而 GoPTX 单列同步安全问题，在控制流合并时对含同步操作的基本块作保守处理。一个合法的依赖图能告诉我们什么顺序允许执行，寄存器和缓存则决定这种顺序是否值得执行。论文对 A100 PCIe 40 GB 上的输入做了共同发射形状的适配，其中 GoPTX 比较使用每块 256 线程、网格 1,048,576 块。作者在图 10 中报告相对原生双流平均提升 11.2%，STMS 与 LUD 的配对提升约 23%，而 WMMA 与 GELU 的配对约慢 2%。两对都能合法交错，收益却不同。这个比较检验的是作者在 A100 上的配对，本机上表测的是人工实现的 HFuse 划分，两处数字没有共同的分母。GoPTX，第 III～IV 节 · GoPTX，第 V 节图 10

类似的依赖判断也能解释软件流水。FlashAttention-3 在 Hopper 上请求下一块键值数据时，消费者可以继续计算手里这一块。同一块的 softmax 仍需等到它自己的分数就绪。这里重叠的是同一算子不同分块的工作，代价是要为在途数据保留缓冲。GoPTX 例子中那条提前的 load B，代价则体现在 AAA、BBB 两份状态可能需要同时存活。FlashAttention-3 论文 · 带分块编号的流水示例

融合后的寄存器活跃区间、线程块驻留与溢出

整数加载发出前，线程可能已经算好了 AAA 的输出地址，直到最终写回都还要用它。这段时间称为地址的活跃区间。提前计算 BBB 的地址并发出读请求，两路的地址和结果就可能有更长的重叠区间。对于 GoPTX，这是用更多同时存活的值换取指令调度空间。编译器先分配寄存器，并在需要时插入溢出读写指令。启动以后，SM 才按这份资源需求接纳线程块，实际走到溢出指令的线程才会发起相应的访存。

关注的对象发生了什么怎样辨认
寄存器分配（allocation）编译器按活跃区间给值安排机器寄存器。不同时间才使用的值可以复用同一个寄存器，PTX 中不同的虚拟寄存器名也不一定对应不同的物理寄存器。看针对目标架构编译后的 ptxas -v 每线程寄存器用量，再读需要的机器指令。
线程块驻留（residency）线程块进入 SM 时，要同时容得下它的线程、寄存器和共享内存，并且仍有可用块槽。已驻留 warp 暂时不发射指令，分给它的寄存器仍在片上。占用率（occupancy）比较已驻留 warp 数和硬件上限。要判断能否发射，还得看就绪 warp 数和发射情况。
寄存器溢出（spilling）同时活跃的值放不下时，编译器可能插入存取，把某些值暂存到别处，之后再读回。常规 CUDA 编译路径会使用线程私有的 local 地址空间。先看编译报告里的 spill loads/stores，再看实际执行的指令和缓存流量。动态索引的私有数组也可能用 local，看到 local 访问还要追溯来源。

当调度器转去运行另一个 warp，等待的 warp 仍然保有自己的寄存器值。发生溢出后，访问线程私有地址的请求也可能由缓存满足，因此实际到达片外 DRAM 的流量要另行测量。较新的 CUDA 还允许显式启用优先向共享内存溢出的编译选项，代价会转到每块的共享内存预算上。只把两个核函数的寄存器数相加，既算不出这些取舍，也无法预测哪一组 warp 能继续发射。CUDA 硬件多线程与 local memory · NVIDIA 的共享内存溢出说明

寄存器文件的容量如何约束一个线程块进场

用一张假定有 65,536 个可供分配的 32 位寄存器的 SM 做个容量估算。若每块 256 个线程，编译后每线程需要 64 个寄存器，仅按寄存器数量算，一个块占 16,384 个，四块正好占满。若一处变换使每线程需求升至 65 个，四块的名义需求就变成 66,560 个，连最乐观的整除估算也只能放三块。实际硬件还会按规定的粒度进行分配，SM 可能分成多个子分区，还存在每 SM 最大块数、线程槽和共享内存上限。这个手算只给寄存器方面的上界，已经足以解释为什么代码改动看似只多保留一个值，运行时却可能少驻留整批 warp。CUDA Programming Guide，硬件多线程与资源分配

同样的估算不能倒过来解释溢出。若只允许三个块进场，每线程本来用到的 64 个寄存器不会因旁边有空槽就自动变成 80 个，已经编进机器码的临时存储也不会自行消失。要利用腾出的空间，必须有允许更多寄存器或改变活跃区间的另一份编译结果。反过来，编译时若强行把每线程寄存器数压低，块也许更容易入驻，但某些尚未完成使命的值就得多写一次再读回来。增加的 warp 能否补回这些访问，是速度问题，仅靠理论占用率无法决定。

诊断一段变慢的交错代码时，先拿相同架构的最终二进制核对每线程寄存器数和汇编器报告的溢出，再定位相应的机器指令所在循环。一个循环外只执行一次的保存，和内层每个元素都要做的恢复，静态报告中可能都出现，动态成本却不同。即使发现 local load，也要追查是否来自可变索引的私有数组、函数栈或真正的寄存器溢出。随后观察 L1、L2 与显存的访问，才知道请求走到了哪一级。若显存流量几乎未变，也可能有额外指令和缓存带宽开销，只是没有传到片外。这条从编译资源到动态访问的因果链，比看见“占用率下降”就断言优化失败更能解释下一步该改变哪里。

持久线程块、弹性分块与 μShare 的 SM 共置条件

两个独立核函数要利用同一 SM 上不同执行单元的并行能力，首先得让各自的线程块同时驻留。持久线程块（persistent thread block，PTB）用较少的物理块轮流处理原来的逻辑块。例如总共 12 个逻辑块，用 4 个物理块做固定步长遍历，物理块 0 就依次负责逻辑块 0、4、8。其他三个块按同一规律补齐余下位置。这样可以给另一任务留出线程槽和片上容量。每个位置的输入仍要读，结果仍要写。一个物理块工作得更久，也不足以判断整卡带宽是否饱和。要看同一时刻有多少 warp 能发出独立请求，以及这些请求在缓存、访存管线和显存总线上能得到多少服务。

网格大小控制有多少块同时参与工作。对同一份机器码，改变网格可以改变 SM 上还有多少空间接纳新块，每线程已经分到的寄存器和代码里的溢出指令则随编译结果固定下来。把原算子改写为 PTB 循环并重新编译时，循环变量、索引和活跃区间才可能一同改变。Plasticine 还为矩阵乘生成弹性分块，进一步缩小每个块负责的矩阵分块。块内要同时保留的 A、B 子矩阵随之缩小，在论文的 Tensor Core 矩阵乘示例中，减半每块线程数并缩小分块后，每块所需的共享内存从 64 KB 降到了 36 KB。代价是原先能在片上复用的值可能需要重新加载，所以最佳的独占分块和最佳的共置分块可能不同。Plasticine 作者原文，第 V 节

逻辑任务数、物理块数与访存并行度

若一个程序原来直接用 blockIdx.x 选择逻辑图块，把网格块数从十二改成四却保留原有索引，只会算前四块，其余八块根本没有执行。PTB 变换必须显式恢复对所有逻辑块的遍历。对于有边界判断的最后一个图块，判断条件也要使用当前的逻辑块号。若原核函数依靠每块的共享内存做局部规约，每轮重新分配任务之前还须确保上一轮的线程已经用完旧数据。调整块的数量可以改变物理并发，正确性需要另靠任务覆盖、尾部条件和工作组同步保证。

同一个持久块依次访问逻辑块 0、4、8，这给出的只是一个块的工作顺序。物理块 1 仍然同时处理 1、5、9，其他驻留 warp 也可能各有待返回的访存。判断带宽是否紧张，需要同时看每个请求传输多少有效数据、一个 SM 能保留多少在途请求、缓存是否反复命中同一分块。让一个块承担更多迭代，有时有利于复用已经读入的状态，有时会减少可供隐藏访存延迟的 warp，总访问量也不会因为循环看上去更长就必然增加。改变逻辑遍历粒度和改变独立访存请求的数量，应当用各自的量来判断。

Plasticine 处理的是两个独立网格在 SM 上相互排挤的问题。仅控制线程槽，仍可能让矩阵乘块以过大的共享内存配额占满 SM，使另一路即使只要很少线程也进不来。降低每块的工作分块以后，共享内存削减了，但单次装入的矩阵数据可能服务更少的输出。与 Welder 的卷积例子联系起来，两处都在调整分块与复用，而 Plasticine 还要给另一个应用的块留驻留位置。一个分块独占 GPU 时最快，并不说明它和另一任务同时运行时也能得到最大的总收益。Plasticine，第 V 节

μShare 给出了另一种做法。论文中的 A40 每个 SM 有 1,536 个线程槽，将一个可调整的核函数设为每块 800 个线程，即半数 768 再加一个 warp。两个这种块需要 1,600 个槽，于是无论调度器怎样选择，都无法把两块同时放进同一个 SM。只要网格足够大，这会促使大块分散。另一个较小的块若想进入同一个 SM，还得放得下它所需的线程、寄存器与共享内存。这里直接排除的是两个大块同驻这一种放置方式。即便原先已经覆盖许多 SM，这项调整仍有可能让两类块在同一 SM 上相遇，实际效果要看它们共置后能否各有进展。作者只在可调且改完仍能正确覆盖输出的核函数上改变块大小，固定分块和隐藏发射形状的库函数另行处理。μShare 论文，Half-plus Blocksize Shaping

Half-plus 排除同类块的堆叠，时间偏差决定何时再次发射

A40 的大块占了 800 个线程槽，剩下 736 个。从单个 SM 的线程数看，一个 224 线程的小块有机会和它共同驻留，两块分属不同的核函数。此处并没有一个合并出来的 1,024 线程块。硬件仍要为两个块分别分配块槽、寄存器和共享内存，调度器也可以选择把它们放在不同的 SM。与之对照，若第一种块只有 512 个线程，仅按线程数允许同一 SM 同时持有三个这种块，它们就可能在小块到达前已占满线程槽。把可能容纳的同类大块数从多个降为一个，才是 half-plus 的直接机制。至于参与工作的 SM 总数，还受网格规模和此前的放置状态支配。

在完整的调度流程中，μShare 还会根据核函数的发射余量排序。论文用靠前的一组候选提供足以覆盖 SM 的块数。对可以修改块大小的工作，A40 上发射余量充足时选择最小的半加值 800，发射已经偏晚时则以一个 warp 为步长考虑增大块形状。这样的改动必须保留对原逻辑任务的覆盖，并服从单块上限。由此可见，800 描述的是给定设备和条件下的一种发射形状，不是所有线程块共同分享的一份整卡线程预算。

这个方法需要实际设备允许“大于一半”的单块大小。A800 每个 SM 有 2,048 个线程槽，半数已是 1,024，而单个 CUDA 块的线程上限也是 1,024。此时再多加一个 warp 就不能合法启动，μShare 为此采用三分之一加一个余量。以最小的 warp 对齐选择 704 为例，同一 SM 能容下两个这种块，共 1,408 个线程，但三个需要 2,112 个，已超出 2,048 的上限。改变的是同类块可叠放的个数及留下的空位，不是把 A40 上那个 800 的数字原样迁到所有显卡。哪一种几何能够填满设备、哪一种几何能保留另一任务可用的资源，要回到具体硬件去算。μShare，A40 与 A800 的块形状

块形状只解决“有没有机会放得下”。μShare 还利用离线剖析检查“现在放进来会不会争用同一类资源”。论文对截获的候选核函数区分优先安排的大块组和其余可考虑错开发射的工作。对于后一组，论文保留默认块大小，与已安排的内核逐项检查 FP32、FP64、INT32、加载/存储（LD/ST）、特殊函数（SFU）和 Tensor 六类利用率。其判据要求每一类的合计不超过 100%，同时还要有足够的共享内存和寄存器。前一项是根据剖析值判断两份工作是否可能互补，后一项关乎资源容量。一项通过不能补偿另一项失败。六个百分数是不同资源上的观测，不能在一个核函数内部相加当成“GPU 总利用率”。

例如仅作纸面判断，若候选甲和乙的加载/存储利用率分别为 62% 和 48%，仅这一项就超过 100%，哪怕两边的 Tensor 指令都很少，仍应推迟乙。若每类合计均在范围内，却没有足够寄存器容纳下一块，也同样推迟。反之，两类条件都满足时，候选可以直接发射。论文选择的时间偏差参数为 β=10 μs\beta=10\,\mathrm{\mu s}β=10μs，是首次条件不满足后等待多久再重新检查。它没有给每对核函数一律加上十微秒间隔。重新检查时会更新发射余量和候选排序，优先级可能改变。设备已经让出需要的资源时，等待没有必要。资源迟迟不释放时，经过一个间隔也不构成自动放行的依据。有关延迟目标的控制建立在这些运行时观测和模型上，单独验证 800 的算术不能等价于复现整套在线调度。μShare，Shaper 的条件与时间偏差策略

Tacker 的块内分工与同步：Tensor Core 矩阵乘和 Stencil

设 VGG16 是在等待响应的前台请求，后台有一批三维 Stencil 要更新。到了能用 Tensor Core 的矩阵乘或卷积层，前台做矩阵乘累加，后台则用常规算术指令组合网格邻点。它们有机会用到同一个 SM 上不同的执行单元。这里的“异构”是 SM 内部执行管线的分工：矩阵乘仍要计算地址、搬运输入和写结果，Stencil 也要加载邻点。两边会分享指令发射能力、片上存储和通往 L2、显存的带宽。因此知道前者调用了 Tensor Core，只能确定值得考察哪种配对，还不能据此把两边独占时的时长完全重叠起来。

Tacker 的公开文件 tzgemm_stencil.cu 可以直接验算这一点。物理线程 0～127 进入矩阵乘分支，协作搬运分块，再用 wmma::mma_sync 更新矩阵累加器。线程 128～255 进入 Stencil 分支，从物理编号中减掉 128，各自按局部编号把邻域读进共享内存。两部分使用不同的块内屏障编号，矩阵乘等待屏障 1，Stencil 等待屏障 2，两处的参与线程数都是 128。这样前半块可以确认矩阵数据已经装好，无须等后半块碰巧也走到相同次数的同步点。若沿用两份原始代码中“全块一起等”的假设，一个组就可能在另一个组根本不会到达的屏障上等待。Tacker 的分组入口 · 矩阵乘及 Stencil 的同步位置

命名屏障怎样限定一组 warp 的可见性与等待

用这份设备代码检查一次矩阵乘法迭代。假设前四个 warp 分批向共享内存填入矩阵片段，最快抵达下一个阶段的 warp 不能立即使用其他三个还没写好的数据。另一方面，Stencil 组的四个 warp 正按自己的图块更新邻点，它们并不负责填入矩阵，于是矩阵组的等待条件只能包括那 128 个实际分担矩阵工作的线程。PTX 的块内命名屏障可以指定屏障编号和预期参与线程数。当这一轮所需参与者都抵达同一编号的屏障，之前的共享内存写入才能按规定对参与者可见。随后下一轮才可重新利用该屏障。PTX ISA，CTA 命名屏障

选择不同编号解决了两类工作不应互相算作“到齐”的问题。若两边都用编号 1、计数都填 128，硬件不会替程序分辨哪四个 warp 是矩阵组，交错到达的 Stencil warp 也可能贡献计数，让矩阵数据尚未写全就开始使用。反过来，若编号虽不同，参与计数却仍填整个块的 256，两个分支都可能等不到预期人数。计数不是线程成员名单，只有分支边界、完整 warp 的参与条件、屏障编号和每次循环的到达轮次都一致，才能形成预期的同步组。一个 SM 上的不同线程块也各有自己的块内屏障，复用相同编号不会借此同步两个块。

公开的 Tacker 代码用了当时常见的 bar.sync 拼写来表达部分线程组的同步意图。在新代码里照搬助记符，还应核对目标架构和 PTX 版本的执行约束。现行 PTX 规范将简写 bar.sync 等同于带 .aligned 的 barrier.cta.sync.aligned，并对条件执行施加额外要求。对支持非对齐形式的目标（sm_70 及以上），不同 warp 走不同分支时，可选择不带 .aligned 的 barrier.cta.sync，同时检查参与的完整 warp 能到达同一阶段，且计数正确。公开代码展示了为什么分组和计数缺一不可，不能仅凭一次运行没有卡住就证明所有分支与输入都安全。本机计时的 Im2Col–缩放这对算子本身不需要块内屏障，因此不能用其速度来验证这里的同步机制。Tacker 公开的同步位置 · HFuse 的线程重编号与部分同步

设备端的这个入口固定了配对、分工和同步方式，是运行前就能准备好的部分。至于发射哪一版，每次前台请求剩下的时间可能不同。VGG16 的计算图决定下一层需要怎样的输入，调度器可以为这一层选择独立执行，或选择一个能附带完成部分后台工作的等价实现。Tacker 的代码生成与运行入口

预测融合耗时的动机也可以从这个块里看出来。前台矩阵乘和后台 Stencil 都在运行时，有一段时间两种管线可以一起提供工作。一旦后台分块先做完，剩下的时间只有前台在推进。若往同一前台工作里继续增加后台负载，过了某个比例，情形又会倒过来，前台已经完成，后台还要独自跑一段。Tacker 用候选配对的数据拟合两段耗时关系，允许增长斜率随谁最后完成而改变。论文还比较不同融合比和顺序执行，发现顺序最好时可以保留独立的候选。公开的 stencil_tzgemm_mix 正好展示了其中一种固定的设备分工，本身既不读取请求到达时刻，也不在设备上决定下一层是谁。Tacker，融合时长的两阶段模型

前后台调度（RT/BE）：截止时间、P99 延迟与后台吞吐

对要求及时响应的请求，计时起点要移到请求到达。假设前台请求在 aaa 时到达，在 fff 时交付，响应时间就是 f−af-af−a，包含排队、等待正在运行的工作以及自身的执行时间。服务质量目标（QoS）可以约定截止时间 ddd，也可以规定一定负载下的第 99 百分位（P99）响应时间。前者可以逐请求统计超时比例，后者要按一批请求的完整响应时间排序。后台的尽力而为任务（best effort，BE）则关心同一观察窗口里每秒完成多少份工作。只量一对核函数从开始到双双完成，无法回答一批请求的 P99 和后台吞吐。Tacker 论文将前台称为延迟敏感任务（LC），REEF 针对的前台则明确称为实时任务（RT）。

假设现在是 ttt 时刻，前台从当前层到结束、单独运行还需 T^remaining\widehat T_{\rm remaining}Tremaining​，留给额外干扰的时间就约为 d−t−T^remainingd-t-\widehat T_{\rm remaining}d−t−Tremaining​。如果当前卷积独占时预计用 TcT_cTc​，与 Stencil 融合后预计用 TfT_fTf​，调度器要从余量里扣的就是多出来的 Tf−TcT_f-T_cTf​−Tc​。它还得给余下的层留够时间。因而同一个卷积的输入形状即使没有变化，当此前的排队耗尽了余量，调度器也可能改为只运行卷积。预测值会受实际争用影响，最终仍要用前台请求的到达与完成记录判断服务质量。

Tacker 如何从离线候选和前台余量决定本次发射

论文式（8）有两个同时成立的条件。先比较融合时间和两路独占时间之和，只有融合预计能少占用总时间，才有吞吐上的理由。再比较前台因融合多等的部分与它剩下的余量，只有预计增加的时间小于可花的余量，才满足这次发射的延迟要求。候选后台工作还必须已经就绪。若待选的融合都不合适，论文继续检查是否有可以完整放入剩余余量内的独立后台核函数。这样，候选的可用性来自算子依赖，候选之间的比较才取决于预计时间。Tacker，第 VII 节、式（7）和式（8）

用一组手算时长代入能区分这两道条件。假设当前前台层独占需 5 ms，后台段独占需 4 ms，合并后预计 7 ms。整个配对比顺序运行少占 2 ms，但这层前台预计要多等 2 ms。如果该请求还有 3 ms 可支配，模型允许这一选择。若此前排队已将余量压到 1 ms，同一组核函数就不应因此被选中。反过来，若融合预计需 10 ms，即便前台还有很宽的余量，这个候选也比 9 ms 的串行总时间更长，无法通过第一个条件。这些是帮助理解论文不等式的假设时长，实际效益仍由对应负载上的测量支持。

Tacker 论文在运行前准备候选融合核函数，为融合耗时建立预测模型。运行时轮到某一层时，核函数管理器再根据前台余量选用原版或融合版。公开仓库的实验循环先计量前台各层单独执行的耗时，由后向前累加，得到从每层到末尾的耗时估计。每轮以 50 ms 为预算。如果剩余预算低于当前估计加 4 ms，就直接发射原算子，否则才按该层标志尝试矩阵乘或卷积的预制融合入口。4 ms 是这段实验代码里的留量。Tacker 论文 · 公开实现的前台计量 · 融合选择与事后记账

公开代码与论文分别提供了两种观察角度。代码先把已有前台序列预热，再多次逐核运行与同步，用于估计各层独占时长，因此运行前已知各层顺序，也已有设备端候选。逐层实验时，余量、当前层的类型和融合入口决定这一次提交什么。同一模型两次抵达这一层时，前面实际花掉的预算可能不同，所以选择也可不同。融合设备程序可以预先编译，整次请求每一步该走哪条路却仍能动态决定。公开实现的 4 ms 保护量是对余下前台工作的额外保留，并非论文通用的优化阈值，也不表示每启动一个算子必然额外等待 4 ms。

此外，该仓库将 Tacker 与后续 Aker 的分支放在同一任务管理器中。代码给可融合的矩阵乘和卷积分别选择已有入口，部分分支还会根据模式决定送入多少后台逻辑块。一次尝试结束后，同步所得的时间可参与更新。若实测没有满足这段测试程序的收益条件，账本有可能扣回相应前台原时间，不把尝试的后台块计为已获收益。已经在 GPU 上消耗的那段真实时间不会被撤销。因此公开代码适合用来理解“何时允许尝试、尝试后怎样记账”。要验证真实请求能否按时交付，还得另看请求的实际时刻。Tacker 与 Aker 的候选分支与预算更新

Tacker 论文另在 RTX 2080 Ti 上评估了 72 组前后台配对。各前台服务的 QoS 目标为 50 ms，请求按泊松过程到达，到达率取该服务在不违反目标时所能承受峰值的 80%。在这个负载下，图 16 报告前台请求的平均及 P99 延迟，图 14 报告相对 Baymax 的后台吞吐平均提高 18.6%，最高提高 41.1%。作者把式（10）中的 TTT 称为后台应用的处理时间，计算 (TTacker−TBaymax)/TBaymax(T_{\rm Tacker}-T_{\rm Baymax})/T_{\rm Baymax}(TTacker​−TBaymax​)/TBaymax​。图中没有列出构成这个比值的逐作业完成计数。若把 TTT 理解为完成固定数量任务所需的耗时，时间变大对应的反而是吞吐下降。因此应保留论文对改进值的定义，不能把这个百分数直接换算为额外完成了多少任务或每秒多少个请求。对自己的服务，可在相同到达负载、相同观察窗口下直接统计有效完成数。Tacker 作者原文，式（10）及图 14、16

REEF 的重置、幂等重放与发射前填充

Tacker 在前台层的发射边界判断还能否并入后台工作。真实服务还要处理决定已经做完以后的请求到达：GPU 可能正执行一段只属于后台的长工作，即使新来的请求本身只有几层，第一层也得先拿到资源。只让主机以后少提交后台任务，可以缩短未来的队列，已经在设备上执行的工作仍有自己的完成时间。REEF 把这段从到达到获得设备的等待单独作为调度对象。其重点在于可否放弃部分已经完成的后台计算，把资源尽快交给实时任务，再用可证明正确的重放恢复后台进度。

用一个写入范围来检查幂等条件。设每个线程从不再改变的输入图取值，计算 out[i] = f(in[i])，不同线程写不同位置，而且调用方只在整张输出就绪后消费它。若执行到一半被打断，重新执行时先前完成的位置会被同一值覆盖，未完成的位置随后补齐。改为 out[i] += f(in[i])，就算每个地址只对应一个线程，已经执行过的前缀也会被累加两遍。若输入与输出共享地址、另一个请求已经观察了部分结果，或内核额外更新了全局计数器，就需要重新判断整段工作的副作用。能否安全重试关乎程序允许观察的状态，不能从“这是推理算子”几个字直接推出来。

REEF 完整实现可以在 AMD 的开放软件栈中处理排队命令并重置计算单元。重置发生时，运行时未必恰好知道哪一个后台核函数执行到了哪条指令。论文通过限制设备队列中的在途工作，从靠近中断位置的保守边界恢复，允许重复一段有限长度的后台工作。它换来的好处是优先让实时请求取得设备，代价落在被撤销工作之后的重新计算。NVIDIA 对照版本 REEF-N 通过控制提交队列和延迟跳过旧命令减少等待，但不能像完整 AMD 路径那样主动终止已经在计算单元上运行的核函数。因此论文的 AMD 抢占时间没有理由直接成为普通 CUDA 高优先级流的等待上限。REEF，第 4.3～4.4 节

在发射每个 RT 核函数之前，REEF 还可以挑选同时运行的 BE 工作，把它们作为参数交给预编译的组合入口。入口按计算单元（CU）编号分工，先为 RT 分配足够的 CU，再把其余 CU 分给 BE。论文的筛选规则要求 BE 核函数独占时长短于 RT，而且 BE 每个 CU 可同时驻留的线程块数高于 RT。前一条约束减少后台拖长整次启动的风险，后一条避免组合入口因后台的资源需求而降低前台原有的驻留能力。抢占管理的是请求到来的时刻，这种运行时填充（dynamic kernel padding）管理的是接下来发射的每个核函数。REEF 论文，第 5.2 节及图 9

按数据依赖、执行瓶颈和交付条件选择融合粒度

拿到一对新算子，先在计算图里追踪下游真正要读的值。若生产者能在寄存器或共享内存里把分块直接交给唯一的消费者，就值得计算能省去几次全局读写，同时核对重叠区域是否增加了重算、外部消费者是否仍然需要完整输出。此时即使 SM 已经很忙，减少必做的工作仍可能缩短执行时间。

两路输出若彼此独立，判断顺序就变了。遇到有空闲发射周期、却很少有就绪 warp 的情况，要先查清 warp 在等什么。加载的数据可能还没返回，前一条算术指令可能还没算完，也可能有线程正在屏障处等同伴。如果 SM 还有驻留空间，可以尝试引入另一类就绪 warp。如果已经很难多放一个块，同一 warp 里能提前执行的独立指令也可能填上这段等待。前一种选择要检查线程块的资源配额，后一种要检查多出来的活跃值。两路工作若已经把同一条访存通路用满，增加并行度反而会增加排队。这些判断可以用来缩小候选范围，最终还要让双方完成相同的工作，与可用的串行及并发方案比较。

最后由调用方定义完成条件。对离线的图像流水线，两张图最早何时都能交付，可以直接决定采用哪种方案。对在线推理，先把前台可接受的 P99 或超时率定下来，再在相同到达负载下，比较后台实际完成的工作量。即使两份实现的双输出完工时间相同，能让前台更早交付的那个实现，也可能为下一批请求留下更多可用时间。
