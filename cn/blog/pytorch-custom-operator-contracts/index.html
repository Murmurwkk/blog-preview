PyTorch 自定义 SwiGLU 算子：CUDA 前向实现与框架集成

PyTorch 张量即使连续，起始地址也可能相差一个 float，迫使 SwiGLU 从一次读写四个数退回逐个读写。在 RTX 5070 Laptop 上，约百万个元素的对齐输入用了 eager 组合约 63% 的时间，把输入偏移一个 float 后，自定义算子反而慢了约 3.3%。

SwiGLU 的逐元素门控只需要一次 sigmoid 和两次乘法，但 PyTorch 调用它时，还要传递裸指针上看不见的信息。同一个连续张量可能是带偏移的视图，也可能刚在非默认 CUDA 流上写完。训练要从输出追溯输入的梯度，编译追踪时则可能只有形状而没有数据。把这几行 CUDA 接入框架，四种情形都要在接口里有明确的处理方式。

这个 SwiGLU 算子接收一个连续的 CUDA FP32 张量，形状为 [2,N]。第一行保存门控值，第二行保存与之相乘的值，算子把结果写入新分配的 [N] 张量。前向的逐元素运算在一个 CUDA 核函数里完成，反向则交给 PyTorch 的可求导运算。

从 Python 发起一次调用，要经过框架分派并分配输出。用主机时钟可以量到提交和等待的过程，CUDA event 则量到 GPU 执行两枚事件之间的时间跨度。主机提交得慢，中途让 GPU 等待，这段空隙也会算进去。要知道 CUDA 一次读四个值究竟能快多少，就得让标量版和向量版读写相同的地址。两种实现比过之后，还可以固定使用其中一种，在同一个内存池里比较反复使用一块缓冲区和轮换使用多块缓冲区的差别。每次计时前都重新核对前向结果，梯度和执行顺序另有专门的测试。

SwiGLU 两路输入的张量布局与读写量

SwiGLU 的前馈层有两路线性投影。把投影结果记作 aaa 和 bbb，要算的是

yi=SiLU⁡(ai)bi=aiσ(ai)bi,σ(a)=11+e−a.y_i=\operatorname{SiLU}(a_i)b_i =a_i\sigma(a_i)b_i,\qquad \sigma(a)=\frac{1}{1+e^{-a}}.yi​=SiLU(ai​)bi​=ai​σ(ai​)bi​,σ(a)=1+e−a1​.

两路线性投影和后面的输出投影都在这个算子之外，所以下面的性能数字只覆盖逐元素门控，不能当成整个 FFN 的加速。SwiGLU 原论文 里的完整一层同样得按这个范围读。

对于连续的 [2,N]，两路投影分别占据独立的一行。前半段是 a0,…,aN−1a_0,\ldots,a_{N-1}a0​,…,aN−1​，后半段是 b0,…,bN−1b_0,\ldots,b_{N-1}b0​,…,bN−1​，因此第 iii 个输出需要的两个值位于 x[i] 和 x[N+i]。

[N,2] 里配对的通常是 x[2*i] 和 x[2*i+1]，元素总数一样，含义完全不同。

图 1　输入排成两行时，门控值的配对元素在下一行的同一列。如果改成交错的两列，这个元素就在它右边。

模型也可能把每个 token 的两路投影并排放在 [batch,tokens,2*hidden] 的最后一维。此时即使元素总数吻合，展平后仍然是一个 token 的两路数据接着下一个 token 的两路数据。直接按 [2,N] 的前后两半取值，就可能把不同 token 的数据配到一起。要接收这种布局，算子得在每个 token 内切出两个半区，或者先重排数据并计入拷贝开销。

在标量实现中，n 表示每行的长度，所以线程找到 x[i] 后，向后移 n 个元素就能取到同一列的另一项。

__device__ __forceinline__ float silu_times(float a, float b) {
    float e = __expf(-fabsf(a));
    float s = a >= 0.f ? 1.f / (1.f + e) : e / (1.f + e);
    return (a * s) * b;
}

__global__ void swiglu_scalar(const float* x, float* out, int64_t n) {
    for (int64_t i = int64_t(blockIdx.x) * blockDim.x + threadIdx.x;
         i < n; i += int64_t(blockDim.x) * gridDim.x) {
        out[i] = silu_times(x[i], x[n + i]);
    }
}

如果直接写 1 / (1 + exp(-a))，当 aaa 是绝对值很大的负数时，sigmoid 的结果本应接近零，分母中的 e−ae^{-a}e−a 却可能先溢出。令 e=e−∣a∣e=e^{-|a|}e=e−∣a∣，再按正负分别计算 1/(1+e)1/(1+e)1/(1+e) 和 e/(1+e)e/(1+e)e/(1+e)，指数项就始终落在零与一之间。__expf 仍有近似误差，如果最终乘积超出 FP32 的表示范围，结果仍可能溢出。

源码层面每个输出读两个 float、写一个 float，理想读写量是 12N12N12N 字节。分开算 SiLU 和乘法，中间结果多一次写、一次读，再加 8N8N8N 字节。这只是张量边界的预算，实际 DRAM 流量还受缓存影响。融合也把两次调用压成一次，NNN 很小时这一点可能比省下的字节更要紧。

float4 访问的地址对齐与标量回退

任意非负 NNN 都可以用标量 kernel 处理。若要让每个线程一次算四个输出，向量版就要读两组 float4。这样除了元素连续，还必须确保两组数据的实际起始地址都满足宽访问的对齐要求。

即使 PyTorch 将张量标为连续，它也可能是从一块更大的存储中切出来的视图。连续性由形状和步幅决定，首元素可以位于整块存储的中间。下面这段代码就构造了这样的切片。

N = 8
storage = torch.randn(2 * N + 8, device="cuda")
x = storage[1 : 1 + 2 * N].view(2, N)
assert x.is_contiguous()

这个 Tensor 两行之间没有空洞，但首地址比底层 allocation 后移了一个 float，即 4 个字节。硬把它解释成 float4*，16 字节对齐就破了。reinterpret_cast 只改指针的解释方式，不会搬数据。

所以向量版本的进入条件是

N mod 4=0,addr⁡(a) mod 16=addr⁡(b) mod 16=addr⁡(y) mod 16=0.N\bmod4=0,\qquad \operatorname{addr}(a)\bmod16= \operatorname{addr}(b)\bmod16= \operatorname{addr}(y)\bmod16=0.Nmod4=0,addr(a)mod16=addr(b)mod16=addr(y)mod16=0.

除了第一行，还得查第二行的起点 x+N 和输出地址。只要有一处不满足 16 字节对齐，或每行的长度不适合四个一组处理，整个调用就走标量路径。这样的回退逻辑也免去了在一次启动中单独处理首尾元素的工作。CUDA 的设备内存访问规则

主机端的入口接收两行合起来的长度，并在提交核函数前检查参数。

cudaError_t swiglu_launch(const float* input, float* output,
                         int64_t total_elements, cudaStream_t stream);

total_elements 是两路合计的元素数，进函数才除以二。总长为负或为奇数直接报错，为零直接返回成功、不启动零个 block；非空任务拒绝空指针。函数不申请内存也不同步，输入输出存储由调用者提供，且不许重叠。

早期的简化入口说明了漏检对齐和长度的后果。被比较的简化入口只按 total_elements/2 取长度、按长度整除四决定走不走 float4，既不查奇数总长也不查指针对齐。总长 7 时它「成功」处理了前后各三个值，漏掉最后一个；总长 0 时它尝试提交零个 block，返回 cudaErrorInvalidValue；在最前面那个偏移一个 float 的输入上，launch 本身成功，等完成时才报 cudaErrorMisalignedAddress。三个问题分别出在参数语义、启动配置和设备访问，补一个尾部循环三个都解决不了。

修正后的入口跑了 96 组长度与地址偏移组合，最大绝对误差 7.15×10−67.15\times10^{-6}7.15×10−6，memcheck、racecheck、synccheck 均未报告错误。反汇编里向量分支确实有 LDG.E.128、STG.E.128，标量分支是 LDG.E、STG.E。这只能说明宽访问被生成了，推不出加速倍数：每线程的工作量、并行线程数和实际调用成本都跟着变了。

从 torch.ops 分派到当前 CUDA 流

裸入口接收指针、长度和 stream，而调用者给 PyTorch 传的是张量。两者之间的 C++ 包装函数需要先验证输入布局、确定设备及当前流，再把合法的指针与长度交给 CUDA。

at::Tensor swiglu_cuda(const at::Tensor& x) {
    TORCH_CHECK(x.is_cuda(), "SwiGLU requires a CUDA tensor");
    TORCH_CHECK(x.scalar_type() == at::kFloat, "SwiGLU requires float32");
    TORCH_CHECK(x.dim() == 2 && x.size(0) == 2,
                "SwiGLU requires shape [2,N]");
    TORCH_CHECK(x.is_contiguous(), "SwiGLU requires contiguous [2,N]");

    c10::cuda::CUDAGuard guard(x.device());
    auto out = at::empty({x.size(1)}, x.options());
    const auto stream = c10::cuda::getCurrentCUDAStream(x.get_device());
    C10_CUDA_CHECK(swiglu_launch(x.const_data_ptr<float>(),
        out.mutable_data_ptr<float>(), x.numel(), stream.stream()));
    return out;
}

输出沿用输入的 device 和 dtype，但重新分配存储，不动输入。这里拒绝非连续 Tensor。若改成内部调 contiguous()，接口能力变大，也多出可能的分配和拷贝，计时必须一起算进去。上一节那种连续偏移切片倒是合法的，交给裸入口挑安全的访问分支即可。

这里需要同时选对设备和流。CUDAGuard 让分配与提交落在输入所在的设备上，current stream 则接续调用者在这个设备上已经建立的顺序。用户完全可以在非默认 stream 里造出 x，紧接着调门控，只要两步提交到同一条 stream，门控就排在生产之后。硬编码默认 stream 会把这个顺序弄丢。

图 2　输入的写入、门控和输出的使用依次发生在同一条流上。如果把门控单独提交到另一条流却没有设置等待，它就可能提前读到旧值。

如果门控已经读了旧值，事后再同步整个设备，也只能等这次错误计算结束。确实需要跨流使用输入时，要用 event 或等待操作建立先写后读的依赖。张量的存储如果被另一条流借用，还要确保那条流用完前存储不会被回收。扩展收到的裸指针没有携带这些信息，因此必须接续调用者建立的顺序。PyTorch stream 语义

Python 通过算子名查找实现，因此还需要在 PyTorch 的分派器（dispatcher）中注册下面的名称和 CUDA 入口。

TORCH_LIBRARY(mur_swiglu, m) {
    m.def("forward(Tensor x) -> Tensor");
}
TORCH_LIBRARY_IMPL(mur_swiglu, CUDA, m) {
    m.impl("forward", TORCH_FN(swiglu_cuda));
}

前一段定义 schema，后一段注册 CUDA 实现。schema 里没有输入修改和输出别名标记，因为实现确实是 out-of-place 的。框架会拿这些信息去检查和变换程序，实际原地写入不能藏在声称纯函数的签名后面。这里只注册了 CUDA dispatch，CPU Tensor 不在支持范围。官方 C++/CUDA 扩展教程

加载扩展动态库后，Python 就可以调用 torch.ops.mur_swiglu.forward(x)。但 dispatcher 只知道怎样执行这次前向，要把自定义节点接入训练，还须告诉 autograd 怎样利用它的输入回传梯度。

用 PyTorch 张量运算注册 SwiGLU 反向传播

把上游梯度记成 gi=∂L/∂yig_i=\partial L/\partial y_igi​=∂L/∂yi​。因为 σ′(a)=σ(a)(1−σ(a))\sigma'(a)=\sigma(a)(1-\sigma(a))σ′(a)=σ(a)(1−σ(a))，对 aσ(a)ba\sigma(a)baσ(a)b 用乘积法则：

∂L∂ai=gibiσ(ai)[1+ai(1−σ(ai))],∂L∂bi=giaiσ(ai).\frac{\partial L}{\partial a_i} =g_i b_i\sigma(a_i) \left[1+a_i(1-\sigma(a_i))\right], \qquad \frac{\partial L}{\partial b_i}=g_i a_i\sigma(a_i).∂ai​∂L​=gi​bi​σ(ai​)[1+ai​(1−σ(ai​))],∂bi​∂L​=gi​ai​σ(ai​).

因为第 iii 个输出只依赖同一列的两个输入，反向可以逐元素计算。分别将这两个偏导乘以上游梯度，再把两路结果按前向的顺序写成 [2,N]，就不需要显式构造 Jacobian 矩阵。

def setup_context(ctx, inputs, output):
    (x,) = inputs
    ctx.save_for_backward(x)

def backward(ctx, grad):
    (x,) = ctx.saved_tensors
    a, b = x[0], x[1]
    s = torch.sigmoid(a)
    da = grad * b * s * (1 + a * (1 - s))
    db = grad * a * s
    return torch.stack((da, db), dim=0)

torch.library.register_autograd(
    "mur_swiglu::forward", backward, setup_context=setup_context)

反向计算依赖前向使用的 a,ba,ba,b。save_for_backward 保存输入张量，使它的存储一直有效，同时保留框架需要的版本信息。如果用户在前向结束后原地修改了输入，再拿新值求导，得到的梯度就对应另一个输入，却会被接到旧输出的计算图上。专门为这种情况设计的测试触发了版本不匹配错误。

图 3　前向在 CUDA 中是一个自定义节点，反向沿框架可以继续求导的普通 PyTorch 运算连接。

反向留成 PyTorch 运算还有一个好处：开高阶求导时框架能接着追。例如对单个输出，

∂2y∂a2=bσ(a)(1−σ(a))[2+a(1−2σ(a))],\frac{\partial^2y}{\partial a^2} =b\sigma(a)(1-\sigma(a))[2+a(1-2\sigma(a))],∂a2∂2y​=bσ(a)(1−σ(a))[2+a(1−2σ(a))], ∂2y∂a∂b=σ(a)[1+a(1−σ(a))].\frac{\partial^2y}{\partial a\partial b} =\sigma(a)[1+a(1-\sigma(a))].∂a∂b∂2y​=σ(a)[1+a(1−σ(a))].

实测二阶梯度与独立 FP64 参考的最大绝对差为 8.39×10−88.39\times10^{-8}8.39×10−8。能继续求导，是因为注册的 backward 仍由可追踪的 PyTorch 运算组成。真把它换成另一个不透明 CUDA kernel，求导支持也得跟着补。

这段 Python 调用把前向输出接到损失函数上，再对输入的两行分别求梯度。

from bench_mur.pytorch.extension import load_extension
import torch

custom = load_extension()  # 编译并加载 C++/CUDA，同时完成 Python 注册
x = torch.randn(2, 33, device="cuda", requires_grad=True)
y = custom(x)
y.sum().backward()
assert y.shape == (33,)
assert x.grad.shape == (2, 33)

33 不是四的倍数，但它是合法的每路长度。这里应该走标量路径，正常返回两行梯度，不该为了迁就 float4 去改模型的合法形状。

FakeTensor 的输出元数据与输入校验

求导规则让 autograd 能够追踪梯度，而编译追踪还需要在没有真实数据时推导输出。FakeTensor 保留输入的 shape、dtype 和 device，本例的输出长度又完全取决于 x.shape[1]，因此可以单独注册以下元数据函数。

@torch.library.register_fake("mur_swiglu::forward")
def fake(x):
    torch._check(x.device.type == "cuda")
    torch._check(x.dim() == 2)
    torch._check(x.shape[0] == 2)
    torch._check(x.dtype == torch.float32)
    torch._check(x.is_contiguous())
    return x.new_empty((x.shape[1],))

编译器需要从这个函数得知，合法输入会产生一个与输入同设备、同类型、长度为 NNN 的新张量。因此函数只操作元数据，无须启动 CUDA 或读取指针。检查范围得和真入口一致，否则会出现编译时放行、运行时拒绝的程序。输出长度依赖数据的算子不能照抄这段；本例能这么写，是因为形状关系已经被接口定死。FakeTensor 注册说明

注册 fake 并不会把 kernel 里的 sigmoid 暴露给编译器。编译图知道怎么连这个节点，不等于能把节点内部和邻接算子融合。实验环境里 aot_eager, fullgraph=True, dynamic=True 对 N=17,33,65N=17,33,65N=17,33,65 的前向和反向都跑通了，最大差分别是 1.19×10−71.19\times10^{-7}1.19×10−7、2.38×10−72.38\times10^{-7}2.38×10−7；默认 Inductor 后端在普通表达式和自定义算子上都报 TritonMissing。所以这里只能确认 AOT 接入，不能宣布 Inductor 跑通，更不能拿 eager 基线冒充编译融合基线。

不同测试回答的问题不一样。opcheck 查的是 schema、FakeTensor、autograd 注册和 AOT dispatch 能不能配合，它不会替我们推导梯度。gradcheck 用有限差分查数值梯度，默认方法面向双精度，而这个接口只实现了 FP32。实验用 eps=0.001, atol=rtol=0.003 做辅助检查，非双精度警告照留；主要数值依据仍是同一批 FP32 输入提升到 FP64 后的独立前向和反向。opcheck 与 gradcheck

数值测试覆盖 N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536N=0,1,3,4,7,8,31,32,33,257,1024,1025,65536，各取 0、1、2、3 个 float 的 storage offset，再分别用随机门值和从 [−100,−40,−5,−0.1,0,0.1,5,40,100][-100,-40,-5,-0.1,0,0.1,5,40,100][−100,−40,−5,−0.1,0,0.1,5,40,100] 循环取出的门值，共 104 组。前向和反向的最大绝对误差都是 1.526×10−51.526\times10^{-5}1.526×10−5，全部有限，并各自通过逐元素绝对加相对误差的预算。

图中每个长度都取四种地址偏移下的最大误差，对数轴的下限是 10−1210^{-12}10−12。空输入、奇数 NNN、对齐输入和偏移输入都通过了 opcheck，七种不受支持的输入也按预期被拒绝。为单独检验执行顺序，测试延后了非默认流上产生输入的操作，结果仍与 eager 参考完全一致。捕获 CUDA Graph 后更换输入并重放，最大差为 2.98×10−82.98\times10^{-8}2.98×10−8。

SwiGLU 自定义调用与 eager 组合的配对计时

在框架层，先将 custom(x) 与 F.silu(x[0]) * x[1] 成对运行。两边读取同一份输入，两者都从 Python 调用、经框架分派并分配输出，也都只保留最近一次输出。表中的 CUDA event 时间覆盖设备端的起止区间，主机分派和分配造成的提交空隙可能落入这个区间，脚本另用主机时钟记录提交和同步完成的时间。生成输入、传输、编译与数值参考置于计时之外。输入不请求梯度，测的是推理时这一小段前向。在 RTX 5070 Laptop 上使用 PyTorch 2.14.1+cu130，数据按每路元素个数 NNN 和视图在存储中的偏移分组。

独立前向核对先查输出有限，再与同一组 FP32 输入提升为 FP64 后算出的 SiLU(a) × b 比较。24 项检查均过，最大绝对误差 1.4246×10−61.4246\times10^{-6}1.4246×10−6，每个正式进程也重新检查自己的输入。CUDA event 包的是整段提交，CPU 来不及提交下一次的间隙同样会算进去。另取 100 次调用做 Nsight Systems 捕获，对齐的两个长度均为 custom 100 个 kernel、eager 200 个。N=32N=32N=32 时首个到最后一个 kernel 的跨度中，被 kernel 活动覆盖的比例分别只有 3.22% 与 3.88%。从中可以看出整次调用与纯 GPU 执行的区别，还无法把中间空隙全记到 Python 上。

SwiGLU 的输入布局、流、梯度与编译接口

这个算子的两行布局决定哪些值配对相乘，对齐检查则决定能否使用 16 字节读写。算子在 PyTorch 当前 CUDA 流上启动：输入若由同一条流产生，流内顺序就能保证先写后读；若来自其他流，需要先建立跨流等待。autograd 和 FakeTensor 分别为这个算子提供梯度与形状推导，这些接口行为都需要独立验证。

这组结果覆盖的是 FP32 连续两行输入、CUDA 前向和可追踪的反向传播。模型如果使用自动混合精度（AMP）、vmap、其他数据类型或多张 GPU，还得分别检查对应的调用方式。完整模型训练也超出了这次实验的范围。
