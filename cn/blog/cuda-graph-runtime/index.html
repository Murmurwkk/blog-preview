CUDA Graph 推理：注意力算子的捕获、重放与端到端耗时

CUDA Graph 把连续四个注意力核函数合为一次提交。24 个独立进程的配对计时显示，在输入已驻留 GPU 时，四种形状的运行时间都缩短了。若从主机传入数据并取回结果，只有最大形状明确变快，约省 9%。图重放期间，调用方仍须保留节点引用的缓冲区。

把四个 Attention 核函数捕获到一张 CUDA Graph 后，程序只需提交一次图重放，就能执行原来要分别提交四次的计算。在输入已经驻留 GPU 的实验中，直接提交的设备区间是图重放的约 1.9–3.0 倍。对于从主机发起的完整请求，输入复制、输出取回和等待仍然需要时间。计入这些环节后，四种形状中有两种略慢，一种的区间包含持平点，只有最大形状快约 9%。要解释这组差别，我们先看捕获改变了哪些操作，再看两种计时各覆盖了请求的哪一段。

显式生成分数和概率矩阵的四个 Attention 核函数

输入是连续 FP32 的 Q∈RM×dQ\in\mathbb R^{M\times d}Q∈RM×d、K,V∈RN×dK,V\in\mathbb R^{N\times d}K,V∈RN×d，输出

O=softmax⁡(QKTd)V.O=\operatorname{softmax}\left(\frac{QK^T}{\sqrt d}\right)V.O=softmax(d​QKT​)V.

MMM 是 query 数，NNN 是 key/value 数，ddd 是每个向量的宽度。这里把每一步的中间结果写入显存。实现先转置 KKK 并计算注意力分数，再对每行分数做 Softmax，最后将概率乘以 VVV。这四个核函数依次提交到调用方提供的 CUDA 流（stream）：

transpose K → QK / sqrt(d) → row softmax → PV

转置缓冲需要 NdNdNd 个 float，分数缓冲需要 MNMNMN 个 float，工作区合计 4(Nd+MN)4(Nd+MN)4(Nd+MN) 字节。Softmax 将分数就地改写为概率，最后一个核函数再用这块缓冲计算 PV。普通接口每次提交四个核函数，Graph 版则捕获同一个入口。两种实现使用相同的计算顺序和中间张量，因此可以单独比较提交方式。

如果同时换用在线 Attention，省去概率矩阵还会改变核函数数量、读写量和计算顺序，测到的时间差便同时包含算法优化。这里用的入口 attention_materialized_launch 只接收现成的输入、输出和工作区，内部不分配也不同步，从而把两种提交方式放在相同条件下比较。

一次普通调用把操作逐项交给 CUDA。四个 kernel 的总工作量再小，host 也得反复准备参数、逐项提交，GPU 还可能在两项之间等下一项到达。Graph 把这份重复准备提前做完：捕获得到节点和依赖的描述，实例化得到可执行实例，此后一次 launch 提交整条工作流。CUDA Graph 编程指南

下面的代码只展示捕获、实例化和重放的调用顺序。调用方已经分配了各指针指向的缓冲区，这里省略错误检查。

cudaStreamBeginCapture(stream, cudaStreamCaptureModeThreadLocal);
attention_materialized_launch(q, k, v, out, M, N, d,
                              score, kt, stream);
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, 0);

// 之后可反复提交；同一 stream 中先更新输入，再执行图。
upload_current_inputs(stream);
cudaGraphLaunch(exec, stream);

graph 描述节点及其依赖，exec 是供重放使用的执行实例。运行时读写的数据仍放在调用方提供的缓冲区中。这里四次提交都在同一条流上，因此捕获会保留它们的先后依赖：分数就绪才能 Softmax，概率就绪才能 PV。测试数了图里正好四个节点，用来防止入口在另一条 stream 提交，导致捕到的对象与预期不符。

捕获还没结束时，程序也可能报错。cudaStreamBeginCapture 已经成功，后续的 C++ 代码却可能抛出异常。这时局部变量退栈，stream 仍然处在捕获状态。因此实现会记录捕获状态，在异常处理分支结束捕获并销毁未完成的图。测试在提交四个节点后主动抛出异常，等清理结束后，再次捕获成功。对已经持有图的对象再次捕获会被拒绝，避免旧句柄被覆盖。捕获失效与结束要求

图节点保存的设备地址与输入缓冲区复用

普通调用在每次提交时读取参数，捕获则将当时的参数值存入图节点。设捕获时 q 指向设备地址 A，之后即使主机上的指针变量改为 B，重放仍会访问 A。只要把新输入写到 A，节点下一次执行时就会读到新内容。

我们可以用同一份图检验设备地址和输入内容能否分别改变。先固定 Q/K/V 的地址，依次写入种子 0、17、42 生成的数据，每次重放后都与独立的 CPU FP64 Attention 结果比较。接着保持地址 A 的内容不变，另行分配一块地址为 B 的缓冲区，用 B 替换普通提交读取的成员 query_input：

query_input = alternative_q;
cudaGraphLaunch(exec, stream); // 节点参数仍指向捕获时的 A

direct();                     // 普通调用读取现在的 query_input，也就是 B

这次重放仍从 A 读取旧 Q，普通提交则从 B 读取新 Q。两边沿用相同的旧 K/V，各自与对应的参考结果一致。随后把指针成员恢复为 A，向 A 写入种子 99 生成的数据，再次重放就得到了新输入的正确结果。由此可以同时确认，图会重新执行计算，但始终从捕获时绑定的地址取数。

如果每次都用同一份输入，即使捕获到的是空图，校验也可能通过。原因是首次普通调用已经写出了正确值，后续重放什么都没做，输出缓冲区却仍保存着上一次的结果。SOL-ExecBench §4.4.1 记录过同类案例，CuTe DSL 没有把捕获 stream 传给 kernel。论文中的 B200 性能不参与本机笔记本 GPU 的比较。论文案例

四组边界形状 1×31×331\times31\times331×31×33、4×127×324\times127\times324×127×32、32×128×6432\times128\times6432×128×64、17×129×6517\times129\times6517×129×65 跑完上面这套，最大绝对误差分别为 5.28×10−85.28\times10^{-8}5.28×10−8、3.91×10−83.91\times10^{-8}3.91×10−8、6.29×10−86.29\times10^{-8}6.29×10−8、8.53×10−88.53\times10^{-8}8.53×10−8。参考先查有限性，再按 2×10−6+2×10−5∣OFP64∣2\times10^{-6}+2\times10^{-5}|O_{\mathrm{FP64}}|2×10−6+2×10−5∣OFP64​∣ 逐元素比较。它们验的是参数绑定和这条 Attention 链，长行归约与极值附近的数值行为需要另开算子实验。

由于节点会持续引用这些设备地址，实现将图和存储交给同一个请求对象管理：一个 Request 同时持有 stream、Q/K/V/O、两个工作区、graph 和 exec，对应一组固定的 (M,N,d)(M,N,d)(M,N,d)。同形状的新输入只需写入这组缓冲区即可重放。如果形状发生变化，入口会在复制前拒绝请求，调用方就需要另建实例。按形状分别保存实例，才能保证重放时的参数仍与实际缓冲区对应。

CUDA Graph 也允许更新已有实例的参数和部分结构。这里选择按形状保存多个固定实例，因此无需为每次重放实现更新协议；如果使用更新接口，就要在更新失败时重新实例化。两条路径都需要区分形状、数据类型、布局、算子或权重版本，以及工作区要求，否则可能为新请求选中不匹配的实例。Graph 更新约束

即使形状完全相同，并发请求也可能互相覆盖中间结果。假设请求 A 和 B 共用同一个 score 缓冲区，A 的 QK 刚写完分数，B 的 QK 就可能先一步覆盖它。等 A 的 Softmax 开始读取，这组分数已经属于 B。每张图内部的依赖只能约束本图的节点，无法替两个请求安排共用内存的读写顺序。

实验给两个 4×127×324\times127\times324×127×32 请求各建 stream、exec 和全套存储，交错提交 20 轮，最大绝对误差 3.86×10−83.86\times10^{-8}3.86×10−8。它检查的是隔离，没有测量两个请求实际重叠多少。也不能用同一个 cudaGraphExec_t 换两条 stream 顶替这个设计：同一个执行实例的 launch 会依该实例先前的 launch 排序，无法与自身并发。Runtime Graph API

直接提交与图重放的驻留执行时间和完整请求延迟

为了比较同一份计算在设备与调用方看到的耗时，24 个独立进程都运行了直接提交和图重放。输入已驻留 GPU 时，用一对 CUDA 事件记录连续 512 次原生调用，仅在末尾等待一次，再算平均每次的设备区间。完整请求用墙钟计时，从复制三份锁页主机输入开始，一直计到设备完成计算、主机取回输出并结束等待。分配缓冲和生成随机数都在计时之外。

四种形状的驻留设备区间都缩短了。将同样的工作放回完整请求，前两种形状略慢，第三种形状的区间包含 1，只有最后一种从约 126 µs 降到 117 µs。输入一直驻留设备的解码阶段适合参考驻留计时；需要向 CPU 交付结果的接口则应参考完整请求计时。这两项实验都未模拟服务排队。

两个设备事件之间也会经历 GPU 等待下一次主机提交的时间，所以各核函数之间的间隙同样影响设备计时。图中用一次独立的 Nsight Systems 记录展示执行顺序与间隙。上表另用未挂载分析器的配对运行计时。相同直接实现换标签的 A/A 对照在 4×128×644\times128\times644×128×64 上给出事件 1.001 [0.992, 1.011]、主机批计时 1.001 [0.991, 1.011]。

计入捕获与实例化的累计重放耗时

稳定重放的收益还要抵偿一次性准备成本。为此，实验对每组复用次数创建新的请求实例，把 R=1,2,4,8,32R=1,2,4,8,32R=1,2,4,8,32 次有用计算直接累加计时。图侧从捕获、实例化、核对四节点开始，第一次真正执行只算一次。驻留条件在 RRR 次后共同等待；完整请求每次都做自己的拷贝和等待。

最大形状的完整请求在 R=1,2,4R=1,2,4R=1,2,4 时倍数分别为 0.973 [0.958, 0.989]、1.031 [1.018, 1.044]、1.051 [1.033, 1.069]。到 32 次时为 1.025 [0.9995, 1.0521]，区间跨过 1。图中空心点标出区间宽于预设精度的比较。是否值得把某个形状放进图缓存，要同时看完整调用怎样重复、静态缓冲占多少以及实测累计成本。

图执行期间的缓冲区所有权与按流释放

cudaGraphLaunch 返回时，主机已经提交了工作，GPU 却可能还在运行最后的 PV。图句柄保留设备地址，所指向存储的所有权仍在 C++ 调用方。封装对象如果在返回后析构、先释放 Q/K/V 或 score，仍在执行的节点就会读到已释放的内存。

固定形状的请求对象会被长期复用，因此可以等到析构时才让主机等待该对象的流，等所有设备操作完成后再销毁 exec、graph 和缓冲区。端到端测试也给锁页主机缓冲指定了所有者，由它在释放前等待相关流。即使程序因异常提前退出，也能保证 H2D 或 D2H 复制结束后才释放主机内存。

当工作区只服务于一次短期调用时，每次在主机上等待再销毁会打断后续的异步提交。设备内存的释放也可以排进 stream：先分配，再初始化、计算，最后提交 cudaFreeAsync。这样，即使主机退出作用域时 GPU 仍在计算，后续操作也只能在前面的设备操作用完这块内存后才复用它。Stream-ordered allocator

前面的 Request 由主机等待整条流，而短期工作区 OrderedWorkspace 将释放排在最后一次使用之后。这个对象保存设备指针和描述完成顺序的依赖，只允许移动构造。移动后由新对象负责释放同一块设备内存，数据始终留在原处。析构在依赖链末尾提交 free，显式 close() 能报错，析构只记录清理失败、不抛异常。

跨 stream 使用还需要补一条事件边。handoff(next) 在旧 stream 记录 event，让新 stream 等待它，再把后续释放的归属交给新 stream：

如果 A、B 两条流同时使用同一工作区，最近一次主机提交所在的流只能代表其中一次使用。释放前要等两条流上所有尚未完成的操作结束。这个封装只支持串行交接，不从最近一次调用推断任意并行借用何时结束。

要检验主机提前退出时多个设备操作是否都能安全读完工作区，生命周期测试选用了状态初值为零的 Selective Scan：

b,t,d,sb,t,d,sb,t,d,s 分别是 batch、时间、通道、状态下标；uuu 是输入，Δ\DeltaΔ 是正步长，前一时刻的状态按 AAA 指定的方式转移，新输入通过 BBB 写入当前状态；输出既包含 CCC 从当前状态读出的结果，也包含 DDD 从输入直接传到输出的分量。实验取负 AAA 和正 Δ\DeltaΔ，只验证这个零初始递推，没有实现跨请求的状态续接，也不等于完整的 Mamba 推理。

实现先算 chunk 的仿射摘要，再传播前缀，最后重算并归约输出，工作区因此被多个 kernel 依次读写。测试尺寸为 batch 2、长度 513、通道 3、状态数 33，切出三个时间 chunk、一个前缀 group、两个状态 tile，按 256 字节对齐后工作区为 32,000 字节。

测试依次覆盖移动后离开作用域、跨流交接、提交后抛异常、显式关闭两次。四种情况都与按时间递推的 CPU FP64 参考一致，最大绝对误差 4.8432×10−84.8432\times10^{-8}4.8432×10−8；每个案例恰好一次分配、一次释放提交，清理错误为零。移动后的源对象置空，重复关闭没有重复释放。

测试在工作开始前人为增加 20,000,000 个 GPU 时钟周期的延迟，以便稳定地观察主机已经返回、GPU 仍在工作的时刻。移除性能分析器后，四个案例都在退出作用域时查询了完成事件，当时 GPU 均未完成。该延迟只用于制造可观察窗口，不参与 Scan 的性能结果。

为了在时间线上看清主机提交释放与设备完成使用的先后关系，图中另外用两个小核函数分别做初始化与读取。紫色是 CPU 提交释放，灰色是人为延迟，橙色是最后一次消费。free API 返回之后消费仍能安全完成，靠的是释放排在消费之后；它没有证明物理显存已经归还操作系统。内存池何时归还页没有测量，长度 513 也没有覆盖超过 1024 个 chunk 的 Scan 长序列边界。

Graph 和 Scan 两条路径的 memcheck、racecheck、synccheck 均为零报告。racecheck 主要检查共享内存访问冲突，因此跨流读写全局内存时仍需显式建立前述依赖。工作区还依赖流、CUDA 上下文和可选的审计对象，所以这些对象都应在工作区之后销毁。一旦上下文先行销毁，工作区便无法再调用 CUDA 接口释放资源。

实验环境、计时方法与原始数据

Windows 11、RTX 5070 Laptop 8 GB、驱动 610.88；Toolkit 13.1.115 的 NVCC 生成 sm_120，进程报告 runtime/driver API 均为 13030。按记录的功耗状态运行，未锁频或主动刷新 L2。三次先导独立进程只用于定样本数，24 个确认进程每个都运行全部条件；驻留条件有 15 批，每批 512 次，完整请求有 30 个样本。每个复用条件每进程用八对新实例。区间在进程配对对数比值上按自由度 23 的 Student-t 计算。八个稳态比较均达到相对区间半宽 2% 的目标。
