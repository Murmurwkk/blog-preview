TVM Relax 算子融合：生成代码中的矩阵遍历与临时缓冲区

TVM Relax 把四个逐元素操作放进同一个函数，但生成的代码仍遍历矩阵四次。将四次遍历合成一次后，八个 CPU 进程的配对计时显示，129 行矩阵的完整调用约快 1.6%；1 行和 32 行的对照还不足以判断哪一种更快。

TVM 把四个逐元素操作编译进同一个融合函数，生成的代码却仍然遍历矩阵四次。要判断这次融合省下了什么，我们用两个分支共享同一矩阵乘积的例子，依次检查 Relax 是否消除了重复计算、TIR 是否合并了循环，以及 LLVM 最后还要申请哪些缓冲区。然后在同一台 CPU 上比较三种实现，检验这些改写怎样影响整次调用的时间。

重复矩阵乘法的消除与常量折叠

X∈RB×DX\in\mathbb R^{B\times D}X∈RB×D 是输入，W∈RD×DW\in\mathbb R^{D\times D}W∈RD×D 是常量权重。先算 Z=XWZ=XWZ=XW，再分两条路：一条加偏置过 ReLU，另一条乘常数，最后相加。

Z=XW,b=b0+b1,Y=ReLU⁡(Z+b)+αZ,α=0.125.Z=XW,\quad b=b_0+b_1,\quad Y=\operatorname{ReLU}(Z+b)+\alpha Z, \qquad\alpha=0.125.Z=XW,b=b0​+b1​,Y=ReLU(Z+b)+αZ,α=0.125.

DDD 固定 64，BBB 是行数。b0,b1b_0,b_1b0​,b1​ 是长度 64 的常量向量，按列广播到每一行。这个人为构造的例子同时包含三种编译机会：能提前算的常量、能共用的重复计算、被两个消费者读取的中间值。

直接按这个式子写成数组运算，会在两个分支中各算一次矩阵乘法：

z0 = x @ W
z1 = x @ W
bias = b0 + b1
r = maximum(z0 + bias, 0)
y = r + 0.125 * z1

要复用 z0，编译器需要确认两次矩阵乘法给出相同结果，而且省去一次求值不会改变后续计算。在这个例子里，两次调用的输入完全相同，矩阵乘法也没有副作用，所以满足条件。如果调用会随机采样、读取可变状态或产生副作用，即使函数名和参数相同，也可能需要执行两次。Relay 论文 §3.1 讨论显式绑定和求值顺序，正是为了在表示数据依赖之外保留这些行为。Relay 原论文

在 Relax 中，bb.emit 给每次计算的结果起一个后续可引用的名字。Python 建图时保留了两次独立的 matmul，因此后面若只剩一次乘法，就能确定是公共子表达式消除（CSE）复用了 z0：

x = relax.Var("x", relax.TensorType((32, 64), "float32"))
bb = relax.BlockBuilder()
with bb.function("main", [x]):
    with bb.dataflow():
        z0 = bb.emit(relax.op.matmul(x, relax.const(W)))
        z1 = bb.emit(relax.op.matmul(x, relax.const(W)))
        bias = bb.emit(relax.op.add(relax.const(b0), relax.const(b1)))
        a = bb.emit(relax.op.add(z0, bias))
        r = bb.emit(relax.op.nn.relu(a))
        s = bb.emit(relax.op.multiply(z1, relax.const(np.float32(.125))))
        y = bb.emit_output(relax.op.add(r, s))
    bb.emit_func_output(y)
mod = bb.get()

检查保存的中间表示可以看到，优化前共有七个高层操作。首先，FoldConstant 把 b0+b1b_0+b_1b0​+b1​ 算成一份常量，剩六个；EliminateCommonSubexpr 把两次 XWXWXW 合成一次，剩五个：

mod = relax.transform.FoldConstant()(mod)
mod = relax.transform.EliminateCommonSubexpr()(mod)

优化后的中间表示（IR）把第二个乘法绑定改成 lv1 = lv，于是缩放支路直接读取第一次乘法产生的 lv。lv 就是公式里的 ZZZ，这里没有另外分配一份。

权重也是常量，矩阵乘却消不掉，因为 XXX 是每次请求才有的输入。编译器能保存和准备好 WWW，XWXWXW 还得运行时算。常量折叠和 CSE 的分界线也在这里：常量折叠预先计算所有输入在编译时都已知的表达式，CSE 则让一次运行中的相同计算只执行一次。

把七个操作减到五个到底能省多少时间，取决于省去的是哪种计算。一次 B×DB\times DB×D 乘 D×DD\times DD×D 大约是 2BD22BD^22BD2 次浮点运算，几个逐元素操作是 BDBDBD 量级。因此图上的操作数只能确认编译器做了哪项改写；要估算它的性能收益，还需区分矩阵乘法与逐元素运算各自的工作量。

Relax 融合后保留的 TIR 循环与临时矩阵

常量折叠和公共子表达式消除确定了哪些结果可以共享，但尚未决定运行时要为它们分配多少存储。Relax 停留在张量级，TIR 把算子展开成循环、归约和缓冲区，最后 LLVM 生成 CPU 代码。TIR 里的 PrimFunc 可以理解成一段显式描述张量计算的底层函数，里面能有多组循环，也能有多块临时数组。

为了区分张量级的共享和循环级的合并，我们将同一份完成常量折叠、消除重复计算的程序用两种方式编译。第一种沿默认构建路径将 Relax 的张量运算转换成底层计算，最终由 LLVM 生成 CPU 代码。第二种在构建前先对同一份程序显式执行下面几步融合变换：

passes = tvm.transform.Sequential([
    relax.transform.LegalizeOps(),
    relax.transform.AnnotateTIROpPattern(),
    relax.transform.FuseOps(),
    relax.transform.FuseTIR(),
])
mod = passes(mod)

LegalizeOps 先把高层算子转成可调用的底层计算。标记逐元素、广播和归约等访问模式后，FuseOps 才能选择融合区域，随后 FuseTIR 将区域内的底层计算合为一个函数。得到一个函数之后，还要继续查看它内部的循环是否也已合并。TVM 融合机制说明

偏置和缩放两条支路都读取 ZZZ，直到最终加法才重新汇合。即使把第一条支路的计算并入矩阵乘，第二条支路仍要读取 ZZZ，因而可能仍须保存这块矩阵。编译器必须检查同一结果的所有用途；如果程序还将 ZZZ 作为额外输出返回，就更不能在其使用者读取之前丢弃它。

比较两条路径的产物，基础路径有 matmul/add/relu/multiply/add1 五个计算 PrimFunc，显式融合路径只剩 matmul 和 fused_add_relu_multiply_add1 两个。后一个函数的名字列出了四个逐元素操作。要知道它们是否也共享一次遍历，还得检查函数内部的循环。

在生成的融合函数中，编译器声明了三块大小相同的 32×6432\times6432×64 的缓冲：

T_add_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))
compute_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))
T_multiply_intermediate = T.sblock_alloc_buffer((T.int64(32), T.int64(64)))

三块缓冲分别保存加偏置、ReLU 和缩放的结果。函数体包含四次完整遍历。下面两段是前两次遍历的原始代码：

for ax0, ax1 in T.grid(T.int64(32), T.int64(64)):
    with T.sblock("T_add"):
        v_ax0, v_ax1 = T.axis.remap("SS", [ax0, ax1])
        T.reads(lv[v_ax0, v_ax1], param_0[v_ax1])
        T.writes(T_add_intermediate[v_ax0, v_ax1])
        T_add_intermediate[v_ax0, v_ax1] = lv[v_ax0, v_ax1] + param_0[v_ax1]
for i0, i1 in T.grid(T.int64(32), T.int64(64)):
    with T.sblock("compute"):
        v_i0, v_i1 = T.axis.remap("SS", [i0, i1])
        T.reads(T_add_intermediate[v_i0, v_i1])
        T.writes(compute_intermediate[v_i0, v_i1])
        compute_intermediate[v_i0, v_i1] = T.max(T_add_intermediate[v_i0, v_i1], T.float32(0.0))

T.grid 指定遍历范围，SS 表示两个都是空间轴，T.reads/writes 列出每个计算块读写的缓冲区。对照两段代码最后的赋值可以看到，第一次遍历把整块 lv+bias 写完，第二次又读回来做 ReLU。缩放的循环和最终加法的循环各在后面。

因此，四个操作虽然已经合并到一个函数里，仍需分别遍历整块矩阵。如果进一步把逐元素部分并为一次遍历，可以把循环写成下面这样：

for i in range(B):
    for j in range(D):
        z = Z[i, j]
        Y[i, j] = max(z + bias[j], 0) + 0.125 * z

那样一个标量 z 就够两条支路用，三块中间矩阵不用完整存。再进一步，让这段逻辑在矩阵乘的尾处理（epilogue）中执行，z 直接来自累加器，连 ZZZ 的写出和读回都能省。每一步前提不同：函数合并已经发生，逐元素循环融合和 GEMM epilogue 在这份产物里都还没有。

这些观察来自 static-fused-fusion.py，是交给 LLVM 之前的 IR。LLVM 后续仍可能复用存储、改写指令，因此 TIR 中出现几个数组，并不能直接换算为 DRAM 访问次数。目标架构、编译变换、调度和版本都可能改变结果。判断这次构建实际保留了什么，还得继续检查目标代码。

结合保存的 LLVM IR 与动态库的反汇编，可以识别实际保留下来的工作区申请。B=32B=32B=32 时，逐元素计算函数申请两块 8,192 字节的工作区，分别对应加法和乘法的中间值。ReLU 复用了已有空间。TIR 的三个逻辑数组在这里对应两个物理工作区请求，几趟循环仍然存在。另写的一次遍历对照让矩阵乘保持原样，只把逐元素部分合在一起，其生成函数内部没有这两笔分配。

独立算子、单趟遍历与乘法尾处理的逻辑读写量

为了估算独立遍历对中间张量读写的影响，设 Q=4BDQ=4BDQ=4BD，也就是一个 FP32 输出矩阵的字节数。这里只计算 ZZZ、AAA、RRR、SSS、YYY 这几个张量边界的读写，矩阵乘的输入 X,WX,WX,W、偏置、标量和缓存都不计。

阶段读取写入
矩阵乘产生 ZZZ此表不计 X,WX,WX,WQQQ
A=Z+bA=Z+bA=Z+bQQQQQQ
R=ReLU⁡(A)R=\operatorname{ReLU}(A)R=ReLU(A)QQQQQQ
S=0.125ZS=0.125ZS=0.125ZQQQQQQ
Y=R+SY=R+SY=R+S2Q2Q2QQQQ
合计5Q5Q5Q5Q5Q5Q

五个阶段分别执行时，表中读写合计为 10Q10Q10Q。四个逐元素操作合为一次遍历后，只剩矩阵乘写 ZZZ、逐元素循环读 ZZZ 写 YYY，合计 3Q3Q3Q。整个 epilogue 接到累加器后面，就只剩最后写 YYY 的 QQQ。

B=256,D=64B=256,D=64B=256,D=64 时，三个层次分别是 640 KiB、192 KiB 和 64 KiB。中间的 192 KiB 是从上面那段循环推出来的预算，图中展示的是前后两种方案的 640 KiB 和 64 KiB。这三个数都由循环边界推导，实际通过内存总线传输的字节数还会受缓存影响。

少读写也不一定同比例加速：乘法的 X,WX,WX,W 读取和 2BD22BD^22BD2 量级的计算一直在；相邻阶段使用的临时矩阵可能部分留在 CPU 缓存中；将更多运算合入一个核函数，还可能改变寄存器压力和向量化方式。下面用实际编译的单趟对照来测完整 VM 调用；物理访存量仍未采样。

由此可以给 CPU 对照实验确定一个具体的改动：保持矩阵乘法不变，只合并四个逐元素循环，去掉这些循环之间完整的临时矩阵读写。

符号批大小的形状推导与数值验证

前面的计时采用固定批大小，但这些改写并不要求编译时知道 BBB。把输入类型第一维从 32 换成符号 batch，矩阵乘、广播和分支汇合的形状关系照样确定，常量折叠和 CSE 的计数也不变，它们不需要知道有多少行。

如果再将权重 WWW 的形状推广到 D×HD\times HD×H，输入、输出和偏置需要满足以下关系：

[B,D]×[D,H]⟶[B,H],[B,H]+[H]⟶[B,H].[B,D]\times[D,H]\longrightarrow[B,H],\qquad [B,H]+[H]\longrightarrow[B,H].[B,D]×[D,H]⟶[B,H],[B,H]+[H]⟶[B,H].

动态第一维不等于任意形状：归约维必须相等，偏置宽度得对上 HHH，两条支路的输出也得相容。这些信息既帮编译器规划存储，也让运行入口有条件拒绝错误输入。类型关系证明不了底层地址访问安全，但至少能拦住把 63 列矩阵送进按 64 列构建的计算。

实跑生成了静态/符号 batch 与基础/显式融合四份 LLVM CPU .so。符号版本编译一次，分别跑 B=1,7,32,129B=1,7,32,129B=1,7,32,129；静态版本跑 B=32B=32B=32。构建的最后几步：

with tvm.target.Target("llvm"):
    lowered = relax.get_pipeline("default")(mod)
executable = relax.build(lowered, target="llvm", relax_pipeline=None)
executable.export_library("model.so")
vm = relax.VirtualMachine(executable, tvm.cpu())
actual = vm["main"](tvm.runtime.tensor(x, tvm.cpu())).numpy()

脚本此前已显式执行编译变换，将 Relax 张量运算转换为包含 TIR 计算函数的程序，并保存了这份中间表示，所以设置 relax_pipeline=None，避免构建时重复运行同一套变换。把导出的库重新加载并创建 VM 后，再输入相同的数组，输出与导出前逐位一致。

要检验符号形状的结果，参考计算也须保留编译时的舍入顺序。b0+b1b_0+b_1b0​+b1​ 在折叠时已经按 FP32 加过，独立参考就得先拿到这份 FP32 偏置，再连同实际存储的 X,WX,WX,W 一起提到 FP64 去算。一上来就用 FP64 加两个偏置，等于把程序里真实存在的一次舍入从参考里抹掉了，比的就不是同一个东西。

符号版本另有一个 shape_func。把它算进去，基础版和融合版的 PrimFunc 总数是六和三；前面说的五和二只数了张量计算函数。对比编译产物时，先说明是否把形状计算也统计在内，两种计数便能对应起来。

这个例子中，实际批大小决定循环边界，计算步骤之间的依赖关系始终固定。如果迭代次数还要根据中间结果决定，就需要表达控制流。Relay 可以用条件、递归和类型结构表示这类程序；本次生成的四份库只验证了符号批大小下的计算。

INT8 量化的舍入、裁剪与数值误差

前面的常量折叠、公共计算共享和函数融合，都以保留既定数值语义为目标。改用 INT8 则会改变可表示的数值，额外引入舍入与饱和。这个边界必须出现在编译器看得见的位置，否则一个看似无害的算术重排就能改掉结果。

为了观察量化怎样影响共享结果，仍取同一个 Z=XWZ=XWZ=XW，对它施加对称量化：

q(z)=clip⁡(round⁡(z/s),−127,127),z^=sq(z),q(z)=\operatorname{clip}(\operatorname{round}(z/s),-127,127), \qquad \hat z=sq(z),q(z)=clip(round(z/s),−127,127),z^=sq(z),

然后让同一份 Z^\hat ZZ^ 进偏置/ReLU 和缩放两条支路。量化点在共享点上，两个消费者看到相同的表示值。如果每条支路各量化一次、尺度还不一样，那已经是另一个程序，不能按原来的共享关系讨论。

sss 越小，普通值分得越细，大幅值越容易饱和；sss 越大，范围宽了，普通值的舍入间隔也变大。这个取舍不会因为融合消失。一般地，q(a+b)q(a+b)q(a+b) 换不成 q(a)+q(b)q(a)+q(b)q(a)+q(b)，一个饱和点也不能随便跨过去。Relay 把量化分成标记、校准和具体实现三步，好让这些数值决定接得上后面的编译变换。Relay §4.2

为了看清校准目标的影响，这里用独立的 NumPy 实验造了 256×64256\times64256×64 的 FP32 输入和 64×6464\times6464×64 权重，把输入第 0 行有意放大 20 倍。只量化 ZZZ，两条后继支路都用反量化值，再比最终 YYY。这是构造输入，不是从真模型里采的激活；四份 TVM CPU 库也没有跑 int8。

放大的第 0 行对整体误差贡献很大，因此按全部行评价时，最大值校准保留大幅值的效果最好。单独评价普通行时，99.5% 分位点反而更好，因为进一步扩大范围会降低小值的分辨率。只看裁剪比例很小也不够：0.1038% 数的是元素个数，没数被裁掉的幅值，整体输出误差还有 22.1182%。

实验只比较构造输入上的数值误差，没有测量下游模型准确率，因而不能据此选定业务阈值。要判断哪种校准更合适，需先明确目标是保护异常大值，还是减小普通输入的误差。业务目标决定阈值，编译器只能在量化运算确定后，将它们合并到更少的循环中。

从中间表示到实际运行，这次构建做出的改变可以逐层对应。Relax 让两个分支共用同一次矩阵乘法；TIR 把四个逐元素操作放进了同一函数，内部仍保留四次遍历和三块逻辑缓冲。即使进一步合成一次遍历，完整 VM 调用还需支付矩阵乘法等成本。若再换成量化表示，则应根据下游任务选取标度，并重新核对输出误差。

编译环境、计时方法与量化记录

当前配对计时在 WSL2、LLVM CPU、Python 3.12.3、NumPy 2.5.4、Apache TVM 0.27.0.post1、Intel Core Ultra 9 285H 上进行。导入库之前把 TVM、OMP、MKL 和 OpenBLAS 固定为单线程。核心亲和性与时钟未锁定。3 个先导进程另存，8 个确认进程的配对对数比值计算 Student-t 95% 区间。本地入口为 bench_mur/tvm/revision.py 和 summarize.py，小记录在 bench_mur/tvm/results/revision-20261115/，LLVM IR、汇编和完整产物位于 rep_mur/experiment-revision-20261115/tvm/run-03/。

Relax 实验与 Relay 论文使用的版本、目标和硬件不同。符号维用独立 NumPy 输出复核；int8 的阈值扫描也是单独的 NumPy 数值实验。逻辑边界字节出自循环读写账本，此处没有采集 CPU DRAM 计数器。
